# Windows 수동 QA 실행 계획

이 문서는 [검증 명세](../sdd/validation.md)의 Windows 대화형 실행 절차다. 결과는 실제 화면과 파일을 보고 기록한다. 현재 프로토타입의 미구현 기능은 통과로 간주하지 않는다.

## 0. 격리된 시험 환경 만들기

PowerShell에서 아래 명령을 실행한다. 출력된 `$qaRoot` 경로를 기록하고 재시작할 때 **같은 경로**를 사용한다. 기존 프로젝트나 `.run-data/organization.sqlite`는 사용하지 않는다.

```powershell
cd D:\projects\utopia_company
$qaRoot = Join-Path (Get-Location) ('.run-data\manual-qa-' + (Get-Date -Format 'yyyyMMdd-HHmmss'))
$project = Join-Path $qaRoot 'project'
New-Item -ItemType Directory -Path $project -Force | Out-Null
Set-Content -LiteralPath (Join-Path $project 'README.md') -Value '# Manual QA fixture'
git -C $project init
git -C $project add README.md
git -C $project -c user.name='Manual QA' -c user.email='qa@local.invalid' commit -m 'QA baseline'
$qaRoot
```

앱을 시작한다. `-CheckOnly`는 프로세스를 띄우지 않고 준비 상태만 확인한다. 실제 실행 명령은 창을 닫을 때까지 PowerShell을 점유한다.

```powershell
& .\scripts\start-windows.ps1 -CheckOnly
& .\scripts\start-windows.ps1 -DataDir (Join-Path $qaRoot 'app-data')
```

스크립트는 Vite 로그를 `.run-data/startup-logs`에 남긴다. 앱 창을 닫으면 자신이 시작한 Vite 프로세스도 종료한다. 앱 데이터와 시험 프로젝트는 삭제하지 않으므로 재시작 검증과 실패 분석에 사용할 수 있다.

## 1. 기본 설정과 지속성

- [ ] **QA-01 실행:** 앱 창과 CEO 데스크가 열리고 오류 배너가 없다. 업무 보드와 Office 탭으로 이동할 수 있다. 창을 닫으면 시작 스크립트가 종료된다.
- [ ] **QA-02 프로젝트:** `프로젝트` → `폴더 선택하기`에서 `$project`를 고른다. Windows에서는 탐색기형 창에 주소 경로, 이동/검색, 하위 폴더 목록과 `이 폴더 선택`이 보여야 한다. 폴더 창이 열리지 않으면 `경로 직접 입력`을 사용한다. 기존 Git 저장소가 그대로 목록에 표시되고, PowerShell에서 `git -C $project status --porcelain`은 비어 있어야 한다. 표시 경로에는 Windows의 `\\?\` 접두사가 없어야 한다.
- [ ] **QA-03 AI 발견:** `AI 연결`의 `다시 검사`를 누른다. 각 도구의 실제 실행 경로·버전·상태가 보이는지 확인한다. Windows에서 확장자 없는 npm 래퍼가 있는 Claude Code는 실행 가능한 `claude.cmd`가 우선 선택되어야 하며 Win32 오류 193이 없어야 한다. Codex의 `등록하기`를 누른 뒤 `등록된 AI`에 표시되고, 연결이 비어 있던 팀원 모두에게 자동 배정되며 기존 배정은 유지되는지 확인한다. 로그인 필요 상태면 해당 CLI에서 직접 로그인하고 다시 검사한다.
- [ ] **QA-03A 백엔드 재시작과 npm CLI:** 코드를 갱신한 뒤 기존 앱 창을 열어 둔 상태라면 AI 연결 화면에 재시작 안내가 보여야 하고 연결 버튼을 누르면 이유가 설명되어야 한다. 창을 닫고 시작 스크립트를 다시 실행한 뒤 안내가 사라지는지 확인한다. `where.exe claude`에서 확장자 없는 파일이 먼저 나오더라도 발견된 경로는 `claude.cmd`여야 한다. 이전에 저장된 Claude 연결 경로가 확장자 없는 파일이었다면 재시작 후 `.cmd`로 복구되어야 한다. 전역 Codex 설치를 확인하려면 PowerShell에서 `npm.cmd list -g @openai/codex --depth=0`, `codex.cmd --version`, `codex.cmd login status`를 실행한다.
- [ ] **QA-03B 목표 실행과 Claude 로그인:** 앱을 재시작하고 AI 연결에서 `다시 검사`를 누른다. 터미널의 `claude.cmd auth status`가 `loggedIn: true`라면 Claude 발견 항목과 기존 등록 연결이 `사용 가능`으로 바뀌어야 한다. CEO 목표에 한국어와 따옴표, `&` 같은 문자가 있어도 `batch file arguments are invalid`가 나타나면 실패다. 분석 단계에서 막힌 기존 목표에만 `다시 실행`이 보여야 하며, 업무나 승인 요청이 이미 생긴 목표에는 이 버튼이 없어야 한다. 목표 실행 후 HTML 산출물은 앱이 선택한 프로젝트 안에 만든 파일로 확인한다.
- [ ] **QA-04 팀 구성:** `Office`에서 CTO, PM, Developer A, Developer B, QA 캐릭터를 클릭하고 각각 등록한 Codex 연결을 배정해 저장한다. Developer A의 이름·역할 프리셋·지침을 바꾸고 캐릭터를 드래그해 위치를 옮긴다. 방향키 이동도 확인한다.
- [ ] **QA-05 재시작 지속성:** 창을 닫고 위와 같은 `-DataDir`로 다시 시작한다. 프로젝트 선택, AI 연결, 다섯 역할의 배정, 수정한 팀 설정과 Office 위치가 유지되어야 한다.

## 1A. 이번 개선 사항의 대화형 검증

- [ ] **QA-05A 막힌 버튼 설명:** 새 격리 프로필에서 프로젝트 없이 CEO 데스크의 `목표 전달`을 누른다. 버튼은 클릭을 받고, 이유와 `프로젝트`에서 할 다음 행동이 다이얼로그에 나와야 한다. 목표 입력이 너무 짧을 때도 같은 방식으로 구체적인 이유가 나와야 한다. AI를 등록하거나 배정하지 않은 채 만든 목표의 `팀 실행 시작`을 누르면 누락된 역할/AI와 Office 또는 AI 연결에서 할 일이 보여야 한다. 프로젝트 직접 경로의 빈 값, Office의 미선택 프리셋, AI 연결 다이얼로그의 빈 필수 정보도 각각 확인한다.
- [ ] **QA-05B 실제 발견과 프리셋:** 미설치 도구는 `이 PC에서 확인됨`에 나타나면 안 된다. 지원 목록의 `왜 안 되나요?`를 누르면 실행 파일을 찾지 못한 이유와 설치 또는 직접 경로 지정 방법이 나와야 한다. 실제 Codex 등록 후에는 `등록됨` 버튼을 다시 눌러 중복 등록 사유가 나타나는지 확인한다.
- [ ] **QA-05C 여러 프로젝트:** `$qaRoot` 아래 빈 폴더와 파일이 있는 비 Git 폴더를 각각 만들고 `폴더 선택하기`로 등록한다. 하위 폴더와 중첩 Git 저장소가 여러 개 있는 `$qaRoot` 자체도 탐색기형 창에서 `이 폴더 선택`으로 등록한다. 선택한 폴더가 그대로 프로젝트 루트가 되고, 자식 폴더를 따로 만들거나 요구하지 않아야 한다. 내용은 그대로여야 하며 `.git`과 README가 자동 생성되지 않아야 한다. 이미 등록한 `$project`를 다시 선택하면 내용 변경 없이 전환되어야 한다. Git 저장소의 하위 폴더도 해당 폴더 범위의 일반 프로젝트로 등록된다. 프로젝트별 목표 목록은 분리되고 기존 목표의 프로젝트 연결은 바뀌지 않아야 한다.
- [ ] **QA-05C Git 전환 재인식:** 등록된 일반 폴더의 내용을 보존한 채 앱 밖에서 Git 저장소와 첫 커밋을 만든다. 앱에서 같은 폴더를 다시 선택하거나 프로젝트 목록에서 전환하면 동일한 프로젝트 ID와 기존 목표·QA 기본값을 유지하면서 Git 방식으로 인식해야 한다. 첫 커밋 전에는 일반 폴더로 남아야 한다. 기존 차단 목표가 자동 완료되면 실패다.
- [ ] **QA-05D Office 설정:** 캐릭터가 이니셜 글자 대신 픽셀 인물로 보이고, 클릭 시 세부 설정이 열리며 드래그 후 위치가 바뀌어야 한다. CTO/PM/Developer/QA 프리셋을 적용하고 저장한 뒤 재시작해 지침과 위치가 유지되는지 확인한다. AI 연결 등록 후 빈 팀원에게 자동 배정되고 기존 연결은 유지되어야 한다. HTTP 모델 연결에는 실제 `/models`에서 받은 모델 선택지가 보이고, CLI에서는 기본 모델 선택을 안내해야 한다.
- [ ] **QA-05E 알림과 간격:** 목표 전달 뒤 알림이 우하단의 작은 토스트로 나타나고, `목표 보기`가 해당 목표 카드로 이동하며, 작업 입력 흐름을 가리지 않고 약 6초 뒤 사라지는지 확인한다. 프로젝트 목록과 폴더 선택 카드, AI 발견 목록·지원 목록·등록 카드, 업무 현황 섹션, Office 두 열 사이의 간격을 각각 확인한다. 창 너비를 줄였을 때 카드가 겹치지 않아야 한다.
- [ ] **QA-05F 직접 AI 연결:** `다른 AI 연결` 버튼을 눌러 다이얼로그가 열리는지 확인한다. HTTP 방식을 고르면 서버 주소 입력 후 `사용 가능한 모델 찾기`를 눌러 목록에서 모델을 선택해야 저장된다. 실패 이유는 대화상자에서 볼 수 있어야 하며, 연결 화면 본문에 입력 양식이 항상 펼쳐져 있으면 실패다.
- [ ] **QA-05G 진행 표시 정책:** 목표 분석 중에는 CTO, 계획 중에는 PM, 구현 중에는 실제 배정된 개발자, 검증 중에는 QA 캐릭터에 말풍선과 `…`이 보여야 한다. 같은 역할의 다른 팀원은 작업 중으로 오인되면 안 된다. 캐릭터 클릭은 기본적으로 `활동` 탭을 열고 목표/업무, 단계 그래프, 실제 시간순 기록을 보여준다. 대기 중 팀원은 `예시 대화 · 실제 AI 응답 아님` 라벨이 있는 역할 소개를 보여준다. `설정` 탭에서 기존 역할·AI 편집이 가능해야 한다. 업무 현황의 담당자 이름을 누르면 해당 Office 활동으로 이동한다. 승인 대기·막힘은 그래프에서 완료로 칠하지 않는다. 재시작 후 이전 기록은 유지되고, 런타임이 세부 이벤트를 제공하지 않으면 빈 기록 안내만 나온다. 좁은 화면과 키보드 이동, 움직임 줄이기 설정도 확인한다.

## 2. 승인 거부 시험

- [ ] **QA-06 거부:** 깨끗한 시험 프로젝트에서 아래 목표를 CEO 데스크에 입력하고 `목표 전달` → `팀 실행 시작`을 누른다. CTO 분석, PM 계획, 업무 보드의 두 개 이상 작업과 `project_write` 승인 요청을 확인한다. 승인 사유에 시험 프로젝트 경로와 작업별 대상 파일이 보여야 한다. `거부`를 누른다. 목표는 거부 이유와 함께 중단되어야 하고 `git -C $project status --porcelain`은 계속 비어 있어야 한다.

```text
이 저장소에 greeting.txt 파일을 만들어 Hello team 한 줄을 쓰고, 별도 독립 작업으로 CommonJS sum.js 및 sum.test.js를 만들어 주세요. sum.test.js는 Node 내장 테스트 러너로 양수, 음수, 0을 확인해 주세요. 두 작업을 병렬로 진행하고 통합 후 QA 결과를 보고해 주세요.
```

## 3. 승인 대기 중 재시작과 전체 실행

- [ ] **QA-07 새 목표:** 같은 목표를 다시 전달하고 실행한다. 승인 요청까지 기다리되 아직 승인하지 않는다. 업무 보드에서 작업별 `대상 파일`이 `greeting.txt`와 `sum.js, sum.test.js`로 분리되어 있는지 확인한다. 모델이 다른 계획을 제안하거나 파일 소유권이 겹치면 그 계획을 승인하지 말고 결과를 기록한다.
- [ ] **QA-08 승인 대기 복구:** 승인 대기 상태에서 앱 창을 닫고, 동일한 `-DataDir`로 다시 시작한다. 목표는 `중단`으로 표시되며 승인은 여전히 대기 상태여야 한다. 구현 파일이 생겨 있으면 실패다.
- [ ] **QA-09 범위 검토와 재개:** `업무 보드`에서 경로·작업·대상 파일을 다시 확인하고 이 시험 저장소에 대해서만 `승인`을 누른다. CEO 데스크의 `승인된 계획 재개`를 누른다. 잘못된 경로나 예상 밖 파일이 보이면 승인하지 않는다.
- [ ] **QA-10 병렬 실행:** 활동 기록에 두 작업의 `task_started`가 나타나고, 각 작업의 격리 작업공간 경로가 서로 다르게 표시되는지 확인한다. 두 작업 모두 시작한 뒤 작업 완료 또는 통합 이벤트가 이어져야 한다. 작업 상태는 에이전트 응답 후 `통합 대기`, 패치 적용 후 `완료`가 된다.
- [ ] **QA-11 통합과 QA:** 목표가 `완료`가 되고 CEO 보고에 CTO 분석, 두 작업 결과, `PASS`로 시작하는 QA 결과와 테스트 근거가 있어야 한다. Office의 역할과 작업 상태가 업무 보드와 모순되지 않아야 한다.
- [ ] **QA-12 실제 파일:** 앱이 보고한 결과를 PowerShell에서 독립적으로 확인한다.

```powershell
Get-Content -LiteralPath (Join-Path $project 'greeting.txt')
git -C $project status --short
Push-Location $project
try { node --test } finally { Pop-Location }
```

기대 결과: `greeting.txt`에 `Hello team` 한 줄이 있고, `sum.js`와 `sum.test.js`가 생성되어 있으며, `node --test`가 양수·음수·0 테스트를 통과한다. 승인 전에 없던 변경은 이 세 파일로 제한된다. Windows의 CRLF 줄바꿈은 허용한다.

## 4. 추가 연결과 실패 경계

- [ ] **QA-13 다른 AI 연결:** 실제로 보유한 다른 CLI 또는 로컬 OpenAI 호환 모델 서버가 있을 때만 `AI 연결`의 `직접 추가`로 등록하고 재시작 후 항목이 유지되는지 확인한다. 외부 어댑터를 시험한다면 신뢰하는 실행 파일만 사용한다. 등록과 지속성은 현재 확인 가능하지만 자동 능력 검증과 모든 런타임의 작업 권한 보장은 아직 완료 기준이 아니다.
- [ ] **QA-14 실행 중 종료:** 현재 `BLOCKED`로 기록하고 실행하지 않는다. 앱 종료 시 하위 AI 프로세스를 확실히 정리하는 기능과 실행 중 세션 재개가 아직 없어, 시험 중에도 에이전트가 계속 작업할 수 있다. 프로세스 종료·복구 기능을 구현한 뒤 별도 시험 저장소에서 검증한다.

### QA-23 Provider Harness와 Claude 연결 진단

- [ ] `src-tauri`에서 `cargo run --locked --bin provider-harness -- offline`을 실행한다. 실제 AI 연결 없이 프로세스 실행·작업 폴더·stdin EOF·응답 파싱이 모두 PASS여야 한다.

### QA-27 외부 SDD와 기존 하네스 명세 가져오기

- [ ] 앱을 새 백엔드로 재시작하고 프로젝트 A를 선택한다. 프로젝트 메뉴에서 JSON 템플릿을 내려받아 내용을 채우거나 여러 Markdown SDD 파일을 선택해 `명세 미리보기 만들기`를 누른다. 프로젝트 설명, 팀원 placeholder, 업무 흐름, 출처와 예외 명세가 적용 전 화면에 표시되어야 한다.

### QA-30 열린 작업 버튼과 담당자 대화

- [ ] 프로젝트 A/B 각각에 미완료 목표를 만들고, B에는 서로 다른 담당자의 미완료 업무를 만든다. 어느 메뉴에서든 우측 하단 `열린 작업` 버튼을 열면 두 프로젝트의 목표가 나오고, 각 업무에 저장된 담당자와 상태가 보여야 한다. 완료된 업무·목표, 새 목표 버전으로 대체된 예전 목표는 목록에서 빠져야 한다. 목표나 업무가 여섯 개 이상이면 먼저 다섯 개를 보여주고 전체 보기로 확장할 수 있어야 한다.
- [ ] 프로젝트 A를 보는 동안 B의 업무를 누른다. B로 전환한 뒤 해당 목표 작업공간에서 선택 업무와 실제 담당자가 표시되고, 그 담당자가 대화 상자의 기본 선택이어야 한다. 저장 오류를 질문에 넣는 버튼은 전송 전 편집 가능한 초안에만 내용을 추가해야 한다. 질문 초안을 확인·수정해 전송하면 실제 AI 답변 또는 실패 상태가 목표 대화에 저장되어야 하며, 연결·모델 정체성이 표시되어야 한다. 앱 재시작 후 같은 기록이 남아야 한다.
- [ ] 담당자의 AI 연결을 끊거나 비활성화한 상태에서 업무를 연다. 다른 팀원으로 조용히 대체하지 않고 담당자를 사용할 수 없는 이유와 팀 설정 이동을 보여줘야 한다. 사용자가 다른 팀원을 명시적으로 선택하면 그 선택으로 읽기 전용 질문을 보낼 수 있어야 한다.
- [ ] 작업자 답변을 받은 뒤 `해결 지침 제안하기`로 CEO 지침을 제출한다. 진행 중인 호출은 다음 안전 지점까지 대기하고, 중단 목표라면 새 목표 버전을 검토하며 새 승인 절차를 거쳐야 한다. 답변만으로 업무 완료·파일 변경·승인이 일어나면 실패다. 승인 대기 및 분석 재시도 목표에서는 기존 복구 버튼으로 다음 단계에 진입해야 한다.
- [ ] 키보드로 FAB 열기·목표/업무 선택·Escape 닫기를 확인한다. 긴 목록은 패널 안에서 스크롤되고 고정 사이드바와 상단 앱바가 움직이지 않아야 한다. 일반 데스크톱 창에서 성공 토스트와 FAB/패널이 서로 가리지 않아야 한다. 다른 프로젝트로 전환 실패 시 현재 프로젝트가 유지되어야 한다.

### QA-31 대화 중심 목표 작업공간

- [ ] 새 목표를 CEO 카드에서 연다. 목표·상태·담당·다음 행동이 짧게 보이고, 질문 예시와 입력창에서 누구에게 무엇을 물을지 바로 이해할 수 있어야 한다. 예시는 초안만 채우며 실제 AI 답변처럼 보이지 않아야 한다.
- [ ] 연결된 팀원에게 질문을 보내 답변/실패/대기 상태와 실제 연결·모델을 대화에서 확인한다. 질문과 답변은 재시작 후 그대로 남아야 한다. 여섯 번 이상 대화하면 최근 다섯 번을 먼저 보여주고 이전 대화를 펼칠 수 있어야 한다.
- [ ] 입력창 하나와 `전송` 버튼 하나로 질문, 작업 지시, 시작/재개 요청을 보낸다. 질문은 답변만 저장하고, 모호한 요청은 확인 질문을 받는다. 명확한 지시는 안전 지점과 연결된 새 목표로 자동 진행하며, 새 파일 작업은 별도 승인 흐름으로 이어져야 한다.
- [ ] 중단 목표와 승인 대기 목표를 연다. 현재 필요한 행동 카드 하나에서 중단 사유 또는 정확한 승인 범위를 열람하고 안전한 다음 행동으로 이동할 수 있어야 한다. 긴 실패 보고서도 원문을 펼칠 수 있어야 한다.
- [ ] `진행 정보`를 펼쳐 단계 그래프, 업무·담당, 최근 운영 기록, QA 근거, 목표 토큰과 추정 여부를 확인한다. 긴 내용은 축약·확장되고 업무 여섯 개 이상일 때 전체를 펼칠 수 있어야 한다. 창을 좁히고 키보드로 헤더·행동 카드·진행 정보·입력창에 접근하며 대화 영역만 스크롤되는지 확인한다.

### QA-32 팀원 답변의 대화체

- [ ] 연결된 팀원에게 `지금 이 목표에서 막힌 점이 뭐야?`처럼 짧은 질문을 한다. 답변은 같은 언어로 핵심부터 말하고, 매번 역할·읽기 전용 선언, 이해 요약, 사실 목록, 인계표, 무관한 연결 상태를 길게 반복하지 않아야 한다.
- [ ] `재작업 1의 방향 변경 지침 초안을 작성해 줘`처럼 명시적으로 상세 산출물을 요청한다. 필요한 범위·단계·검증 기준은 충분히 작성하되, 실제 상태 변경이나 승인 완료를 주장하면 실패다. 확인하지 않은 파일·명령 결과는 확인했다고 말하지 않아야 한다.
- [ ] 길어진 답변은 원문을 펼쳐 읽고 재시작 후에도 동일하게 확인한다. 과거에 저장된 답변이 새 말투로 조용히 변경되면 실패다.

### QA-33 팀원 전달·CTO/PM 영향 분석·선택 재개

- [ ] 격리 프로젝트에서 한 목표의 파일 작업을 완료·통합한다. 목표 대화에서 그 업무의 담당 팀원을 선택해 방향 변경 지침을 보낸다. 즉시 `접수/안전 지점 대기`로 보이며 팀원이 이미 읽거나 작업 상태가 바뀐 것처럼 표시되지 않아야 한다. 새 목표를 만든 뒤 실행하면 선택 팀원의 실제 읽기 전용 인계 기록 → CTO 영향 분석 → PM 남은 작업 계획 순서가 기록되어야 한다.
- [ ] PM이 기존 완료 작업을 재사용하도록 계획한 사례를 확인한다. 새 목표에 재사용 작업 ID와 새 작업 수가 표시되고, 새 파일 작업만 새 승인 범위에 포함되어야 한다. 이전 목표의 승인으로 새 작업이 실행되면 실패다. 재사용 파일을 외부에서 바꾸고 QA 전에 재확인했을 때 목표가 완료되면 실패다.
- [ ] 새 파일 작업이 전혀 없는 변경에서는 통합 증거가 있는 작업만 재사용하고 독립 QA가 실행되어야 한다. 이 경우 프로젝트 쓰기 승인을 요구하거나, QA 없이 완료되면 실패다. QA 실패 시 새 파일 작업과 승인 필요성을 안내해야 한다.
- [ ] 통합 전 상태의 업무, 증거가 없는 기존 업무, 바뀐 파일, 외부 목표의 ID, 중복 ID, 신규 작업과 같은 파일을 소유하는 재사용 제안은 각각 거부되어야 한다. 어떤 작업을 건너뛰지 못했는지 이유가 남아야 한다.
- [ ] 앱을 재시작하고 인계·재사용 결정·새 작업·QA 기록을 다시 확인한다. 새 목표에서 한 번 더 방향을 변경해도 이전에 검증해 재사용한 업무의 출처가 유지되어야 한다. 이전 버전에 다시 지침을 보내 두 갈래 목표를 만들 수 없어야 한다.
- [ ] 선택 팀원의 AI 연결을 사용할 수 없게 한 뒤 새 버전을 실행한다. 실제 인계가 없는 상태에서 CTO에게 전달됐다고 표시하지 않고 목표가 수리 가능한 이유와 함께 멈춰야 한다. Git 저장소 초기화/첫 커밋처럼 `.git` 메타데이터를 바꾸는 작업은 일반 파일 재사용·통합 단계로 성공 처리되면 실패다.

### QA-34 대화에서 자동 작업 라우팅

- [ ] 연결된 팀원에게 짧은 질문을 `전송`한다. 실제 AI 답변만 저장되고 목표·승인·파일이 바뀌지 않아야 한다. 모호한 문장은 한 가지 확인 질문으로 되돌아오며 작업을 시작하지 않아야 한다.
- [ ] 새 목표에 `이 목표를 시작해줘`를 보낸다. 같은 목표의 실행이 시작되고 CTO 분석·PM 계획으로 진행해야 한다. 승인 대기에서 `승인해줘`를 보내도 승인 상태가 바뀌면 실패다.
- [ ] 실행 중인 목표에 명확한 방향 변경을 자연어로 보낸다. CEO 원문과 AI의 접수 응답, 별도 작업 상태가 대화에 보이고, 현재 호출이 끝나는 안전 지점에서 옛 목표가 멈춰야 한다. 연결된 새 목표가 자동 생성되어 CTO·PM 재계획을 시작하고, 새 파일 작업 전에는 별도 승인 요청이 나타나야 한다.
- [ ] 같은 목표에 지시를 두 번 보내거나 완료 직전 다른 창에서 상태를 바꾼다. 중복 분기나 완료 후 옛 목표 변경이 없어야 한다. 앱 재시작 후 대기 중이던 자동 지시는 한 번만 재개되고 원문·연결 관계가 보존되어야 한다.
- [ ] AI가 구조화된 대화 결과를 잘못 반환하거나 연결에 실패하면 목표 상태를 바꾸지 않고 실패 이유를 대화에 보여야 한다. 자동 재계획이 실패하면 이유와 수동 검토 경로를 보여야 한다.
- [ ] 대화 기록이 여섯 항목 이상이면 최근 다섯 항목이 기본 표시되고 이전 질문과 지침을 모두 펼쳐 볼 수 있어야 한다. 좁은 창에서도 전송 버튼과 상태를 확인할 수 있어야 한다.

### QA-35 GOAL CONVERSATION에서 승인된 Git 첫 커밋

- [ ] 앱을 새 백엔드로 재시작한다. **별도의 격리된 비 Git 폴더**에서 Git 초기화/첫 커밋 업무가 `Task produced no file changes`로 중단된 목표를 연다. 과거에 저장된 Claude 답변이 수동 명령을 안내하더라도 대화 안에 `앱에서 Git 저장소 시작`이 보여야 한다. 일반 목표나 Git과 무관한 중단 목표에는 이 작업이 열리거나 실행되면 실패다.
- [ ] `범위 확인`을 열어 등록된 폴더의 실제 경로, `main`, 파일 목록, 현재 Git 작성자 제안을 확인한다. AI 답변에 적힌 이메일·명령·파일 목록이 자동 선택되면 실패다. 일부 파일만 선택하고 작성자와 메시지를 입력한다. 취소하면 `.git`과 파일이 바뀌지 않아야 한다.
- [ ] 다시 미리본 뒤 파일 하나를 외부 편집기에서 변경하고 승인해 본다. 변경된 미리보기 거부 이유가 나와야 하며 커밋이 생기면 실패다. 새 미리보기에서 **원래 실패 업무에 선언된 파일만** 선택해 승인한다. 선택하지 않은 파일은 첫 커밋에 들어가지 않아야 한다. `main` 커밋 한 건, 동일 프로젝트 ID와 목표 이력, Git 모드 전환을 확인한다. 원격 추가·push·전역 Git 설정 변경은 없어야 한다.
- [ ] 원래 실패 업무의 선언 파일과 커밋 파일이 정확히 일치하고 다른 미완료 업무가 없다면 독립 QA가 시작되어야 한다. QA 통과 전 목표가 완료되면 실패다. 파일 범위가 다르면 커밋 사실은 보이되 원래 목표는 중단 상태로 남아야 한다. QA 연결이 없거나 QA가 실패하면 이유가 보여야 한다.
- [ ] Git init 이후 커밋 전 실패한 격리 폴더에서는 기존 `main` 미커밋 저장소의 범위를 다시 확인해 재시도한다. 앱 재시작 후 커밋 결과와 목표·QA 상태가 남아야 한다. 실제 사용자 프로젝트에서는 이 절차를 시험하지 않는다.

### QA-36 v2 간결한 탐색과 정보 소유권

- [ ] `v2/start-windows.ps1 -DataDir .run-data\v2-qa`로 실행한다. 다섯 메뉴, 전역 프로젝트 전환, 설정의 프로젝트·AI 연결·팀·명세 하위 항목을 확인한다. 원래 앱과 같은 포트 1420을 동시에 사용할 수 없음을 확인한다.
- [ ] 폴더 등록, AI 발견/저장/로그인 확인, 팀 일괄 배정, 새 목표 전달/실행, 승인·중단 복구, 목표 대화, 토큰 상세를 실제 버튼으로 따라간다. 주요 행동이 막히면 이유와 다음 행동이 보여야 한다.
- [ ] 홈에서는 결정할 일과 목표 입력이 우선이고, 업무에서는 목표를 선택해야 그 목표의 업무·실제 기록이 펼쳐지는지 확인한다. Office의 개인 설정과 설정 > 팀의 일괄 설정을 구분한다.
- [ ] 재시작, 다른 프로젝트의 열린 작업, 여섯 개 이상 목표/AI/업무, 좁은 창, 키보드 포커스, 승인 범위와 보안 경계를 확인한다. Ubuntu에서는 별도로 앱을 빌드·실행해 같은 핵심 경로를 검사한다.

상세 과제 순서는 [v2 대화형 QA](../v2/README.md#interactive-qa)를 따른다. 빌드 성공만으로 이 항목을 통과 처리하지 않는다.

### QA-37 v2 중요 알림과 소리

- [ ] 격리 데이터에서 설정 > 알림의 두 스위치가 기본 꺼짐인지 확인한다. 앱 소리를 켜고 시험한 뒤 재시작해 설정 유지 여부를 확인한다.
- [ ] 새 승인 요청과 새 중단 목표를 각각 만든다. 활성 앱에서 종류별 신호가 한 번씩 나타나고 반복 새로고침에서는 다시 울리지 않아야 한다. 앱 재시작 시 기존 대기/중단 항목을 일괄 알리면 실패다.
- [ ] 설치된 Windows v2 빌드에서만 시스템 알림 권한과 실제 알림 센터 표시를 확인한다. 거부 시 스위치가 켜지지 않고 이유가 보이는지, 켜진 뒤 시험 알림이 샘플로 표시되는지 확인한다. 개발 스크립트 결과만으로 Windows 네이티브 알림을 합격 처리하지 않는다.
- [ ] 소리만 켠 경우 앱 생성 소리만 검사하고, 시스템 알림만 켠 경우 앱 생성 소리가 나지 않는지 확인한다. Windows 자체 알림 소리는 OS 설정의 영향을 받는다. 알림 클릭이나 시험 버튼이 승인·목표 상태를 바꾸면 실패다.
- [ ] Ubuntu에서 별도 설치/실행 환경의 알림 표시와 소리를 검증한다. 앱이 닫혀 있는 동안 발생한 일을 백그라운드 알림으로 기대하지 않는다.

### QA-38 v2 Office 캐릭터 회의 (오프라인 시험 → 실제 Claude/Codex)

추가 확인(MAM-014): 앱/백엔드 프로토콜이 27 이상(2026-10-10 기준 28, ADR-0038)으로 일치하는지 먼저 확인한다. 이전 버전 차단 기록은 시각과 빌드를 표시해야 한다. 계획 카드에서 자료 크기·예비 호출 2회를 보고, 승인 전 모든 단계 최대 패킷이 한도 안인지 오프라인 속성 시험 결과를 확인한다. 제안 전 자료를 바꾸어 스냅샷 계속/재검토를 각각 시험하고 제안 뒤 변경은 안내만 나오는지 확인한다. 실패한 한 단계의 재요청과 결과 불명 중복 경고, CRLF 인용, capabilities만 바뀐 연결을 확인한다. - [ ] 10. 실제 응답이 형식을 어기면 예비 호출 안에서 같은 단계·팀원에게 형식 수정 요청을 한 번 기록하고, 두 번째 위반은 이유와 함께 멈춰야 한다. 자료에 없는 인용은 `인용을 자료에서 찾지 못함`으로 표시한다. 앱이 응답 내용을 잘라 보내거나 없는 근거를 지어내면 실패다. 실패 패킷은 CEO가 해당 단계에서 다시 요청할 수 있고, 결과 불명 패킷은 별도 중복 확인 없이 다시 보내지 않아야 한다.

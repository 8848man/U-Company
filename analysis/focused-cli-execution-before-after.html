구현됨 · 실제 Claude 재실행 대기

유지되는 구현 프로세스

CTO 분석→PM 계획 지침→CEO 파일 승인→격리 개발 지침→허용 파일 통합→독립 QA·재작업

강조한 두 단계의 요청문만 달라졌다. 승인 범위, 수용 기준, 격리 작업, 통합 검사와 QA 판정은 변경하지 않았다.

Before / After: 다음 실행에서 달라지는 지시

BEFORE · 이전 요청문

업무는 상세하지만 조사 순서는 넓다

  1. PM이 산출물·파일·수용 기준·근거 경로를 제안한다.
  2. 개발자는 격리 폴더에서 선언 파일을 구현하고 집중 테스트를 한다.
  3. 필수 지침과 근거를 언제 읽고, 전체 검색·긴 명령 출력을 얼마나 제한할지는 일반적으로 안내하지 않는다.
  4. QA 재작업 계획에도 같은 집중 조사 지침은 없었다.
AFTER · 다음 요청문

먼저 문맥을 줄이고, 불필요한 왕복을 줄인다

  1. PM은 업무마다 필요한 기존 근거 파일과 유용한 집중 검증을 지시문에 명시한다. QA 재작업 계획에도 적용된다.
  2. 개발자는 필수 프로젝트 지침과 선언된 근거를 먼저 읽고, 수용 기준에 필요한 다른 파일을 확인한다.
  3. 대상 경로 검색과 필요한 범위의 명령 출력을 우선하고, 바뀌지 않은 큰 파일이나 긴 출력을 필요 없이 반복해서 읽지 않는다.
  4. 중간 설명과 최종 요약을 간결하게 쓰되 변경 사항과 검증 근거는 남긴다. 요구된 넓은 검증은 완료 전에 모두 실행한다.
유지 조건: 토큰을 줄이려고 필수 지침, 근거, 승인된 산출물 파일, 수용 기준 또는 필수 검증을 생략할 수 없다. 모델이 이 권고를 실제로 따랐는지는 다음 실행에서 확인해야 한다.

새 분석으로 정한 우선순위

① 응답마다 읽는 문맥

Claude의 응답당 평균 입력은 같은 레벨 Codex의 약 2.0배(레벨 4), 2.5배(레벨 5)였다. 파일·도구 출력을 필요한 범위로 읽는지 먼저 확인한다.

② 내부 응답 횟수

Claude의 내부 응답은 약 1.65배였다. 반복 조사와 확인을 줄일 수 있는지 본다. 도구 호출 건수만을 목표로 삼지는 않는다.

두 수치는 같은 종류의 업무 두 쌍에서 관측한 차이다. 특정 CLI 전략이 원인이라는 증거는 아니며, 양쪽 모두 입력 캐시를 많이 사용했다.

변경 전 기준선

Dev1과 Dev2는 각 레벨에서 수용 기준이 같고 파일 구성도 dev1/dev2 경로 부분만 다르다. 작업 이벤트 기준 시간이며, 이후 재작업 비용은 위 구현 호출 수치에 포함하지 않았다.

가정으로 살펴보는 기대 효과

아래 조절값은 실제 측정 결과나 절감 약속이 아니다. 변경된 지침이 내부 응답 횟수와 응답당 평균 입력을 줄였을 때 총 입력이 어떻게 달라지는지만 계산한다.

입력 토큰 비교

Codex는 같은 레벨의 참고선이다. 새 지침은 모든 개발자에게 적용되지만, 이 계산은 Claude의 이전 기록만 변경한다고 가정한다. 캐시 읽기·생성 비율과 비용은 예측하지 않는다.

앱에서 CLI까지: 실제 호출 경로

같은 엔진, 공급자별 실행 인자

Codex CLI

codex exec --json --skip-git-repo-check --sandbox workspace-write --cd <격리 작업 폴더> <요청문>읽기 전용 단계에서는 --sandbox read-only. 모델 지정이 있으면 --model 추가.

Claude Code CLI

claude -p <요청문> --output-format stream-json --verbose --permission-mode acceptEdits읽기 전용 단계에서는 --permission-mode plan. 모델 지정이 있으면 --model 추가.

둘 다 저장된 연결의 실행 파일을 셸 문자열 없이 실행한다. 현재 프로덕션 전송은 요청문을 인자로 전달하고 빈 stdin을 닫는다. 실행 호출 제한은 30분이며, CLI 내부 모델 호출 수를 앱이 직접 제한하지는 않는다.

동일 업무 쌍 비교

앱에 저장된 입력 토큰

Codex 입력에는 캐시 입력이 이미 포함된다. Claude 입력은 기본 입력·캐시 생성·캐시 읽기를 합한 값이다.

CLI 내부의 모델 응답 횟수

Codex 로컬 기록의 token_count 이벤트, Claude 로컬 기록의 고유 assistant 메시지를 센 값. 내부 구현 단위가 완전히 같다고 가정하지 않는다.

큰 숫자의 대부분은 캐시 읽기

캐시 읽기캐시 생성기본 입력

캐시 읽기는 같은 맥락을 다시 이용한 양이다. 이를 없애는 것이 개선 목표는 아니다. 내부 모델 호출 횟수와 호출마다 다시 읽는 맥락의 크기를 함께 줄여야 총량이 내려간다. 이 화면의 토큰 수는 청구 비용이 아니다.

  • 확인된 산술적 설명: Claude는 두 쌍 모두 내부 응답이 많고, 응답당 평균 입력도 컸다. 입력 총량의 차이는 이 두 값의 곱으로 설명된다.
  • 확인된 캐시 사실: Codex도 입력의 88~92%가 캐시 입력이었다. “Claude만 캐시를 쓴다”는 설명은 틀리다.
  • 아직 단정할 수 없는 원인: 모델 자체의 효율, 도구 선택 전략, 자동 맥락 관리, 생성 코드 품질 중 무엇이 차이를 만들었는지는 이 두 실행만으로 분리할 수 없다.
  • 결과 범위: 같은 수용 기준과 경로 구성을 가졌지만 생성 결과는 독립적이다. 레벨 4 Dev2는 첫 QA 실패 뒤 별도 재작업을 거쳤다.

앱에서 먼저 개선할 관측값

사용량 기록

호출별 시작·종료 시각, 기본 입력, 캐시 생성, 캐시 읽기, 출력, 내부 응답 횟수를 분리 저장한다. 제공자가 주지 않는 값은 “없음”으로 둔다.

실행 분석

같은 수용 기준의 작업을 짝지어 총량과 QA 재작업을 비교한다. 반복 파일 읽기와 큰 도구 결과는 필요한 경우에만 자세히 조사한다.

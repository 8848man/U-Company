Codex가 적은 토큰으로 끝낸 핵심은 더 짧고 적은 내부 왕복이었다.

레벨 4·5의 Dev1(Codex)과 Dev2(Claude)는 같은 수용 기준과 같은 파일 수의 독립 구현 업무를 받았다. 저장된 호출 기록과 로컬 CLI 세션 로그를 대조하면, Codex는 내부 모델 응답 횟수가 적고 각 응답에서 읽은 평균 문맥도 작다.

여기서 “대용량 데이터”는 앱이 거대한 데이터셋을 한 번 보냈다는 뜻이 아니다. 수차례 파일 조사·작성 중 누적된 모델 입력 문맥을 말한다. 원인에 관한 설명은 관측 사실과 가설을 나눴다.

앱과 두 CLI가 실제로 만나는 지점

① PM이 같은 종류의 업무 배정수용 기준·허용 파일·작업 폴더를 요청문으로 구성한다.
→
② 앱이 CLI를 한 번 실행요청문을 인수로 전달하고 구조화 이벤트를 읽는다.
→
③ CLI가 내부 작업 수행모델 응답 ↔ 파일·명령 도구를 반복한 뒤 최종 답을 돌려준다.
Codex CLIcodex exec --json --sandbox workspace-write --cd … <prompt>

로컬 로그: 응답별 token_usage_record, exec 도구 호출.

Claude CLIclaude -p <prompt> --output-format stream-json --verbose --permission-mode acceptEdits

로컬 로그: assistant 메시지별 usage, 여러 종류의 tool_use.

앱은 CLI 내부의 반복 횟수나 문맥 재구성을 직접 지휘하지 않는다. 두 CLI의 이벤트 이름과 도구 종류가 다르므로 도구 건수는 작업량의 완전한 공통 척도가 아니다.

출력과 도구 패턴

Claude의 출력 토큰도 레벨 4에서 5.6배, 레벨 5에서 7.0배였다. 로컬 로그의 고유 도구 호출은 Codex 16·14회, Claude 31·32회였다. 단, exec 한 번과 파일 도구 한 번은 같은 작업 단위가 아니다.

확인됨

Codex 입력의 88~92%, Claude 입력의 94~95%가 캐시 관련 입력이었다. 따라서 “Claude에 캐시가 없어서”라는 설명은 기록과 맞지 않는다. 캐시 읽기가 많아도 누적 입력 토큰 수는 커질 수 있다.

추론

CLI 내부 전략의 영향

조사·파일 작성·검증을 나누는 방식, 긴 출력의 재투입, 문맥 정리 방식이 왕복 수와 평균 입력을 바꿨을 수 있다. 이 로그만으로 어느 특정 내부 전략이나 모델 고유 능력이 원인이라고 단정할 수 없다.

가장 설득력 있는 답: 이 실행에서 Codex는 같은 종류의 구현을 더 적은 내부 응답으로 진행했고, 매 응답에서 누적된 문맥도 더 작게 유지했다. 캐시 효율 차이 하나로 설명되는 현상은 아니다.

전체 비교와 해석 범위

같은 종류의 업무내부 응답누적 입력평균 입력/응답출력고유 도구소요첫 QA
  • 두 쌍은 저장된 수용 기준이 같고 선언 파일 수와 구조가 대응한다. 구현자가 다른 독립 작업이므로 생성 코드와 경로는 완전히 같지 않다.
  • 시간과 첫 QA는 결과 확인용이다. 시간 차이를 토큰 차이의 단독 원인으로 해석하지 않는다. 레벨 4 Claude의 첫 QA는 실패했고 이후 재작업이 있었다.
  • 서로 다른 제공자의 토큰 정의, 모델, 캐시 가격 정책이 다를 수 있다. 이 자료는 청구 비용, 성능 일반화, 모든 대용량 데이터 처리 성능을 주장하지 않는다.
근거와 계산

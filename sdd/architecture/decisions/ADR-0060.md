# ADR-0060 — Stop the QA loop: criteria the team cannot meet go to the CEO instead of another rework

Status: Accepted (2026-10-26, CEO). Owners: [UF-05 승인](../../userFlow/UF-05-approval.md), [UF-06 복구](../../userFlow/UF-06-recovery.md), [Validation](../../validation.md), [Security](../../security.md), [AI-03 모의 AI](../../aiIntegration/AI-03-adapter.md).

## Context

PostGen's follow-up pass 75e84dac (2026-10-26) failed QA twice with the same three of four criteria, was resumed, and failed again in the same way. The criteria asked for the pre-change commit ID and file hashes and a GitHub push, but `D:\projects\postgen` has no `.git`, teammates and QA work in copies without `.git`, and the team may not push (security). The developer honestly reported "미확인"; QA honestly failed it. The loop had four causes:

1. A planner may write criteria that need something the team cannot have (Git history, a remote, a push, a CEO-only action), and nothing catches it.
2. QA always judges the original tasks' criteria; `재작업` tasks are not judged (`review_targets`), so a repair that relaxes its own criteria changes nothing.
3. QA can only say FAIL, so an impossible criterion spends every rework round before the goal stops.
4. The objective judgement (ADR-0059) lists CEO-only actions as remaining work, so `이어서 하기` plans the same impossible work again.

## Decision

1. **Precondition verdict.** For each unmet criterion QA may add `precondition`: what is missing that the team cannot provide in its folder (history or a commit that does not exist, a remote, network, a push or deployment, an account, data only the CEO has). Teammates are told not to fake such a criterion and to name the missing precondition in their report.
2. **No-progress rule.** After a FAIL, the engine compares the unmet criteria with the previous verdict of the same goal. If they are the same set, the rework did not move anything and no further rework starts.
3. **Criteria card instead of rework.** When any unmet criterion has a precondition, when the no-progress rule fires, or when the repair planner proposes criteria changes (`criteriaChanges` in the repair JSON, optional), the engine stops before rework at a `criteria_decision` card. It lists each stuck criterion with QA's evidence and reason and, when the planner proposed one, a replacement. For each the CEO chooses `빼기`, `바꾸기` (editable text) or `그대로`. `결정대로 다시 확인` applies the changes to the original tasks' criteria (recorded with the old text) and runs QA again on the unchanged files without spending a rework round. `멈추기` blocks the goal as `criteria_blocked`. A rework round is never spent on a stuck criterion.
4. **Recovery.** `해결 요청` on a `criteria_blocked` goal plans a new goal version whose brief names the criteria the team could not meet and why, so the planner drops or rewrites them; it never repeats them unchanged.
5. **Planner facts.** CTO, PM and repair prompts state the facts the planner cannot see: whether the project is a Git repository, that teammates and QA work in copies without Git history, network or push rights, and that criteria needing those, or any CEO-only action, must not be written. A CEO-only request goes in the analysis as a CEO action.
6. **CEO actions in the objective.** The objective judgement separates `remaining` (team work inside the project) from `ceoActions` (push, deploy, publish, accounts, credentials, installing software, creating Git history). When only CEO actions remain, `이어서 하기` starts no pass: the conversation shows the CEO actions and stays open until the CEO does them or closes it.

## Alternatives

- **Reject such criteria with a regular expression at planning:** a criterion like "README does not claim the push happened without evidence" is satisfiable but contains the same words; false rejections would block plans.
- **Let QA pass criteria it cannot check:** hides real failures and breaks the evidence rule (ADR-0038).
- **Lower the rework limit:** stops sooner but still spends a round and gives the CEO no way to change the criterion.

## Consequences

- `criteria.rs` (stuck detection, card, decisions), `engine.rs` (review loop, prompts), `delegation.rs` (`precondition`), `model.rs`, `team_fix.rs`, `objective.rs` (`ceoActions`), `lib.rs` (`decide_criteria`, protocol 42); snapshot `criteriaRequests`; v3 card and objective line; mock AI modes `qa-precondition`, `qa-fail-always`, `repair-criteria`, `objective-ceo`; QA-54.
- Changing or dropping a criterion is a CEO decision recorded with the old text; QA still needs evidence for every remaining criterion.

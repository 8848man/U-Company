# ADR-0064 — Keep a repairable QA criterion and fix its file

Status: Implemented for review (2026-11-07). Owners: [Security](../../security.md), [DM-03](../../domain/DM-03-execution.md), [UF-05](../../userFlow/UF-05-approval.md), [Validation](../../validation.md).

## Context

QA marked a report criterion as unfillable because the `source/` folder was absent, although the criterion explicitly allowed a fallback sentence in the report. The missing sentence was ordinary file work. The engine trusted QA's nonempty `precondition` and stopped at a CEO card offering only criterion changes, unchanged-file QA, or a new goal version. Unchanged-file QA would fail again.

## Decision

QA's `precondition` text alone no longer opens a CEO card. On the first QA failure the engine sends the saved criterion and QA evidence to the PM for an ordinary repair plan. The PM must use the criterion's achievable fallback when one exists, then the developer repairs the approved file and QA checks the integrated result. An unfulfillable criterion reaches the CEO only if the PM proposes `criteriaChanges`, or a repair leaves the same criteria unmet. The existing rework limit and separate new-file scope approval still apply. QA is also instructed to leave `precondition` empty when the criterion itself provides an achievable fallback.

If a no-progress card does appear, the CEO can keep all original criteria and request another file repair on the same goal when a rework round remains. That choice changes no criterion or approved path. The planner cannot propose `criteriaChanges` on this route.

The existing drop, replace, unchanged-file QA, and stop actions remain explicit CEO choices. A false QA precondition is model output, not proof that the team cannot fix the file.

## Alternatives

- Changing the original criterion to accept the incomplete document would hide a real omission.
- Treating QA's precondition as an authoritative immediate stop would repeat the reported false positive.
- Stopping and starting a new goal version would repeat planning and approval for an already approved file.

## Verification

The focused engine tests check that a QA precondition first starts an ordinary repair, that an unchanged failure reaches the CEO after that repair, and that a CEO retry from the no-progress card preserves the criterion. Provider and Windows app behavior require separate verification.

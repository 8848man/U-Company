# ADR-0062 — Application technology and structure presets

Status: Accepted (v4 decision; partial implementation, release verification pending)

Date: 2026-10-31

Affects: [Product](../../product.md), [Architecture](../../architecture.md), [DM-02](../../domain/DM-02-goal.md), [DM-03](../../domain/DM-03-execution.md), [DM-05](../../domain/DM-05-recovery.md), [Security](../../security.md), [Validation](../../validation.md)

## Context

The [design proposal](../../../technology-structure-presets-design.md) leaves D-1 through D-3 open. The existing portable `ai-org-spec/v1` owns project, role, workflow and exception content, not operational selections. `plan_review.rs` calls `PlanRevision` the CEO's note on a pending approval; it has no selection snapshot. [ADR-0046](ADR-0046.md) replans before approval on the same Goal; [ADR-0027](ADR-0027.md) uses a linked Goal and verified reuse after approval. A preset must not expand either approval.

## Decision

1. **D-1, portability:** Store definitions, drafts, and per-project active selections in app-local SQLite. Apply them only to application deliverables of execution Goals. Do not extend or synchronize `ai-org-spec/v1` or write a preset into the project. Sharing or portability needs a later versioned schema, import review, and a new decision in the portable-spec owner.
2. **D-2, plan binding:** Create a separate immutable selection snapshot for each execution plan revision, keyed by project ID, Goal ID, and monotonically increasing plan revision. It contains selected preset IDs, versions, definition digests, resolved decisions, validation result, capture time, and a canonical fingerprint. The plan and its project-write approval bind to that fingerprint and revision in the same transaction. `PlanRevision` remains the CEO's improvement note keyed by replaced approval ID. A setting change only affects a future plan; it does not mutate a pending card, an approved snapshot, or an executing task. The engine rejects a stale or mismatched card before approval or work claim. Replanning captures a new snapshot; older snapshots remain readable.
3. **D-3, reflection:** Automatically put resolved choices only into the new plan draft, its QA checklist, and an expected artifact impact preview. Neither selecting nor saving a preset creates or edits code, config, SDD, accounts, or external resources. Actual writes require the existing declared-file project-write approval; external operations and command permissions keep their separate gates.

The three stages describe decision depth, never quality, skill, or authority. Each is optional and may have at most one active preset. AI creates a complete or explicitly incomplete draft; it cannot activate one. Deterministic validation blocks unresolved dependencies and conflicts. Numeric goals without measurements under stated conditions are `미검증`, never achieved.

## Alternatives and consequences

Putting selections in the portable spec would silently change that schema's owner and import boundary. Reusing `PlanRevision` would conflate a CEO note with a plan snapshot. Applying a choice directly to files would bypass the scoped write decision. These alternatives are rejected. This ADR defines target behavior, not a claim that current code or UI already implements it. A numbered migration, atomic plan/approval binding, and recovery tests are required before enabling it.

## Implementation evidence at 2026-10-31

`WLG-060` records the v5 storage migration, nine built-ins, deterministic combination checks, immutable plan snapshot binding, stale-card rejection, and focused Rust tests. `WLG-061` records a v4 settings/plan screen and focused screen tests, while desktop verification remains open. The current `v4/src/PresetSettings.tsx` invokes `ask_goal` for an AI draft without the exact final payload/provider approval required by Security; `answer_goal_question` adds saved goal, role, task, QA and prior conversation text after that UI request. The current validator checks existing path collisions but has no proven project SDD or API contract owner comparison. Numeric targets can be marked unmeasured, but measured, mismatched and failed desktop QA outcomes have not been verified. The previous focused Vitest run passed while `npm run build:v4` failed at an incomplete `TechPreview` test fixture; this is not a passing v4 build. These are implementation and verification gaps, not revisions to D-1 through D-3 or to the accepted approval boundary.

## Decisions still needed

The owning portable-spec schema must decide any future export/import. The planner and storage implementation must choose a canonical serialization and migration while preserving the fingerprint, key, and atomicity contract above. Framework support versions and measured default targets must be reviewed against a maintained catalog before release; example targets alone are not performance promises.

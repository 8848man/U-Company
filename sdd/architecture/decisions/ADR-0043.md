# ADR-0043 — Goal archive (hide) and permanent delete from 설정 › 백업 삭제

Status: Accepted (2026-10-12, CEO). Owners: [DM-04 Lifecycle](../../domain/DM-04-lifecycle.md), [Security](../../security.md), [UF-10 목표 보관과 백업 삭제](../../userFlow/UF-10-archive.md).

## Context

Finished, abandoned or test goals and meetings stay on every screen (홈, 업무, Office 레일, 토론) forever. The CEO asked for a way to remove a goal from the UI without physically deleting it, and a separate place, 설정 › 백업 삭제, to see what was hidden as short summaries and delete it for good when disk space matters. The hidden list must not clutter a screen; it opens as one dialog.

## Decision

1. **Archive is a visibility overlay, not a status.** `archive_goal` stores a `goal_archive` record (id = goal id, `archivedAt`). The goal keeps its status, records, events and worktrees. The snapshot omits archived goals and everything owned by them (meetings, packets, transmission approvals, contributions, lineage, turns, guidance, tasks, reviews, squads, summaries, approvals, events) and returns only `archivedGoals` summaries: title, kind, status and dates. The title is the AI summary, the meeting topic summary or an 80-character excerpt (ADR-0042).
2. **Only idle goals can be archived.** Execution goals in `new`, `completed` or `blocked` with no `running` or `awaiting_integration` task; deliberation goals that are `completed` or whose meeting is `decision_recorded`, `legacy_closed`, `blocked` or `stopped`. Anything else is refused with a plain reason, and the button shows the same reason. Archiving releases contracted external staff of that goal (ADR-0041). `run_goal`/`resume_goal` refuse archived goals.
3. **Restore** (`restore_goal`) removes the archive record; nothing else changes.
4. **Permanent delete** (`purge_goal`) needs `confirmed = true`, which the UI sends only after the CEO ticks "되돌릴 수 없다는 것을 확인했어요" and presses 영구 삭제. Only archived goals can be purged. It is refused while a goal that is still visible was created from it (a revision via guidance `replacementGoalId`, or a goal drafted from its meeting via lineage). In one transaction it deletes the goal's own records (the kinds in decision 1, plus the revision request that created it) and its events, then logs one `goal_purged` event without a goal id. After the transaction it removes `<app data>/worktrees/<goalId>` if it is a real directory, never following a symbolic link. It never touches the selected project's files.
5. **Token usage records are kept** so project totals stay true; they are not shown as a goal on any screen.
6. **Size shown is an estimate:** stored record bytes, event text and the goal's worktree folder (`backup_usage`). It is read only when the dialog opens.
7. **UI.** The workspace header and the meeting dialog (depth 1) have a two-step `목표 보관`/`회의 보관` button. 설정 gains the `백업 삭제` tab: one card with the count and `보관함 열기`. The dialog shows at most five rows (title, kind, archived date, size, 되돌리기, 영구 삭제…) and a `모두 보기` disclosure, following the content-density rule.

## Alternatives

- **A new `archived` goal status:** rejected. Status drives recovery, assignment and busy rules; changing it would break restore and mix visibility with lifecycle.
- **Delete immediately without an archive:** rejected. The CEO asked for a reversible hide first; permanent deletion stays a separate, confirmed step.
- **Delete token usage too:** rejected. Usage totals would silently drop.
- **Run `git worktree prune` in the project:** rejected. It writes inside the user's repository. For Git projects the removed worktree's admin entry under `.git/worktrees` becomes "prunable" and Git removes it during its own housekeeping (`git worktree prune` or `git gc`).

## Consequences

- Backend protocol 32; frontend minimum 32.
- A purged revision's parent keeps its own records; its revision link disappears with the purged goal.
- Real Windows verification is QA-42.

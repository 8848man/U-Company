# ADR-0074 — 재계획 결함 근거와 재작업 종류 저장

Status: Accepted (2026-11-14, CEO). 구현·실앱 검증 상태는 Worklog를 따른다.
Date: 2026-11-14

Owners: [DM-03](../../domain/DM-03-execution.md), [DM-04](../../domain/DM-04-lifecycle.md), [Security](../../security.md).

## 맥락

ADR-0072의 변경 없음 복구 뒤 PM은 같은 파일을 다시 수정하는 계획을 만들 수 있다. 지금은 그 결함 근거를 요청문으로만 요구해, 근거 없는 수정 계획도 CEO 승인 카드까지 도달한다. QA 재작업 여부는 저장 필드가 아닌 `재작업 N:` 제목 접두어로 판단한다. 사용자가 붙인 제목이 내부 상태를 바꿀 수 있고 제목 수정에 약하다.

## 결정

1. 변경 없음으로 차단된 목표의 연결된 재계획에서 이전 차수의 선언 파일을 다시 수정하거나 삭제하려는 작업은 파일별 `defectEvidence`를 낸다. 엔진은 계획 승인 전에 각 근거의 파일이 그 작업의 선언 파일이자 이전 변경 없음 작업의 파일인지 확인한다. 근거는 현재 파일의 정확한 비어 있지 않은 인용문이거나, 저장된 실패 QA 판정의 ID와 기준 번호다. 인용문은 엔진이 현재 파일을 읽어 다시 확인하고, QA 항목은 저장된 판정의 실패·파일 소유권을 확인한다. 근거가 없거나 맞지 않으면 PM에게 계획을 다시 요청한다. 근거는 수정 필요성의 관찰 자료이고, 완료 판정이나 쓰기 승인이 아니다. 이 규칙은 일반 새 기능 계획이나 다른 파일의 변경을 막지 않는다.
2. 새 QA 재작업 업무는 제목과 별도로 `repairRound` 숫자를 저장한다. 상태·승인 범위·QA 대상 판단은 이 필드를 읽는다. 기존 저장 업무에는 필드가 없으므로 정해진 `재작업 N:` 접두어를 읽는 호환 경로를 둔다. 새 업무 제목은 PM의 원래 제목을 저장하고 화면에 재작업 회차가 필요할 때만 별도 필드를 표시한다. 제목 문자열만 재작업처럼 보여도 새 업무로 분류하지 않는다.
3. 기존 승인 경계와 QA 판정은 유지한다. 계획 근거를 확인해도 계획 카드의 CEO 승인과 독립 QA를 건너뛰지 않는다.

# ADR-0049 — Reference material (long text, images) as app-managed files with an index, and a curator role

Status: Accepted (2026-10-14, CEO; plan document "참조 자료(긴 글·이미지) 입력 기능 개선 계획서", all recommended options). Applies to the engine and the v3 composer. Owners: [DM-06 참조 자료](../../domain/DM-06-references.md), [Security](../../security.md), [GC-03 공유 대화 작업공간](../../goalConversation/GC-03-workspace.md).

## Context

The goal sentence was sent whole to the CTO, the PM, every teammate and QA. Long pasted material was repeated in every call, there was no way to attach a file or an image, and teammates did not receive evidence files at all (fixed separately the same day). The CEO proposed a `work-references/` folder per goal with indexes and an ontology-style relation model, file-based handling of long text like Cowork/Codex, and resized images, and asked for a review. The review kept the direction and changed who creates files: an AI never decides folder or file structure.

## Decision

1. **Storage.** Material lives in `work-references/<YYYY-MM-DD>_<goal id 6>/` inside the project: `text/R<n>-<ascii name>.md`, split text in `text/R<n>-<name>/NN.md` with `00-outline.md`, images in `images/R<n>-<name>.webp`. The app creates, names and deletes these only on CEO actions (attach, remove, send, delete a backup) from fixed rules. Git projects add `/work-references/` to the repository's local `.git/info/exclude` (never `.gitignore`).
2. **Source of truth and indexes.** SQLite `reference` records hold everything; `work-references/INDEX.md`/`index.json` and each goal folder's pair are regenerated views (after every change and at start). An edited index is overwritten; a deleted file is marked `missing`.
3. **Relations (light ontology).** Goal `has_reference` reference; section `part_of` reference; reference `derived_from` its original (name, bytes, SHA-256); task `uses` reference or section (validated evidence); task `assigned_to` teammate; a later goal version `inherits` the earlier version's material without copying. The curator may add `illustrates` and `relates_to` between material, kept only after checks.
4. **Long text.** A paste over 4,000 characters becomes a reference chip; an attached `.md`/`.txt` is always a reference (UTF-8/16, 1 MB). Over 20,000 characters the text is split by rule: headings `#`/`##` (else `###`), then paragraphs, at most about 8,000 characters per section, sections under 1,000 merged, never inside a code block, a table or a sentence. Each section file starts with a source line. The parts concatenate to the original exactly.
5. **Images.** The screen resizes to what the model sees without shrinking again (Claude: 28 px patches; at most 1,568 px and 1,568 patches, or 2,576 px and 4,784 with `세밀하게`), re-encodes as WebP (quality 0.95 for few-colour screens, 0.85 for photos), keeps only the first frame and drops metadata. The original is not stored; its name, size and SHA-256 are. The backend re-checks the WebP header, size and dimensions. A task whose evidence includes an image is assigned only to a teammate whose connection can view images (Claude Code CLI, or a connection marked `images`).
6. **Curator role.** A new role (`reference curation`, seeded as Curator, added once to existing teams) runs when material is attached, only for text over 20,000 characters without headings and for images. It sees numbered paragraphs (or the image) and returns JSON: title, summary, tags, section starts by paragraph number, relations. The app applies a proposal only if sections cover every paragraph once, in order, within 1.5× the size limit, and relations point to known material; otherwise the rule result stays. Without a curator or connection, rules alone apply and the chip says why.
7. **Who reads what.** CTO and PM get the goal index, not the material; the CTO may open files and adds `자료 요약 R<n>[ §k]: …` lines for material without a summary (no extra call). The PM names reference paths in a task's `evidence`; the engine accepts only paths of this goal's (or an inherited) material and refuses `work-references/` as a file to change. Teammates and QA get only their task's evidence, with one index line each; the engine copies it into the isolated workspace and removes the copies before integration. A folder-project copy skips `work-references/`.
8. **Scope.** The v3 new-goal composer first; conversation messages later.

## Revision (2026-10-14, CEO, same day)

Reviewed against how Cowork and Codex handle large inputs (files kept as files; the agent that needs material opens it, heavy reading goes to sub-agents; no pre-curation step), decisions 6 and 7 change:

- **Material has a role.** `요구사항` (requirements) or `참고` (reference) on each text chip; a name or first heading with 요구사항·요건·명세·기획서·spec·PRD·requirement suggests `요구사항`.
- **The PM reads requirements.** The PM still gets the index, but opens and reads the requirement sections before planning; other material it opens only when needed. The engine checks that every requirement section (every section, or the whole file when unsplit) is some task's evidence, or is listed in the plan's `requirementExclusions` with a reason. A miss is a plan-format error and goes back to the PM once (ADR-0048). The approval scope states the coverage, the exclusions and any background sections; the plan card shows `요구사항 N절 중 M절을 업무에 반영`.
- **The curator is off by default** (setting `자료 정리 담당 사용`). On, it runs only for split text that has no headings (topic grouping) or is requirement material, where it may mark a section `background` with a one-line reason; a mark without a reason is ignored, and when unsure it must leave the section a requirement. Off, every section of requirement material counts. Images are not curated; their line comes from the CEO caption or the CTO's `자료 요약`.

## Alternatives

- **PM creates the folders and files:** rejected. Planning is read-only before approval, the PM would have to read all material (the cost this saves), results vary per run, and pasted text could steer file creation.
- **Index files as the source of truth:** rejected; AI or manual edits would drift from the records.
- **Full ontology (RDF/OWL):** rejected; costs tokens to read and adds nothing the six relations do not answer.
- **Separate summary call per attachment:** rejected; the curator runs only where rules fall short, and the CTO already reads the material.
- **App-data folder outside the project:** rejected; CLI teammates and the CTO could not open the files where they work.

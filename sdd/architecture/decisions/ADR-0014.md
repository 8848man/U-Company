# ADR-0014: Goal-scoped dialogue and checkpointed steering

Status: Accepted 2026-10-02

## Context

The engine currently runs a whole goal in a background thread and waits for approval, while the UI reads snapshots. It has no channel for goal-specific discussion or in-flight CEO guidance. Sending a new prompt directly into an active provider call is not a portable adapter capability and could bypass already approved file scope.

## Decision

Persist goal-scoped conversation turns separately from operational events and keep the CEO's exact text. Read-only understanding/discussion calls use the configured AI connection and do not change execution state. Guidance is an explicit, versioned command with status and checkpoint metadata. The engine consumes it only at safe persisted boundaries; a semantic pivot triggers re-analysis and approval review before further writes. A provider's acknowledgment cannot mark guidance applied. The original goal and previous plan/approval remain available for audit.

## Alternatives considered

- Append CEO messages to the currently running CLI stdin: many runtimes do not support it, and timing/approval scope would be ambiguous.
- Rewrite the goal intent in place: loses attribution and makes old tasks/approvals appear to authorize a new objective.
- Create a new goal for every clarification: simple but fragments the team's work and makes mid-task guidance unusable.

## Consequences

The first slice can offer a genuine understanding conversation before full steering is available, but the UI must label that limitation. Checkpoint delivery needs durable revision and scope handling and real concurrency tests. Conversation content is untrusted model output for rendering and is never an approval source. Storage may use the existing object table initially; a later indexed turn table is warranted only after measured query needs.

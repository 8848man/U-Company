# ADR-0033 — Separate v2 frontend over the existing organization engine

Status: Accepted (2026-10-08)

## Context

The UX simplification plan changes navigation and information ownership, while the existing Rust/SQLite engine, approval checks, and several React features remain valid. The current `src/App.tsx` couples six screens to one controller, making a wholesale replacement risky.

## Decision

Build `v2/` as a separate Vite entry and Windows launcher. It uses the same Tauri command contract and app data as the existing UI, reuses stable components from `src/`, and owns the five-destination shell and compact screens. Keep goal execution, approvals, recovery, and persistence in the existing engine. Keep the original launcher and frontend available while v2 is verified. New v2 screens accept typed data and callbacks rather than invoking backend commands themselves. The first v2 release is a source/dev launcher, not a second packaged product.

## Alternatives

- Edit the current screen in place: simpler build setup, but no way to compare or recover the existing interface during migration.
- Fork frontend and backend: independent evolution, but duplicates approval and persistence logic and risks inconsistent stored state.
- Hide old sections with CSS: fast, but leaves duplicated information and inaccessible behavior in the component tree.

## Consequences

The two frontends must honor the same backend protocol and share UI component types. V2 validation includes its own TypeScript/Vite build and navigation smoke check; the original build remains a regression gate. Only one development server can own port 1420 at a time. The v2 launcher reports that conflict. UX completion still requires real Windows and Ubuntu interaction checks recorded in WORKLOG.

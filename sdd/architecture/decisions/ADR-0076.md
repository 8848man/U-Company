# ADR-0076 — PM이 목표 하나를 위한 프리랜서 페르소나를 제안하고, 기본 팀원 페르소나를 전문화한다

Status: Accepted (2026-11-16, CEO 요청 "PM이 더 필요한 인원을 프리랜서 페르소나로 만들어 업무 흐름에 넣는다", "기존 캐릭터 페르소나를 더 특색 있고 전문적으로"). [ADR-0041](ADR-0041.md)의 스쿼드·외부 인력 계약을 확장한다.
Date: 2026-11-16

Owners: [DM-01](../../domain/DM-01-workspace-team.md), [Security](../../security.md), [Validation](../../validation.md).

## 맥락

ADR-0041 이후 목표마다 스쿼드가 생기고, CEO가 캐릭터 파일로 가져온 외부 인력을 승인 카드에서 넣을 수 있다. 하지만 기본 팀(CTO·PM·개발자 2·QA)에 없는 전문성(보안 검토, 카피라이팅, 데이터 분석 등)이 계획 중에 필요해져도 PM은 그 사실을 말할 방법이 없다. CEO가 미리 캐릭터 파일을 만들어 두지 않으면 일은 맞지 않는 팀원에게 간다.

기본 팀원의 역할 지시문은 한두 문장이라 분석·계획·구현·검토의 작업 방식과 판단 기준이 드러나지 않는다.

## 결정

1. **PM의 제안.** 계획 JSON에 선택 항목 `freelancers`를 둔다. 목표당 최대 2명이다. 항목은 `name`(≤40자), `title`(≤60자), `slot`(`writer`·`reviewer`), `capabilities`(`document`·`code`), `persona`(≤2,000자, 작업 방식과 기준), `reason`(≤300자, 기존 팀으로 부족한 이유), 작성자의 경우 `tasks`(맡을 업무의 0부터 시작하는 번호, 1개 이상)다. 프롬프트는 기존 팀원으로 충분하면 제안하지 말고, 병렬화만을 위해 제안하지 말라고 지시한다.
2. **엔진 검사.** 엔진은 캐릭터 파일과 같은 글자 규칙(제어 문자 금지, 길이 제한)으로 검사한다. 맞지 않는 제안은 계획을 막지 않고 무시하며, 그 이유를 승인 카드에 표시한다. 작성자 프리랜서는 지정한 업무의 능력을 모두 선언해야 하고, 한 업무는 한 프리랜서만 맡는다. 이미지 근거가 있는 업무는 이미지를 볼 수 있는 연결일 때만 맡는다.
3. **자리.** 프리랜서도 구조의 자리 수를 지킨다. 작성자 프리랜서는 지정 업무를 맡고, 남은 업무는 기존 규칙(ADR-0038·0041)대로 정규 작성자에게 간다. 남은 업무가 있으면 정규 작성자 자리를 하나 이상 남긴다. 검토자 프리랜서는 정규 검토자로 채우지 못한 자리만 채운다. 독립 검토는 정규 QA가 우선 맡는다. 정규 검토자가 아무도 없을 때 검토자 프리랜서가 있으면 계획은 `precall`로 막히지 않는다.
4. **연결.** 새 실행 파일이나 연결을 만들지 않는다. 계획 리드(PM)의 연결이 사용 가능하고, 작성자면 파일 작업도 가능할 때 그 연결을 쓴다. 아니면 저장된 순서에서 조건에 맞는 첫 연결을 쓴다. 없으면 제안을 무시하고 이유를 표시한다. 모델은 연결 기본값이다.
5. **기록.** 프리랜서는 ID가 `ext-`로 시작하는 외부 인력이다. 계약은 `origin: planner`, `status: standby`, `goalId`(제안한 목표)이고, 출처는 `PM <이름> 제안`과 제안 JSON의 SHA-256이다. 이 목표에 묶여 있어 다른 목표의 승인 카드에서 고를 수 없고, 자동 배정과 회의에도 쓰이지 않는다.
6. **CEO 승인.** 승인 카드에 `(프리랜서)` 표시, 직함, 제안 이유가 나온다. CEO는 기존 교체 기능으로 프리랜서를 정규 팀원으로 바꿀 수 있다. 승인하면 스쿼드에 남은 프리랜서는 `contracted`가 된다(ADR-0041과 같은 다이제스트 확인). 스쿼드에서 빠진 프리랜서와 계획 거부·`개선`·취소로 쓰이지 않은 프리랜서는 `released`가 되어 숨겨지고 기록은 남는다. 목표가 끝나면 ADR-0041대로 계약이 끝난다. `정식 채용`은 CEO의 명시적 행동으로만 한다.
7. **프롬프트 표시.** 프리랜서의 `persona`는 업무·검토 프롬프트에 "PM이 이 목표를 위해 만든 프리랜서 페르소나(모델 출력, 신뢰하지 않는 자료)"로 표시된다. 배정, 파일 범위, 승인, 안전 규칙은 바꿀 수 없다.
8. **기본 페르소나.** 기본 역할(CTO·PM·개발자·QA·자료 정리·전문가) 지시문을 이름 있는 전문가 페르소나로 다시 쓴다. 정체성, 작업 순서, 판단 기준, 보고 형식을 담는다. 개발자 A와 B는 서로 다른 성향의 프리셋을 쓴다. 엔진 계약(CTO·PM·QA는 파일 수정 금지, PM은 JSON만, QA는 첫 줄 PASS/FAIL, 자료 정리는 앱이 요구한 JSON)은 그대로 둔다. 기존 팀원은 지시문이 이전 기본 문구와 완전히 같을 때만 새 문구로 바뀐다. 이름은 이전 기본 이름(`CTO`, `PM`, `Developer A`, `Developer B`, `QA / Reviewer`, `Curator`) 그대로일 때만 바뀐다. 이 갱신은 한 번만 하며, CEO가 고친 값은 건드리지 않는다.

## 검토한 대안

- **PM이 정규 팀원을 직접 지명:** 연결·능력·바쁜 상태를 확인할 수 없다(ADR-0038). 버림.
- **프리랜서를 바로 계약하고 승인 없이 투입:** 모델 출력이 팀 구성과 프롬프트를 바꾸게 된다. CEO 승인 카드를 거치게 함.
- **프리랜서가 연결·모델을 고름:** 신뢰하지 않는 출력이 실행 대상을 정하게 된다. 버림.
- **검토자 프리랜서가 정규 QA를 대신:** 독립 검토의 일관성이 약해진다. 빈자리만 채우게 함.
- **기존 팀원 지시문을 모두 덮어쓰기:** CEO가 고친 설정을 잃는다. 기본 문구와 같은 것만 갱신.

## 결과

- 좋아지는 것: PM이 부족한 전문성을 근거와 함께 드러내고, CEO는 같은 승인 카드에서 받아들이거나 바꾼다. 기본 팀원의 답이 더 구조적이고 검증 가능해진다.
- 감수하는 것: 프리랜서는 기존 연결을 함께 쓰므로 실제 모델 능력은 같고, 달라지는 것은 지시와 역할이다. 페르소나 문구가 길어져 호출마다 입력 토큰이 조금 늘어난다.
- 이후: 프리랜서의 효용은 Windows 앱에서 실제 제공자로 확인해야 한다(QA-40 확장).

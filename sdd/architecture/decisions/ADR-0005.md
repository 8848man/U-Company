# ADR-0005 — Keep a project registry and bind goals to stable project IDs

Status: Accepted

Date: 2026-10-01

Affects: [Product](../../product.md), [Domain](../../domain/00_index.md), [Security](../../security.md)

Context: A single mutable `selected` project made switching obscure and could redirect an older goal to a different repository. The user needs several projects in one workspace and a folder chooser. Adding a cross-platform dialog plugin would introduce a new dependency when the existing Windows environment can use its native folder interface.

Decision: Persist registered projects with stable IDs while retaining one active project pointer. Capture the ID on goal creation and resolve it for every execution or resume. Add existing Git folders through a native OS folder chooser and offer an explicit new-project action that creates a previously nonexistent child directory and initial Git repository. The platform boundary owns Windows folder selection and macOS/Linux equivalents; unavailable pickers return a clear error and keep a path-entry fallback. Use the current SQLite object store with a versioned data migration so existing selected projects and goals remain readable.

Alternatives: One project per app data profile hides switching and fragments team setup. Binding goals to a path string preserves safety but makes rename/re-registration harder. Adding the Tauri dialog plugin gives one API but requires fetching and installing new project dependencies on this machine.

Consequences: Project switching is safe for queued goals and visible in the UI. Existing goals without a project ID remain visible but cannot execute or resume until the user submits a new goal under a known project; silently assigning a historical goal to the current project would be unsafe. OS picker availability differs by platform and needs platform-specific checks.

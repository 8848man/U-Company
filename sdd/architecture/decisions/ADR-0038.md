# ADR-0038 — Deliverable task contract, checked single assignment and per-deliverable review

Status: Accepted (2026-10-10). Implements the first slice of the [v3 improvement plan](../../v3-improvement-plan.md) ("1차 v3 개선 패키지"). Extends, without rewriting, the parallel task and recovery decisions of [ADR-0003](ADR-0003.md), [ADR-0008](ADR-0008.md) and [ADR-0010](ADR-0010.md)/[ADR-0012](ADR-0012.md) as recorded in [DM-03](../../domain/DM-03-execution.md) and [DM-04](../../domain/DM-04-lifecycle.md).

## Context

The first v3 customer goal is a launch-preparation pilot: from local material, the team produces three separately owned documents (for example a customer/problem hypothesis, an offer/message draft and a pre-launch checklist) and the CEO accepts them as one package. The current engine decomposes every goal into file-changing tasks, assigns developers round-robin by list position, marks tasks `running` before checking the connection, and completes a goal when the QA reply's first line starts with `PASS`. Nothing stores per-deliverable acceptance criteria, the input evidence a deliverable was based on, why a teammate was chosen, or which criterion QA checked. A provider failure before any process starts leaves the task `running` and the goal unrecoverable without a new goal version. Paperclip's delegation and atomic checkout and Pixel Agents' state display are design references only; the U Company engine stays the only owner of state and approval ([v3 plan](../../v3-improvement-plan.md)).

## Decision

1. **Deliverable task contract.** Each PM-proposed task carries, in addition to title, instructions, declared output files and dependencies: one-line `deliverable`, 1–8 `acceptance` criteria, 0–8 `evidence` input paths inside the selected project, and a required `capability` (`document` or `code`). The engine rejects, before any approval is requested, a task with no criterion, an unknown capability, or an evidence path that is unsafe, outside the project or not an existing regular file. Evidence paths are read-only context: they never enter the write approval and their contents are not copied into the plan. Legacy tasks without these fields remain readable and keep the previous QA rule.
2. **Checked single assignment.** The engine, not the PM, chooses one assignee per task from enabled implementation characters whose saved connection is usable and can write files in an isolated workspace (a CLI or an adapter declaring file capability; HTTP text endpoints are excluded) and who is not busy under the shared [DM-01](../../domain/DM-01-workspace-team.md) rule for any other goal or meeting. It balances by the number of tasks already assigned in the plan, then by stable roster order, and records the reason. QA, PM and CTO are never assigned implementation tasks. No eligible candidate blocks the plan before approval with the reason per task; the engine never substitutes another AI silently.
3. **Transactional claim before any call.** Moving a task from `pending` to `running` happens in one SQLite transaction that re-checks: the task is still pending, its dependencies are completed, the goal's project-write approval is still approved, the assignee is enabled, its connection is still usable and capable, and it holds no other running task or meeting reservation. Only after the claim commits is a workspace prepared and a provider called. A failed claim leaves the task `pending`, makes no call, and blocks the goal with a pre-call reason.
4. **Resume of never-started approved work.** A blocked goal whose project-write approval is approved, whose not-completed tasks are all `pending`, and which has no running, awaiting-integration, failed or interrupted task may resume its existing plan through the guarded resume command. Integrated tasks stay completed by their proof; nothing is re-sent automatically.
5. **Per-deliverable review.** For contract tasks, QA returns one JSON object: overall verdict, and for every task its verdict, one result per acceptance criterion with `met` and concrete evidence, and unverified items. The engine stores a review record per task and round. A goal completes only when the overall verdict is pass and every contract task passes with every criterion met and evidenced. A failing verdict uses the existing rework loop and cap. A missing or malformed per-deliverable answer is a QA failure of form, not a pass: the goal blocks with that reason and the rework counter is not spent.
6. **Classified block reasons.** The engine records a block kind (`precall`, `approval_denied`, `interrupted`, `integration_conflict`, `qa_failed`, `qa_form`, `provider`, `other`) with the reason when it blocks a goal. The kind comes from the engine site that blocked, never from model text. Recovery choices still follow saved state ([GC-04](../../goalConversation/GC-04-recovery.md)).

## Alternatives

- Keep round-robin assignment and let the model choose by prose: rejected; it cannot check capability or busy state and hides why a teammate was chosen.
- Import Paperclip's scheduler and database: rejected for the first slice; it would create a second state owner and approval model.
- Let QA keep free-form `PASS`/`FAIL` and parse criteria loosely: rejected; a first-line `PASS` cannot show which deliverable met which criterion.
- Auto-retry a failed claim or provider call: rejected; it can duplicate external work and widen effective scope without a CEO decision.

## Consequences

Plans become slightly longer and a PM reply missing criteria now fails before approval instead of after. A goal may block where it previously completed on a bare `PASS`. Two concurrent goals cannot share an implementation teammate. The new fields are additive (`serde(default)`), so no schema version change is needed; older records display without contract details. Real Windows behaviour of the PM/QA JSON contract with Claude/Codex is an acceptance check, not an assumption.

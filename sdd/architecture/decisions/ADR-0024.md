# ADR-0024 — Persisted-state recovery in one goal workspace

Status: Accepted

Date: 2026-10-08

Affects: [Goal conversation](../../goalConversation/00_index.md), [Security](../../security.md)

## Context

Blocked-goal controls opened a reason-only dialog while retry, approval, and revision lived elsewhere. Users could see why work stopped but could not continue from that point. The engine supports only narrow same-goal retries; treating every failure as resumable would misrepresent isolated task and approval state.

## Decision

Route blocked-goal entry points into the existing goal workspace. Select recovery actions from stored goal stage, tasks, approvals, and guidance. Show the persisted report as evidence, but never parse its prose as authorization. Reuse existing approval, retry, approved-plan resume, and versioned CEO guidance commands. For later failures, require a CEO-authored new goal version and fresh plan/approval. Provider diagnosis links to the AI connection controls without running a login or retry automatically.

## Alternatives

- Add action buttons to each reason dialog: duplicates state logic and leaves Office, board, and CEO inconsistent.
- Automatically replay failed developer sessions: existing adapters and worktree integration do not provide a safe generic replay contract.
- Create a new goal from the failure report automatically: adapter output is untrusted and cannot define CEO intent.

## Consequences

The workspace becomes the recovery surface while the engine remains the authority for every transition. Native continuation after execution/integration failure remains a separate backend capability to design and validate later; the UI must describe a linked revision truthfully.

# ADR-0025 — Open-work launcher reuses goal conversation

Status: Accepted

Date: 2026-10-08

Affects: [Goal conversation](../../goalConversation/00_index.md), [Security](../../security.md)

## Context

Unfinished work is spread across the CEO, board, Office, and project views. A user needs a stable entry from any tab to the worker responsible for one task and a path from discussion to an actionable resolution. A second task-chat store or a direct worker command would fragment the goal history and blur read-only advice versus approved execution.

## Decision

Build a viewport-fixed launcher from persisted goals, tasks, and guidance. Selecting a task opens the existing goal workspace with a task focus and its assigned agent selected. Use the existing `ask_goal` read-only turn and saved goal conversation; display task context in the UI and editable question draft. State changes continue through existing approval, retry, and CEO guidance/revision commands. Cross-project selection invokes the existing project switch before opening a goal.

## Alternatives

- New task-specific conversation and command endpoints: duplicates persistence, provider identity, and approval rules before task-level steering has a safe engine contract.
- Worker reply directly resolves a task: model output cannot authorize project writes or mark engine transitions complete.
- Launcher limited to the current project: hides unfinished work after switching projects.

## Consequences

The worker can diagnose and recommend a next step, while the CEO makes the state-changing decision. Task-level execution continuation remains governed by the engine's current recovery limits. A later dedicated task conversation would need an explicit task ID, durable turn identity, and new approval semantics rather than treating a goal turn as a task command.

# ADR-0039 — v3 frontend shell over the same engine

Status: Accepted (2026-10-10). Follows the pattern of [ADR-0033](ADR-0033.md) (separate v2 frontend over the existing engine).

## Context

The CEO asked for a v3 app in the project root built from the first v3 package ([v3 improvement plan](../../v3-improvement-plan.md), [ADR-0038](ADR-0038.md)). The package requires the existing five menus and single goal workspace, the engine as the only owner of state and approval, and the simplest possible CEO flow for the launch-preparation pilot.

## Decision

Add `v3/` as a separate Vite entry (`v3/index.html`, `v3/vite.config.ts`, launchers) that runs the same Tauri binary, commands, SQLite data and security rules as v2. It reuses v2 navigation, Work, Projects, Connections and notification screens and the shared `src/` components. Only Home differs: a readiness card when the team cannot run, one command box with an optional pilot example, a decision inbox using the shared reason → last fact → owner → next action reading, and per-deliverable goal cards. The approval dialog, goal workspace and Office rail use the shared `DeliverablePanel`/`deliverables.ts` selectors so every surface shows the same saved facts. The backend protocol gate (28) applies to v3 as to v2.

## Alternatives and consequences

Changing v2's Home in place would remove the comparison point the user keeps for v2 QA. A new backend or a Paperclip-style server would create a second state owner, which ADR-0038 rejects. The chosen shell copies the v2 controller (`v3/src/App.tsx`); this duplication is migration debt to remove by extracting a shared controller hook. Only one launcher can use port 1420 at a time. v2 and v3 read the same data unless a separate `-DataDir` is given.

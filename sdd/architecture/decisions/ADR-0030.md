# ADR-0030 — First-class approved Git bootstrap

Status: Accepted

Date: 2026-10-08

Affects: [Security](../../security.md), [Goal conversation](../../goalConversation/00_index.md)

## Context

ADR-0023 kept Git initialization outside the agent file-task loop because `.git` metadata from an isolated task copy cannot be integrated. A blocked goal therefore receives a chat answer containing commands for the CEO to run manually. This does not provide the intended in-app permission and recovery flow.

## Decision

Keep `.git` metadata outside ordinary file-delta tasks. Add a fixed local Git bootstrap operation: preview the registered root and candidate files, let the CEO select exact paths and enter author/message, then approve and execute Git init, explicit-path staging, and one initial commit in the project root. Revalidate preview fingerprints and reject changed files. Refresh the existing project record on success. Persist approval and outcome evidence. Never execute AI-generated command text. This supersedes ADR-0023's external-only bootstrap conclusion while preserving its isolation rationale.

## Alternatives

- Copy `.git` from an agent workspace: bypasses the integration allowlist and live repository checks.
- Execute shell commands extracted from the AI reply: untrusted model output would gain command authority.
- Keep asking the CEO to run commands: leaves the blocked work unrecoverable within the app.

## Consequences

The operation is deliberately narrower than arbitrary terminal access. It can leave an unborn `.git` after a Git failure; the UI must report that partial state and allow an inspected retry. A successful commit proves repository setup only. If its file scope exactly matches a blocked bootstrap task and all other tasks are complete, the engine may record integration proof and ask independent QA to validate the goal. Unrelated work is never declared complete by the commit.

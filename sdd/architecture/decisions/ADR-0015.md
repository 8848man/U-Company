# ADR-0015: Separate provider protocols from process transport

Status: Accepted 2026-10-04

## Context

One `runtime.rs` function currently selects a vendor, constructs its CLI arguments, spawns the process, handles stdin/stdout/stderr and timeouts, and parses the response. A goal reported a Claude failure, but its invocation ledger showed Codex. The generic exit message also discarded structured stdout errors. The organization engine cannot be used as an isolated provider diagnostic tool.

## Decision

Keep `AiConnection` and the engine call shape. Introduce a provider boundary that chooses a built-in CLI protocol and parses the provider response. Keep process spawning, closed stdin, output draining, timeout, and exit handling in a shared process transport. Retain HTTP and external adapter protocols behind the same engine-facing entry point. Add a standalone harness that exercises the provider entry point with a synthetic fixture before optional real calls. Failure messages carry provider, transport, operation, class, exit code, and bounded safe details.

## Alternatives

- Switching Claude to an API/SDK would add credential and approval changes without evidence that Claude caused the recorded failure.
- Adding a PTY or interactive runtime would increase lifecycle and security complexity; the synthetic Claude print call works without one.
- Replacing the entire adapter registry and persistence schema would be disproportionate to this diagnostic boundary.
- Treating the stdin notice or exit code 1 as success would hide a failed invocation.

## Consequences

Built-in CLI providers remain easy to add without changing the process supervisor. The harness can establish provider health independently of Tauri and SQLite. An actual historical failure cannot be declared fixed until a fresh authorized app invocation succeeds; synthetic checks only verify the shared execution path.

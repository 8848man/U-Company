# ADR-0063 — Fewer command cards, and an opt-in "allow all commands" mode per goal conversation

Status: Accepted (2026-10-31, CEO). Owners: [Security](../../security.md), [AI-03 어댑터](../../aiIntegration/AI-03-adapter.md), [UF-05 승인](../../userFlow/UF-05-approval.md). Refines [ADR-0058](ADR-0058.md); supersedes its decision 1 for safe rules only.

## Context

After ADR-0058 the CEO saw work stop for commands nobody needs to approve. The cause, read from `permissions.rs` and the Claude Code permission rules (code.claude.com/docs/en/permissions, 2026-10-31):

- Claude Code refuses a chained line such as `cd <path> && npm test` when any part is not allowed. `cd` alone is a built-in read-only command, but `cd` outside the working directory, `cd` followed by `git`, or `cd` with a redirect is refused in `acceptEdits`.
- The engine split the refused line and made a rule for every part, so `cd …` appeared on the card. A rule keeps the first argument, so `cd C:\…` or `cd ..` was classified "outside the project" and left out of `모두 승인`. A grant for `cd A` never covered `cd B`, so the card came back whenever the folder changed.
- Grants lived only in one goal conversation, so the same safe test command was asked again in every new goal of the project.

The CEO also asked for a mode where a trusted goal runs without command cards. A command denylist cannot provide that safely: the same effect is reachable through other programs (`node -e`, scripts, `npm test` running package scripts), Claude Code documents that Bash rules are not a security boundary, and on native Windows Claude Code runs commands unsandboxed with the user's rights. The isolated task folder and declared-file integration already protect the selected project's files; what such a mode cannot protect is the rest of the computer, the network and the user's accounts.

## Decision

1. **Read-only commands are not rules.** `cd`, `ls`, `dir`, `pwd`, `echo`, `cat`, `type`, `head`, `tail`, `grep`, `findstr`, `wc`, `which`, `where`, `diff`, `stat`, `du`, `true` never become a card line or a grant, and are ignored when the engine checks whether grants already cover a refused line. The app grants nothing for them; Claude Code still decides whether they run. A refused line made only of such commands (for example `cd` outside the task folder) is not resumable: the task continues as reported and QA judges it.
2. **Run from the task folder.** Every writing and QA prompt tells the teammate to run commands from the task folder root and not to change directory outside it.
3. **Safe grants belong to the project.** A rule the app classifies `safe` (the class `모두 승인` already uses) that the CEO approves on a plan card or a command card is saved for the goal's project and applies to later goals of that project. `individual` rules stay in the goal conversation as in ADR-0058. `blocked` rules are never granted. Grants still reach no other project, and model output still cannot add a rule.
4. **Allow-all mode (`명령 전부 허용`) is opt-in per goal conversation.**
   - Off by default. The CEO can turn it on only with a button on a pending plan card of the conversation (the moment the goal is proposed), after a confirmation dialog that states the risks in plain words; the backend requires the explicit confirmation flag and a pending plan approval of that conversation. Chat text, model output and repository text cannot turn it on. It can be turned off at any time; turning it off affects the next provider call.
   - It applies to Claude writing tasks and their resumes only: they run with `--permission-mode bypassPermissions`. QA (`dontAsk` in a disposable copy), analysis, planning and meetings (`plan`) are unchanged. Codex keeps `workspace-write`; other providers are unchanged.
   - Every other safeguard stays: the isolated task folder, integration of declared files only, baseline conflict checks, scoped project-write approval, and CEO-only push, deployment, publishing, accounts and credentials.
   - It never reaches another goal conversation or project and is not inherited by a new conversation.
5. **No push or pull request in allow-all mode.** The Claude call gets three layers:
   - deny rules `--disallowedTools` for `git push`, `gh pr`, `gh api`, `gh repo`, `gh release`, `gh workflow`, `npm publish`, `cargo publish` (deny rules apply in every mode);
   - process environment: `GIT_CONFIG_COUNT` entries that rewrite every push URL to an unusable transport (`url.ucompany-push-blocked://.pushInsteadOf` with an empty prefix) and clear `credential.helper`, plus `GIT_TERMINAL_PROMPT=0` and `GCM_INTERACTIVE=never`; fetch is unaffected;
   - GitHub CLI isolation: `GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN`, `GITHUB_ENTERPRISE_TOKEN` removed and `GH_CONFIG_DIR` pointed at an empty app-owned folder, so `gh` is signed out.
   The card and the confirmation dialog say this is a strong default, not a guarantee against a command written to evade it.
6. **What ran is recorded.** For a Claude writing call the provider reads the `Bash`/`PowerShell` commands from the `tool_use` stream events and the engine records them as a `commands_run` task event (third depth), in both modes.
7. **The mode is always visible.** While it is on, the goal conversation has a red band on its outer edge and a header line `명령 전부 허용 중` with `끄기`; the plan card shows the same state. This is the UXP-3 control line for this mode.

## Alternatives

- **A denylist (`allow everything except delete …`)**: rejected; bypassable and gives a false sense of safety.
- **Run Claude in a WSL2 sandbox with OS-level file and network limits**: the real long-term answer, deferred; it needs WSL2 setup and a different process model on Windows.
- **Project-wide allow-all switch**: wider than one goal the CEO looked at.

## Consequences

- `permissions.rs` (read-only commands, coverage), `permissions_flow.rs` (project grants, mode, executed-command record), `provider.rs` (bypass profile, push/PR block, executed commands), `engine.rs` (one line recording executed commands), `lib.rs` (mode commands), `src/CommandModeControl.tsx` and `GoalChat.tsx` (band, toggle).
- The mode toggle loads and changes its own state through two backend commands instead of the shared v3 controller, because the controller file was being changed by another task; the duplication and its removal path are recorded in the worklog.
- Requires a Claude Code version that knows `bypassPermissions` and `--disallowedTools` (both exist in 2.1.310).

# ADR-0072 — 변경 없는 작업의 검증과 반복 복구

Status: Accepted (2026-11-10, CEO). 구현·실앱 검증 상태는 Worklog를 따른다.
Date: 2026-11-10

Owners: [DM-03](../../domain/DM-03-execution.md), [DM-05](../../domain/DM-05-recovery.md), [GC-04](../../goalConversation/GC-04-recovery.md), [Security](../../security.md).

## 맥락

일반 작업이 선언 파일을 바꾸지 않으면 통합 함수가 오류를 내고, 실행 루프가 이를 실제 패치 충돌과 같은 `integration_conflict`로 저장한다. ADR-0053은 재작업에만 예외를 둔다. 해결 요청은 새 목표 버전을 만들지만 변경할 것이 없었다는 사실을 전달하지 않아 같은 계획이 반복될 수 있다. 첫 통합 오류는 같은 차례의 다른 작업 통합도 막는다.

## 결정

1. Dev의 `no_change_needed`는 관찰 보고다. 기존 응답 본문에 넣는 구조화된 JSON의 존재 근거 `{file, quote}`는 선언 파일의 현재 바이트에서 확인한다. 부재 근거 `{pattern, files}`는 모든 경로가 선언 파일 안에 있어야 하며 엔진이 동일한 **리터럴** 패턴 검색을 각 파일의 현재 내용에서 다시 실행한다. 패턴은 비어 있거나 지나치게 길 수 없다. Dev가 주장한 검색 결과는 쓰지 않는다. 결과와 파일별 SHA-256, 확인 시각을 별도 `task_no_change_proof`로 저장한다. 유효하지 않은 형식이나 확인 실패는 통상 변경 0건 실패다.
2. 근거가 유효하고 변경이 없으면 작업을 `completed`로 옮겨 다음 의존 작업을 진행할 수 있게 한다. 이 상태는 구현 작업의 종료일 뿐 산출물 합격이 아니다. 독립 QA는 목표의 모든 원래 산출물 수용 기준을 판정하며, 변경 없음 근거는 자료로만 받는다. QA 합격 뒤에만 기록에 QA 판정 연결을 넣는다. QA 불합격은 기존 재작업 흐름을 따른다. 변경 없는 작업에는 `task_integrated` 이벤트나 `task_proof`를 만들지 않는다.
3. 재작업의 변경 0건은 ADR-0053처럼 다음 QA로 보낸다. 새 재작업은 같은 별도 기록에 파일 해시와 확인 시각을 남긴다. 근거가 없으면 빈 근거로 명시하고 재사용 후보에서는 제외한다. 기존 `task_unchanged`만 남은 저장 데이터는 읽을 수 있으나 자동 재사용 후보는 아니다. 재작업 종류 필드를 작업 저장 모델에 추가하는 일은 기존 제목 접두어를 읽는 여러 경로의 마이그레이션이 필요하므로 이 라운드에서는 접두어를 유지하고 후속 구조 정리 후보로 둔다.
4. 다음 버전에서 변경 없음 작업을 재사용하려면 기록의 모든 선언 파일 SHA-256이 현재와 일치하고 연결된 독립 QA가 합격했어야 한다. ADR-0068의 **수정 파일 소유권 전환**은 변경 없는 작업에 발생하지 않는다. 기존 통합 증거와 변경 없음 기록은 별개의 증거 유형이며 섞어 쓰지 않는다.
5. 통합 오류는 `NoChanges`, `PatchConflict`, `ScopeViolation`, `ReuseMismatch`, `Other`로 구분한다. 변경 0건은 `no_changes`, 실제 패치 충돌은 `integration_conflict`, 승인 범위·재사용 증거 문제는 각 원래의 차단 의미를 보존한다. 같은 차례의 독립 작업은 각각 통합을 시도한 뒤 오류를 모두 기록하고 다음 차례로는 넘어가지 않는다. 대표 멈춤 유형 우선순위는 승인 범위 위반 → 재사용 증거 불일치 → 실제 충돌 → 근거 없는 변경 0건 → 기타다. 개별 오류의 종류는 모두 남긴다.
6. `no_changes` 복구 카드는 `충족 처리`와 `재계획`을 보여 준다. 충족 처리는 엔진 확인 근거가 있을 때만 가능하다. 근거가 없으면 버튼은 필요한 확인 자료를 안내하며 완료로 옮기지 않는다. 엔진이 확인한 근거가 있으면 해당 작업을 `completed`로 옮기고 같은 차례의 독립 작업 결과를 보존한 뒤 남은 `pending` 작업을 기존 승인 범위에서 계속 실행한다. 모든 작업이 끝나면 목표 전체의 원래 산출물을 독립 QA가 판정한다. 새 파일이 없고 기존 승인 범위가 유지되므로 새 쓰기 승인은 없다.
7. 재계획은 새 목표 버전과 새 계획 승인을 사용한다. 요청문은 저장된 파일·변경 없음 사실을 명시하고, 같은 파일의 새 수정 작업에는 현재 결함 인용 또는 실패 시험을 요구한다. 같은 목표 계보에서 동일 `(오류 종류, 정렬한 선언 파일 집합)`이 두 번 발생하면 자동 새 버전 생성은 중단하고 CEO에게 충족 처리 또는 직접 지시만 보여 준다. 서명은 작업 ID와 표시 문구를 사용하지 않는다.
8. CEO 문구에는 일어난 일, 원본 프로젝트 파일의 변경 여부를 **저장된 통합 기록으로 확인 가능한 범위에서만**, 권장 행동을 보여 준다. 확인할 수 없으면 변경 여부를 모른다고 표시한다. 영어 내부 오류는 상세 기록에 남긴다.

## 대안과 한계

- 파일에 인용문이 있다는 이유만으로 작업 완료를 인정하지 않는다. 부재 근거도 정규식 대신 리터럴 검색으로 시작한다. 복잡한 정적 분석은 QA의 몫이다.
- 변경 없는 일반 작업을 무조건 실패시키면 이미 충족된 목표가 막힌다. 무조건 성공시키면 Dev의 주장만으로 완료가 된다.
- 부분 통합 뒤 일부 작업이 막히면 통합된 변경을 롤백하지 않는다. 저장된 작업별 증거와 원본 파일 상태를 보여 준다.
- 수정·삭제 계획의 결함 근거를 계획 단계에서 강제하는 M4는 이번 범위에서 제외하고 다음 후보로 기록한다.

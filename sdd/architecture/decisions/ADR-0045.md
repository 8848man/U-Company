# ADR-0045 — SDD origin in onboarding and planning: folder first, development goals only

Status: Accepted (2026-10-13, CEO); implemented the same day (backend protocol 34). Owners: [SI-03 SDD 구조 감지와 부트스트랩](../../specImport/SI-03-origin.md), [DM-03 실행](../../domain/DM-03-execution.md), [UF-05 범위 승인](../../userFlow/UF-05-approval.md), [Security](../../security.md).

## Context

[ADR-0044](ADR-0044.md) placed the SDD origin card in 설정 › 프로젝트 명세 and deferred five questions to the onboarding design: the order of AI connection and project creation, when an AI reads ambiguous candidates, the final screen wording, the preview form and a "do not ask" setting, and whether structure v0 is final. The CEO decided them on 2026-10-13. One further requirement came with them: a goal that is not development work (documents, research, planning) must not trigger an SDD bootstrap.

## Decision

1. **Folder first.** Registering a folder, static detection and the three structure actions need no AI connection. First-run onboarding and the "사용 방법 튜토리얼" button show the same steps: choose a folder, see what was found, then connect an AI when the first AI step needs one. The tutorial reopens those steps; it is not a separate flow.
2. **Development goals only.** CTO analysis of each goal also classifies it as `development` (changes to an application or code in the project) or `other`. The origin is offered only for `development` goals. An `other` goal never proposes, plans or writes the structure, and runs as it does today. The classification is per goal, so one folder can hold both kinds. When the analysis is missing or unclear, the engine treats the goal as `other` and offers nothing; the settings card stays available for a manual choice.
3. **One planning decision card.** For a `development` goal whose project has no `.ucompany/sdd/`, the plan approval card asks two things together: whether to set up the structure (the same `bootstrap`/`add_section`/`convert` actions, preview and digest as SI-03; `convert` is never the recommended choice), and whether to connect an AI for a planned role that has no usable connection. Each answer is recorded separately. Approving the plan does not approve a structure write, and a structure write does not approve project file work. Declining the structure leaves the plan unchanged.
4. **AI reading of ambiguous candidates happens at the first in-app goal.** During CTO analysis of the first `development` goal, the CTO reads only the candidates that static detection listed (path and reason), under the same read-only project access as any analysis. Its judgement appears in the planning card as advice; it changes no file and no classification by itself. Projects that only ever open in other tools are not covered; writing a "확인 필요" note into project files before consent is rejected.
5. **Screen wording.** The implemented wording (`src/sddOrigin.ts`, covered by its tests) is the original. The policy record follows it. Depth-1 and depth-2 text shows no IDs (ADR-0042).
6. **Preview and "do not ask".** The confirmation lists every file as now. For files that get `append` or `replace` (`AGENTS.md`, `CLAUDE.md`), it also shows before and after. New files show only their paths. "이 폴더는 묻지 않기" is a per-project app setting stored in the local database, never in project files. It is added together with the planning card, and 설정 › 프로젝트 명세 shows it and can undo it.
7. **Structure v0 is frozen.** Node types, relations and file layout in SI-03 are fixed as v0. Additions such as feature dependencies or test nodes need a new ADR backed by the Claude ↔ GPT handoff checks (D1–D3).

## Alternatives

- **AI connection before the folder:** rejected. The origin works without AI, and a failed connection at the first screen would block everything.
- **AI reads candidates when the folder is selected:** rejected. Spends tokens when no work is planned, and usually no AI is connected yet under decision 1.
- **Project-level development/other setting:** rejected. Folders mix work kinds; per-goal analysis needs no extra question.
- **Bootstrap regardless of work kind:** rejected. Document and research goals do not benefit from a spec → plan → task structure and should leave the folder untouched.
- **Full content preview of every new file:** rejected. Hides the one change people check: what happens to their own `AGENTS.md`.

## Consequences

- The CTO analysis gains a `업무:` line and, when a structure could be offered, a `구조 조언:` line; the engine stores both in a `goal_origin` record. The plan approval card gains an optional structure section and a missing-connection section. Backend protocol 34; the frontend minimum is unchanged, and an older backend simply shows no new section.
- The offline harness `tests/sdd-origin/` checks that no fixture is offered the structure for an `other` goal or a muted project, and reads the CTO analysis examples in `goal_cases.json` with the app's own parser.
- The tool-only "connect other tools to the same rules" button (P11) is still not designed and stays open.
- QA-43 continues to cover the settings card; QA-44 covers the planning card.

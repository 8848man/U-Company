# ADR-0048 — One-click `해결 요청` for a blocked goal, and one automatic retry for a malformed plan

Status: Accepted (2026-10-14, CEO). Applies to the engine and to the recovery card in v1/v2/v3. Owners: [DM-05 재시작과 복구](../../domain/DM-05-recovery.md), [GC-03 공유 대화 작업공간](../../goalConversation/GC-03-workspace.md), [Security](../../security.md). Plan document reviewed by the CEO: "'팀원에게 해결 요청' 원클릭 복구 개선 계획" (2026-10-14).

## Context

On Windows a test goal stopped after QA: the PM's repair plan gave one README deliverable more than eight acceptance criteria, `validate_contract` refused it, and the goal blocked with kind `other`. The recovery card's `팀원에게 해결 요청` button only moved the cursor to the composer, so it looked dead. Recovery then needed the CEO to write a message, an AI to classify it as a direction change, a new goal version, a new plan and a new approval. The repair prompt did not state the 1–8 criteria limit that the first plan prompt states.

## Decision

1. **Stated limits.** The first plan and the QA repair plan state the same contract limits the validator enforces (1–8 criteria per task, each at most 300 characters, at most 8 evidence files).
2. **One automatic retry.** A plan that fails the app's checks (JSON, task count, independence, plan rules, contract, continuation, repair scope) goes back to the same planner once with the exact error. The retry uses no QA rework round and leaves one stage line. A second failure blocks with the new kind `plan_form`; an error that already has a kind (a repair needing unapproved files stays `qa_failed`) keeps it. The engine never trims criteria itself.
3. **One-click fix.** The card's main button sends `request_team_fix`. The engine decides the route from saved records, not from model text:
   - **Repair on the same goal** when the goal stopped at review (`validating`) with kind `plan_form`, `qa_failed`, `qa_form` or `other`, every task completed, an approved project-write approval and no direction-change record. The planning lead plans a rework inside the approved files and work continues without a new approval. A click past the QA rework limit raises that goal's limit by one and records it.
   - **New goal version** otherwise (`interrupted`, `integration_conflict`, unfinished tasks, no approved scope): an automatic direction change addressed to the planning lead; the new plan waits for approval on its plan card.
   - **Refused** for `provider`/`precall` (open connections) and `approval_denied` (the CEO writes what to change).
4. **The request text is app-built.** It quotes the block message and the failed criteria of the latest QA round. QA text is passed as untrusted data and cannot widen the approved files. The request and the route are saved as a CEO turn (`route: team_fix`) in the goal conversation.
5. **Feedback.** The button names the receiver (`<planning lead>에게 해결 요청`) and shows one line about what will happen. On success the dialog closes and the progress line shows the planning lead. `직접 지시하기` keeps the old composer focus as a secondary action.

## Alternatives

- **Truncate to eight criteria:** rejected; it silently changes what QA will judge.
- **Always make a new goal version:** rejected for review-stage blocks; nothing outside the approved files changes, and a version split adds history without meaning.
- **Route the click through `send_goal_message`:** rejected; an AI classification can misroute a button press.
- **Two automatic retries:** rejected; a second identical failure rarely recovers and spends tokens.

## Consequences

- Engine: `plan_with_retry`, `after_plan_failure`, `plan_repair`, `repair_planner`, `request_team_fix` in `src-tauri/src/engine.rs`; route and request text in `src-tauri/src/team_fix.rs`; block kind `plan_form` in `delegation.rs`; command `request_team_fix`, backend protocol 36.
- Screens: `src/goalRecovery.ts` (`teamFixRoute`, `fixReceiver`, card label), `src/GoalChat.tsx`, `src/GoalConversationChat.tsx`, the three `App.tsx`.
- QA-46 checks the button on a blocked goal on Windows.

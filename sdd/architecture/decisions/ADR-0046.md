# ADR-0046 — One conversation per goal: plan card, revise, cancel, and an in-app Office window

Status: Accepted (2026-10-14, CEO). Applies to v3 only; v1/v2 keep their current screens. Owners: [GC-03 공유 대화 작업공간](../../goalConversation/GC-03-workspace.md), [UF-03 목표 실행](../../userFlow/UF-03-goal.md), [UF-05 범위 승인](../../userFlow/UF-05-approval.md), [DM-04 수명 주기](../../domain/DM-04-lifecycle.md), [진행 표시 정책](../../progress-visibility.md), [Security](../../security.md).

## Context

In v3 a goal is entered on Home, started with a separate `팀 실행 시작` button, approved in a modal opened from the work board or from the goal workspace (which closes the conversation), recovered from a `지금 할 일` card that floats above the conversation, and watched on a separate Office page. The engine already records who works on what (`runtime_progress`, handoffs, task assignees), but the conversation does not show it. The CEO wants one chat-shaped flow, like Claude Cowork or Codex: instruct → the team plans (only a "who is doing what" line) → a plan summary with approve / revise / reject → chat during work → result, with Office watchable in a window inside the app.

## Decision

1. **One conversation per execution goal.** The goal workspace is the main surface. Its stream holds CEO and teammate turns, a one-line message at each stage change, and decision cards in place: the plan card, the structure question ([ADR-0045](ADR-0045.md)), and recovery. The approval modal is removed from v3. The approval scope stays fully inspectable inside the card.
2. **Start on send.** Sending a goal creates it and starts team analysis at once with the existing `submit_goal` and `run_goal` commands. If the run is refused (no usable AI, busy team), the conversation shows the reason and the fixing action instead of a start button.
3. **Planning shows only a progress line.** CTO analysis and PM planning are not posted as messages. A single line above the composer says who is doing what, built only from saved facts (goal stage, latest `runtime_progress`, running tasks and their assignees). It is replaced in place, never stacked.
4. **Plan card with three choices.**
   - `승인`: the existing `decide_approval` with the squad digest. Unchanged.
   - `개선`: the next CEO message becomes the revision note (`revise_plan`, never AI-interpreted). The pending approval becomes `revise_requested`; the engine removes the replaced plan's tasks, which never started, and asks the PM to plan again **on the same goal** with the CTO analysis kept and the note added (plan revision 2, 3, …). The new plan gets a new approval. If the note changes the goal itself, the PM says so and the CEO can start a new goal version through the existing direction route.
   - `거부`: the goal becomes `cancelled`. No file changes. The conversation offers `다시 시작`, which submits the same goal text as a new goal.
   Revise and cancel apply only while the goal is `awaiting_approval`. After approval, direction changes keep the existing safe-checkpoint revision route ([GC-02](../../goalConversation/GC-02-guidance.md)).
5. **Approval is a button.** Chat text, an AI's interpretation, closing a window or elapsed time never approve, revise or cancel. A revision note is not approval of the revised plan.
6. **Home is a goal list plus the conversation.** Recent goals sit in a left list. The center is the selected goal's conversation, or a new-goal composer. The work board stays as a secondary overview.
7. **Office is an in-app floating window.** It opens from the conversation header, the progress line or the Office menu, can be moved, resized, docked to the right, minimized and closed, and remembers its place on this computer (local display preference). Inside: a stage strip (분석 → 계획 → 승인 → 작업 → 합치기 → 검토 → 완료), the existing pixel office with this goal's members emphasized, and a member list (role, task, state). Everything shown is saved state; animation is not evidence and stops under reduced motion. Docked, the app narrows instead of covering the conversation. The `Office 창` button in the top bar toggles it; the Office page stays for team settings.
8. **Meetings are out of scope.** Deliberation goals keep their current workspace.

## Alternatives

- **Keep the start button:** rejected. Analysis and planning write no project file and need no approval, and a chat that does not answer on send reads as broken.
- **Revise as a new goal version (current direction route):** rejected before approval. Nothing has been written, so splitting the record adds history without meaning. Kept after approval, where integrated work must stay attributed.
- **Re-run CTO analysis on revise:** rejected as the default. The note usually changes the plan, not the analysis. The PM flags a goal-level change instead.
- **Reject as today's `blocked`:** rejected. With revise available, reject must mean "do not do this"; a blocked goal invites retry.
- **Right-side fixed panel or OS window for Office:** rejected. Docking gives the panel; an OS window adds window management for no gain.
- **Post analysis and plan text in the chat:** rejected. The card's summary and the expandable detail carry it; long model text in the stream hides the decision.

## Consequences

- M1 (screen only): plan card, recovery card and stage messages inside the stream; progress line. Existing commands.
- M2 (screen only): goal list + conversation home; send starts the run.
- M3 (engine): `revise_plan` and `cancel_goal` commands (`src-tauri/src/plan_review.rs`), approval status `revise_requested`, goal status `cancelled`, the planning-to-approval part of the engine repeated per plan pass; backend protocol 35; Rust tests that a revised or cancelled plan can never start work, that a revision is refused once work started, and that a cancelled goal keeps nobody busy.
- M4 (screen only): floating Office window (`src/OfficeWindow.tsx`, `src/officeWindow.ts`); its status line is the conversation's progress line.
- QA-45 covers the whole conversational flow on Windows with real Claude and Codex.

# ADR-0051 — Goal versions read as one conversation

Status: Accepted (2026-10-15, CEO). Owners: [GC-02 지침](../../goalConversation/GC-02-guidance.md), [DM-02 목표](../../domain/DM-02-goal.md).

## Context

When a fix request or a direction change cannot stay inside the approved scope, the app creates a replacement goal (GC-02: a linked new goal ID, not an in-place rewrite) and the screen moved to it, so the CEO found the work continuing in a new chat. On 2026-10-15 the CEO noted that QA blocks often ended this way and asked whether the original chat could pivot instead. The new ID exists for approval scope, audit and duplicate-replacement safety; none of those needs a separate chat.

Also, a `해결 요청` whose repair planning failed (goal blocked from `planning`) went to a new version even though the approved work QA had judged was untouched, and a repair that needed a new file was marked `qa_failed` like a used-up rework limit, so the two could not be told apart.

## Decision

1. **Storage unchanged.** Each version stays its own goal with its own tasks, approvals and reviews (GC-02, DM-02).
2. **One conversation on screen (v3).** A goal and the versions linked by `revised` guidance are one conversation: the list shows one row (the newest version, titled with the first version's words); opening any version shows the newest; earlier versions' turns, stage lines and closed plan cards stay above a `계획 vN` divider that says why the version was made and what was reused. A fix request or direction change never moves the CEO to another chat.
3. **Archive together.** Archiving any version archives every visible version of the conversation in one transaction, and only if all are archivable; restoring one restores the archived versions with it.
4. **Repair more often.** `해결 요청` repairs on the same goal (no new approval) also when the goal is blocked from `planning` with every task completed and an approved plan, which only happens when an earlier repair's planning failed.
5. **`needs_scope` block kind.** A repair that needs a file outside the approved scope, or reused work that failed QA with nothing approved, blocks as `needs_scope` and goes to the next plan version, whose plan card asks for the new scope.

## Alternatives

- **Plan rounds inside one goal:** the same experience, but approvals, tasks, reviews, archive and references would all need a round key; a larger change with more regression risk.
- **Keep separate chats with a link:** the existing behaviour the CEO found confusing.

## Consequences

- `src/goalChain.ts` (chain, newest version, list rows, reason), `src/GoalChat.tsx` (`earlier`, version divider, chain turns), `v3/src/App.tsx`, `v3/src/v3.css`.
- `src-tauri/src/archive.rs` (`version_chain`, archive/restore together), `team_fix.rs` (planning repair), `engine.rs` and `delegation.rs` (`needs_scope`), `src/goalRecovery.ts`, `src/deliverables.ts`, `src/types.ts`.
- v1/v2 shells keep separate chats with links.
- QA-49.

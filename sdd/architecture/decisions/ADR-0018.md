# ADR-0018 — User-initiated provider login and fixed recovery guidance

Status: Accepted

Date: 2026-10-05

Affects: [Integrations](../../aiIntegration/00_index.md), [Security](../../security.md)

Context: CLI authentication requires a browser or terminal interaction. A saved Claude connection can truthfully return `loggedIn=false`, while a generic instruction to open a separate shell is hard to follow. Provider errors also have different remedies.

Decision: Start only documented, fixed login commands for registered built-in CLIs in a visible local terminal after a user click. Use the connection's saved path, quote it as a literal, and leave all credential entry to the provider. Recheck the exact saved path after the user finishes. Classify common failures using fixed provider-aware guidance; never execute diagnostic text.

Alternatives: Feed `/login` to a background process or silently trigger login during goal execution; both hide credential interactions and conflate a launched flow with completed authentication. Parse provider text into shell commands; this crosses the untrusted-output boundary.

Consequences: A login button opens an interactive window but cannot itself prove login. The app remains usable when a provider changes its login method; a failed launch produces an actionable explanation rather than a false ready state.

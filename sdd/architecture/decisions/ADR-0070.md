# ADR-0070 — External adapter protocol: progress events, cancel, declared resume

Status: Accepted (2026-11-10, CEO request to proceed). Owners: [AI-03 어댑터](../../aiIntegration/AI-03-adapter.md), [AI-04 진행·토큰](../../aiIntegration/AI-04-telemetry.md), [Security](../../security.md). Refines [ADR-0015](ADR-0015.md).

Date: 2026-11-10

## Context

[AI-03](../../aiIntegration/AI-03-adapter.md) lists `stream_events`, `cancel` and `resume` as adapter methods "where supported", but the external adapter protocol v1 had only `initialize` → `send_task` → one final result. While an adapter worked (up to 30 minutes) the goal showed no progress and no token count, unlike built-in CLIs whose stream is summarised by the process transport. Nothing could stop a running call except the timeout, which killed the process without telling the adapter. `resumeSession` was always sent, so an adapter could not tell the app it cannot resume. No running provider call of any kind could be cancelled from inside the app.

## Decision

The protocol stays at major version 1; every addition is optional and ignored by older adapters.

1. **Declared capabilities.** The `initialize` result may carry `capabilities`, a list from `events`, `cancel`, `resume`. Unknown entries are ignored. An adapter that declares nothing behaves exactly as before.
2. **Progress events.** While a `send_task` runs, the adapter may write JSON-RPC notifications without `id`: `{"method":"event","params":{"kind":"progress","text":"…"}}` and `{"method":"event","params":{"kind":"usage","outputTokens":N}}`. The app treats event text as untrusted display text: first line only, control characters removed, at most 120 characters, consecutive duplicates dropped, at most 80 per call. Usage events update the running token count as reported values. Events never change goal, task, approval or file state. The final `send_task` response remains the only result.
3. **Cancel.** Every provider call can take a cancel signal (`CallOptions.cancel`). When it is raised, or when the call times out, the app sends `{"id":3,"method":"cancel"}` to an adapter that declared `cancel`, waits up to five seconds for it to exit or answer, then ends the process. A built-in CLI process is ended directly. A cancelled call returns a `cancelled:` failure and its partial output is never integrated, because only the final result of a completed task reaches integration.
4. **Declared resume.** `resumeSession` is sent only to an adapter that declared `resume`. Without it a resumed task starts a fresh session with the same prompt, as for a built-in CLI without a session.
5. **What starts a cancel.** This decision adds the signal and the protocol. The screen actions that raise it for a running goal or meeting are a separate product decision; until then the signal is raised by the call's own timeout. The meeting rule "already started calls are not recovered" ([UF-09](../../userFlow/UF-09-meeting.md)) is unchanged.

## Alternatives

- **A second protocol version (v2):** rejected; all additions are optional and v1 already ignores unknown fields.
- **Streaming partial results into the goal:** rejected; partial text is not reviewed by QA and could be mistaken for a result.
- **Killing without a cancel request:** kept only as the fallback after five seconds; an adapter that is told can stop its own child processes and clean up its session.

## Consequences

- `runtime::run_plugin` reads every stdout line until its result instead of exactly two lines, and reports progress and usage through the same observers the CLI transport uses.
- `CallOptions` gains `cancel`; the process transport and the adapter loop both check it.
- The mock AI declares `events` and `cancel`, sends a progress event before each result, and exits on `cancel`.
- Adding a CEO stop action for a running goal or meeting call needs its own UX and state decision.

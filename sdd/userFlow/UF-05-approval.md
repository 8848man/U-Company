# UF-05 — 범위 승인

## 목적과 시작 조건

CEO가 실제로 변경될 대상과 이유를 보고 앱 안에서 명시적으로 결정한다. PM의 파일 작업 계획, 또는 중단된 Git 첫 커밋의 고정 복구 작업처럼 승인 대상이 생성됐을 때 시작한다.

## 사용자 흐름

1. 목표 카드나 대화의 `확인하기`에서 요청된 프로젝트·작업·파일 범위와 이유를 확인한다. v2에서 새 요청의 시스템 알림·소리를 켰다면 짧은 신호를 받을 수 있지만, 실제 범위와 결정은 앱의 목표 작업공간에서 확인한다. 승인 대상이 없으면 버튼은 이유와 다음 행동을 설명한다. CTO가 개발 목표로 판단했고 프로젝트에 U 컴퍼니 구조가 없으면 같은 창에 `작업 구조`가 함께 나온다(권장 동작, 바꾸기, `이번엔 건너뛰기`, `이 폴더는 묻지 않기`). 계획에 필요한 역할에 쓸 AI가 부족하면 `AI 연결`도 함께 나온다. 이 답들은 계획 승인과 따로 기록되고, 답하지 않아도 승인 결정은 할 수 있다([SI-03](../specImport/SI-03-origin.md), [ADR-0045](../architecture/decisions/ADR-0045.md)).
2. CEO가 승인하거나 거절한다. v3에서는 이 범위가 목표 대화 안의 계획 카드로 나오고 선택지가 셋이다([ADR-0046](../architecture/decisions/ADR-0046.md)): `승인`, `개선`(다음 메시지를 방침으로 같은 목표에서 다시 계획, 새 계획은 다시 승인), `거부`(목표를 취소, 파일 변경 없음). 단순 대화 문장, AI의 권고, 창 닫기, 시간 경과는 승인으로 해석하지 않는다.
3. 승인된 범위에서만 엔진이 작업을 이어간다. 범위가 바뀐 새 목표 버전에는 이전 승인을 재사용하지 않는다. 거절은 기록되고 자동 재시도하지 않는다.
4. QA 재작업에 승인되지 않은 새 파일이 필요하면 v3 대화에 `고칠 때 새 파일이 필요해요` 카드가 나온다([ADR-0053](../architecture/decisions/ADR-0053.md)). 새 파일 목록과 재작업 계획을 보고 `파일 추가 승인`하면 같은 목표에서 재작업이 이어지고, `거절`하면 파일을 바꾸지 않고 목표가 멈춰 `해결 요청`으로 새 계획 버전을 만들 수 있다. 이 카드에는 `개선`이 없다.
5. Git 첫 커밋은 별도 미리보기에서 실제 폴더·선택 파일·작성자·메시지를 확인한 뒤 승인한다. 앱은 승인한 고정 Git 작업만 수행하고 결과를 목표에 기록한다.

## 종료와 분기

승인하면 저장된 현재 계획의 다음 유효 단계로 돌아간다. 거절 또는 오래된 요청이면 목표는 새로운 판단을 기다린다. Git 미리보기 뒤 파일이 바뀌면 승인이 거부되고 다시 범위를 확인한다. Git 커밋이 성공해도 원래 업무 범위가 맞지 않으면 목표가 자동 완료되지 않는다.

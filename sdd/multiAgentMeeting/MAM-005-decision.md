# MAM-004의 전송 승인 모드와 v2 → v3 순서 결정

이 문서는 사용자가 [MAM-004](MAM-004-revision.md)의 두 열린 결정에 답한 기록이다. **제품·구현 방향에 대한 결정**이며, 지금 이 대화에서 실제 프로젝트 파일을 수정하거나 AI 제공자에게 자료를 전송하라는 승인이 아니다. 현행 승인 규칙은 [Security](../security.md)가 소유한다. 구현 전에는 이 결정의 승인 계약을 소유 Spec과 ADR에 이관하고 검증해야 한다.

## D1 / MAM-002#C5 — 회의 중 교차 제공자 전송 승인 모드

**사용자 원문:** “C5는 모드로 설정하자. 기본적으로는 건별 미리보기 및 승인으로 설계하고, 승인할 때, '미리 승인'버튼을 눌러서 해당 회의에 대해 일괄 승인하는 모드로 진행하기로 하자.”

**결정:** 회의의 기본 전송 모드는 **건별 미리보기·승인**이다. 사용자가 전송 승인 화면에서 **`미리 승인`**을 명시적으로 누르면, **그 회의의 남은 허용 범위에 한해서** 이후 교차 제공자 전송을 일괄 승인하는 모드로 전환한다. 다른 회의나 새로운 프로젝트의 기본 설정으로 전파하지 않는다. 미리 승인하지 않았거나 범위를 확인할 수 없으면 건별 모드를 유지한다.

**이관할 계약:**

- 건별 승인 화면은 실제 전송할 묶음의 내용·출처, 수신 제공자/연결, 목적을 보여준다. `미리 승인`을 선택할 때에는 앞으로 허용할 **회의 ID, 고정된 입력 스냅샷/해시, 참여 제공자와 목적지, 교차 전달될 생성물 종류와 길이 제한, 라운드·호출 상한, 승인 유효 기간**을 한 화면에서 검토하게 한다. 미래 발언의 정확한 내용은 아직 알 수 없음을 명시한다.
- 엔진은 승인 범위를 저장하고 **각 호출 직전** 목적지, 입력 스냅샷, 자료 종류·크기, 회차·호출 수가 범위 안인지 검사한다. 벗어나면 해당 호출을 중단하고 새로운 미리보기·승인을 요구한다. 새 파일, 바뀐 해시, 새 제공자/연결, 확대된 한도는 기존 미리 승인을 상속하지 않는다.
- `미리 승인`은 언제든 철회할 수 있다. 철회와 사용자 중단은 **새 호출을 막는 것**이며 이미 시작한 호출이나 외부로 전송된 내용을 소급 취소했다고 표시하지 않는다([MAM-003#N1](MAM-003-response.md#mam-003n1--중단승인-철회와-진행-중-호출)). 회의 종료 시 승인은 만료된다.
- 이 모드는 일반 프로젝트 파일 쓰기, 배포, 외부 앱 게시, 새로운 실행 파일 등록의 승인이 아니다. 회의 결과를 실행 목표로 인계할 때에도 각 작업의 승인 정책을 새로 적용한다.

**남은 설계·검증:** 현재 일반 `Approval` 저장 필드에는 전송 목적지·내용 해시·회의 전체 범위를 기록할 자리가 없다([MAM-003#C5](MAM-003-response.md#mam-002c5--복수-제공자-전송-승인-범위)). 또한 [Security](../security.md)의 외부 SDD 전송은 정확한 선택 내용·제공자 목적지를 보인 뒤 승인하도록 정한다. 따라서 미래 생성 발언을 포함하는 `미리 승인`은 **새 승인 계약을 Security와 ADR에서 정의하고, 경계 시험을 통과하기 전에는 실행 기능으로 제공하지 않는다.** 결정은 이 모드를 만들 방향을 확정한 것이지 기존 정책의 예외를 즉시 만든 것이 아니다.

## D2 / MAM-002#C9 — 첫 검증과 v3의 순서

**사용자 원문:** “C9은 v2회의를 첫 검증 사례로 진행하고싶어. v3는 다른 문제를 해결해야하고, v2로 먼저 빌드 후 해당프로그램으로 v3 개선을 정리, 자기 구현을 할거야”

**결정:** 공통 증거 어휘·계약을 먼저 설계하고, **v2 다관점 회의를 첫 검증 사례**로 빌드·검증한다. 이후 작동하는 U컴퍼니의 회의 기능을 사용해 **v3 개선안을 다관점으로 정리**하고, 그 결정 자료를 기반으로 U컴퍼니 자신의 v3 구현을 추진한다. v3는 회의 기능 자체와 다른 제품 문제를 다루며, 기존 [v3 개선안](../v3-improvement-plan.md)의 범용 고객 목표·비코드 산출물 과제를 회의 기능으로 대체하지 않는다.

**이관할 순서:**

1. 열린 v2 실사용 QA와 회의의 증거·승인·격리 계약을 확인하고, 첫 회의 수직 사례를 구현·실측한다.
2. 실제 v2 개선안 회의로 상호 비판·수정·결정 자료의 가치와 사용량/UX를 검증한다.
3. 검증된 프로그램 안에서 v3의 별도 문제와 우선순위를 논의해 근거·미해결 반론이 있는 개선안을 만든다.
4. 사용자가 채택한 v3 계획을 소유 Spec·ADR·userFlow·Validation에 이관하고, 파일 변경을 포함한 자기 구현은 해당 목표의 명시적 승인·독립 QA 절차를 따른다.

이 순서는 v3를 폐기하거나 v3 계획의 고객 목표를 바꾸는 결정이 아니다. 기존 v3 문서의 **착수 순서를 v2 회의 검증 이후로 배치**하는 결정이다. 회의의 앱 내부 결정 자료와 v3의 승인된 프로젝트 파일 산출물은 동일한 `Claim / SourceRef / Assumption / Unknown / Acceptance` 어휘를 공유하되 저장·승인·완료 조건은 분리한다([MAM-004#R5](MAM-004-revision.md#6-v3와-공유할-증거-계약-분리할-완료-조건-r5-c9)).

## 이 결정 뒤의 검토 상태

MAM-004의 **D1·D2는 결정됨**으로 표시한다. MAM-004 전체 설계, 특히 `awaiting_decision` 상태, 미리 승인 범위 강제, CLI 읽기 격리와 UX는 후속 교차 검토 대상이다. 다음 문서는 Claude Cowork가 MAM-004와 이 결정을 함께 읽고 비판한다. 이 문서 자체로 코드·소유 Spec·ADR을 변경하거나 모델 호출을 시작하지 않는다.

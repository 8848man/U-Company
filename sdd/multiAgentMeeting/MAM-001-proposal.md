> **MAM-001 · 제안 · 작성: Codex · 2026-10-09.** [다관점 AI 회의 검토 폴더](00_index.md)의 첫 문서다. 문서 상태와 다른 문서와의 관계는 폴더 인덱스가 소유한다. 2026-10-09 `sdd/v2-multi-agent-meeting-proposal.md`에서 이동했으며 이동 시 상대 링크 깊이만 조정했다.

Status: **검토 제안, 미구현** (2026-10-09). Claude Cowork의 비판과 사용자 결정을 받기 위한 명세다. 현재 동작이나 승인 권한을 변경하지 않는다. 현행 목표·팀·작업 규칙은 [Product](../product.md), [Domain](../domain/00_index.md), [Security](../security.md)가 소유하며 구현·검증 여부는 [WORKLOG](../../WORKLOG.md)가 소유한다.

## 1. 문제와 목표

현재 목표 엔진은 CTO 분석 → PM의 파일 변경 계획 → 개발자 실행 → QA 검증 → 보고를 진행한다. QA 실패 시 승인된 파일 범위 안에서 재작업을 반복하지만, **실행 전에 여러 관점이 서로의 안을 비판·보완하는 회의**는 표현하지 못한다. CTO·PM·QA는 고정 ID로 찾고 개발자는 역할 문자열로 식별하므로 팀원을 화면에서 바꾸는 것만으로 범용 회의가 되지 않는다. [DM-04](../domain/DM-04-lifecycle.md), [engine.rs](../../src-tauri/src/engine.rs).

v2 개선의 첫 사례는 사용자가 **v2 자체의 개선안을 검토**하도록 여러 AI 역할에 같은 안건을 맡기는 것이다. 결과는 코드 변경이 아니라 사용자가 채택·수정·보류할 수 있는 **근거 있는 결정 자료**다. 팀원들이 독립 제안, 교차 비판, 수정, 평가를 수행하는 동안 진행과 사용량을 확인할 수 있어야 한다.

### 범위

- v2에 `개발 실행팀`(기존 CTO–PM–Dev–QA)과 별개의 `개선 회의팀` 프리셋을 제공한다. 이후 다른 일의 팀·회의 프리셋을 추가할 수 있는 계약을 정의한다.
- 첫 회의는 읽기 전용이다. 선택한 로컬 프로젝트의 v2 코드·SDD·WORKLOG를 근거로 문제와 대안을 검토하고 결과를 앱 내부에 저장한다.
- 회의 결과의 채택과 후속 구현은 별도 단계다. 회의의 합의·평가 점수·AI 출력은 프로젝트 파일 수정, 외부 전송, 배포의 승인이 아니다.
- 실시간 음성 회의, 무제한 자율 루프, 여러 사용자 계정, 중앙 SaaS 과금, 자동 코드 수정은 첫 범위에서 제외한다.

## 2. 팀과 회의의 분리

**팀 프리셋**은 역할 슬롯, 각 역할의 책임·기본 지침·필요한 런타임 능력·참여 여부를 정의한다. 슬롯과 실제 팀원, AI 연결, 모델은 별개다. 사용자는 슬롯마다 설치·등록된 연결을 배정한다. Claude/GPT 같은 공급자명은 역할이나 관점의 이름이 아니다. 회의를 시작할 때 역할 지침, 연결·모델 식별자, 프리셋 버전을 스냅샷으로 고정한다. 나중의 팀 설정 변경은 진행 중 회의와 과거 기록을 다시 쓰지 않는다. 이는 [ADR-0002](../architecture/decisions/ADR-0002.md)의 역할·런타임·모델 분리를 따른다.

**회의 프로세스 프리셋**은 단계, 라운드 상한, 발언 순서, 피드백 대상, 평가 기준, 종료 조건, 결과물 형식을 정의한다. 팀과 회의 프로세스는 독립적으로 선택한다. 기존 `개발 실행팀`은 현행 엔진을 계속 사용하며, 이 제안이 그 팀의 업무·QA 수명주기를 암묵적으로 대체하지 않는다.

첫 `v2 개선 회의팀`은 다음 관점으로 시작한다. 같은 연결을 둘 이상의 역할에 배정할 수 있지만, 회의 결과에는 어느 연결이 어느 역할을 수행했는지 남긴다.

| 슬롯 | 질문과 책임 | 필수 출력 |
| --- | --- | --- |
| 제품·고객 | 실제 사용자의 막힘과 구매 가치가 개선되는가? | 고객 문제·우선순위·가정 |
| 사용 경험 | 첫 사용, 제어감, 결과 인수 과정이 명확한가? | 여정·오류/복구 관점의 반론 |
| 엔진·구현 | 현행 코드와 SDD에서 실현 가능한가? | 영향 범위·의존성·대안 |
| 운영·비용 | 사용량, 복구, 공급자 한도에 견디는가? | 비용·실패 시나리오 |
| 보안·검증 | 근거, 승인 범위, 테스트 가능성이 충분한가? | 치명 쟁점·검증 조건 |

진행자/기록자는 논점 선택과 회의 기록을 관리한다. 평가자는 제안자와 분리해 근거와 품질 기준을 확인한다. 첫 구현은 위 다섯 관점 중 **3~5개를 선택**하고 진행·평가 기능을 제공한다. 진행자가 모델이어도 순서, 한도, 상태 전이, 종료 판정의 최종 실행은 엔진이 담당한다.

## 3. 회의 계획 계약

회의 시작 전 사용자에게 다음을 한 화면에서 검토하게 한다.

1. 안건과 기대 결과: 예를 들어 “v2에서 목표 완료까지의 사용자 조율을 줄일 우선 개선안 3개”.
2. 입력 자료: 선택한 로컬 파일·저장 상태의 범위와 각 자료의 출처/버전. 읽지 못한 자료는 근거로 표시하지 않는다.
3. 역할·연결·모델: 실제 사용 가능한 연결과 읽기/도구 능력을 확인한다. 없는 연결의 발언을 시뮬레이션하지 않는다.
4. 평가 기준: 사용자 가치, 근거, 구현 가능성, 비용/시간, 보안/복구에 대한 질문과 통과 조건.
5. 회의 한도: 참여자 수, 라운드 수, 총 호출 수, 총 추정 토큰, 요청당 입력·출력 상한, 시간 상한. 결과 정리용 호출 한도를 미리 예약한다.
6. 전송 범위: 어떤 로컬 자료와 회의 중 생성된 발언이 어느 AI 제공자에게 전송될 수 있는지. [Security](../security.md)의 실제 승인 정책을 적용한다. 시작 버튼이나 프리셋 선택만으로 승인을 추정하지 않는다.

계획을 저장해도 모델 호출은 시작되지 않는다. 사용자의 명시적 시작과 필요한 승인이 충족되면 고정된 계획 스냅샷으로 실행한다. 자료·참여자·전송 대상·한도가 바뀌면 변경분을 다시 검토하고 필요한 승인을 새로 받아야 한다.

## 4. 회의 루프

| 단계 | 엔진이 하는 일 | 남겨야 할 기록 |
| --- | --- | --- |
| 독립 제안 | 동일한 안건·근거 묶음을 각 관점에 전달한다. 다른 참여자의 초안을 보지 않고 먼저 제안한다. | 역할별 주장, 근거 참조, 가정, 불확실성 |
| 논점 선별 | 중복을 합치고 결정에 영향을 주는 충돌·누락을 고른다. 모든 발언을 전원에게 매번 보내는 전원 교차 방식은 기본값이 아니다. | 쟁점 ID, 영향, 회신 대상, 선별 이유 |
| 교차 비판 | 서로 다른 관점이 특정 주장에 반론·실패 사례·대안을 제시한다. | 원 주장 ID, 반론, 근거, 필요한 수정 |
| 수정 | 원 제안자가 비판을 수용·반박·보류하고 제안을 수정한다. | 이전 버전 대비 변경, 반론 처리 상태 |
| 평가 | 분리된 평가자가 기준별 근거와 남은 치명 쟁점을 확인한다. 엔진은 형식·한도·출처 연결을 검사한다. | 기준별 평가, 누락, 미해결 쟁점, 다음 라운드 필요 여부 |
| 종료/다음 라운드 | 품질·진전·한도를 함께 판정한다. | 종료 이유, 소진량, 최종 결과 또는 미완료 상태 |

첫 프리셋의 기본값은 **2라운드, 최대 3라운드, 3~5개 관점**이다. 한 라운드는 교차 비판 → 수정 → 평가를 뜻하며 독립 제안은 한 번만 한다. 최대 호출 수와 토큰 상한은 시작 전에 사용자에게 보이고 수정 가능해야 한다. 기본 총량 수치는 실제 제공자별 측정 전에는 확정하지 않는다.

### 품질 게이트와 종료

- 평가는 다섯 기준(사용자 가치, 근거, 구현 가능성, 비용/운영, 보안/검증)을 각각 `충족/부분 충족/미충족/판정 불가`로 기록한다. 숫자 점수나 다수결만으로 품질을 보증하지 않는다.
- 모든 기준이 충족되고 근거 없는 중대한 주장·미해결 치명 쟁점이 없으면 `기준 충족`으로 종료한다. 평가자는 다른 팀원의 동의를 근거로 대신 사용할 수 없다.
- 새 근거, 새 대안, 중대한 수정 없이 같은 쟁점이 반복되면 `진전 정체`로 조기 종료한다. 반대 의견이 남아도 합의로 꾸미지 않는다.
- 라운드·호출·토큰·시간 상한 또는 제공자 한도에 닿으면 종료하고 현재까지의 결정 자료를 만든다. 품질 미달인 경우 `검토 필요`로 표시하며, 사용자가 명시적으로 새 한도를 정하지 않는 한 자동 연장하지 않는다.
- 평가가 서로 모순되거나 근거를 확인할 수 없으면 `판정 불가`로 남긴다. 최종 채택 여부는 사용자 결정이다.

## 5. 사용량 방어와 실패 처리

- 엔진은 **호출 전** 남은 호출 수·추정 토큰·시간을 확인하고 최종 정리 예약분을 침범할 호출을 시작하지 않는다. 요청 크기와 출력 길이를 제공자가 제한할 수 있으면 적용한다. 제공자가 정확한 출력 상한을 지원하지 않으면 토큰 상한은 사전 추정에 따른 방어선이며 **금전적 하드캡으로 표시하지 않는다**.
- 전원 교차 전달로 호출 수가 참여자 수의 제곱에 가까워지지 않도록, 진행자는 라운드당 핵심 쟁점과 반론 대상을 제한한다. 다음 호출에는 전체 원문 대신 현재 주장·반론·결정 기록과 필요한 출처만 넣는다. 요약은 원문 기록을 대체하지 않는다.
- 한 역할·연결에 장애나 구독 한도가 발생하면 해당 발언을 실패로 기록한다. 다른 AI가 그 역할의 답변을 지어내지 않는다. 회의는 재시도 가능 여부와 결과 신뢰도를 표시하고 `중단/부분 결과`로 마친다.
- 호출별 연결·모델, 보고/추정 토큰, 입력 자료 식별자, 시작/종료 상태를 저장한다. 구독 잔량과 실제 청구액은 공급자가 제공하지 않는 한 표시하지 않는다. [AI-04](../aiIntegration/AI-04-telemetry.md)의 출처 구분을 따른다.
- 앱 중단 뒤에는 저장된 완료 발언만 복구한다. 진행 중이던 호출의 성공을 추정하거나 같은 요청을 조용히 다시 보내지 않는다. 사용자가 재개하면 미완료 단계와 남은 한도·전송 범위를 다시 확인한다.

## 6. 결과물과 사용자 경험

결과는 회의록 전문보다 먼저 **결정 자료**를 보여준다: (1) 권고 개선안과 우선순위, (2) 근거가 확인된 사실과 가정, (3) 채택하지 않은 대안과 이유, (4) 남은 반대 의견·미해결 위험, (5) 예상 구현 범위와 검증 방법, (6) 사용자가 채택·수정·보류할 결정. 각 항목에서 근거 발언과 로컬 자료로 돌아갈 수 있어야 한다. 평가 미달·중단·부분 결과도 같은 형식으로 표시하되 완료로 위장하지 않는다.

v2 UI에는 목표 생성/설정 경로에서 팀과 프로세스를 선택하고, 시작 전 계획·전송·한도를 검토하며, 진행 중에는 현재 라운드·활성 관점·핵심 쟁점·남은 한도를 표시한다. 전체 발언과 호출 사용량은 펼쳐 볼 수 있게 한다. 모델의 비공개 추론이나 임의 stdout은 진행 기록으로 노출하지 않는다. 회의 결과에서 `개발 실행팀에 인계`를 선택해도 새 실행 목표·파일 변경 범위·승인은 현행 규칙대로 별도 생성·검토한다.

## 7. 제안 데이터와 상태 경계

아래는 구현 전 검토할 **개념 모델**이며 현재 저장 스키마가 아니다.

- `TeamPreset`/`ProcessPreset`: 버전이 있는 역할 및 회의 절차 템플릿.
- `Meeting`: 프로젝트와 선택적 목표에 묶인 안건, 계획 스냅샷, 상태, 상한, 종료 이유.
- `Contribution`: 역할·라운드·단계에 속한 제안/비판/수정/평가. 원 주장 ID, 근거 참조, 이전 버전 관계를 포함한다.
- `Issue`: 중복을 합친 쟁점, 영향, 대상 역할, 처리 상태.
- `MeetingUsage`: 호출별 연결·모델 스냅샷과 보고/추정 사용량.
- `DecisionPackage`: 사용자에게 인계한 결과 버전과 명시적 채택 상태.

회의 상태 후보는 `draft → awaiting_approval → proposing → critiquing → revising → evaluating → completed`이며, 어느 활성 단계에서나 `blocked`, 사용자 중단 시 `stopped`, 품질 미달·한도 종료 시 `needs_decision`으로 이동한다. 각 상태 변경과 상한 사용은 같은 저장 단위에서 기록한다. 회의 상태는 기존 [DM-04 목표 수명주기](../domain/DM-04-lifecycle.md)와 구분하고, 후속 구현 목표는 기존 상태를 따른다. 새로운 상태/엔티티의 최종 소유권과 저장·복구 설계는 수용 후 관련 Spec 및 ADR에서 확정한다.

## 8. 첫 수용 시나리오

1. 사용자가 v2 개선 안건과 로컬 자료, 3개 이상 관점, 서로 다른 두 AI 연결, 회의 한도를 선택한다. 계획 화면에 전송 대상과 자료 범위가 보이고 승인 전 호출은 0건이다.
2. 각 관점의 독립 제안 후 실제 교차 비판과 수정이 한 차례 이상 일어난다. 결과에서 원 주장 → 반론 → 수정 연결을 따라갈 수 있다.
3. 근거 없는 주장은 미확인으로 남는다. 평가자가 반론을 무시한 채 `완료`로 처리하거나 단순 동의를 검증 근거로 삼을 수 없다.
4. 품질 기준을 충족하면 조기 종료하고, 미충족이면 한도까지 진행하되 정체·상한 도달 시 추가 호출을 멈추고 반대 의견을 포함한 `검토 필요` 결과를 낸다.
5. 제공자 실패, 사용자 중단, 앱 재시작 뒤 상태·호출 기록·남은 한도를 복구한다. 불확실한 호출을 완료로 추정하거나 자동 중복 전송하지 않는다.
6. 회의의 제안이나 저장된 자료의 악성 지시로 승인 범위가 넓어지지 않는다. 결과를 개발팀에 넘겨도 새 파일 작업은 별도 승인 없이는 시작되지 않는다.
7. 원래의 CTO–PM–Dev–QA 목표를 같은 빌드에서 실행해 회의 프리셋 추가가 기존 계획·QA·보고 경로를 바꾸지 않았음을 확인한다.

문서 검토만으로 구현이나 데스크톱 동작이 검증되지는 않는다. 수용 후 [Validation](../validation.md), 사용자 여정, 수동 QA에 위 시나리오를 소유권에 맞춰 편입한다.

## 9. Claude Cowork 비판 요청과 열린 결정

Claude Cowork는 이 문서를 **제안으로 취급**하고 [Product](../product.md), [DM-01](../domain/DM-01-workspace-team.md), [DM-03](../domain/DM-03-execution.md), [DM-04](../domain/DM-04-lifecycle.md), [AI-04](../aiIntegration/AI-04-telemetry.md), [Security](../security.md) 및 관련 코드를 대조해 비판한다. 특히 아래 질문에 대해 `문제 → 근거 → 대안 → 영향 → 권고` 형식으로 답한다.

1. 회의를 기존 Goal의 한 모드로 둘지, 독립 Meeting으로 두고 Goal에 연결할지. 저장·복구·UI 복잡도와 승인의 차이는 무엇인가?
2. 다섯 관점과 별도 평가자가 첫 프리셋에 과도한가? 품질을 유지하면서 최소 인원·호출 수를 어떻게 정할 것인가?
3. 품질 게이트의 `충족`이 실제로 검증 가능한가? 자기 평가와 가짜 합의를 막는 더 나은 기준은 무엇인가?
4. 교차 전달 자료와 생성된 발언을 복수 공급자에게 보낼 때 승인 범위·민감정보·보존 정책의 빠진 경계는 무엇인가?
5. 구독형 CLI의 한도·토큰 보고가 불완전할 때 사용량 방어가 실제로 어느 정도 보장되는가?
6. 첫 수직 구현을 어디까지 줄여야 기존 v2 목표 엔진과 충돌 없이 검증할 수 있는가?

검토자는 이 문서나 AI 답변을 승인 권한으로 해석하지 않는다. 비판 결과와 사용자의 선택을 받은 뒤 소유 Spec, 사용자 여정, 검증 기준, 필요한 새 ADR을 갱신하고 구현한다.

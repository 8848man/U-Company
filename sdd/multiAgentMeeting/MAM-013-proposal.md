# 회의 진행 중 차단 엣지케이스 조사와 개선 계획

## 1. 배경과 목표

Windows 시험 중 회의가 계획 승인 뒤 제안 단계에서 "CTO 패킷이 23671자로 안전 길이 12000자를 넘습니다"로 멈췄다. 직전 수정(WORKLOG "Meeting packet length checked at plan validation")은 **제안 단계 하나**만 고쳤다. 같은 종류의 "승인 뒤에야 드러나는 차단"이 다른 단계·다른 원인에도 남아 있는지 코드를 다시 읽어 조사했다.

목표는 두 가지다.

- **승인 뒤 예측 가능한 차단 0건**: 길이·호출 수·자료·연결처럼 미리 계산할 수 있는 한도는 계획 검토 화면에서 오류로 보이고, 승인 버튼을 막는다.
- **예측할 수 없는 문제는 한 번에 회복**: 모델 응답 형식 오류, 일시적 호출 실패처럼 미리 알 수 없는 문제는 회의를 처음부터 다시 만들지 않고 CEO의 한 번 클릭으로 그 단계만 다시 진행한다.

지키는 원칙은 그대로다: 내용을 몰래 자르거나 지어내지 않는다, 결과를 알 수 없는 호출은 자동으로 다시 보내지 않는다, 계획에 없는 전송은 막는다([Security](../security.md), ME-02).

## 2. 이번에 보인 오류 문구에 대해

사용자가 다시 본 문구 "안전 길이 12000자 … 자료를 줄여 새 회의를 만드세요"는 **수정 전 코드에만 있는 문구**다. 현재 코드는 "전송 길이 …자로 한도 30000자 … 재개해서 계획의 자료를 줄여 주세요"를 쓴다. 따라서 다음 둘 중 하나다.

1. 수정 전에 실행한 앱 창(이전 백엔드)이 그대로 떠 있었다.
2. 수정 전에 막힌 회의를 열어, 그때 저장된 차단 이유를 본 것이다(차단 이유는 회의 기록에 저장되어 업그레이드 뒤에도 그대로 보인다).

두 경우 모두 사용자가 구분할 수 없었다는 점이 그 자체로 엣지케이스(E10)다. 백엔드 프로토콜 번호를 22로 둔 채 동작을 바꿨기 때문에 화면이 "이전 백엔드"를 감지하지 못했다.

## 3. 조사한 엣지케이스

근거는 `src-tauri/src/meeting.rs`(`build_payload`, `prepare_stage`, `run_dispatch`, `complete`, `validate_contribution`, `validate_meeting_inputs`, `connection_fingerprint`), `provider.rs`(`run_cli`)와 `runtime.rs`(`capture_with_timeout`)다. "가능성"은 실제 Claude/Codex로 한 라운드를 돌릴 때 기준의 판단이다.

## 4. 개선 계획

단계마다 수용 기준(시험)을 함께 둔다. 순서는 위험이 큰 것과 다른 항목의 전제가 되는 것부터다.

### P0 — 이전 백엔드와 이전 기록을 구분한다 (E10)

- 회의 동작을 바꾸는 변경마다 백엔드 프로토콜 번호를 올린다(23). 화면은 기대 번호보다 낮으면 회의 버튼을 막고 "앱을 다시 시작하세요"를 띄운다.
- 차단 이유에 기록 시각과 앱 빌드 번호를 함께 저장하고 화면에 보인다. 이전 빌드에서 기록된 차단이면 "이전 버전에서 기록된 이유입니다. 재개하면 현재 규칙으로 다시 확인합니다"를 덧붙인다.
- 수용 기준: 프로토콜 22 백엔드에 새 화면을 붙이면 회의 시작·승인 버튼이 막히고 이유가 보인다(Vitest). 저장된 차단 이유가 빌드 번호와 함께 보인다.

### P1 — 패킷을 명령줄 인자가 아니라 표준 입력으로 보낸다 (E1~E3의 구조적 해결)

- `run_cli`가 긴 프롬프트를 표준 입력으로 넘긴다. Claude는 `claude -p`에 프롬프트 인자 없이 표준 입력, Codex는 `codex exec … -`(프롬프트 자리 `-`)로 받는 방식을 우선 검토한다. 두 CLI의 실제 동작은 Windows에서 확인하기 전까지 가정이다.
- 실행 목표와 회의가 같은 경로를 쓰므로 한 번에 해결된다. 지금 실행 목표의 전체 프롬프트에는 명령줄 길이 검사가 없다.
- 표준 입력이 확인되면 명령줄 32,767자 한계는 사라지고, 패킷 상한은 "실패를 막는 한계"가 아니라 "비용 예산"이 된다.
- 위험: 공급자 런타임 조사에서 표준 입력을 열어 두면 CLI가 입력을 기다리며 멈춘 기록이 있다([조사 기록](../provider-runtime-investigation.md)). 쓰고 바로 닫는 방식으로 하고, 공급자 하네스로 먼저 확인한다.
- 수용 기준: 공급자 하네스로 Claude·Codex에 5만 자 합성 프롬프트를 표준 입력으로 보내 정상 응답을 받는다(Windows 수동 QA). 단위 시험은 표준 입력 기록과 인자 구성을 확인한다.

### P2 — 모든 단계의 길이를 승인 전에 계산한다 (E1, E2, E11)

- **응답을 정규화한 뒤의 크기에 상한**을 둔다. 다음 단계에 실리는 것은 원문이 아니라 정규화된 JSON이므로, 주장 수·글자 수·인용 수 상한으로 단계별 최대 크기가 정해진다.
- **평가자 패킷을 압축**한다. 들여쓰기 없는 JSON, 인용은 원문 대신 `S1 확인됨/못 찾음` 상태와 짧은 앞부분만, 참여자별로 주장·비판·처리·수정만 싣는다. 근거 원문은 이미 제안 단계 기록에 있다.
- 계획 검증이 제안 패킷뿐 아니라 **비판·수정·평가 패킷의 최악 크기**를 상한으로 계산해, 넘으면 계획 오류로 보인다. 최악 크기가 넘을 수 없도록 상한을 정하는 것이 기본값이다.
- 계획 카드에 **자료 예산 막대**(파일별 글자 수, 합계/한도)와 파일별 "빼기" 버튼을 둔다. 의장 요청에는 후보 파일 크기를 함께 알려 준다.
- 수용 기준: 모든 응답이 상한 끝까지 찬 합성 회의(참여자 2명·3명)에서 모든 단계 패킷이 한도 이하임을 확인하는 속성 시험. "계획 승인 뒤 길이 오류"가 나오면 실패한다.

### P3 — 모델 응답 형식 문제를 회의 전체 차단이 아니라 한 번의 수정 요청으로 처리한다 (E4)

- **관대한 읽기**: 응답 안의 첫 번째 완전한 JSON 객체를 읽고, 앞뒤 설명 문장은 원문 기록에만 남긴다. `C01`→`C1`처럼 의미가 같은 ID는 정규화하고, 바꾼 사실을 기록에 남긴다.
- **형식 수정 요청**: 그래도 규칙을 어기면(길이 초과, 누락, 근거 없는 반박) 같은 팀원에게 "무엇이 왜 틀렸는지"만 담은 짧은 재요청을 **한 번** 보낸다. 내용을 앱이 고치지 않는다. 이 호출은 계획 승인 범위 안의 예비 호출로 계산하고, 계획 카드에 "형식 수정 예비 호출 N회"로 보인다(기본 2회, 상한 12회 안에서).
- 예비 호출을 다 쓰거나 같은 팀원이 두 번 연속 틀리면 그때 차단한다.
- 수용 기준: 설명 문장이 섞인 응답, `C01` ID, 801자 주장, 비판 누락 응답 각각에 대해 차단 없이 진행되거나 정확히 1회 수정 요청 뒤 진행되는 시험.

### P4 — 차단되면 그 단계에서 바로 회복한다 (E5, E8, E9)

- `failed`(실패가 확실한 호출)와 형식 오류는 회의 화면에 **"이 팀원에게 다시 요청"**을 둔다. 계획 지문이 같고 호출 상한 안이면 계획 재승인 없이 그 패킷만 새 revision으로 다시 만든다.
- `outcome_unknown`(전송 여부 불명)은 자동 재전송을 계속 금지한다. 같은 버튼을 두되 "같은 내용이 두 번 갈 수 있습니다" 확인을 거친다.
- 재시작 뒤 재개는 계획 내용이 그대로면 "계획 재승인" 한 번으로 **이미 끝난 단계를 건너뛰고** 남은 단계부터 이어간다(지금 코드도 기록된 발언은 다시 보내지 않으므로, 화면 안내만 맞춘다).
- 호출 상한 기본값을 "필요 호출 + 예비 2회"로 제안한다.
- 수용 기준: 시간 초과로 실패한 비판 패킷 1건을 "다시 요청"으로 회복해 평가까지 가는 시험. 결과 불명 패킷은 확인 없이 다시 보낼 수 없는 시험.

### P5 — 회의에 영향 없는 변경으로는 막지 않는다 (E6, E7, E12, E13)

- **자료 변경**: 승인 뒤 자료는 고정 스냅샷이며 실제로 보내는 것도 스냅샷이다. 원본 파일이 바뀌어도 막지 않고 "회의는 승인 시점 내용을 사용합니다" 안내만 보인다. 제안 단계 전송 직전에 바뀐 경우에만 CEO에게 "승인 시점 내용으로 계속 / 계획을 새 내용으로 다시 검토"를 묻는다.
- **연결 지문**: 지문은 실행 파일·종류·인자·모델만으로 계산하고 `capabilities`·상태 검사 결과는 뺀다. 실제로 다른 실행 파일이나 모델로 바뀐 경우에만 막는다.
- **인용 확인**: CRLF/LF와 연속 공백을 정규화한 뒤 찾고, 원문 위치는 원래 바이트 기준으로 기록한다.
- **팀원 사용 중**: 승인이 거절되면 같은 역할의 다른 참여 가능 팀원을 제안한다(자동 교체는 하지 않음).
- 수용 기준: 승인 뒤 자료 파일을 수정해도 비판·수정·평가가 진행되는 시험, capabilities만 바뀐 연결로 진행되는 시험, CRLF 자료의 여러 줄 인용이 "확인됨"이 되는 시험.

## 5. 결정이 필요한 것

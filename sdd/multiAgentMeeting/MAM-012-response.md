# MAM-011 비판에 대한 응답과 첫 구현 계약

[MAM-011](MAM-011-critique.md)의 C1~C10에 응답한다. [MAM-010](MAM-010-decision.md)의 D3·D4와 [MAM-005](MAM-005-decision.md) D2는 확정 요구사항이며 다시 선택지로 올리지 않는다. 이 문서는 승인이 아니다. 아래 계약은 소유 Spec·ADR로 이관된 뒤에만 실행 규칙이 된다.

**표기:** [사실]은 이 문서 작성 시점(2026-10-09)의 현재 파일에서 읽어 확인한 내용이다. [추론]은 설계 판단이다. [미검증]은 실제 앱이나 CLI로 확인하지 않은 동작이다. 줄 번호는 현재 파일 기준이다. 이번 응답을 쓰면서 앱·CLI·제공자 호출은 실행하지 않았다.

## 첫 구현 범위 (C5 축소 수용)

- **참여:** Office 팀원 2~3명이 토론에 참여하고, 별도 평가자 1명을 둔다. 의장은 토론 참여자도 평가자도 아니다.
- **의장:** PM을 우선하고 CTO가 대체한다. 고정 ID로만 고른다.
- **진행:** `propose_critique_revise` 1라운드다. 필요 호출 = 의장 1 + 3n + 평가 1(n=참여자 수)이고, 하드 상한은 12다.
- **승인:** 계획 1회 승인이 기본이고, 단계별 패킷 확인은 옵션이다.
- **후속 범위:** N라운드, `position_rebuttal`, `review_panel`, 해시 체인, 회의록 MD 내보내기, Office 테이블 애니메이션.

## MAM-011#C1 — 의장 선택과 첫 호출 · 판정: 수용

- **근거:**
  - [사실] `engine.rs::run`(384–393)은 `cto`/`pm` 고정 ID가 없으면 `architect`/`plan` 역할 문자열로 대체 선택한다.
  - [사실] `engine.rs::discussion_runtime`(371–381)은 활성 팀원과 연결을 고르고, 팀원의 모델 지정을 연결에 덮어쓴다.
  - [사실] `model.rs::Meeting`(96)에는 의장 필드가 없다.
- **계약:**
  - 회의 의장은 `pm` → `cto` 순서의 고정 ID로만 고른다. 활성 상태, 읽기 전용 적격 연결(C4), 바쁘지 않음(C8)을 모두 통과해야 한다.
  - 역할 문자열로 대체 선택하지 않는다. 둘 다 안 되면 회의를 만들지 않고 이유를 반환한다.
  - 홈 `회의 시작` 버튼 옆에 다음을 보인다: 의장 이름, 연결·모델, "안건이 이 AI에 전송되고 AI는 프로젝트 폴더를 읽을 수 있음, 파일은 바꾸지 않음". `회의 시작` 클릭이 의장 호출 1회의 승인이다(MAM-009 §2.5, D3).
  - 의장 호출도 패킷으로 기록한다(단계 `planning`, 승인 모드 `start`). 사용량·전송 기록·호출 수에 포함한다.
  - 첫 구현은 계획 카드에서 의장을 바꾸지 않는다. 의장을 바꾸려면 회의를 닫고 다시 시작한다.
- **수용 시험:** PM 활성·적격이면 PM이 선택된다. PM이 없거나 바쁘면 CTO가 선택된다. 둘 다 없으면 회의 0건이고 이유 문구가 나온다. 역할 문자열만 맞는 팀원은 의장이 되지 않는다.

## MAM-011#C2 — 계획 버전과 검증 · 판정: 수용

- **근거:**
  - [사실] `meeting.rs::create`(17)는 연결 ID 4개와 고정 슬롯으로 회의를 만든다.
  - [사실] `MeetingSlot`(model.rs 74)에는 Agent ID가 없다.
- **계약:**
  - `MeetingPlan { revision, digest, objective, constraints, participants[{agentId, stance}], evaluatorAgentId, protocol, rounds, maxCalls, sources[{path, reason}], successCriteria, origin(chair|ceo), errors }`
  - `digest`는 errors를 뺀 정규화 JSON의 SHA-256이다.
  - **엔진 검증(백엔드 단일 함수):**
    - 의장 JSON 형식
    - 참여자 2~3명, ID 중복 금지
    - 의장은 참여자·평가자가 될 수 없고, 평가자는 참여자와 다르다
    - 모든 팀원은 활성·연결 적격(C4)·바쁘지 않음(C8)
    - protocol = `propose_critique_revise`, rounds = 1
    - 필요 호출 ≤ maxCalls ≤ 12
    - 자료: 상대 경로, 프로젝트 안, UTF-8, 파일당 16KB·합계 24KB 이하. 자료 바이트·해시는 검증 시점에 고정한다
  - 의장 제안이 검증에 실패해도 엔진이 조용히 고치지 않는다. 오류 목록과 함께 `plan_review` 단계로 보여 주고, CEO가 편집한다.
  - CEO 편집 = `update_meeting_plan(meetingId, baseRevision, plan)`. 새 revision과 digest를 만들고, 오래된 baseRevision은 거부한다.
  - 승인 = `approve_meeting_plan(meetingId, revision, digest, mode)`. 같은 트랜잭션에서 다시 검증하고, 오류가 남아 있거나 revision·digest가 맞지 않으면 거부한다. 바쁨 예약도 같은 트랜잭션에서 한다(C8).
- **수용 시험:** 깨진 JSON, 중복 팀원, 의장 겸직, 평가자 겸직, 상한 초과, 프로젝트 밖 자료는 오류로 표시되고 승인이 거부된다. 오래된 revision으로 승인하면 거부된다. 승인 직전에 연결 모델이 바뀌면 거부된다.

## MAM-011#C3 — D4 승인 상태 · 판정: 수용

- **근거:**
  - [사실] `TransmissionApproval`(model.rs 308)은 패킷 단위 승인이다.
  - [사실] `grant_scoped`(meeting.rs 326)는 닫힌 텍스트 정책에 묶여 있다.
  - [사실] `reserve`(458)는 승인·해시·지문·상한을 하나의 트랜잭션에서 검사한다.
  - [사실] 자료·연결 재검사는 `run_dispatch`(526~)의 트랜잭션 밖에서 한다.
- **계약:**
  - 별도 `MeetingPlanApproval { revision, digest, mode(plan|per_stage), status(approved|revoked|expired|rejected), decidedAt }`를 Meeting에 저장한다. 회의용 미리 승인(`scoped_grant`)은 새 모델에서 쓰지 않는다. 필드는 이전 회의 역직렬화용으로만 남긴다.
  - 모든 패킷은 승인된 계획에서만 파생되며 `planDigest`를 가진다.
    - `plan` 모드: 단계 패킷이 만들어질 때 승인(`mode=plan`, 계획 digest 결합)이 자동으로 기록되고 바로 이어서 보낸다.
    - `per_stage` 모드: 계획 승인 **위에** 단계마다 패킷 승인이 추가로 필요하다(기존 건별 결정 사용).
  - `reserve` 트랜잭션은 다음을 모두 확인한다: 계획 승인 상태 approved, 패킷·승인의 planDigest가 현재 승인 digest와 같음, 패킷 바이트·digest·revision, 연결 지문, 호출 상한, 단계 일치.
  - 자료 파일 재검사는 예약 직전에 하지만 파일은 트랜잭션으로 잠기지 않는다. 그래서 실제 전송 내용은 고정된 스냅샷 바이트만 쓴다. 변경을 발견하면 해당 패킷을 무효화하고 중단한다. 이 범위가 보장의 한계임을 명시한다.
  - **철회** `revoke_meeting_plan`은 예약과 같은 잠금에서 승인을 revoked로 바꾸고, 아직 보내지 않은 패킷을 void로 만든 뒤 `blocked`로 둔다. 이미 시작한 호출은 회수하지 않는다.
  - **재시작**하면 계획 승인이 expired가 된다. 재개 시 `plan_review`로 돌아가 다시 승인받는다.
  - `outcome_unknown` 패킷은 자동으로 다시 보내지 않는다.
- **수용 시험:** 승인 전 토론 호출 0건, 계획 밖 digest 패킷 차단, 철회 경합(철회 후 새 호출 0), 재시작 후 계획 재승인 필요, per_stage 모드에서 단계 승인 전 호출 0건.

## MAM-011#C5 — 프로토콜 호출 공식 · 판정: 부분 수용

- **수용:** 첫 구현은 1라운드 `propose_critique_revise`로 줄인다. 필요 호출은 `1 + 3n + 1`이다(정리 호출 없음, 의장 정리문은 후속).
- **짝짓기:** 참여자를 정렬된 순서로 놓고 i번째가 (i+1) mod n번째의 제안을 비판한다. 자기 주장은 비판하지 않고, 모든 참여자가 한 번씩 비판받는다.
- **받아들이지 않은 부분:** 정체 종료와 평가자 종료 권고 규칙은 N라운드에서만 의미가 있으므로 후속 범위에 함께 정한다. 대안으로, 첫 구현의 종료 이유는 `한 라운드 완료`, `부분 결과(중단·거절·형식 오류)` 두 가지로 고정한다.
- **수용 시험:** n=2와 n=3에서 짝짓기와 호출 수가 맞는다. 계획 maxCalls가 필요 호출보다 작으면 오류다.

## MAM-011#C7 — 해시 체인과 MD · 판정: 수용(후속)

- 해시 체인은 "로컬 기록의 자기 일관성 검증"으로만 설명한다. 외부 기준점이 없으면 DB 전체를 다시 쓴 변조는 증명하지 못한다는 MAM-011의 지적이 맞다.
- 첫 구현은 패킷 바이트와 SHA-256(현행)을 유지한다. 응답은 엄격하게 받는다: JSON 객체 하나, 또는 정확히 하나의 코드 블록 안 JSON. 모호하면 원문을 보존하고 차단한다.
- 해시 체인과 MD 렌더링·내보내기는 후속 범위다.

## MAM-011#C8 — Agent 점유와 귀속 · 판정: 수용

- **근거:**
  - [사실] `complete`(491)는 사용량의 agent_id를 `meeting:<회의>:<슬롯>`으로 쓴다.
  - [사실] `engine.rs::start`(47)와 `run`(384)에는 회의 점유 확인이 없다.
- **계약:**
  - 바쁨은 저장된 사실에서 계산하는 백엔드 함수 하나로 정한다. 새 예약 테이블은 만들지 않는다. 판정 기준은 다음과 같다:
    - (a) 승인된 계획 또는 진행 중인 의장 호출이 있는 회의(`planning`, `awaiting_transfer_approval`, `proposing`~`evaluating`)의 의장·참여자·평가자
    - (b) `dispatching` 상태 패킷의 수신 팀원
    - (c) 실행 Goal이 `analyzing`/`planning`/`validating`이면 해당 CTO·PM·QA
    - (d) 상태가 `running`·`pending`·`awaiting_integration`인 Task의 담당자
  - `blocked`/`stopped` 회의는 점유를 풀되, 결과 불명 패킷이 있으면 그 팀원은 계속 점유된 것으로 본다.
  - 계획 승인 트랜잭션과 실행 `start` 트랜잭션에서 이 판정을 다시 한다. 실행 `start`는 회의 중인 CTO·PM·QA·개발자가 있으면 이유와 함께 거부한다.
  - 사용량은 실제 팀원 ID로 기록하고 `meeting_id` 필드를 더한다. 기존 합성 ID 기록은 역사 데이터로 그대로 둔다.
- **수용 시험:** 한 팀원을 두 회의에 넣을 수 없다. 회의 중인 PM이 있으면 실행 목표 시작이 거부된다. 실행 업무 중인 개발자는 회의 계획에서 오류가 된다. 결과 불명 패킷의 팀원은 계속 점유로 표시된다.

## MAM-011#C9 — 홈 모드 · 판정: 수용

- **계약:**
  - 홈 상태는 `mode: goal | meeting`이다. 제출 명령은 `submit_goal`과 `start_meeting_from_home(topic)`으로 분리하고, 백엔드는 각각 kind를 검사한다.
  - 채택 초안의 출처(lineage)는 `goal` 모드에서만 전송한다. `meeting`으로 바꾸면 텍스트는 그대로 두고, 출처 배지에 "회의 모드에서는 출처 연결이 쓰이지 않습니다"를 표시한다.
  - 버튼은 `busy` 동안 비활성화해 연타를 막는다. 프로젝트를 전환하면 모드는 그대로 두고, 백엔드가 선택된 프로젝트로 판정한다.
  - 회의 Goal 작업공간은 자유 입력 없이 계획·승인·복구·결정 카드만 보인다.
- **수용 시험:** 회의 모드 제출 시 실행 Goal 0건·회의 Goal 1건이 생기고, 반대도 마찬가지다. 회의 모드에서는 lineage가 전송되지 않는다. 기본값은 `goal`이다.

## MAM-011#C10 — 이전 데이터 · 판정: 수용

- **근거:**
  - [사실] `SCHEMA_VERSION=3`(storage.rs 13), `migrate`(471)는 더 높은 버전의 DB를 거부한다.
  - [사실] `expire_on_restart`(meeting.rs 374)는 이전 패킷과 승인을 만료한다.
- **계약:**
  - `SCHEMA_VERSION=4`로 올리고 Meeting에 `modelVersion`을 둔다. 0 = 이전 고정 슬롯 모델, 2 = Office 캐릭터 모델.
  - 이전 모델 회의는 다음과 같이 처리한다:
    - 시작할 때 진행 중이던 회의를 `legacy_closed`로 닫는다.
    - 대기·승인 패킷과 승인을 만료한다.
    - 회의 Goal은 완료 처리한다.
    - 결정 자료와 원기록은 읽기 전용으로 보인다.
    - 모든 회의 명령(시작·계획·승인·재개·전송·결정)은 `modelVersion != 2`이면 서버에서 거부한다.
  - 버전 3 DB는 4로 올라간다. 구 바이너리는 버전 4 DB를 거부한다.
- **수용 시험:** 버전 3 DB의 진행 중 회의가 legacy_closed로 바뀌고, 이전 승인 재사용과 재개가 거부되며, 결정 자료는 읽을 수 있다.

## MAM-009 §9의 두 질문

1. **의장의 토론 참여:** 첫 구현에서 의장은 계획만 하고 토론 참여자와 평가자에서 분리한다. `review_panel`은 후속 범위다. 의장 참여 범위의 최종 선택(MAM-011 A/B)은 `review_panel` 착수 전까지 미뤄도 첫 구현이 막히지 않는다.
2. **회의록 MD의 프로젝트 폴더 저장:** 회의 계획 승인과 분리한다. 경로, 작성할 파일, 기존 파일 충돌, 실제 바이트를 보여 주고 **별도 프로젝트 파일 쓰기 승인**으로 다룬다. 첫 구현에는 내보내기를 넣지 않는다.

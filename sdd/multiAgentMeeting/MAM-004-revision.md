# v2 다관점 AI 회의 개정 제안 — 목표 중심 UX 통합

이 문서는 [MAM-001](MAM-001-proposal.md)을 대체하는 **검토 제안**이다. [MAM-002](MAM-002-critique.md)의 C1~C9와 [MAM-003](MAM-003-response.md)의 판정을 반영하고, 이미 v2에 적용된 [UX 간소화 전략](../uxSimplification/00_index.md)과 결합한다. 현행 제품 규칙, 구현 완료 주장, 파일 쓰기나 외부 전송의 승인이 아니다. 채택된 내용만 사용자 결정 후 소유 Spec·ADR·userFlow·Validation에 이관한다. C5와 C9는 아직 사용자가 결정하지 않았다.

## 1. 목적과 첫 범위

사용자는 같은 안건을 세 관점의 AI에게 **독립적으로** 제안하게 하고, 각 안에 대한 **서로의 비판과 수정**을 본 뒤, 분리된 평가자의 의견과 미해결 반론을 근거로 결정한다. 첫 사례는 **U컴퍼니 v2 개선안 검토**이며 프로젝트 파일은 바꾸지 않는다. 결과는 앱 안의 결정 자료다. 기존 CTO → PM → Dev → QA 실행 목표와 파일 통합·QA 계약은 그대로 별도 흐름이다([DM-04](../domain/DM-04-lifecycle.md), [GC-03](../goalConversation/GC-03-workspace.md)).

첫 수직 구현은 **고정된 세 제안 관점 + 평가자 한 명, 한 라운드, 최대 열 번의 모델 호출**로 제안한다. 제안 3회 → 대상이 지정된 교차 비판 3회 → 수정 3회 → 독립 평가 1회다. 논점 선택과 최종 묶음 조립은 엔진이 구조화 기록으로 수행하며 추가 요약 모델을 부르지 않는다. 모델 진행자, 프리셋 편집기, 동적 인원·다중 라운드, Office 전용 캐릭터, 자동 구현 인계는 첫 범위에서 제외한다. 연결이 부족하면 가상의 참여자를 채우지 않고 시작 불가 이유와 설정 경로를 보여준다.

| 첫 프리셋 슬롯 | 책임 | 필수 산출 |
| --- | --- | --- |
| 사용자·제품 | 실제 문제와 구매 가치 | 제안, 사용자 가정, 실패 조건 |
| UX·운영 | 첫 사용, 승인·복구, 사용량 제어 | 사용자 여정, 조작 부담, 운영 위험 |
| 엔진·보안 | 코드·SDD 실현성, 데이터·권한 경계 | 영향 범위, 근거, 경계 실패 사례 |
| 평가 | 세 안과 반론을 독립 검토 | 확인된 근거, 미확인 주장, 미해결 반론, 결정 선택지 |

관점과 공급자 이름은 다르다. 같은 모델을 여러 슬롯에 배정할 수 있어도 결과에는 연결·모델 중복과 평가 독립성의 한계를 표시한다. 이 구성이 단일 AI 호출보다 유용한지 **같은 안건의 단일 호출 기준선**과 발견한 중대 쟁점, 근거 연결, 호출·토큰 사용량으로 비교한다. 실측 전에는 확대하지 않는다([MAM-003#C3](MAM-003-response.md#mam-002c3--최소-참여-역할과-호출-수)).

## 2. 목표·회의·결정의 계약 (#R1, C1·C2)

`Goal.kind=execution|deliberation`을 제안하고 기존 목표의 이행 기본값은 `execution`으로 둔다. 회의 목표는 `Meeting`과 필수 1:1로 연결한다. Goal은 프로젝트 귀속, 사용자 탐색, 사용량 귀속, 대략의 상태를 담당한다. Meeting은 계획 스냅샷, 슬롯, 단계, 발언·쟁점, 사용량 한도, 결정 자료와 선택 기록을 담당한다. 기존 `TokenUsageRecord.goal_id`는 필수이고 현재 Goal에는 `kind`가 없으므로 모델·저장·스냅샷·UI 변경이 모두 필요하다([model.rs의 Goal/TokenUsageRecord](../../src-tauri/src/model.rs), [storage.rs의 snapshot](../../src-tauri/src/storage.rs), [MAM-003#C1](MAM-003-response.md#mam-002c1--회의와-goal의-관계)).

| Goal의 사용자 상태 제안 | Meeting의 세부 상태 | 의미와 홈의 다음 행동 |
| --- | --- | --- |
| 시작 전 | `draft`, `ready` | 계획·연결·자료 범위를 검토하고 명시적으로 시작 |
| 승인 대기 | `awaiting_transfer_approval` | 수신자와 실제 전송 자료를 확인·승인/거절 |
| 진행 중 | `proposing`, `critiquing`, `revising`, `evaluating` | 현재 관점·단계·다음 확인 시점 보기, 새 호출 중단 가능 |
| 중단 | `blocked`, `stopped`, `partial` | 원인·이미 전송된 범위·안전한 재개/종료 보기 |
| **결정 대기** | `package_ready`, `decision_pending` | 결정 자료와 미해결 쟁점을 보고 채택·수정 요청·보류/종결 중 선택 |
| 완료 | `decision_recorded` | 사용자의 선택과 당시 자료 버전을 조회 |

**UX 통합으로 MAM-003의 상태 제안을 한 단계 수정한다.** MAM-003은 결정 자료가 만들어지면 Goal을 `completed`로 표시하자고 했지만, [UX-01](../uxSimplification/UX-01-navigation.md)과 [UX-03](../uxSimplification/UX-03-delivery.md)의 홈·열린 작업은 아직 필요한 결정을 바로 보여야 한다. 따라서 이 개정은 `Goal.status=awaiting_decision`이라는 **새 대략 상태**를 제안한다. 자료 생성은 회의 완료/결정 대기의 시작이며, 사용자 선택이 저장되기 전 Goal을 완료로 표기하지 않는다. 사용자의 `보류`도 명시적 결정으로 기록할 수 있지만 자동 채택이나 구현 승인은 아니다. 이 상태 확장과 기존 `goalBrief`·`goalRecovery`·열린 작업 필터 변경은 채택 후 DM-04·GC-03·userFlow와 ADR에서 확정해야 한다. 이 문서만으로 현행 상태를 바꾸지 않는다.

회의 슬롯은 전역 `Agent`를 만들지 않고 회의마다 `participant_id`, 관점, 지침, 연결·모델 스냅샷을 고정한다. 기록의 가상 사용량 ID는 `meeting:<meeting-id>:<slot-id>`처럼 기존 팀원 ID와 충돌하지 않게 하고, 토큰 UI에서는 슬롯 이름·연결·모델로 해석한다. 현재 Office와 사용량 표시가 `agentId` 중심이라는 사실 때문에 이 매핑은 별도 구현 대상이다([MAM-003#C2](MAM-003-response.md#mam-002c2--공유-팀원-풀의-역할-충돌)). 회의 슬롯을 기존 Office 팀원처럼 그려 가상의 업무를 암시하지 않는다.

회의 Goal에서 현행 `answer_goal_message()`의 `direction`, `continue`, `git_bootstrap` 실행 라우팅은 엔진 경계에서 허용하지 않는다([engine.rs](../../src-tauri/src/engine.rs), [GC-01](../goalConversation/GC-01-turns.md), [GC-02](../goalConversation/GC-02-guidance.md)). 첫 수직 구현의 회의 기록은 조회 가능하며 사용자의 질문 입력을 제공한다면 읽기 전용 답변만 허용한다. 질문 기능 자체는 첫 구현의 필수 조건이 아니다. 회의 결과를 구현하려면 **별도 execution Goal**과 결정 자료 버전의 lineage를 만들고, 파일 변경·QA는 기존 승인 절차를 따른다.

## 3. 시작 전 계약과 전송 경계 (#R2, C5·C6)

계획은 안건, 기대 결과, 세 관점·평가 슬롯과 연결/모델, 평가 질문, 선택 자료의 경로·스냅샷 해시·범위, 제공자별 수신 자료, 한 라운드·최대 10호출, 호출당 시간 제한, 예상/보고 사용량 표시 방식을 고정한다. 계획을 저장하는 것은 시작이나 전송 승인이 아니다. 자료 바이트·연결·목적지가 달라지면 기존 승인을 재사용하지 않고 멈춘다. 승인 자료의 보존·삭제 기간도 채택 시 계약으로 정한다.

첫 화면에는 간단한 안건과 **`회의 계획 검토` 한 행동**을 놓는다. 계획 상세는 평범한 장문 양식 대신 `자료 → AI별 수신 범위 → 예상 호출/시간 → 승인 필요 항목`의 순서로 보여준다. 승인 다이얼로그에서는 수신자, 실제 전송 텍스트와 로컬 출처·해시를 전부 열어 확인할 수 있어야 한다. 표시 축약은 원문을 누락할 수 없다([UX-02](../uxSimplification/UX-02-surfaces.md), [정보 밀도 정책](../content-density.md), [Security](../security.md)).

제공자 A가 생성한 발언을 B에게 전달하는 규칙은 **#D1, 사용자 결정 대기**다.

| 선택 | 전송 직전 UX | 장단점 |
| --- | --- | --- |
| A — 실제 전송 묶음별 미리보기·승인 (**추천**) | 다음 호출을 멈추고 B에게 갈 정확한 발언·근거·목적지를 결정 카드에서 검토 | 승인 범위가 명확하다. 1라운드라도 사용자 대기가 여러 번 생긴다. |
| B — 제한된 회의 전체 사전 승인 | 생성물 종류·최대 길이·목적지·회차·민감자료 범위를 시작 전에 지정 | 루프가 자연스럽다. 동적 발언을 포괄하는 Security 개정·ADR 및 범위 강제 시험이 먼저 필요하다. |

두 선택 중 어느 것도 이번 문서로 승인되지 않는다. 첫 구현의 설계 기준은 A로 두되, 사용자 결정이 B라면 승인 객체와 화면·시험을 다시 설계한다. 초기 로컬 자료 전송도 현재의 일반 `Approval` 필드만으로 목적지와 바이트 범위를 표현할 수 없으므로 별도 승인 계약이 필요하다([MAM-003#C5](MAM-003-response.md#mam-002c5--복수-제공자-전송-승인-범위)).

선택 파일을 스냅샷으로 만들되 `cwd`만 제한한 CLI를 **읽기 범위 강제**라고 부르지 않는다. 현재 Codex/Claude CLI 플래그, Gemini/OpenCode/custom CLI, 플러그인의 `writable` 전달은 동일한 OS 수준 읽기 격리를 증명하지 않는다([MAM-003#C6](MAM-003-response.md#mam-002c6--읽기-전용입력-범위가-강제되지-않음)). 첫 실제 호출은 전송 프롬프트를 확인할 수 있는 텍스트 전용 연결 또는 선택 폴더 밖 읽기와 모든 쓰기의 거부가 실험으로 확인된 도구형 연결에 한정한다. 미검증 연결은 시작을 막고 정확한 이유와 연결 설정/검증 경로를 표시한다. 저장소 문구와 모델 발언은 지시가 아닌 자료다.

## 4. 회의 기록·검증·종료 (#R3, C3·C4·C7·N1)

| 순서 | 저장해야 할 사실 | 엔진의 확인 |
| --- | --- | --- |
| 독립 제안 3회 | 슬롯, 주장 ID, 출처/가정/미확인, 대안 | 각 제안자는 다른 초안을 받지 않았는지 입력 묶음 확인 |
| 대상 교차 비판 3회 | 원 주장 ID, 반론 ID, 영향, 근거와 제안된 수정 | 대상 주장 존재, 비판 대상을 중복·누락 없이 지정 |
| 수정 3회 | 각 반론의 수용/근거를 든 반박/보류, 이전 주장과 수정 관계 | 모든 반론에 처리 기록이 있는지 확인 |
| 분리 평가 1회 | 근거 확인·미확인, 미해결 반론, 선택지와 조건 | 평가자의 슬롯·연결 독립성 정보 표시 |
| 결정 자료 조립 | 제안·근거·반대 의견·사용량·종료 이유 | 원기록을 결정적으로 연결; 추가 모델 호출 없음 |

공통 증거 어휘는 `Claim / SourceRef / Assumption / Unknown / Acceptance`를 제안한다. `SourceRef`의 로컬 경로, 스냅샷 해시, 인용 위치와 짧은 인용문이 실제 바이트에 맞는지는 엔진이 확인한다. 이는 **출처 연결 검사**다. 해석의 진실성, 사용자 가치, 보안 적합성을 자동 증명하지 않는다. 평가자의 의견은 별도 출처로 보존하고 `기준 충족` 같은 품질 보증 라벨을 쓰지 않는다. 결정 자료는 `근거 확인`, `근거 미확인`, `미해결 반론`, `평가자의 견해`를 구분한다. 미해결 반론이 있어도 사용자에게 자료를 보여주되 상단에서 숨기지 않는다([MAM-003#C4](MAM-003-response.md#mam-002c4--품질-판정의-신뢰성)).

엔진이 **강제**할 수 있는 것은 라운드/호출 수와 제공자 호출당 타임아웃이다. 회의 누적 보고/추정 토큰 및 경과 시간은 **다음 호출을 차단**하는 방어선으로 사용한다. 호출 내부 토큰, 구독 잔량, 실제 청구액은 보장할 수 없고 금액 하드캡으로 표시하지 않는다. 실패·중단 호출의 사용량을 0으로 되돌리지 않고 보수적 추정을 남긴다([AI-04](../aiIntegration/AI-04-telemetry.md), [MAM-003#C7](MAM-003-response.md#mam-002c7--토큰-방어의-실제-보장-수준)). 기본 토큰 수치는 실측 전 정하지 않는다.

`중단`은 첫 구현에서 **새 모델 호출 금지**를 뜻한다. 이미 시작한 호출이 즉시 취소되거나 보낸 자료가 회수됐다고 표시하지 않는다. 현재 호출의 결과와 최종 사용량은 `미확정`으로 기록하고, 재시작 후 자동 재전송하지 않는다. 재개에는 남은 한도·입력 해시·전송 범위 재확인이 필요하다. 실제 호출 취소는 런타임 인터페이스와 제공자별 검증 후 별도 기능이다([MAM-003#N1](MAM-003-response.md#mam-003n1--중단승인-철회와-진행-중-호출)).

## 5. UX 최적화와 결합한 사용자 여정 (#R4)

회의는 여섯 번째 상위 메뉴나 독립된 회의실이 아니다. v2의 **홈·업무·Office·토큰·설정**과 전역 프로젝트 선택기를 유지한다([UX-01](../uxSimplification/UX-01-navigation.md), [ADR-0033](../architecture/decisions/ADR-0033.md)). 새 상태의 해석은 저장 사실에 대한 공통 selector 한곳에서 계산하고 홈·업무·Office는 같은 목표 ID를 연다. 기존 `V2Home`과 `V2Work`는 목표 목록·열기 콜백을 이미 갖고, `GoalConversation`은 상태 카드와 `진행 정보`를 갖지만 회의 kind·단계·결정 대기는 아직 표현하지 않는다([V2Home.tsx](../../v2/src/V2Home.tsx), [V2Work.tsx](../../v2/src/V2Work.tsx), [GoalConversationChat.tsx](../../src/GoalConversationChat.tsx)). 아래는 **변경 제안**이지 현행 UI 설명이 아니다.

| 순간 | 기본 화면의 한 줄 상태와 주 행동 | 상세의 소유 위치 |
| --- | --- | --- |
| 시작 | 홈의 목표 입력 뒤 `개발 실행 / 개선안 회의` 중 목적 선택, 선택 시 `회의 계획 검토` | 프로젝트·AI 연결의 세부 설정은 설정 |
| 계획 | 선택 자료·세 관점·평가자·예상 10호출과 필요한 승인 요약, `계획 확인` | 실제 전송 자료와 목적지, 한도·모델은 목표 작업공간의 계획 상세 |
| 승인 대기 | 홈·열린 작업에서 `전송 검토 필요`, 목표 안 결정 카드의 `범위 확인` | 완전한 바이트·목적지는 승인 다이얼로그; 일반 진행 정보 안에 묻지 않음 |
| 진행 | 홈/Office에는 `비판 중 · UX 관점 · 다음: 엔진 검증` 같은 실제 저장 상태 한 줄, `회의 열기` | 같은 목표 작업공간의 현재 쟁점·응답 연결, 전체 발언·호출·사용량은 `진행 정보` |
| 결정 대기 | 홈·열린 작업에 `결정 자료 검토 필요`, `결정 열기` | 목표 작업공간 상단에 권고·근거 미확인·미해결 반론·선택지, 아래에 원기록 링크 |
| 중단/복구 | `중단 사유 확인`, 실제 재개 가능 여부와 다음 행동 | 목표 결정 카드에 마지막 승인·전송·호출 상태, 불확실한 호출은 명시 |

공통 목표 작업공간은 **제목 → 상태·현재 관점·다음 행동 한 줄 → 지금 필요한 결정 한 카드 → 최근 발언/쟁점 → 입력 또는 안전한 행동 → `진행 정보`** 순서를 따른다([GC-03](../goalConversation/GC-03-workspace.md)). 회의의 최초 구현은 읽기 전용 기록과 결정 행동을 우선하고, 기존 실행 목표의 대화 작성기를 그대로 재사용해 방향 변경을 허용하지 않는다. 중요한 승인·복구·결정 자료는 다섯 항목 접기 규칙의 예외로 항상 보이며, 긴 발언·자료는 원문 복원 가능한 확장으로 처리한다([정보 밀도 정책](../content-density.md)). 화면 요약을 위해 AI를 다시 호출하지 않는다.

**표시 소유권**은 다음과 같다. 홈은 급한 결정과 짧은 상태만, 업무는 목표별 비교와 선택 목표 진입만, Office는 실제 활동과 목표 링크만 갖는다. 회의 슬롯을 Office 팀원으로 중복 등록하지 않는다. 토큰 메뉴는 프로젝트/목표/회의 슬롯/연결·모델의 사용량 및 보고/추정 출처를 소유하며 홈·Office에는 한 줄 요약만 허용한다. 설정은 AI 연결 상태와 이후의 프리셋 편집 진입을 소유한다. 승인·단계·쟁점·결정 자료의 **상세 원본은 목표 작업공간 하나**다([UX-02](../uxSimplification/UX-02-surfaces.md)). 다른 프로젝트의 승인 대기·진행 중·결정 대기 회의 목표는 `열린 작업`에서 같은 작업공간으로 돌아갈 수 있어야 한다. 열린 작업은 업무 목록의 복제품이 아니다.

## 6. v3와 공유할 증거 계약, 분리할 완료 조건 (#R5, C9)

회의 결정 자료와 [v3 개선안](../v3-improvement-plan.md)의 고객·문제 가설/메시지 초안/출시 확인 목록은 **근거·가정·미확인·인수 기준**이라는 어휘를 공유할 수 있다. 회의는 앱 내부 자료를 사용자에게 제시하고 선택을 기록한다. v3 비코드 결과는 **명시된 프로젝트 파일**을 만들고 독립 검토와 파일 통합 증거를 요구한다. 두 경로의 저장·승인·완료 조건을 하나로 합치지 않는다. 이 공유 어휘의 단일 소유 Spec과 두 어댑터는 사용자 채택 후 정한다.

**#D2, 사용자 결정 대기:** 공통 증거 계약을 먼저 정한 뒤 A) 읽기 전용 v2 개선 회의를 첫 소비자로 검증할지(**추천**), B) 기존 v3 계획의 출시 준비 파일 작업을 먼저 구현할지 선택한다. A는 이번 사용 목적과 직접 이어지고 파일 통합 위험이 작다. B는 v3 착수 순서를 보존한다. 두 경로를 별도 계약으로 병행하면 근거·인수 규칙이 중복되므로 추천하지 않는다. 어느 선택도 이 문서가 확정하지 않는다([MAM-003#C9](MAM-003-response.md#mam-002c9--v3-비코드-산출물-계약과의-중복)).

## 7. 구현 순서와 검증 게이트 (#R6, C8)

1. **기준선:** 열린 [QA-36](../uxSimplification/UX-03-delivery.md)의 Windows/Ubuntu 실사용 과제와 현재 UI 캡처·막힘을 기록한다. 기존 v2 탐색이 검증됐다고 가정하지 않는다.
2. **소유 규칙 이관:** 사용자 결정 D1·D2를 받은 후 Product/DM-04/AI/Security/GC-03/UX/userFlow/Validation과 필요한 ADR에 한 번만 계약을 이관한다. 새 `awaiting_decision`, 전송 승인, 사용량 슬롯의 원본과 화면 소유를 정한다.
3. **오프라인 회의 코어:** Goal kind, Meeting·슬롯·자료 해시·구조화 발언·결정 자료, 단계/호출 수, 중단·재시작·중복 전송 방지를 픽스처로 확인한다. 기존 실행 목표의 CTO–PM–Dev–QA 경로를 함께 회귀 확인한다.
4. **실제 수직 흐름:** 자료 전송 승인과 읽기/쓰기 격리가 확인된 연결로 3관점+평가자, 1라운드를 실행한다. 목표 작업공간·홈·열린 작업·업무·토큰에서 같은 저장 사실을 확인한다. 알림을 포함하면 열린 [QA-37](../../qa/MANUAL-QA.md)의 설치 앱 검증을 추가한다.
5. **사용성 측정:** 3~5명의 제품 비숙련 사용자가 설명 없이 회의 시작, 승인 범위 판독, 반론 찾기, 중단, 결정 자료 비교, 다른 프로젝트의 열린 회의 복귀, 토큰 추정 구분을 수행한다. 기준선 측정 후 [UX-03](../uxSimplification/UX-03-delivery.md)의 성공률·시간 제안 목표를 확정한다.

수용 시나리오는 다음을 모두 확인해야 한다. 승인 전 제공자 호출은 0건이다. 세 독립 제안과 각 반론·수정의 ID 연결을 추적할 수 있다. 근거 일치와 해석 평가는 별도로 표시되고 미해결 반론이 상단에 남는다. `중단` 후 새 호출은 없으며 진행 중 호출의 불확실성을 숨기지 않는다. `결정 대기`는 홈과 열린 작업에 나타나고 사용자가 선택한 뒤에만 완료된다. 좁은 창·키보드·포커스 복귀·여섯 개 이상 기록·여러 프로젝트에서도 긴급 승인과 복구가 접힌 로그에 묻히지 않는다. 토큰 총량은 호출 기록과 일치하고 추정/보고 출처를 복원할 수 있다. 어느 검증도 이 제안 문서 작성으로 완료된 것은 아니다.

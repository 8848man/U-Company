# MAM-002 — 다관점 AI 회의 제안에 대한 비판

> **MAM-002 · 비판 · 작성: Claude Cowork · 2026-10-09 · 대상: [MAM-001](MAM-001-proposal.md).** 상태와 후속 관계는 [폴더 인덱스](00_index.md)가 소유한다. 이 문서는 제안에 대한 의견이며 Spec, 승인, 구현 지시가 아니다.

## C1. 회의와 기존 Goal의 관계

**문제.** 제안은 `Meeting`을 “선택적 목표에 묶인” 독립 엔티티로 둔다(§7). 그러나 사용량·이벤트·알림·v2 업무 화면·Office 레일·대화는 모두 `goal_id`를 축으로 동작한다. 반대로 Goal에 그대로 넣으면 DM-04 수명주기와 대화 라우팅이 파일 작업을 전제로 움직인다.

**근거.**
- `TokenUsageRecord.goal_id`는 Optional이 아닌 `String`이다(`model.rs` `TokenUsageRecord`). 모든 모델 호출은 `execute_tracked(… goal_id …)`를 거친다(`engine.rs:208`). 토큰 화면은 프로젝트 → 목표 → 팀원으로 집계한다([Product](../product.md)).
- 알림은 저장된 목표·승인 상태 변화를 감지한다(ADR-0034).
- `answer_goal_message()`(`engine.rs:266~`)는 모델이 `continue`로 분류하면 `start()`를 호출해 개발 엔진을 시작하고, `direction`이면 파일 작업용 새 목표 버전을 만든다.
- 저장소는 범용 `objects(kind,id,payload)` 테이블이므로 새 엔티티 추가 비용은 낮다(`storage.rs` 스키마).

**대안.**
- A. 독립 Meeting + 선택적 Goal 연결: 사용량·알림·화면을 재구현하고 기록이 둘로 나뉜다.
- B. Goal의 한 모드로 흡수하고 회의 단계를 DM-04 상태에 추가: 수명주기 규칙이 오염된다.
- C. Goal에 `kind: "deliberation"`을 두고 `Meeting`을 1:1 **필수** 연결한다. Goal 상태는 굵은 단위만 사용한다(회의 중 `analyzing`, 결정 자료 생성 시 `completed`, 실패·한도는 `blocked`). 세부 단계는 Meeting에만 둔다.

**영향.** C는 사용량·이벤트·알림·업무 화면을 재사용한다. 대신 `start()`, 대화 라우팅, 재시도, 알림 문구에 kind 분기가 필요하다. `completed`가 품질 통과가 아니라 “결정 자료 생성”임을 화면에서 구분해야 한다.

**권고.** C를 채택하고 ADR로 기록한다. 첫 구현에서 deliberation 목표의 대화는 `discuss`만 허용하고 `direction`/`continue`/`git_bootstrap`은 막는다. 개발팀 인계는 회의 Goal을 전환하지 않고 lineage로 연결된 **새 개발 Goal**을 만든다.

## C2. 공유 팀원 풀의 역할 충돌

**문제.** 제안은 개선 회의팀과 개발 실행팀을 “별개”로 정의하지만, 저장 구조에는 팀 소속이 없다. 회의 참여자를 Agent로 추가하면 개발 엔진이 역할 문자열 부분 일치로 그 팀원을 개발자·QA·PM으로 선택할 수 있다.

**근거.**
- 개발자 선택: `role.to_ascii_lowercase().contains("implement")`(`engine.rs:93, 391`).
- QA·PM·CTO는 고정 ID가 없거나 비활성이면 `contains("review")`, `contains("plan")`, `contains("architect")`로 대체 선택한다(`engine.rs:389~392`, `565`).
- `Agent`에는 프로젝트·팀 필드가 없다(`model.rs` `Agent`). [DM-01](../domain/DM-01-workspace-team.md)은 Organization을 프로젝트 범위라고 쓰지만 구현은 워크스페이스 전역 풀이다.
- 예: 슬롯 “엔진·구현”의 role이 “implementation feasibility”이면 개발 목표의 작업이 배정된다.

**대안.** (a) Agent에 `team_id`를 추가하고 개발 엔진이 개발 실행팀만 고르게 한다. (b) 회의 참여자는 Agent를 만들지 않고 회의 시작 시 슬롯 스냅샷(지침·연결·모델)으로만 존재한다.

**영향.** (a)는 기존 선택 로직을 바꿔 회귀 위험이 있다. (b)는 Office 캐릭터 표시와 팀원별 토큰 집계가 줄어든다.

**권고.** 첫 구현은 (b). 사용량의 `agent_id`는 `meeting:<slot>` 네임스페이스를 쓴다. DM-01과 구현의 불일치는 별도로 WORKLOG에 기록한다.

## C3. 최소 참여 역할과 호출 수

**문제.** 5관점 + 진행자 + 평가자, 2~3라운드는 다관점이 단일 호출보다 낫다는 가설이 검증되기 전의 첫 프리셋으로 과하다.

**근거.**
- 5관점 개산: 1라운드 = 제안 5 + 선별 1 + 비판 약 5 + 수정 5 + 평가 1 ≈ 17회, 2라운드 ≈ 12회, 정리 1회 → 약 30회.
- 읽기 전용 호출도 `cwd = 프로젝트 루트`인 에이전트 세션이라 한 호출이 여러 파일을 읽을 수 있다(`engine.rs` `run()`의 CTO·PM 호출).
- `.run-data` 아래 QA용 SQLite 4개에는 사용량 기록이 0건이다. 기본 한도의 실측 근거가 없다.
- 같은 연결을 여러 역할에 배정하면 관점 간 오류가 상관된다.

**대안.** 제안자 2(예: 제품·사용 경험 / 엔진·운영) + 평가자 1(보안·검증 겸 비판). 진행자는 엔진의 결정적 규칙(A의 주장 → B가 비판, B → A). 제안 2 → 상호 비판 2 → 수정 2 → 평가 1 = **7회, 1라운드 고정**. 결정 자료는 엔진이 구조화 기록으로 조립하여 정리 호출을 없앤다.

**영향.** 호출 수 약 1/4, 상태 기계 단순화. 관점의 폭이 줄어드는 손실은 실측으로 판단한다.

**권고.** 3슬롯·1라운드로 시작한다. 두 제안자는 서로 다른 연결을 강제하거나, 같으면 “관점 다양성 낮음”을 표시한다. 수용 기준에 **단일 호출 기준선 비교**(같은 안건을 1회 호출로 수행해 근거 연결 수, 치명 쟁점 발견, 사용량 비교)를 추가한다. 기준선보다 낫지 않으면 확장하지 않는다.

## C4. 품질 판정의 신뢰성

**문제.** 다섯 기준의 `충족/부분/미충족/판정 불가`는 LLM 평가자의 자기 신고다. “모든 기준 충족 → `기준 충족` 종료”는 엔진이 품질을 확인한 것처럼 읽힌다. “진전 정체”에도 기계적 정의가 없다.

**근거.**
- 현행 QA 판정은 응답 첫 줄의 `PASS` 접두어만 본다(`engine.rs:558`, 부트스트랩 `132`). 개발 목표는 통합된 파일과 테스트라는 외부 증거가 있지만 회의 결과에는 없다.
- 평가자와 제안자가 같은 모델·연결이면 “분리된 평가자”가 독립성을 보장하지 않는다.

**대안.** 엔진이 검사하는 형식 게이트와 모델 평가를 분리한다.
1. 근거 해석: 모든 주장의 근거 참조(`path#Lstart-Lend` + 인용문)를 엔진이 실제 파일에서 다시 읽어 확인한다. 불일치 시 `미확인`.
2. 반론 처리: 모든 비판 ID에 `수용/반박/보류`가 있어야 하며 반박에는 근거 참조가 있어야 한다.
3. 반대 의견 보존: 미해결 반론이 있으면 결과 상단에 표시하고 완료 라벨을 금지한다.
4. 정체: 한 라운드에 새 근거 참조 0건이고 주장 상태 변화 0건.
5. 독립성 표시: 평가자 연결·모델이 제안자와 같으면 표시.

**영향.** 구조화 출력과 인용 검증기가 필요하다(`parse_plan`의 엄격 파싱 방식 재사용 가능). 형식 위반에 따른 실패율이 늘 수 있다.

**권고.** `기준 충족` 라벨을 폐기하고 **형식 검증(엔진)** 과 **평가자 의견(모델)** 을 분리 표시한다. 조기 종료는 형식 검증 통과 + 미해결 치명 쟁점 0건. MAM-001 §8 시나리오 3에 “평가자가 전부 충족이라고 해도 인용 검증 실패 시 완료 라벨 금지” 반례를 추가한다.

## C5. 복수 제공자 전송 승인 범위

**문제.** 제안은 전송 범위를 보여주고 “실제 승인 정책을 적용”한다고만 한다(§3-6). 현재 보안 명세와 데이터 모델에는 전송 승인 객체가 없다. 회의는 기존에 없던 **제공자 A의 생성물 → 제공자 B** 흐름을 만든다.

**근거.**
- [Security](../security.md)는 “External transmission … require CEO approval”이라고 하지만, 현행 목표 분석은 `project_context()`(AGENTS.md, CLAUDE.md, README.md, package.json, Cargo.toml 각 최대 6천 자)를 연결 배정만으로 제공자에게 보낸다. 일반 제공자 호출이 외부 전송인지 명세가 모호하다.
- [제공자 조사 기록](../provider-runtime-investigation.md)에는 자동 승인 검토자가 저장 목표·문서의 Codex 전송을 승인 부재로 거부한 사례가 있다.
- `Approval`은 `{goal_id, operation, reason, status, created_at}`뿐이다(`model.rs:186`). 목적지, 자료 목록, 해시, 만료를 표현하지 못한다.
- 비판 단계에서 A가 읽은 파일 내용(목록 밖 비밀값 포함 가능)을 인용하면 B로 전달된다. 비밀값 마스킹은 로그·이벤트에만 규정돼 있다.
- 발언 전문은 SQLite에 무기한 저장되며(대화 답변 기준 2만 자), 제공자 측 보존은 앱이 알 수 없다.

**대안.** `TransmissionGrant`(가칭): `meeting_id`, 목적지별 연결 ID·종류(cli/http/plugin)·엔드포인트·로컬/원격, 자료 목록(경로+sha256), 목적지 쌍별 생성 발언 교차 전달 허용 여부, 계획 스냅샷 한정 유효 범위. 실행 직전 해시 재검사 후 변경 시 재승인. 교차 전달 전 목록 밖 경로 인용과 비밀값 패턴을 마스킹·차단. 로컬 회의 기록의 보존 기간과 삭제 동작 명시.

**영향.** 승인 UI가 한 단계 늘지만, v3 출시 준비 파일럿의 외부 전송 승인과 같은 객체를 공유할 수 있다.

**권고.** 구현 전에 Security에 “제공자 호출에 포함되는 로컬 자료와 다른 제공자의 생성물은 전송이며 목적지·자료 목록 단위로 승인한다”를 명문화하고 ADR을 남긴다. 기존 개발 목표에 소급할지는 별도 사용자 결정으로 분리한다.

## C6. 읽기 전용·입력 범위가 강제되지 않음

**문제.** “선택한 로컬 자료만 근거”와 “첫 회의는 읽기 전용”은 현재 런타임에서 보장되지 않는다.

**근거.**
- 읽기 전용 호출도 `cwd = 프로젝트 루트`다. Codex `--sandbox read-only`와 Claude `--permission-mode plan`은 쓰기를 막지만 프로젝트 내 읽기는 막지 않는다(`provider.rs` `run_cli`).
- Gemini·OpenCode 분기는 `writable` 값을 인자에 반영하지 않는다. 읽기 전용 여부가 CLI 기본값에 의존한다. 사용자 정의 CLI도 `writable`을 무시한다.
- HTTP 제공자만 프롬프트가 전송 내용의 전부다. 다만 요청 본문에 `max_tokens`가 없다.

**대안.** 회의 호출의 `cwd`를 앱 데이터 아래 **자료 목록 전용 스냅샷 폴더**로 둔다(일반 폴더용 격리 복사 재사용). 읽기 전용 강제 인자가 없는 공급자는 능력 검사(`read_only_enforced` 등)에서 회의 참여를 거부한다.

**영향.** 스냅샷 비용은 작다. 작업 폴더 밖 읽기가 비대화형 모드에서 실제로 막히는지는 CLI마다 다르므로 provider-harness 검증이 필요하다.

**권고.** 수용 기준에 (1) 목록 밖 파일의 표식 문자열이 어떤 발언에도 나타나지 않음, (2) 읽기 전용 미강제 공급자 거부를 추가한다. Gemini·OpenCode의 `writable` 미반영은 기존 대화 경로에도 해당하므로 회의와 별도로 WORKLOG에 결함으로 기록한다.

## C7. 토큰 방어의 실제 보장 수준

**문제.** §5는 호출 전 점검과 정리 예약을 말하지만, 실제로 강제할 수 있는 것은 호출 수뿐이다. 항목별 보장 수준이 구분돼 있지 않다.

**근거.**

| 항목 | 현재 코드 기준 보장 수준 |
| --- | --- |
| 호출 수 | **강제 가능.** 엔진이 호출 시작을 결정한다. |
| 호출당 시간 | CLI 30분, HTTP 120초 타임아웃만 있다(`provider.rs`, `runtime.rs`). 회의 전체 시간 상한은 신규 구현. |
| 호출당 입력 | **불가.** 추정은 `prompt.chars()/4`(`engine.rs:210`)이며 세션 중 에이전트가 읽은 파일은 반영되지 않는다. 실제 값은 종료 후 `result.usage`/`turn.completed`로만 안다. |
| 호출당 출력 | **불가.** CLI에 출력·턴 상한 인자가 없고 HTTP 본문에 `max_tokens`가 없다. |
| 진행 중 중단 | **불가.** `usage_progress` 콜백이 `()`를 반환해 예산 초과 시 프로세스를 끊을 경로가 없다. |
| 구독 한도 | 사전에 알 수 없고 실패로만 드러난다. |
| 재시작 | 진행 중 사용량은 `interrupted`가 되지만 소진량은 불명이다(`storage.rs` `recover_interrupted`). |

**대안.** 한도를 `강제`(호출 수·라운드), `사전 차단`(누적 보고·추정이 상한을 넘으면 다음 호출 미시작), `추정`(토큰·시간)으로 표시한다. 남은 예산 계산에 `interrupted`·추정치 호출은 보수적 상한값으로 넣는다. 진행 중 중단(콜백이 중단 신호 반환 → `child.kill`)과 HTTP `max_tokens`는 별도 작업으로 검증한다.

**영향.** UI 문구가 정직해지고, 실측 전에는 기본 토큰 상한을 정할 수 없음이 분명해진다.

**권고.** 첫 구현은 호출 수만 하드 리밋으로 약속하고 토큰은 “다음 호출 차단” 수준으로 표기한다. 첫 실측 회의 3~5회의 보고 사용량을 WORKLOG에 남긴 뒤 기본값을 정한다.

## C8. 첫 구현 단위

**문제.** §2~§8을 그대로 수용 범위로 삼으면 프리셋 계약, 3~5관점, 진행자, 다중 라운드, 정체 감지, 개발팀 인계, 재시작 복구, UI가 한 번에 들어간다. v2 데스크톱 QA(QA-36/37)도 열려 있다.

**근거.** WORKLOG의 QA-36/37 미완료, v3 계획 검증 순서 1번(열린 v2 QA 우선), v2 `App.tsx`의 v1 컨트롤러 복제 부채([v2 README](../../v2/README.md)).

**대안.**
- 0단계(UI 없음, 오프라인): `tests/mock-adapter.mjs`·`echo-cli.mjs` 등 픽스처 제공자로 상태 기계를 Rust 테스트로 검증 — 승인 전 호출 0건, 호출 수 상한, 재시작 시 `interrupted`·자동 재전송 금지, 인용 검증, 스냅샷 밖 읽기 차단.
- 1단계(최소 수직): deliberation Goal + 3슬롯 + 1라운드 + 결정적 비판 배정 + 엔진 조립 결정 자료 + TransmissionGrant 1회 + v2 업무 상세의 읽기 전용 결과 패널.
- 제외: 프리셋 편집기, 모델 진행자, 다중 라운드·정체 감지, `개발팀에 인계` 버튼(수동 새 목표), Office 표시.

**영향.** `run()`/`execute_planned()`를 바꾸지 않고 `start()`의 kind 분기만 추가하므로 MAM-001 §8 시나리오 7을 구조적으로 지킨다.

**권고.** 1단계 전에 v2 QA-36을 통과시킨다. 1단계 수용 기준은 MAM-001 §8의 1·3·5·6·7에 단일 호출 기준선 비교(C3), 목록 밖 표식 미노출(C6), 읽기 전용 미강제 공급자 거부(C6)를 더한다.

## C9. v3 비파일 산출물 계약과의 중복

**문제.** WORKLOG의 “v3 first implementation slice audit”는 첫 코딩 작업을 **근거가 붙은 비파일 산출물 계약**으로 정했다. MAM-001의 `DecisionPackage`·`Contribution`(근거 참조, 가정, 미확인 항목)은 그 계약의 한 사례다. 따로 진행하면 근거·인수 모델이 두 벌 생긴다.

**근거.** WORKLOG “v3 first implementation slice audit”: PM 작업은 반드시 파일을 바꾸고, QA·보고는 자유 텍스트라는 한계를 첫 격차로 지목했다. [v3 계획](../v3-improvement-plan.md)의 후속 2번(결과 증거와 인수 화면)도 같은 문제다.

**대안.** 근거 참조, 주장 상태, 인수 묶음을 공통 계약 하나(ADR 하나)로 정의하고, (a) 회의를 그 첫 사용처로 삼거나 (b) 회의를 v3 계약 이후로 미룬다.

**영향.** 일정은 늦어지지만 인수 화면과 회의 결과 화면을 하나로 만들 수 있다.

**권고.** 사용자 결정 필요. 제안: 공통 계약을 먼저 정의하고, 파일 쓰기가 없는 회의를 첫 사용처로 삼는다.

## MAM-001 §9 질문에 대한 요약 답

1. 회의와 Goal: `kind=deliberation` Goal + Meeting 1:1 필수 연결, 대화는 `discuss`만(C1).

# Office 캐릭터 회의 개정안 비판

[MAM-009](MAM-009-revision.md)을 [MAM-010](MAM-010-decision.md)의 확정 결정 D3·D4와 MAM-005 D2 아래에서 검토한다. D3의 실행 목표와 같은 읽기 전용 신뢰 경계, D4의 계획 1회 승인 기본·단계별 확인 옵션을 되돌리지 않는다. 아래 **확인 사실**은 현재 소스와 소유 SDD에서 직접 읽은 내용, **설계 추론**은 그 사실에서 도출한 위험과 대안이다. 앱·CLI·실제 제공자 호출은 이번 검토에서 실행하지 않았으며 동작 검증으로 주장하지 않는다. [WORKLOG](../../WORKLOG.md)의 이전 시험 기록은 별도 선행 기록이다. 이 문서는 구현·전송·파일 쓰기 승인이 아니다([Security](../security.md)).

## MAM-011#C1 — 의장 선택과 첫 호출의 경계가 불완전함

- **중요도:** 높음 · **첫 구현 차단:** 예
- **문제:** 고정 ID `pm`→`cto`는 실행 엔진의 대체 선택과 기준이 다르다. `회의 시작` 즉시 발생하는 의장 호출은 계획 카드 전에 실행되므로 안건·프로젝트 맥락·팀 명단이 어디로 전송되는지 먼저 보여 주어야 한다. 계획 카드에서 의장을 바꾸면 이미 끝난 호출을 바꾸는 것이 아니다.
- **근거 — 확인 사실:** MAM-009 §2는 고정 ID와 `회의 시작`을 첫 호출 승인으로 정한다. `engine.rs::discussion_runtime`(371–381)은 활성 Agent/연결을 선택하고, `engine.rs::run`(384–398)은 CTO/PM의 고정 ID가 없으면 역할 문자열의 `architect`/`plan` 대체를 사용한다. `engine.rs::project_context`(662–673)는 AGENTS.md·CLAUDE.md·README.md 등에서 맥락을 읽는다. `model.rs::Meeting`(96–120)에는 의장/계획 상태가 없다. **설계 추론:** 실행 목표는 대체 Agent로 진행해도 같은 팀의 회의는 의장이 없다고 막힐 수 있다. 이것은 코드 충돌이라기보다 선택 정책의 불일치다.
- **대안:** 회의용 의장 선택 규칙을 명시적으로 분리한다. 활성·연결 적격·공통 바쁨 상태를 통과한 `pm`, 없으면 `cto`만 자동 선택하고 둘 다 없으면 이유를 표시한다. 계획 카드의 의장 변경은 기존 계획과 승인을 폐기하고 새 의장 호출부터 시작한다. 시작 버튼 직전에 의장·연결·프로젝트 읽기 범위·첫 전송을 보인다.
- **영향:** 구현 가능한 대체 PM이 있어도 회의는 막힐 수 있으나, 사용자는 누구의 계획인지 일관되게 알 수 있다. 첫 호출도 회의 사용량·전송 기록에 포함한다.
- **권고:** 자동 대체는 MAM-009의 고정 ID 규칙을 유지하고, 대체 불가 이유와 첫 전송 고지를 수용 기준에 넣는다.

## MAM-011#C2 — CEO 편집 뒤 계획을 승인 범위로 고정하는 계약이 없음

- **중요도:** 치명 · **첫 구현 차단:** 예
- **문제:** 참여자 수·평가자 분리·바쁜 팀원·연결·자료·라운드/호출 수 검사는 나열되어 있으나, 중복 Agent, 의장 겸직, 유일한 평가자 가용성, 프로토콜별 역할, 편집 뒤 재검사 시점과 승인한 정확한 계획 버전이 정의되지 않았다.
- **근거 — 확인 사실:** MAM-009 §2.3–2.4는 2–5명, 평가자 분리, 바쁨, 연결, 상한, 자료, 프로토콜 검증과 CEO 편집 후 재검사를 요구한다. 현재 `meeting.rs::create`(17–53)는 연결 ID 4개와 고정 슬롯을 받으며, `model.rs::MeetingSlot`(74–81)은 Agent ID·이름·역할 스냅샷이 없다. `model.rs::Meeting`(96–120)에도 계획 해시·수정판이 없다. **설계 추론:** UI에서 재검사를 해도 승인 저장과 첫 전송 사이의 팀원/연결 변화를 막지 못한다.
- **대안:** 의장 JSON을 정해진 스키마로 파싱하고 중복 ID, 활성/숨김, chair/participant/evaluator 겸직 규칙, 각자의 연결 적격성·모델, 자료 canonical 경로·크기·해시, 프로토콜별 최소 인원·호출 공식, 상한을 검증한다. CEO 편집은 새 `planRevision`과 정규화된 `planDigest`를 만들고 기존 승인을 무효화한다. 승인 저장과 각 호출 예약에서 같은 서버 검증을 수행하며, 바쁨은 C8의 원자적 예약으로 판정한다.
- **영향:** 카드에 보인 계획과 실제 실행 계획이 일치한다. 편집 중 연결/자료가 바뀌면 새 카드가 필요하다.
- **권고:** 계획을 불변 버전으로 저장하고 계획 승인 명령에 `meetingId`, `planRevision`, `planDigest`, 승인 모드를 요구한다. 잘못된 JSON·편집 후 오래된 revision·중복 Agent·용량 초과를 첫 수용 시험으로 삼는다.

## MAM-011#C3 — D4 계획 승인을 기존 패킷 승인에 겹치면 우회·중복 상태가 생김

- **중요도:** 치명 · **첫 구현 차단:** 예
- **문제:** 현재 `TransmissionApproval`은 표시된 **패킷**의 승인이지 회의 **계획**의 승인이 아니다. `scoped_grant`도 닫힌 텍스트와 미리 승인 정책에 묶여 있어 이름만 바꿔 재사용할 수 없다. 기본 계획 승인과 옵션 단계별 확인의 우선순위, 거절·철회·중단·재시작 전이를 정의해야 한다.
- **근거 — 확인 사실:** `model.rs::TransmissionApproval`(308–325)은 packet ID/digest/revision/mode를 저장하고, `meeting.rs::grant_scoped`(326–356)는 닫힌 텍스트 적격성을 요구한다. `meeting.rs::reserve`(458–486)는 승인된 패킷·원문 해시·연결 지문·호출 수를 한 SQLite 거래에서 검사하고 dispatching으로 바꾼다. `meeting.rs::stop`(578–589)과 `storage.rs::recover_interrupted`(408–424)는 중단/결과 불명을 다룬다. `meeting.rs::run_dispatch`(534–547)는 자료·연결 재검사를 거래 밖 538–539행에서 수행한 뒤 예약하고 호출한다. **설계 추론:** 계획 계약 없이 패킷 승인만 자동 생성하면 계획의 참여자/프로토콜/라운드 변경을 식별할 수 없고, 거래 밖 자료 확인과 예약 사이에는 파일 변경 가능 시간이 남는다.
- **대안:** 별도 `MeetingPlanApproval`을 만들고 회의·정규화 계획 해시·참여 Agent/모델·연결 지문·자료 해시·프로토콜/라운드/호출 상한·모드·상태를 묶는다. 모든 패킷은 승인된 계획에서만 파생되며 예약 거래에서 부모 계획 revision/상태와 패킷 digest, 목적지, stage/round, 호출 상한을 검사한다. 자료 확인은 예약 직전 다시 하되 파일이 거래로 잠기지 않는 한 엄밀한 원자성 보장은 없으므로, 실제 전송 내용은 승인된 고정 스냅샷만 사용하고 변경 발견 시 중단한다. `per_stage`는 **계획 승인에 더해** 해당 단계 패킷 승인이 필요하다. 단계 거절은 현재 단계 전체 중단/수정 카드로 가고 다른 승인 패킷도 보내지 않는다. 철회·중단은 예약과 직렬화하며 이미 시작된 호출은 회수 불가, 결과 불명은 자동 재전송 금지, 재시작은 계획 재승인을 요구한다.
- **영향:** D4 기본 흐름은 계획 카드 1회로 유지하면서 옵션 확인은 추가 관문이 된다. 기존 scoped grant와 새 계획 승인은 서로 다른 기록으로 남는다.
- **권고:** 계획 승인 계약/상태도를 소유 Spec에 먼저 이관하고, 계획 밖 패킷·모드 변경·동시 stop/revoke/dispatch·재시작·unknown outcome 시험을 첫 구현 관문으로 삼는다.

## MAM-011#C4 — D3의 ‘같은 경계’는 현재 회의 전송 코드와 소유 문서에 아직 없음

- **중요도:** 치명 · **첫 구현 차단:** 예
- **문제:** MAM-009 §7의 ‘전송 직전 검사 재사용’은 일부만 성립한다. 현재 회의 transport는 실제 제공자를 호출하지 않으며, 실행 목표의 CLI 동작과 회의 허용 목록을 하나의 적격성 함수로 연결하지 않았다.
- **근거 — 확인 사실:** `engine.rs::answer_goal_question`(242–255), 목표 메시지 경로(268–280), CTO/PM 호출(424–435)은 프로젝트 루트와 `writable=false`를 사용한다. `provider.rs::run_cli`(65–91)는 Codex `--sandbox read-only --cd`, Claude `--permission-mode plan`, `current_dir(cwd)`를 사용한다. Gemini/OpenCode 분기(76–82)와 사용자 정의 인자는 이 플래그를 강제하지 않는다. `provider.rs::execute_with_observer`(53–63)는 plugin과 HTTP도 연결한다. HTTP는 `writable=true`를 거부한다(36행)지만 CLI와 같은 폴더 읽기 경계는 아니다. `meeting.rs::closed_text_eligibility`(90–95)와 `AppTransport`(106–115)는 실제 연결을 거부하고 fixture만 응답한다. `security.md` 31행, `AI-03-adapter.md` 5행, ADR-0035는 아직 닫힌 텍스트·건별 기본 계약이다. **설계 추론:** `writable=false` 전달만으로 플러그인/커스텀 CLI가 읽기 전용인지는 입증되지 않으며 실제 Windows 호출도 미검증이다.
- **대안:** 실행 목표와 회의가 공유할 **읽기 전용 지원 프로필**을 제공자별로 명시한다. 첫 실구현은 Codex·Claude CLI의 정확한 실행파일/버전/인자와 모델 연결 지문만 허용한다. Gemini·OpenCode·커스텀 CLI·plugin은 읽기 전용 반영 계약과 시험이 생길 때까지 제외하고 이유를 표시한다. HTTP는 현재 `writable` 거부와 별개로 프로젝트 읽기·전송 범위가 다르므로 첫 범위에서 제외해 별도 프로필로 판단한다. `security.md` 31행은 D3 프로젝트 루트 읽기 공개와 D4 계획 승인·옵션 패킷 관문으로, `AI-03` 5행은 닫힌 텍스트 게이트를 공통 읽기 전용 프로필/명령줄 전달 계약으로, ADR-0035는 대체 또는 보완 ADR로 이관한다.
- **영향:** 실제 Claude·Codex 회의가 가능해질 수 있으나, 선택 자료 밖 프로젝트 파일 열람과 제공자 전송은 D3의 공개 범위다. 읽기 전용 플래그의 실제 효과는 제공자별 검증 전에는 주장할 수 없다.
- **권고:** 소유 Security/AI-03/ADR 이관과 Windows 실제 제공자 수용 시험을 실전 회의의 필수 선행 조건으로 적는다.

## MAM-011#C5 — N라운드·3프로토콜의 호출 공식과 종료 순서가 미정

- **중요도:** 높음 · **첫 구현 차단:** 예(첫 범위를 줄이면 해소)
- **문제:** ‘호출 수는 프로토콜로 계산’과 ‘진전 정체/조기 종료’만으로는 계획 카드를 계산하거나 상한을 검증하기 어렵다. 평가자를 마지막 한 번 부르면서 ‘평가자가 조기 종료를 권하면’이라는 조건은 마지막 평가 전 조기 종료와 양립하지 않는다.
- **근거 — 확인 사실:** MAM-009 §3은 3프로토콜, N라운드, 평가자 마지막 1회, 정체/조기 종료를 제시하지만 후속 라운드의 누가 몇 번 답하는지는 고정하지 않는다. `meeting.rs::stage_slots`/`next_stage`(84–85), `prepare_proposals`(261–265), `advance`(562–575)는 3+3+3+1의 10호출·1라운드 고정이다. **설계 추론:** 쟁점당 호출인지 Agent당 묶음 호출인지 정하지 않으면 20호출 상한의 안전성도 예측할 수 없다.
- **대안:** 첫 구현은 `propose_critique_revise`, 참여자 2–3명, 1라운드, 평가자 1명으로 제한하고 의장 호출/선택적 정리 호출까지 상한에 포함한다. 다음 단계에서는 프로토콜별 ‘각 stage에서 각 Agent 최대 1호출’ 스케줄과 최악 호출 공식, 결정적 짝짓기(자기 주장 비판 금지·상대 최소 1회), 미응답/invalid 결과를 명세한다. 예컨대 첫 프로토콜 첫 라운드는 참여자 n명이 제안·비판·수정 각 1회라 `3n+1` 평가 호출이며 의장 호출과 정리 호출은 별도 더한다. 이후 라운드는 미해결 쟁점이 있어도 Agent별 묶음 횟수를 고정해야 한다. 평가 전 정체 종료는 ‘정체로 토론 종료 후 평가’로, 평가 권고는 최종 종료 사유로 기록한다.
- **영향:** 3프로토콜 동시 구현은 늦어지지만 D3/D4와 실제 캐릭터 회의를 먼저 검증할 수 있다.
- **권고:** 의장 계획 카드에 최악/남은 호출 수를 동일 공식으로 표시하고, 상한·짝짓기·정체·invalid 응답 시험을 먼저 만든다.

## MAM-011#C6 — 현재 결정 자료는 전체 논증 그래프와 미해결 반론 보증을 담지 못함

- **중요도:** 높음 · **첫 구현 차단:** 예(추적성 최소 계약)
- **문제:** MAM-009의 양방향 ‘권고→주장→출처→비판→처리→수정’은 지금 구조의 `DecisionPackage`만으로 성립하지 않는다. 평가자의 미해결 ID가 유효한지만 검사하면 빠뜨린 치명 반론을 엔진이 발견하지 못한다.
- **근거 — 확인 사실:** `model.rs::MeetingContribution`(171–184)은 단계/슬롯/원문/정규화 JSON을 보존하지만 round·노드 관계·체인 해시가 없다. `model.rs::PackageClaim`/`PackageRecommendation`(188–205)은 주장 요약과 연결 ID만 갖는다. `meeting.rs::validate_contribution`(778–779)은 평가자의 `unresolvedCritiqueIds`가 기존 비판 ID인지만 검사한다. `meeting.rs::assemble_package`(790–823)는 accept되지 않은 비판 또는 평가자가 표시한 비판만 `dissent`에 넣는다. `SourceCheck`(model.rs 160–167)의 경로·오프셋은 별도 그래프 노드가 아니다. **설계 추론:** 수용된 비판, 처리 후 수정 이전 버전, 평가자가 누락한 미해결 비판을 화면에서 모두 거슬러 올라갈 수 없다.
- **대안:** 노드/간선을 엔진이 정규화해 별도 저장하고 원문 발언은 그대로 보존한다. Agent가 낸 임시 ID를 회의+라운드+Agent 스냅샷+순번의 엔진 ID로 변환하고 참조 존재/유형/사이클·역방향 인덱스를 검사한다. `SourceRef`는 선택 자료 해시와 인용 위치/길이를 기록하되 반복 인용은 모든 일치 위치 중 선택 방식이 필요하다. 모든 Critique에 명시적 처리 상태를 요구하고, 미처리는 엔진이 원자료에서 파생해 결정 자료에 **항상** 넣는다. 의장 정리문은 그 위에 주석으로만 추가한다.
- **영향:** 저장·UI가 늘지만 사용자의 핵심 요구인 주장·비판·근거 추적성을 실제로 충족한다.
- **권고:** 첫 구현부터 주장/비판/응답/수정/출처와 권고의 최소 간선을 저장하고, ‘평가자가 빈 미해결 목록을 보낸 경우’에도 엔진이 미처리 반론을 표시하는 시험을 둔다.

## MAM-011#C7 — 해시 체인과 Markdown의 보증 범위를 좁혀야 함

- **중요도:** 중간 · **첫 구현 차단:** 아니오(내보내기는 후속 가능)
- **문제:** MAM-009 §5의 ‘나중에 기록을 고치면 드러난다’는 표현은 신뢰할 기준 해시가 외부에 고정돼 있지 않으면 과하다. MD 패킷 렌더링을 바꾸면 승인 digest도 달라지며, JSON 코드 블록 하나만 파싱하는 규칙은 모델 답변의 여분 블록·코드펜스 탈출 처리를 정의하지 않는다.
- **근거 — 확인 사실:** `meeting.rs::build_payload`(146–185)는 현재 JSON 원문 문자열을 만들고, `MeetingPacket`은 그 바이트와 SHA-256을 저장한다(`model.rs` 281–304). `meeting.rs::assemble_package`(831–832)의 package 해시는 패키지 자체의 직렬화 해시이며 체인/외부 기준점이 아니다. `security.md` 7, 25, 29행은 외부 전송과 프로젝트 파일 쓰기를 별도 승인으로 다룬다. **설계 추론:** 공격자가 DB와 저장된 최종 해시를 함께 다시 쓰면 로컬 체인만으로는 변조를 증명할 수 없다. 해시는 기록 간 연결과 우발적/부분 변조 탐지에 유용하다.
- **대안:** 원문 응답 해시·정규화 노드 해시·이전 해시·정해진 직렬화 버전을 각 발언에 저장하고, 검증 시 회의 생성부터 패키지까지 다시 계산한다. ‘로컬 기록의 자기 일관성 검증’으로 설명하고 저자 신원·모델 진실성·DB 전체 롤백을 증명한다고 말하지 않는다. MD는 엔진이 이스케이프/길이 제한을 걸어 렌더링하며 실제 전송 바이트를 패킷에 보존한다. 응답은 엄격한 단일 JSON 응답 또는 정확히 한 개의 허용 코드 블록만 받아들이고 모호하면 원문 보존 후 차단한다. 앱 데이터 내보내기와 프로젝트 폴더 내보내기를 분리한다.
- **영향:** 사람이 읽는 기록은 얻되 승인 원문과 검증 범위가 정직해진다. Agent 직접 MD 쓰기를 기각한 근거는 프로젝트 쓰기 승인·동시성·참조 검증 면에서 타당하다. 더 나은 대안은 엔진이 앱 데이터에 구조화 기록을 쓰고 MD를 결정적으로 렌더링하는 것이다.
- **권고:** MD 내보내기를 첫 실전 호출의 선행 조건으로 삼지 말고, 패킷 바이트 버전과 그래프 정규화부터 고정한다.

## MAM-011#C8 — 공통 바쁨 상태·Office 발언·토큰 귀속이 아직 실제 Agent를 쓰지 않음

- **중요도:** 높음 · **첫 구현 차단:** 예(동시 배정 방지)
- **문제:** ‘한 캐릭터 한 세션’을 화면 계산만으로 지킬 수 없다. 실행 목표와 회의가 동시에 Agent를 예약하는 서버 규칙이 필요하고, 의장·평가자도 세션에 포함해야 한다.
- **근거 — 확인 사실:** `meeting.rs::create`(17–53)는 `MeetingSlot`만 만들고 Agent ID가 없으며 `meeting.rs::complete`(491–521)는 usage.agent_id를 `meeting:<회의>:<슬롯>`으로 기록한다. `engine.rs::run`(384–398)의 CTO/PM 선택과 업무 배정(453–455)에는 회의 Agent 예약 확인이 없다. `src/meetingStatus.ts::meetingAttention`(17–35)은 Goal/Meeting 단계를 표시할 뿐 개인 점유를 산출하지 않는다. `src/OfficeGoalRail.tsx` 19행은 현재 회의 관점이 Office 팀원이 **아니라**고 표시한다. `sdd/progress-visibility.md` 7–12, 16–18행은 저장된 담당/이벤트를 사실 기준으로 하고 꾸민 진행을 금한다. **설계 추론:** 프런트에서만 바쁨을 보이면 중복 호출이 가능하다.
- **대안:** 저장소에 `AgentSession` 또는 동등한 예약을 두고 계획 승인·실행 업무 배정·의장/평가자 호출 예약 시 같은 거래에서 충돌을 검사한다. 예약 해제는 정상 종료/차단/중단/재시작 불명 상태를 분리하고, 결과 불명인 호출은 안전하게 보류한다. Office는 실제 저장된 발언의 ID와 발언 원문 발췌만 표시하되 ‘지난 발언’과 ‘현재 호출 중’을 구별하고 민감한 원문을 기본 말풍선에 과하게 노출하지 않는다. 토큰 기록은 이후 실제 Agent ID와 meeting ID를 별도 저장하며 기존 합성 ID 기록은 역사 데이터로 보존/표시한다.
- **영향:** 실행 업무와 회의의 잘못된 동시 배정을 막는다. 분석 화면의 과거 합성 ID 집계는 마이그레이션/표시 규칙이 필요하다.
- **권고:** 한 Agent에 대한 두 회의, 회의+실행, 의장+참여자, 재시작 불명 호출의 경쟁 시험을 첫 구현에 포함한다.

## MAM-011#C9 — 홈 모드 전환이 초안 출처와 실행 경로를 섞을 수 있음

- **중요도:** 높음 · **첫 구현 차단:** 예
- **문제:** 모드 드롭다운 자체는 UX-01/02의 홈 주 행동 하나와 맞지만, 같은 입력칸의 텍스트와 채택 초안 출처가 다른 모드에서도 살아 있으면 의도하지 않은 회의/실행 Goal이 생길 수 있다. `회의 시작`이 의장에게 즉시 전송한다는 점도 버튼 옆에서 명확해야 한다.
- **근거 — 확인 사실:** `v2/src/App.tsx` 220행은 회의 초안을 `intent`와 `draftSource`로 홈에 넘기며 272행의 제출은 `submit_goal`과 lineage를 함께 보낸다. `v2/src/V2Home.tsx`는 현재 목표 전달 버튼과 보조 회의 링크를 가진다. `UX-02-surfaces.md` 5, 9, 18행은 홈 주 행동 하나·회의 Goal의 공통 작업공간·정보 소유권을 정하고, `UX-01-navigation.md` 15행은 열린 작업에서 다른 프로젝트 목표로 복귀하도록 한다. **설계 추론:** 드롭다운만 추가하고 핸들러를 공유하면 채택 초안이 회의 안건으로 넘어가거나 모드 표시와 다른 명령이 호출될 수 있다.
- **대안:** 모드는 `goal|meeting` 판별형 상태로 두고 제출 명령/결과를 타입과 백엔드 Goal.kind 검사로 분리한다. 채택 초안은 `goal` 모드로 고정해 출처 배지를 보여 주며 `meeting`으로 바꾸면 출처를 유지할지 해제할지 명시적으로 처리한다(권고: 텍스트는 보존, lineage는 목표 수행에만 유효). 입력 중 모드/프로젝트 변경, Enter 키 제출, 더블클릭을 같은 검증 경로에 묶고 버튼에 결과와 첫 전송을 짧게 쓴다. 회의 Goal 작업공간의 자유 입력창은 계속 숨기고 계획 승인/복구/결정 카드만 보인다.
- **영향:** 홈은 한 입력/한 주 행동을 유지하고, 사용자는 전송과 Goal 종류를 구분한다. 열린 작업·Office·업무는 같은 `meetingAttention`을 사용해야 한다.
- **권고:** 실행 Goal 0건/회의 Goal 1건 및 반대 경우, 채택 초안 출처, 키보드·연타·프로젝트 전환을 수용 시험에 넣는다.

## MAM-011#C10 — 이전 회의 만료만으로 스키마·구버전 호환이 끝나지 않음

- **중요도:** 높음 · **첫 구현 차단:** 예
- **문제:** 새 필드를 붙이고 템플릿/계약만 올리면 구 바이너리가 새 DB를 열어 알 수 없는 JSON 필드를 제거할 수 있다. 이전 회의를 읽기 전용으로 보여 주려면 UI·백엔드 명령 양쪽에서 역사 기록임을 판별해야 한다.
- **근거 — 확인 사실:** `storage.rs` 13행 `SCHEMA_VERSION=3`, `migrate`(471–474)는 더 높은 DB 버전을 구 바이너리에서 거부한다. `meeting.rs::expire_on_restart`(374–407)는 패킷/승인 버전과 scoped grant를 만료하지만 새 의장·계획·그래프 모델로 이전 회의를 변환하지 않는다. `model.rs::Meeting`(96–120)과 `MeetingSlot`(74–81)의 새 필드는 아직 없다. **설계 추론:** 스키마를 그대로 두면 구 바이너리의 역직렬화·재직렬화 경로가 새 필드를 보존한다는 보장이 없다.
- **대안:** 저장 형식 변경과 함께 SCHEMA_VERSION을 올려 구 바이너리 열기를 막고 백업/복구 경로를 마련한다. 이전 구조에는 `legacy_v1` 등 명시적 모델 버전을 붙여 읽기 전용 표시·내보내기만 허용한다. 모든 이전 패킷/승인/scoped grant를 만료하고 이전 회의의 재개/승인/전송 명령은 서버에서 거부한다. 새 데이터는 필수 계획 해시·Agent ID·프로토콜/라운드와 체인 형식에 대해 검증한다.
- **영향:** 새 바이너리의 이전 자료 열람은 유지되고 구 바이너리의 조용한 손실을 막는다. 사용자는 옛 회의를 다시 실행할 수 없음을 보게 된다.
- **권고:** 새/옛 DB 업그레이드, 구 바이너리 거부, 과거 결정 자료 열람, 이전 승인 재사용 거부를 마이그레이션 수용 시험에 넣는다.

## MAM-009 §9 열린 질문에 대한 의견

1. **의장의 토론 참여:** 기본은 의장과 평가자를 참여자에서 분리하는 안을 추천한다. `review_panel`에서는 의장을 초안 작성자로 허용하되 자기 초안을 평가하지 못하게 하고, 의장 초안·수정·정리 호출을 계획 상한과 점유에 포함한다. 이 겸직 규칙이 확정되기 전에는 `review_panel`을 첫 구현에 넣지 않는다. 선택지: **A** 진행 전담, `review_panel`에서만 초안 작성(추천) / **B** 모든 프로토콜에서 일반 참여. B는 독립성·호출 수·바쁨 계산을 더 복잡하게 한다.
2. **프로젝트 폴더 MD 저장:** 계획 승인은 전송 범위만 승인한다. 프로젝트 경로·작성 파일·기존 파일 충돌/심볼릭 링크·실제 바이트를 미리 보여 주고 **별도 프로젝트 파일 쓰기 승인**을 받을 것을 추천한다. 기본 앱 데이터 내보내기는 프로젝트 쓰기와 분리한다. 이는 `security.md` 25, 29행과 D4 범위를 지키는 해석이므로 D4를 다시 묻는 결정은 아니다.

## 첫 구현 축소와 검증 순서

1. 소유 Spec·ADR에 D3/D4와 의장/계획 승인 계약을 먼저 이관한다. 코드 착수 전의 설계 수용이지, 이 문서 자체의 실행 허가가 아니다.
2. Office Agent 2–3명 + 별도 평가자, PM/CTO 의장, `propose_critique_revise` 1라운드, 명시적인 호출 상한으로 **한 실전 회의**를 끝까지 수행한다. 첫 범위에서도 C2·C3·C4·C6의 기본 관문과 C8의 바쁨 배제, C9의 안전한 제출, C10의 마이그레이션은 생략할 수 없다.
3. N라운드·`position_rebuttal`·`review_panel`·해시 체인/MD 내보내기·Office 테이블 애니메이션은 단계적으로 추가한다. 단, 초기 결정 자료의 주장·비판·근거 최소 추적성과 미해결 반론 표시를 후속으로 미루지 않는다.
4. 오프라인 경쟁/승인/마이그레이션 시험과 Windows Claude·Codex 실제 읽기 전용 호출을 분리해 보고한다. 실제 앱/CLI 동작은 이번 문서 검토에서 확인하지 않았다.

# v2 다관점 AI 회의 — 두 번째 개정 제안

이 문서는 [MAM-004](MAM-004-revision.md)를 대체하는 검토 기록이다. [MAM-005](MAM-005-decision.md)의 사용자 결정 D1·D2를 확정 요구사항으로 유지하고 [MAM-007](MAM-007-response.md)의 C1~C10 판정과 N1을 반영한다. 현재 구현이나 소유 Spec이 아니다. 회의 결과·이 문서·AI 출력은 실제 파일 쓰기 또는 외부 전송 승인이 아니다([Security](../security.md)).

## 1. 목적, 첫 사례, 순서

사용자는 v2 개선 안건과 명시된 로컬 자료를 선택한다. 제품·고객, UX·운영, 엔진·보안의 **세 독립 관점**이 제안하고 서로 지정된 주장에 비판한 뒤 수정한다. 분리된 평가자가 확인 근거, 가정, 미해결 반론을 표시한다. 엔진이 구조화 기록을 결정적으로 묶어 **결정 자료**를 제시한다. 첫 사례는 1라운드, 제안 3 + 비판 3 + 수정 3 + 평가 1로 **최대 10번의 모델 호출**이다. 초과 호출과 새 라운드는 자동으로 시작하지 않는다. 단일 호출 기준선과 중대 쟁점 발견·근거 연결·사용량을 비교하기 전 범위를 늘리지 않는다.

공통 `Claim / SourceRef / Assumption / Unknown / Acceptance` 어휘는 v3의 비코드 파일 산출물과 공유할 후보지만, 회의 자료는 앱 내부 결정 자료이고 v3는 승인된 프로젝트 파일과 독립 QA를 필요로 한다. **v2 회의를 먼저 빌드·검증**하고 그 프로그램에서 **별도의 v3 문제**를 논의·정리한 뒤, CEO가 채택한 목표만 기존 승인 흐름으로 자기 구현한다. 이것이 D2의 순서다. 회의가 v3 고객 목표를 대체하지 않는다([v3 개선안](../v3-improvement-plan.md)).

## 2. 데이터·상태와 호환성 (#R1: C1·C2·N1)

`Goal.kind=execution|deliberation`을 필수로 하고 기존 목표는 스키마 2→3 마이그레이션에서 `execution`으로 채운다. Goal과 Meeting은 1:1이며 Meeting은 계획·참여 슬롯·단계·자료·승인·발언·결정 자료를 소유한다. 슬롯은 전역 Agent를 만들지 않는 스냅샷이고 연결·모델·지침·관점을 고정한다. `TokenUsageRecord.goal_id`는 회의 Goal ID, `agent_id`는 이름 공간이 분리된 회의 슬롯 ID를 사용한다. UI는 슬롯 ID를 실제 팀원처럼 오해하지 않고 연결·모델을 표시한다.

| Goal.kind | 저장할 Goal.status | Meeting.stage/설명 |
| --- | --- | --- |
| execution | 현행 `new→analyzing→planning→awaiting_approval→executing→integrating→validating→completed`, `blocked` | Meeting 없음. 기존 CTO–PM–Dev–QA 흐름 유지 |
| deliberation | `deliberating` | `draft/ready/awaiting_transfer_approval/proposing/critiquing/revising/evaluating/blocked/stopped`; 세부 복구와 지금 할 일을 Meeting에서 결정 |
| deliberation | `awaiting_decision` | `package_ready`; 부분 결과, 미확인 출처·반론도 포함할 수 있으나 상단에 표시 |
| deliberation | `completed` | `decision_recorded`; CEO 선택·자료 버전이 저장됨. 자동 구현 승인 아님 |

개발 엔진의 `run_goal/start/run`, `resume_goal/resume_approved`, 기존 목표 메시지·지침·revision, Git bootstrap, 일반 `decide_approval`, `save_task`, 목표 QA 한도/그룹 변경 및 내부 저장 경계는 `kind=execution`을 요구한다. UI 가드만으로 허용하지 않는다. 회의는 전용 `create_meeting/start_meeting/decide_transmission/revoke_meeting_grant/stop_meeting/resume_meeting/decide_meeting` 명령으로만 전이한다. `kind × status × 명령` 전수 행렬과 다른 종류에 저장 변경·이벤트가 생기지 않는 시험을 구현 게이트로 둔다. 회의가 중단되거나 앱이 재시작되면 진행 중 호출은 미확정으로 보존하고 `Meeting.stage=blocked`; 자동 재전송하지 않는다. `resume_meeting`은 자료·범위·사용량을 다시 확인한다([DM-05](../domain/DM-05-recovery.md)).

첫 회의 데이터를 쓰기 **전에** `SCHEMA_VERSION=3`으로 올리고 2→3 이행을 트랜잭션으로 마친다. 구 바이너리는 기존 높은 버전 거부 검사로 3 DB를 열지 못한다. QA에는 실사용 데이터와 분리된 `-DataDir`/`UTOPIA_DATA_DIR`를 쓰며, 실제 데이터 승격 전 백업·복구 경로를 정한다. 2→3 기존 Goal/승인 보존, 3 DB 구 바이너리 거부, 재시작·중복 호출 금지가 수용 기준이다([MAM-007#C2](MAM-007-response.md)).

## 3. 자료·근거·회의 단계 (#R2: C3·C4)

계획은 안건, 고정된 참가 슬롯, 사용자 선택 파일의 정규 경로·해시·허용 길이, 공급자별 목적지, 단계·호출 상한을 스냅샷으로 보존한다. 출처 ID·인용 위치·짧은 원문이 스냅샷 바이트와 일치하는지는 엔진이 검증한다. 이 검사는 **출처 연결**이며 해석의 진실성이나 고객 가치의 증명이 아니다. 구조화된 주장·비판·수정 ID와 각 반론의 `수용/근거를 든 반박/보류`를 기록한다. 평가자도 별도 슬롯과 연결·모델을 남긴다. 동일 연결 재사용 시 독립성 제한을 표시한다.

엔진이 단계 시작 시 전송 packet을 모두 확정·저장하고 다음 단계의 packet은 현재 단계 출력이 완료되기 전에는 만들지 않는다. 각 단계의 발언은 독립성 요구와 원 주장→비판→수정 연결을 지킨다. 미해결 반론이 있어도 결정 자료를 만들 수 있지만 합의나 객관적 품질 인증으로 표시하지 않는다. 생성 결과는 `확인된 출처`, `미확인 주장`, `가정`, `미해결 반론`, `평가자의 견해`, `종료 이유`로 구분한다. 모델 출력의 악성 지시, 비밀값 패턴, 가짜 출처는 신뢰하거나 전송 범위를 넓히는 근거가 아니다.

## 4. 건별 전송 승인과 미리 승인 모드 (#R3: C4·C5·C6·C8)

**기본값은 건별 미리보기·승인**이다. `TransmissionApproval`은 일반 프로젝트 쓰기 `Approval`과 별도 객체다. packet별 `meeting_id`, `packet_id`, **엔진이 저장한 불변 전송 바이트**, `payload_sha256`, `byte_length`, 출처 스냅샷 ID, 목적지 연결 지문, 표시 revision, 상태와 전송 결과를 가진다. UI는 그 바이트와 목적지를 보여준다. 승인 명령은 ID·표시 revision·다이제스트를 제출하고 서버가 저장 바이트와 일치하는지 확인한다. 송신 직전 동일 바이트·승인 상태·파일 해시·목적지 지문을 다시 확인한다. 변경되면 멈추고 **새 packet/미리보기**를 요구한다. 승인 대기는 24시간 폴링 스레드가 아니라 `Meeting.stage=awaiting_transfer_approval`의 저장 상태다.

한 단계의 packet 여러 개는 **한 결정 카드**에 묶어 보여 주되 각 행에서 수신자·전체 내용·다이제스트를 열고 **개별 승인/거절**한다. 한 번에 선택을 제출해 화면 전환을 줄일 수 있어도 개별 전송 범위는 합치지 않는다. 거절된 packet은 보내지 않는다. 고정된 첫 회의에서 하나라도 거절되면 결손 발언을 꾸며 계속하지 않고 `blocked` 및 부분 결정 자료로 전환한다. CEO가 자료를 수정해 새 packet을 건별 승인하거나 부분 결과로 종결한다. 기존 승인 ID를 다시 쓰지 않는다.

전송 승인 카드에는 확정된 D1의 **`미리 승인`**을 제공한다. 선택 시 오직 **해당 회의의 남은 호출**에 대한 범위 승인으로 바뀐다. 범위는 회의 ID, 고정 입력 해시, 허용 단계/고정 packet 조립 템플릿과 Contribution/SourceRef 관계, 수신 연결 지문(`kind`, 정규 실행 파일/endpoint, 모델, args, CLI 버전·도구 정책), payload 바이트 상한, 라운드·호출 상한, 만료 시각으로 한정한다. ‘비판/수정’은 엔진 조립 단계 분류이지 자유 텍스트의 의미 검증이 아님을 UI에 설명한다. 민감정보 탐지는 경고이며 부재 보증이 아니다. 연결 변경, 자료 해시 변경, 사용자 철회, 앱 재시작, 회의 종료, 기간 만료에서 범위 승인은 비활성화하고 건별로 돌아간다. 모든 전송의 packet ID·해시·목적지·시각·결과와 원문 복원 경로를 회의 기록에 남긴다.

범위 승인과 건별 승인 모두 전송 packet 외의 파일 읽기나 제3자 도구 전송을 허용하지 않는다. **`미리 승인`은 검증된 닫힌 텍스트 흐름 연결에만** 제공한다. Security의 현행 ‘정확한 내용 승인’과 미래 생성 발언의 ‘범위 승인’을 소유 Spec·ADR에 분리해 이관하고 시험하기 전에는 미리 승인 버튼을 실행 가능하게 하지 않는다. 이 모드가 프로젝트 파일 쓰기·배포·새 실행 파일을 승인하지 않는다([Security](../security.md), [MAM-005](MAM-005-decision.md)).

철회와 호출 시작의 경합은 DB 상태 검사만으로 해결되지 않는다. 엔진은 회의별 호출 시작 게이트에서 승인 확인→예약·사용량 기록→실제 호출 착수를 직렬화한다. 철회가 게이트를 먼저 얻으면 이후 새 호출은 0건이고, 이미 시작한 호출은 완료 여부가 불확실할 수 있다. 착수 여부가 불명확하면 `outcome_unknown`을 남겨 자동 재전송하지 않는다. 실제 송신 bytes와 표시 bytes의 해시, 재시작 후 대기 상태, 철회 경합, 지문 변경, packet 거절 후 새 호출 0건을 검증한다.

## 5. 제공자와 사용량 경계 (#R4: C6·C7)

첫 실제 회의는 **검증된 텍스트 전용 연결**만 사용한다. 엔진 생성의 빈 작업 디렉터리, 고정된 입력 packet, 도구·MCP·웹 차단 설정, 승인 범위 밖 파일 읽기/쓰기/전송의 실제 거부가 필요하다. 빈 `cwd`와 `read-only`/`plan` 플래그만으로 격리를 주장하지 않는다. 연결의 실행 파일·버전·정책이 바뀌면 검증을 무효화한다. Codex/Claude CLI, Gemini/OpenCode/custom/plugin 가운데 검증하지 못한 연결은 회의 시작을 막고 이유를 보인다. 하네스는 파일 열기 시도 거부, 쓰기 거부, 도구/MCP/웹 호출 0건, 실제 전송 목적지 확인을 검사한다. 이 문서 시점에는 연결별 통과 기록이 없다.

초기 작은 packet은 CLI 명령줄 인자를 쓰되 **전체 명령줄 길이**를 연결별 검증값 아래로 검사한다. Windows 제안 상한은 24,000 UTF-16 코드 단위이며 더 낮은 연결별 값이 우선한다. 큰 자료의 stdin 프로토콜은 제공자별 지원을 확인한 뒤 후속으로 넣는다. 상한 초과는 임의로 잘라 보내지 않고 실행 전 막는다.

호출 수와 라운드, 호출당 타임아웃은 **강제**한다. 누적 토큰/시간은 보고 또는 보수적 추정으로 **다음 호출을 차단**한다. 구독 잔량·금전 하드캡은 약속하지 않는다. 실패·중단 호출의 사용량을 0으로 만들지 않고 `estimated/reported`와 불확실성을 표시한다([AI-04](../aiIntegration/AI-04-telemetry.md)). 모델 진행자·무제한 토론·자동 연장은 첫 사례에 없다.

## 6. 5메뉴 안의 사용자 여정 (#R5: C3·C8·C10)

상위 탐색은 **홈·업무·Office·토큰·설정**과 전역 프로젝트 선택기를 유지한다([UX-01](../uxSimplification/UX-01-navigation.md)). 홈의 실행 목표 입력은 `팀에 전달` 한 주 행동을 유지하고 **`여러 관점으로 먼저 검토` 보조 링크**가 회의 계획으로 간다. 회의 Goal은 홈/업무/Office/열린 작업에서 **같은 목표 작업공간**을 연다. 자세한 승인 범위, 현재 단계·관점, 반론, 결정 자료는 그곳이 원본이다. 홈/Office는 저장 상태의 한 줄 요약, 토큰 전용 메뉴는 목표·슬롯·연결/모델별 보고/추정 사용량을 소유한다([UX-02](../uxSimplification/UX-02-surfaces.md), [GC-03](../goalConversation/GC-03-workspace.md)).

공통 selector가 Goal.kind·Goal.status·Meeting.stage·대기 전송 packet으로 **현재 상태·담당 관점·다음 행동·긴급 정렬**을 계산한다. `awaiting_decision`은 열린 작업에 남아 홈의 ‘지금 결정할 일’에 올라온다. 우선순위는 **전송 승인 > 중단 복구 > 결정 자료**이고 한 번에 활성 카드 하나만 보인다. 전송·결정 자료는 일반 다섯 항목 접기 규칙으로 숨기지 않는다. 첫 구현의 회의 작업공간은 자유 대화 입력창을 숨기고 전용 안전 행동만 보인다. 회의에 개발 QA 한도·작업 그룹·CTO/PM 개발 그래프·가상 Office 캐릭터를 표시하지 않는다. 회의 단계 그래프는 `제안→비판→수정→평가→결정`이다. 표시 요약을 위해 새 AI 호출을 하지 않는다.

결정 자료 준비에 새 OS/소리 알림은 첫 사례에서 추가하지 않는다. 저장된 새 승인·중단에 대한 현행 [알림 정책](../notifications.md)을 유지하고 재시작 backlog를 다시 울리지 않는다. 홈/열린 작업의 발견성은 실제 QA-36에서 검증한다. 좁은 창, 키보드, 포커스 복귀, 여섯 개 이상 packet/목표/연결, 다른 프로젝트 복귀, 승인 카드 처리 시간과 이탈률을 측정한다([UX-03](../uxSimplification/UX-03-delivery.md)).

## 7. 결정 자료의 인계와 자기 구현 (#R6: C9)

CEO의 `채택`은 결정 자료 버전을 기록할 뿐 실행 Goal·Task·Approval을 자동 생성하지 않는다. 선택된 권고는 **편집 가능한 새 실행 목표 초안**에만 채운다. CEO가 직접 제출하면 새 `execution` Goal이 생기고 결정 자료 ID·버전 해시를 lineage로 남긴다. CTO/PM은 결정 자료를 `참고용·모델 생성물·비권위`로 취급한다. PM이 파일 범위를 계획한 뒤 기존 `project_write` 승인과 독립 QA를 거친다. `Goal.intent`는 CEO가 제출한 실제 텍스트만 담는다([Security](../security.md)).

D2 마지막 단계의 U컴퍼니 자기 구현은 현재 비Git 루트를 일반 폴더로 바로 실행할 수 있다고 가정하지 않는다. 기본 추천은 **별도 등록된 Git 소스 복사/체크아웃**과 설치 앱 또는 분리된 실행 프로세스를 쓰고, 빌드 산출물을 범위에서 제외하며 승인된 변경만 검토해 반영하는 방식이다. 실제 폴더 경로·Git 준비 방법은 그 단계 직전 CEO가 선택한다. 이 문서는 Git 초기화·복사·원본 변경 승인이 아니다. 현재 일반 폴더 복사는 20,000파일/512 MiB 제한이다([platform.rs](../../src-tauri/src/platform.rs)).

## 8. 구현·검증 순서와 종료 조건

| 단계 | 결과·차단 게이트 | 검증 |
| --- | --- | --- |
| 0. v2 기존 기준선 | 열린 QA-36의 Windows/Ubuntu 실제 앱 흐름 기록 | 홈·승인·복구·좁은 창·프로젝트 전환의 현재 상태 |
| 1. 소유 문서·ADR 이관 | Product/DM/AI/Security/GC/UX/userFlow/Validation의 소유 규칙과 새 데이터·범위 승인 ADR | 원본 하나씩, 실행 승인과 전송 승인 분리 |
| 2. 오프라인 코어 | Goal kind·스키마 3·Meeting 단계·슬롯·구조화 발언·증거·사용량·복구·kind 가드 | 상태×kind×명령 행렬, 기존 실행 흐름 회귀, 2→3·구 DB 거부 |
| 3. 건별 전송 | 불변 packet·내용 결합 승인·전송 직전 검사·재시작 복구 | 승인 전 0호출, 변경 packet 거부, 거절 후 0호출, 전송 기록 |

| 6. UX 실사용 | 같은 목표 작업공간과 5메뉴, 결정 대기·부분 결과 | QA-36·필요 시 QA-37, 3~5명 비숙련 과제와 회귀 |

모든 단계에서 모델 출력/저장소 문구를 승인으로 해석하지 않는다. 실제 앱·CLI 격리와 토큰 비용은 **실행 후에만** 확인할 수 있다. 첫 실제 호출을 막는 C4·C7을 충족하지 못하면 오프라인 코어 결과만 완료로 기록한다. MAM-008은 두 번째 개정이다. [폴더 인덱스](00_index.md)의 ‘개정이 2회를 넘으면 종료’ 조건에는 아직 닿지 않았고, 이후 새 근거 없는 반복은 멈추고 사용자의 채택 범위와 남은 쟁점을 확인한다.

# MAM-004 개정안과 MAM-005 결정의 구현 가능성 비판

이 문서는 [MAM-004](MAM-004-revision.md)를 비판하고 [MAM-005](MAM-005-decision.md)의 사용자 결정을 **확정 요구사항**으로 참조한다. D1(건별 미리보기·승인 기본 + 회의별 `미리 승인` 모드)과 D2(v2 회의 먼저 빌드·검증 → 그 프로그램으로 v3 정리·자기 구현)는 다시 선택지로 되돌리지 않는다. 쟁점은 이 결정을 **안전하고 쓰기 쉽게 구현할 수 있는가**에 한정한다. 이 문서는 Spec, 승인, 구현 지시가 아니다. 상태와 관계는 [폴더 인덱스](00_index.md)가 소유한다.

## C1. 회의 Goal의 진행 중 상태가 정의되지 않아 엔진 경로로 새어 나감

**문제.** MAM-004 §2의 표는 사용자 표시 상태(시작 전·승인 대기·진행 중·중단·결정 대기·완료)와 Meeting 세부 상태만 정한다. 실제 `Goal.status`에 어떤 값을 저장할지는 새 값 `awaiting_decision` 하나만 명시한다. 진행 중 회의를 기존 `analyzing`·`awaiting_approval`·`blocked`로 저장하면, 그 상태를 이미 해석하는 엔진과 화면 코드가 회의를 개발 목표처럼 다룬다.

**근거.**
- [사실] `recover_interrupted()`(`storage.rs:353`, 목표 처리 `389~393`)는 `analyzing`, `planning`, `awaiting_approval`, `executing`, `integrating`, `validating` 목표를 재시작 시 `blocked` + `resumed_from=<이전 상태>`로 바꾼다.
- [사실] `can_retry_before_write()`(`engine.rs:71`)는 `blocked` + `resumed_from ∈ {analyzing, planning}` + 해당 목표의 Task·Approval이 없으면 재시도를 허용한다. 재시도 명령 `run_goal`(`lib.rs:379`) → `start()`(`engine.rs:47`)는 kind 구분 없이 `run()`으로 CTO 분석을 시작한다.
- [사실] `resume_approved()`(`engine.rs:78`)는 `resumed_from=awaiting_approval`이면 `operation == "project_write"` 승인만 찾는다.
- [사실] 원래 UI(`src/App.tsx:290`)는 `status === 'new'`인 모든 목표에 `run_goal` 버튼을 보인다. [ADR-0033](../architecture/decisions/ADR-0033.md)에 따라 원래 UI는 같은 데이터로 계속 실행할 수 있다.
- [사실] `goalBrief`(`src/goalBrief.ts:27`)와 `stageAssignee()`(`src/progress.ts:14`)는 `analyzing`이면 CTO를 담당자·활성 캐릭터로 표시한다.
- [추론] 진행 중 회의를 `analyzing`으로 저장하면 Office와 홈이 일하지 않는 CTO를 담당자로 보여준다. 재시작 후에는 재시도 버튼이 개발 엔진을 실행할 수 있다. 전송 승인을 `Approval`이 아닌 별도 객체에 저장하면 `can_retry_before_write()`가 Approval 0건으로 판단해 이 경로가 열린다.

**대안.**
- A. 진행 중 회의를 위해 kind 전용 상태(예: `deliberating`)와 `awaiting_decision`을 모두 새로 둔다. 기존 엔진 함수는 상태 값만으로 회의를 받지 않는다.
- B. 기존 상태 값을 재사용하고, 상태를 읽는 모든 백엔드·프런트 경로에서 kind를 먼저 검사한다.

**영향.** A는 새 상태 두 개를 DM-04와 모든 selector에 추가해야 한다. 그러나 누락된 경로는 "알 수 없는 상태"로 실패한다. B는 변경 수는 적지만 누락된 경로가 조용히 개발 엔진을 실행한다.

**권고.** A를 택한다. 백엔드의 `start()`, `resume_approved()`, `can_retry_before_write()`, `decide_approval()`, `propose_goal_guidance()`, `recover_interrupted()` 입구에서 kind를 검사해 거부한다. 이 검사는 UI 가드와 별개로 필수다. 회의 재시작 복구는 회의 전용 명령(`resume_meeting`)으로만 한다. 수용 기준에 **status × kind 전수 행렬 테스트**를 넣는다. 각 조합에서 위 명령들의 허용·거부를 확인한다.

## C2. `kind`·새 상태를 이해하지 못하는 구 바이너리가 회의를 실행 목표로 되돌림

**문제.** MAM-004는 저장소가 범용 `objects` 테이블이라 스키마 비용이 낮다고 본다. 하지만 같은 데이터 폴더를 쓰는 구 버전 바이너리가 회의 Goal을 읽고 다시 쓰면 `kind`가 사라진다.

**근거.**
- [사실] `Goal` 구조체(`model.rs:51`)에는 `kind`가 없고, 알 수 없는 필드를 거부하는 설정도 없다. serde 기본 동작상 구 바이너리는 `kind`를 무시하고 읽은 뒤, 다시 저장할 때 그 필드 없이 쓴다.
- [사실] `recover_interrupted()`는 시작할 때마다 특정 상태의 목표를 다시 저장한다.
- [사실] `SCHEMA_VERSION`은 2(`storage.rs:13`)이고, 더 높은 버전의 DB는 열기 전에 거부한다(`storage.rs:403`).
- [사실] [v2 README](../../v2/README.md)에 따르면 설치 앱과 개발 실행기는 `-DataDir`이나 `UTOPIA_DATA_DIR`를 주지 않으면 같은 일반 데이터 위치를 쓴다.
- [추론] QA-37용 설치 앱(구 버전)과 회의 기능 개발 빌드가 같은 데이터를 열면 회의 Goal이 `execution`으로 바뀐다. 이후 C1의 경로로 개발 엔진이 실행될 수 있다.

**대안.**
- A. 회의 엔티티나 `kind`를 처음 쓰는 마이그레이션에서 `SCHEMA_VERSION`을 3으로 올린다. 구 바이너리는 기존 검사로 DB를 열지 못한다.
- B. 필드를 추가하지 않고 회의 여부를 Meeting 레코드 존재로만 판단한다. 이 경우 구 바이너리가 Meeting을 모르므로 같은 위험이 남는다.

**영향.** A를 택하면 회의 빌드로 연 데이터는 구 앱에서 쓸 수 없다. QA 데이터 분리 절차가 필요하다.

**권고.** A를 택한다. 수동 QA에 "회의 빌드는 분리된 `-DataDir`로 시작한다"를 명시한다. 마이그레이션 테스트에는 버전 2 → 3 승격과, 버전 3 DB를 구 버전이 거부하는 시나리오를 넣는다.

## C3. `awaiting_decision`을 처리하는 프런트 selector가 하나도 없음

**문제.** MAM-004 §5는 결정 대기 상태가 홈과 열린 작업에서 "결정 자료 검토 필요"로 보인다고 가정한다. 하지만 현행 selector는 모두 상태 문자열을 하드코딩하고 있어, 새 상태는 기본값으로 처리되거나 아예 빠진다.

**근거.**
- [사실] `openWork()`(`src/openWork.ts:11, 16`)는 `completed`가 아닌 목표를 모두 열린 작업에 넣는다. 하지만 `needsDecision`은 `blocked`·`awaiting_approval`·대기 승인일 때만 참이다. 결정 대기 회의는 목록에 나타나지만 결정 필요로 정렬되지 않는다(`:18`).
- [사실] 홈의 긴급 목록(`v2/src/V2Home.tsx:12`)도 같은 세 조건만 본다.
- [사실] `goalRecovery()`(`src/goalRecovery.ts:6`)는 `blocked`·`awaiting_approval`이 아니면 `null`을 반환한다.
- [사실] `goalStageLabel()`(`src/goalBrief.ts:7`)은 모르는 상태를 `상태 확인 필요`로 표시한다.
- [사실] `detectAttentionTransitions()`(`src/attentionNotifications.ts:30~36`)는 새 대기 Approval과 `blocked`·`failed` 진입만 알린다. [알림 정책](../notifications.md)도 이 두 전이만 허용한다.
- [사실] 단계 그래프(`src/progress.ts:47~53`)는 DM-04 단계 순서로 현재 위치를 계산한다.

**대안.**
- A. 상태 해석을 하나의 공통 selector(`goalAttention(goal, kind, meeting, approvals)` 등)로 모으고, 기존 함수들이 이를 호출하게 한다.
- B. 각 파일에 회의 분기를 추가한다.

**영향.** A는 [UX-03](../uxSimplification/UX-03-delivery.md) 1단계의 "정보 소유자 고정"과 같은 작업이다. 기존 실행 목표의 회귀 범위가 넓다. B는 빠르지만 화면마다 해석이 갈라진다.

**권고.** A를 택하되 회의 UI보다 먼저 별도 단계로 수행한다. "결정 자료 준비됨"을 알림 대상에 넣을지는 [알림 정책](../notifications.md)을 개정할지의 문제이며 MAM-004가 정하지 않았다. 넣지 않으면 사용자는 앱을 열어야만 결정 대기를 알 수 있다는 점을 계약에 적는다. 결정 대기 회의의 단계 그래프는 DM-04 단계가 아니라 회의 단계(제안 → 비판 → 수정 → 평가 → 결정)로 그린다.

## C4. 현행 승인은 사용자가 본 내용과 실제 전송 내용을 묶지 않음

**문제.** MAM-005 D1은 건별 승인 화면에서 실제 전송 묶음을 보여주라고 한다. 하지만 현행 승인은 상태 플래그일 뿐이다. 사용자가 본 묶음과 엔진이 보낼 묶음이 같다는 보장이 없다.

**근거.**
- [사실] `Approval`(`model.rs:186`)은 `{id, goal_id, operation, reason, status, created_at}`뿐이다.
- [사실] `decide_approval()`(`lib.rs:368~373`)은 `(id, approved)`만 받아 상태를 바꾼다. 화면에 보인 내용의 다이제스트를 받지 않는다.
- [사실] 엔진은 승인을 만든 스레드에서 300ms 간격으로 상태를 확인하며 최대 24시간 대기한다(`engine.rs:466~476`). 재시작하면 스레드는 사라지고 목표는 C1의 경로로 `blocked`가 된다.
- [추론] 승인 대기 중 입력 파일이 바뀌거나 앞 단계 발언이 재생성되면, 승인 후 실제로 보내는 묶음이 사용자가 본 것과 다를 수 있다(TOCTOU). 회의 하나에 승인이 여러 번 필요하므로 24시간 폴링 스레드도 여러 번 생긴다.

**대안.** `TransmissionApproval`을 `Approval`과 별도 종류로 둔다. 필드는 목적지 연결 지문, 정확한 payload의 sha256, 출처 ID 목록, 바이트 수, 상태, 모드(`per_bundle`·`scoped`)다. 승인 명령은 사용자가 본 payload 다이제스트를 함께 받는다. 엔진은 **전송 직전** payload를 다시 직렬화해 같은 다이제스트인지 확인한다. 대기는 스레드 폴링 대신 Meeting 상태(`awaiting_transfer_approval`)로 저장하고, 결정 명령이 다음 단계를 재개한다.

**영향.** 새 명령과 저장 종류가 필요하고, 재시작에 강해진다. 대기 중인 전송 승인이 있으면 C1의 재시도 판단(Approval 존재 여부)에도 반영해야 한다.

**권고.** 첫 실제 호출 전에 구현한다. 수용 기준: (1) 승인 후 입력 파일을 바꾸면 전송이 거부되고 새 미리보기가 생성된다. (2) 재시작 후 대기 중 전송 승인이 그대로 남고, 승인하면 해당 묶음부터 재개된다. (3) 화면에 표시한 바이트와 실제 전송 바이트의 다이제스트를 이벤트 기록에서 대조할 수 있다.

## C5. `미리 승인` 범위 중 엔진이 검사할 수 없는 항목과 빠진 만료 조건

**문제.** MAM-005 D1은 미리 승인 범위로 회의 ID, 입력 스냅샷·해시, 제공자·목적지, **생성물 종류와 길이 제한**, 라운드·호출 상한, 유효 기간을 나열하고 "각 호출 직전 검사"를 요구한다. 이 중 일부는 엔진이 기계적으로 검사할 수 없다. 또 만료·철회 조건 몇 가지가 빠져 있다.

**근거와 항목별 판정.**

| 범위 항목 | 엔진 검사 가능성 | 근거 |
| --- | --- | --- |
| 회의 ID·호출 수·라운드 | 가능 | 엔진이 호출 시작을 결정한다. |
| 입력 스냅샷 해시 | 가능 | 전송 직전 다시 해시한다. |
| 목적지 | **부분적** | [사실] 실행 시 쓰는 `AiConnection`의 `model_id`·`executable`·`endpoint`·`args`는 설정에서 바꿀 수 있다(`model.rs` `AiConnection`, `provider.rs:65~90`). 연결 ID만 저장하면 같은 ID 아래 모델·엔드포인트가 바뀌어도 범위 안으로 판정된다. |
| 길이 | 가능 | 바이트·문자 수로 검사한다. |
| 생성물 **종류** | **불가** | [추론] "비판 발언"이라는 라벨은 엔진이 붙인 구조이며, 텍스트 안에 무엇이 들었는지는 보장하지 않는다. 확인 가능한 것은 payload가 엔진 템플릿 + 저장된 Contribution ID들로만 조립됐다는 **구조적 사실**뿐이다. |
| 민감 정보 없음 | **휴리스틱** | [추론] 비밀값 패턴 검사는 탐지율이 불완전하며, 보장으로 표시할 수 없다. |

**빠진 조건.**
- [추론] **재시작:** 앱 재시작 후에도 미리 승인이 살아 있으면 사용자가 자리에 없는 동안 자동 전송이 재개될 수 있다. MAM-004 §4는 재개 시 재확인을 요구하지만, 미리 승인과의 관계는 정하지 않았다.
- [추론] **철회 경합:** 철회와 "호출 직전 검사"가 같은 잠금 안에 있지 않으면, 철회 직후 호출이 시작될 수 있다. 현재 `execute_tracked()`(`engine.rs:208`)는 사용량 레코드를 쓴 뒤 바로 호출하며, 승인 재검사 지점이 없다.
- [추론] **사후 감사:** 미리 승인 모드에서 실제로 보낸 내용을 사용자가 나중에 확인할 수단이 없다.

**대안.** 범위 객체에 연결 지문(kind·executable 정규 경로·endpoint·model_id·args 해시)을 저장한다. 범위 검사는 "구조적 조립 + 바이트 상한 + 목적지 지문 + 입력 해시 + 호출 수" 같은 **검사 가능 항목만** 강제한다고 표시하고, 비밀값 검사는 "경고"로 따로 표시한다. 미리 승인은 회의 종료, 앱 재시작, 연결 지문 변경, 사용자 철회, 유효 기간 중 가장 이른 시점에 끝난다. 재시작 후에는 건별 모드로 돌아간다. 철회 검사와 사용량 레코드 생성을 하나의 저장 트랜잭션에서 처리한다. 미리 승인 중 보낸 모든 payload는 다이제스트·목적지·시각과 함께 `전송 기록`으로 남기고 결정 자료에서 열람할 수 있게 한다.

**영향.** 미리 승인 화면에 "검사하는 것 / 검사할 수 없는 것"을 나눠 보여줘야 한다. 사용자의 기대("종류 제한")와 실제 보장의 차이가 화면에 드러난다.

**권고.** 위 대안을 Security·ADR 이관 문안에 포함한다. 수용 기준: 연결의 `model_id`를 바꾼 뒤 다음 호출이 건별 승인으로 돌아가는지, 철회 직후 새 호출이 0건인지, 재시작 후 미리 승인이 비활성인지 확인한다.

## C6. 미래 발언의 일괄 승인은 정보 흐름이 닫혀 있을 때만 Security와 양립

**문제.** [Security](../security.md)는 외부 전송에 CEO 승인을 요구하고, 엔진이 CEO의 허락보다 넓게 응답하지 못하게 한다. 외부 SDD 전송에는 "정확한 선택 내용과 목적지를 보여준 뒤 승인"을 요구한다. 미리 승인은 아직 존재하지 않는 내용을 승인하므로, "정확한 내용" 대신 **범위 승인**이라는 새 범주가 필요하다. 이 범주가 안전하려면 미래 발언이 승인된 입력 바깥의 로컬 정보를 담을 수 없어야 한다.

**근거.**
- [사실] Security의 외부 SDD 전송 조항과 일반 조항("External transmission … require CEO approval", "cannot silently answer them more broadly than the CEO's grant").
- [추론] 모델이 받은 입력이 모두 승인된 자료와 이미 승인된 발언뿐이면, 출력은 그 자료와 모델 자체의 지식에서만 나온다. 이 경우 미래 발언을 다른 제공자에게 넘겨도, **새로 노출되는 로컬 정보**는 이미 승인한 자료의 범위를 벗어나지 않는다(정보 흐름의 닫힘).
- [추론] 반대로 참여자가 도구로 프로젝트 파일을 읽을 수 있으면(C7), 발언에 승인 목록 밖의 로컬 내용이 섞일 수 있다. 이 경우 미리 승인은 사실상 "그 에이전트가 읽은 모든 것"의 전송 승인이 된다.

**대안.**
- A. 미리 승인을 **닫힌 흐름이 검증된 참여자로만 구성된 회의**에서만 제공한다. 닫힌 흐름이란 도구 없는 텍스트 호출, 빈 작업 폴더, 입력 = 프롬프트를 뜻한다.
- B. 모든 회의에 제공하되, 화면에 "에이전트가 읽은 파일 내용도 포함될 수 있음"을 고지한다.

**영향.** A는 첫 회의에서 쓸 수 있는 연결의 종류를 좁힌다. B는 범위 승인의 의미를 사용자가 판단하기 어렵게 만든다.

**권고.** A를 택한다. Security 개정 문안: "정확한 내용 승인"과 "범위 승인"을 구분한다. 범위 승인은 (1) 같은 회의, (2) 닫힌 흐름이 검증된 연결, (3) C5의 검사 가능 항목, (4) 전송 기록 보존을 모두 충족할 때만 성립하며, 프로젝트 쓰기·배포·새 실행 파일 등록으로 확장되지 않는다. 이 문안과 ADR이 채택되기 전에는 MAM-005가 정한 대로 미리 승인을 실행 기능으로 내놓지 않는다. 건별 모드만으로 첫 실제 회의는 가능하다.

## C7. 첫 사례에서 CLI의 읽기·도구·쓰기 범위를 강제할 방법이 없음

**문제.** MAM-004 §3은 "스냅샷 + cwd 제한을 읽기 격리라고 부르지 않는다"는 점을 정확히 지적한다. 하지만 어떤 연결이 첫 실제 호출에 쓰일 수 있는지 판정하는 구체적 방법은 비어 있다. 첫 사례는 U컴퍼니 자신의 폴더이고, 이 폴더에는 회의 입력이 되어서는 안 되는 자료가 들어 있다.

**근거.**
- [사실] 모든 CLI 호출은 `cmd.current_dir(cwd)`(`provider.rs:90`)로 실행된다. 현행 읽기 전용 호출은 프로젝트 루트를 cwd로 준다(`engine.rs` `run()`의 CTO·PM 호출, `answer_goal_question()`).
- [사실] Codex는 `--sandbox read-only`(`provider.rs:69`), Claude는 `--permission-mode plan`(`:74`)을 받는다. Gemini(`:76`)·OpenCode(`:79`)·사용자 정의 CLI는 `writable`을 인자에 반영하지 않는다.
- [사실] 이 프로젝트 루트에는 `.run-data/organization.sqlite`가 있다. 앱 DB로, 과거 목표·대화·사용량 기록이 담겨 있다. 회의가 U컴퍼니 폴더를 대상으로 하면, 프로젝트 안을 읽을 수 있는 에이전트는 이 파일도 읽을 수 있다. 회의 빌드를 `-DataDir .run-data\...`로 띄우면 회의 자신의 기록도 같은 폴더에 쌓인다.
- [사실] 프롬프트는 프로세스 인자로 전달된다(`provider.rs:69~80`, [AI-03](../aiIntegration/AI-03-adapter.md)). [미검증] Windows의 명령줄 길이 한계(약 32K자)를 고려하면, 자료를 프롬프트에 넣는 방식은 자료 크기가 제한된다.
- [미검증] Claude·Codex CLI는 사용자의 전역 설정(MCP 서버, 웹 도구)을 비대화형 호출에서도 불러올 수 있다. 그렇다면 자료가 제공자 외의 서버로 갈 수 있다. 이 저장소에는 이를 확인한 기록이 없다.
- [미검증] Windows에서 Codex `read-only` 샌드박스의 실효성은 이 저장소의 하네스 기록에 없다.

**대안.**
- A. 첫 실제 회의는 **텍스트 전용 호출**로 한정한다. cwd는 앱 데이터 아래의 빈 임시 폴더로 두고, 승인된 자료는 프롬프트에만 넣고, CLI의 도구·MCP를 끄는 인자를 적용한다(인자 이름은 CLI별로 하네스에서 확인). 그러면 C6의 닫힌 흐름이 성립한다.
- B. 도구형 연결을 허용하되 provider-harness로 "cwd 밖 표식 파일 읽기 거부, 쓰기 거부, 네트워크 도구 거부"를 연결별로 실험하고, 통과한 연결만 허용한다.

**영향.** A는 자료 크기가 인자 한계에 묶이므로, 첫 회의 자료를 수십 KB 이하로 제한하거나 stdin 전달을 별도로 구현해야 한다. B는 연결마다 실험이 필요하고, CLI가 업데이트되면 다시 검증해야 한다.

**권고.** 첫 실제 회의는 A로 한다. 연결 능력 검사에 `closed_text_mode_verified`를 추가하고, 하네스 시험에 (1) cwd와 그 상위 폴더에 표식 파일을 두고 모델에 읽으라고 지시했을 때 표식이 출력에 없을 것, (2) 쓰기 시도 0건, (3) MCP·웹 도구 호출 0건을 넣는다. 통과 전에는 해당 연결로 회의를 시작할 수 없다. Gemini·OpenCode·사용자 정의 CLI의 `writable` 미반영은 회의와 별도로 기존 대화 경로의 결함으로 기록한다(MAM-002#C6과 같은 사실, 아직 미해결).

## C8. 건별 승인 기본값이 1라운드에서도 최대 10번의 정지를 만듦

**문제.** MAM-004의 3관점 + 평가자 1라운드는 호출 10회이고, 모든 호출이 제공자에게 자료를 보낸다. MAM-005 D1의 기본값(건별)을 호출 단위로 구현하면 사용자는 최대 10번 승인해야 한다. 승인할 때마다 알림이 울리고, 사용자가 자리를 비우면 회의가 멈춘다.

**근거.**
- [사실] [알림 정책](../notifications.md)은 새 대기 승인마다 한 번 알린다. `detectAttentionTransitions()`는 `goalId`가 있는 새 대기 Approval마다 신호를 만든다(`src/attentionNotifications.ts:33`).
- [추론] 제안 3회는 같은 입력을 세 제공자에게 보낸다. 비판 3회와 수정 3회는 각각 다른 제공자의 발언을 전달하고, 평가 1회는 전체 기록을 보낸다. 같은 단계의 묶음들은 그 단계가 시작될 때 내용이 모두 확정돼 있다.

**대안.** "건별"의 단위를 **호출**이 아니라 **동시에 확정되는 전송 묶음 집합(단계)**으로 구현한다. 한 승인 카드에 그 단계의 묶음(예: 비판 3개)을 각각 원문·목적지·다이제스트와 함께 보여주고, 묶음마다 개별로 거절할 수 있게 한다. 모든 내용이 전송 전에 정확히 표시되므로 "건별 미리보기·승인"의 의미는 유지된다. 1라운드의 정지는 제안·비판·수정·평가 4회로 줄어든다. `미리 승인` 버튼은 첫 교차 제공자 단계(비판)의 카드에 둔다. 카드에는 남은 예상 승인 횟수를 표시한다.

**영향.** 묶음 하나를 거절했을 때의 의미를 정해야 한다. 예: 해당 비판은 `거절됨`으로 기록하고, 대상 제안은 "비판 없음"으로 수정 단계에 들어간다. 알림은 단계 카드 하나당 한 번으로 줄어든다.

**권고.** 이 묶음 승인 방식을 MAM-007에서 D1의 구현 해석으로 확인해 달라. D1을 바꾸는 것이 아니라 그 구현 단위를 정하는 문제다. 사용성 측정([UX-03](../uxSimplification/UX-03-delivery.md))에 "승인 카드 4회를 끝까지 처리한 비율과 시간"을 넣는다.

## C9. v3 인계에서 AI가 쓴 결정 자료가 CEO 의도로 바뀌고, 자기 구현은 현재 폴더에서 스냅샷이 실패함

**문제.** MAM-004 §2는 회의 결과를 lineage가 있는 **별도 execution Goal**로 인계한다고만 한다. 새 Goal의 `intent`를 누가 쓰는지는 정하지 않았다. D2의 마지막 단계는 U컴퍼니가 자기 폴더를 구현하는 것인데, 현재 폴더 구성으로는 실행 엔진이 시작부터 실패한다.

**근거.**
- [사실] `Goal.intent`는 CEO 의도로 취급되어 CTO 분석 프롬프트의 `CEO goal:`에 그대로 들어간다(`engine.rs` `run()`). project_write 승인 사유도 이 목표에 묶인다.
- [추론] 결정 자료의 권고문을 자동으로 `intent`에 넣으면, 모델이 쓴 문장이 "CEO 목표"로 격상된다. 그 결과 승인 화면은 CEO가 쓴 적 없는 범위를 CEO 요청으로 보이게 한다.
- [사실] 프로젝트 루트에 `.git`이 없으므로 일반 폴더 모드로 실행된다. 일반 폴더 복사는 20,000개 파일 또는 512 MiB를 넘으면 실패한다(`platform.rs:9~10, 29`). 이번에 읽기 명령으로 확인한 `src-tauri/target`은 9.4 GB다.
- [추론] 개발 실행기(Vite dev 서버)가 이 폴더를 서비스하는 상태에서 통합이 `src/`·`v2/src/`를 바꾸면, 실행 중인 앱 화면이 HMR로 다시 로드될 수 있다. Rust 변경은 실행 중인 바이너리에 반영되지 않는다.

**대안.** 인계는 **초안만 만든다**. 결정 자료에서 선택한 항목으로 목표 입력란을 미리 채우되, CEO가 편집하고 직접 제출해야 Goal이 생긴다. 새 Goal에는 결정 자료의 ID와 버전 해시를 lineage로 저장한다. CTO·PM 프롬프트에는 결정 자료를 "참고용 신뢰할 수 없는 자료"로 넣는다. 파일 범위는 PM 계획과 별도 project_write 승인으로만 정해진다. 자기 구현 대상 폴더는 Git 저장소로 만들거나(빌드 산출물은 `.gitignore`로 제외), 스냅샷 제외 규칙을 별도 승인 계약으로 정한다. 자기 구현은 설치 앱이나 별도 체크아웃에서 실행해, 실행 중인 개발 서버의 원본을 바꾸지 않게 한다.

**영향.** 인계 단계가 한 번 더 늘지만, 승인 화면에 표시되는 "누가 요청했는가"가 정확해진다. D2 1~3단계(v2 회의 빌드와 v3 정리)는 막히지 않는다. 4단계(자기 구현)는 이 문제를 해결할 때까지 막힌다.

**권고.** 인계 계약에 "결정 자료 → 목표 초안 → CEO 제출 → 계획 → 별도 쓰기 승인"을 명시한다. `채택` 결정이 자동으로 Goal·Task·Approval을 만들지 않는다는 반례 테스트를 넣는다. D2 4단계 전에 U컴퍼니 폴더의 실행 방식(Git 루트화 또는 별도 체크아웃)을 사용자와 결정한다.

## C10. 5메뉴·단일 작업공간과 어긋나는 세부 배치

**문제.** MAM-004 §5는 대체로 [UX-01](../uxSimplification/UX-01-navigation.md)~[UX-03](../uxSimplification/UX-03-delivery.md)과 맞다. 다만 몇 가지 배치가 정보 소유권이나 단일 주 행동 원칙과 어긋난다.

**근거.**
- [사실] UX-01의 첫 목표 작성 화면은 "목표 입력과 `팀에 전달`" 하나를 주 행동으로 둔다. MAM-004는 목표 입력 뒤에 `개발 실행 / 개선안 회의` 선택을 추가한다.
- [사실] [GC-03](../goalConversation/GC-03-workspace.md)의 작업공간은 대화 작성기가 하단에 항상 있고, 메시지를 AI가 해석해 방향 변경·시작으로 연결한다. MAM-004는 회의 Goal에서 이 라우팅을 막는다고만 하고, 입력창을 어떻게 보일지는 정하지 않았다.
- [사실] [UX-02](../uxSimplification/UX-02-surfaces.md)의 표시 소유 표에서 "목표 단계·다음 행동·승인/복구"의 원본은 공통 목표 작업공간이다. MAM-004는 계획 상세·전송 미리보기·결정 자료도 같은 작업공간에 둔다. 이는 맞다. 하지만 C8의 단계별 승인 카드와 결정 자료가 한 번에 "지금 필요한 결정 한 카드" 규칙과 경쟁할 수 있다.
- [사실] 개별 목표 카드마다 0~5 QA 재작업 한도 컨트롤이 붙는다([Product](../product.md)). 회의 Goal에는 의미가 없다.
- [사실] 토큰 화면과 Office는 `agentId`로 사람을 해석한다. MAM-004는 `meeting:<id>:<slot>` 매핑을 별도 구현 대상으로 인정했다.

**대안.** 홈의 목표 입력은 기존처럼 `팀에 전달` 하나를 주 행동으로 두고, 회의는 보조 링크(`여러 관점으로 먼저 검토`)로 둔다. 회의 Goal의 작업공간 입력창은 "회의 중에는 질문만 가능"이라고 표시하거나 숨긴다. 첫 구현에서 질문이 필수가 아니라면 숨긴다. 결정 카드의 우선순위는 `전송 승인 > 중단 복구 > 결정 자료` 한 줄 규칙으로 정한다. 회의 Goal에서는 QA 한도·작업 그룹 컨트롤을 표시하지 않는다.

**영향.** 기존 홈의 시각 구조는 유지되고 회의 진입은 한 단계 깊어진다.

**권고.** MAM-007에서 홈의 주 행동 구성과 작업공간 입력창 처리를 확정하고, 이를 UX-02 표시 소유 표에 회의 행으로 추가하는 이관 문안을 낸다.

## 첫 구현의 차단 요인 정리

| 단계(MAM-004 §7) | 해결해야 할 쟁점 |
| --- | --- |
| 3. 오프라인 회의 코어 | C1(상태·kind 가드와 전수 행렬 테스트), C2(스키마 버전 3) |
| 4. 첫 실제 수직 흐름 (건별 모드) | C4(내용 다이제스트 결합 승인), C7(닫힌 텍스트 모드 검증) |
| 4. 홈·열린 작업 표시 | C3(공통 selector) |
| `미리 승인` 기능 | C5(검사 가능 범위·만료·철회·전송 기록), C6(Security 범위 승인 문안 + ADR) |
| D2 4단계 자기 구현 | C9(인계 초안 계약, 폴더 실행 방식) |

C8과 C10은 첫 구현을 막지 않는다. 사용성 측정과 이관 문안에서 다룬다.

## MAM-007에서 답해야 할 질문

1. **C1:** 진행 중 회의의 `Goal.status` 값은 무엇인가? 백엔드의 어느 명령에서 kind를 검사해 거부하는가?
2. **C2:** 회의 엔티티를 쓰는 첫 마이그레이션에서 `SCHEMA_VERSION`을 올리는가? 올리지 않는다면 구 바이너리가 `kind`를 지우는 경로를 어떻게 막는가?
3. **C4:** 전송 승인은 기존 `Approval`을 확장하는가, 별도 종류인가? 사용자가 본 payload 다이제스트를 어떻게 전송 직전 검사에 연결하는가?
4. **C5·C6:** 미리 승인 범위 중 "생성물 종류"를 어떻게 표현할 것인가(구조적 조립 검사로 대체할지)? 재시작·연결 지문 변경 시 만료에 동의하는가? 닫힌 흐름이 아닌 연결에서 미리 승인을 막는 데 동의하는가?
5. **C7:** 첫 실제 회의를 텍스트 전용(빈 cwd, 도구·MCP 끔)으로 한정하는가? 자료 크기 한계는 인자로 할지 stdin으로 할지?
6. **C8:** 단계 단위 묶음 승인을 D1 "건별"의 구현 단위로 받아들이는가? 묶음 하나를 거절했을 때 회의는 어떻게 진행되는가?
7. **C9:** 결정 자료 → 목표 초안 → CEO 제출의 인계 방식에 동의하는가? 자기 구현 폴더의 실행 방식은 무엇으로 제안하는가?
8. **C10:** 홈의 회의 진입 위치와, 회의 Goal 작업공간의 입력창 처리는 어떻게 할 것인가?

# 회의 차단 개선 — 결정 반영 구현 계획 (인계용)

이 문서는 [MAM-013](MAM-013-proposal.md)의 계획에 [MAM-014](MAM-014-decision.md) 결정(D1·D2·D3 모두 채택)을 반영한, **다른 에이전트가 이어서 구현할 수 있는 작업 단위 계획**이다. 엣지케이스 E1~E13의 근거와 설명은 MAM-013을 그대로 참조한다. 이 문서는 현행 Spec이 아니다. W0에서 소유 문서로 이관한 뒤 그 문서가 규칙의 원본이 된다.

## 1. 출발 상태 (2026-10-09 기준)

구현되어 있고 단위 시험으로 확인된 것:

- Office 캐릭터 회의 첫 구현(MAM-012 범위): `src-tauri/src/meeting.rs`, 계획 승인(`plan`/`per_stage`), 읽기 전용 Claude/Codex CLI(`read_only_profile`, `ProviderTransport`), 공유 사용 중 규칙, 추적 그래프, 홈 드롭다운. 백엔드 프로토콜 **22**.
- 계획 정규화 `bounded_trim`(자르기 전후 trim)과 승인 시 저장 계획의 자기 지문·자료 해시를 따로 확인.
- 패킷 한도 `PACKET_CHAR_CAP = 30_000`을 `command_arg_len`(Windows 명령줄 인자 인용 길이)으로 측정. 자료 한도 파일당 16,000자·합계 26,000자. 계획 검증이 **제안 단계** 패킷만 실제로 만들어 길이를 확인함(`proposing_payload`).
- `discovery.rs`: 버전 확인 15초·로그인 확인 20초, 로그인 콘솔을 `cmd /c start`와 `-EncodedCommand`로 분리.
- `cargo test --locked --lib` 70 통과(1 무시), `cargo check --locked --all-targets` 경고 없음, v2 `tsc`, `vitest` 31 통과.

확인되지 않은 것: Windows 앱에서 실제 Claude/Codex로 회의 한 라운드 완주, 긴 패킷의 실제 CLI 수용, 위 `discovery.rs` 변경의 Windows 컴파일과 동작.

## 2. 작업 원칙

- 내용을 앱이 자르거나 고쳐 쓰지 않는다. 결과 불명(`outcome_unknown`) 호출은 자동으로 다시 보내지 않는다. 계획에 없는 팀원·자료·호출은 막는다. 이 세 가지는 어떤 단계에서도 바꾸지 않는다.
- 실제 공급자 호출에는 **합성 프롬프트만** 쓴다. 저장된 CEO 목표, 팀원 지침, 프로젝트 문서를 외부 공급자에 다시 보내는 시험은 하지 않는다([조사 기록](../provider-runtime-investigation.md)).
- 각 작업 단위마다 단위 시험을 먼저 추가하고, 끝나면 WORKLOG에 범위·통과한 검사·검증하지 못한 것을 남긴다. 오프라인 시험과 Windows 실제 실행을 구분해 적는다.
- 기존 파일의 줄바꿈을 유지한다(예: `engine.rs`, `lib.rs`, `storage.rs`, `v2/src/App.tsx`, 일부 SDD는 CRLF).
- 회의 동작이나 명령을 바꾸는 단위마다 백엔드 프로토콜 번호를 올리고, 프런트의 최소 프로토콜 확인도 함께 올린다.

## 3. 작업 단위

순서대로 진행한다. W1이 끝나기 전에 다른 단위를 사용자에게 배포하지 않는다(이전 백엔드 감지가 전제).

### W0 — 소유 문서 이관

- ME-01: 계획 검증이 모든 단계 패킷의 최악 길이를 확인한다(W3), 형식 수정 요청과 예비 호출(W4), 단계 회복(W5), 자료 스냅샷 계속 규칙(W6).
- ME-02: 표준 입력 전달(W2), 패킷 길이 측정 방식, 형식 수정 패킷, 재요청 명령과 결과 불명 확인, 연결 지문 v2(W6).
- AI-03: CLI 프롬프트 전달 방식(인자/표준 입력)과 공급자별 확인 상태.
- Validation, UF-09, QA-38: 아래 각 단위의 수용 기준.
- 새 ADR-0037: MAM-014 D1~D3을 기록하고 ADR-0036의 해당 부분을 부분 대체한다. ADR 색인 갱신.

### W1 — 이전 백엔드와 이전 기록 구분 (MAM-013 P0, E10)

- `lib.rs` `get_backend_info`의 프로토콜을 23으로 올리고, `v2/src/App.tsx`의 `backendOutdated` 기준도 23으로 올린다. 회의 버튼은 `backendOutdated`일 때 이미 막히는지 확인하고, 아니면 막는다.
- `Meeting`에 `blocked_at: String`, `block_build: String`(빌드 식별자, 예: `CARGO_PKG_VERSION` + 빌드 시각 또는 git 해시를 `build.rs`나 `option_env!`로)을 추가하고 `block_tx`·`stop`·`revoke_plan`·`expire_on_restart`에서 함께 기록한다.
- 회의 화면은 차단 이유 옆에 기록 시각을 보이고, `block_build`가 현재 빌드와 다르면 "이전 버전에서 기록된 이유입니다. 재개하면 현재 규칙으로 다시 확인합니다"를 덧붙인다.
- 시험: 프로토콜 22 응답에서 회의 시작·승인이 막히는 Vitest. `block_tx`가 시각·빌드를 남기는 Rust 시험.

### W2 — 표준 입력 전달 (D1, MAM-013 P1, E3)

- `runtime::capture_with_timeout`에 선택적 표준 입력 바이트를 받는 인자를 추가한다. 있으면 쓰고 즉시 닫고, 없으면 지금처럼 빈 파이프를 바로 닫는다. 쓰기는 별도 스레드로 해 큰 입력과 출력 읽기가 서로 막지 않게 한다.
- `provider::run_cli`에서 공급자별로 전달 방식을 고른다. 후보 방식(**Windows에서 확인 전까지 가정**):
  - Claude: `claude -p --output-format stream-json --verbose --permission-mode <plan|acceptEdits> [--model …]`, 프롬프트는 표준 입력.
  - Codex: `codex exec --json --skip-git-repo-check --sandbox <read-only|workspace-write> --cd <cwd> [--model …] -`, 프롬프트는 표준 입력.
- 공급자별 사용 여부는 코드의 명시적 표(예: `stdin_prompt(stem) -> bool`)로 둔다. 기본값은 **인자 방식**이고, 하네스와 Windows 확인을 마친 공급자만 표준 입력으로 켠다. 켜진 공급자는 회의 패킷 길이 검사에서 명령줄 인용 길이 대신 글자 수 예산을 쓴다(한도 값은 그대로 30,000을 비용 예산으로 유지).
- 공급자 하네스(`src-tauri/src/provider_harness.rs`, `npm run provider:test`)에 표준 입력 확인 모드를 추가한다: 5만 자 합성 프롬프트(의미 없는 반복 문장 + "마지막 줄의 단어를 그대로 답하라")를 표준 입력으로 보내 정확히 답하는지 확인.
- 실행 목표도 같은 `run_cli`를 쓰므로 함께 바뀐다. 인자 방식이 남는 공급자(Gemini, OpenCode, 사용자 정의 CLI)는 실행 목표 프롬프트에도 `command_arg_len` 검사를 넣어, 넘으면 실행 전에 이유와 함께 막는다.
- 시험: 가짜 CLI 스크립트가 표준 입력으로 받은 내용을 그대로 출력하는 단위 시험(Linux/Windows 공용), 표준 입력 대형 입력(10만 자)에서 교착이 없는 시험, 공급자 표의 인자 구성 시험. Windows 수동: 하네스로 Claude·Codex 각각 확인 후 결과를 WORKLOG에 기록하고 그때 표를 켠다.

### W3 — 모든 단계 길이를 승인 전에 계산 (MAM-013 P2, E1·E2·E11)

- 정규화 응답 상한을 단계 예산이 맞도록 정한다. 시작값(시험으로 조정 가능):
  - 제안: 주장 ≤6, 주장 본문 ≤600자, 주장당 근거 ≤3·인용 ≤300자, 가정·미확인 각 ≤3개·≤200자, 대안 ≤4개·≤200자.
  - 비판: ≤4개, 본문 ≤500자, 수정 제안 ≤300자, 근거 ≤2.
  - 수정: 처리 본문 ≤400자, 수정 주장은 제안 상한과 같음.
- 평가자 패킷을 압축 형식으로 바꾼다: 들여쓰기 없는 JSON, 인용은 `sourceId`·확인 상태·앞 80자만, 참여자별로 주장(수정본이 있으면 수정본)·받은 비판·처리만. 패킷 템플릿 버전(`PACKET_TEMPLATE_VERSION`)을 올린다.
- `stage_budget(plan, sources, slots)`를 만들어 비판·수정·평가 패킷의 **최악 길이**(모든 응답이 상한까지 찼다고 가정)를 계산하고, 넘으면 계획 오류로 보인다. 제안 단계는 지금처럼 실제 패킷을 만들어 잰다.
- 계획 카드: 자료별 글자 수와 합계/한도 막대, 자료별 "빼기" 버튼. 의장 계획 요청에는 의장이 고를 만한 후보가 아니라 "고른 파일 크기 합계 한도"만 알리고, 계획 검증 오류에 파일별 크기를 보인다(지금 동작 유지).
- 시험: 참여자 2명·3명 각각, 모든 응답이 상한까지 찬 합성 회의에서 **모든 단계 패킷 ≤ 한도**인 속성 시험. 이 시험이 실패하면 상한 값을 조정한다.

### W4 — 형식 수정 요청 (D2, MAM-013 P3, E4)

- `extract_json`을 관대하게 바꾼다: 응답 안의 첫 번째 완전한 JSON 객체(괄호 균형, 문자열 안 괄호 무시)를 찾는다. 앞뒤 문장은 원문 기록에만 남는다.
- ID 정규화: `C01`→`C1`, `c1`→`C1`처럼 같은 뜻의 표기만 바꾸고, 바꾼 내역을 기여 기록(`MeetingContribution`)에 남긴다.
- 그 밖의 규칙 위반(길이·개수 초과, 필수 비판 누락, 근거 없는 반박, 알 수 없는 ID)은 차단 대신 **형식 수정 패킷** 1건을 만든다: 같은 단계·같은 팀원, 원래 패킷 ID와 위반 목록, "원래 답의 내용을 유지하고 형식만 고쳐 다시 답하라"만 담는다. 원래 응답 원문을 다시 싣지 않고, 위반 항목과 해당 ID만 인용한다.
- 예비 호출: 계획 기본값 `maxCalls = min(필요 호출 + 2, 12)`. 형식 수정 패킷은 `calls_used`를 쓰며 남은 호출이 없으면 차단한다. 한 팀원·한 단계에서 수정 요청은 1회까지이고, 두 번째 위반은 차단한다. `plan` 승인이면 자동 진행, `per_stage`면 CEO가 다른 패킷과 같이 확인한다.
- 계획 카드에 "형식 수정 예비 호출 N회"를 보인다.
- 시험: 설명 문장이 섞인 JSON, `C01` ID, 601자 주장, 비판 하나 누락, 두 번 연속 위반, 예비 호출 0회 각각의 결과.

### W5 — 단계에서 바로 회복 (MAM-013 P4, E5·E8·E9)

- 새 명령 `retry_meeting_packet(meetingId, packetId, confirmDuplicate)`:
  - 대상이 `failed` 또는 형식 수정까지 실패한 `sent_invalid`이면, 계획 지문이 승인과 같고 남은 호출이 있을 때 같은 단계·팀원의 새 revision 패킷을 만들고 진행한다. 계획 재승인은 필요 없다.
  - 대상이 `outcome_unknown`이면 `confirmDuplicate=true`일 때만 허용하고, 화면은 "같은 내용이 두 번 갈 수 있습니다"를 확인받는다.
  - `blocked` 상태에서만 허용하며, 예약(`reserve`)과 같은 트랜잭션 규칙을 따른다.
- 재시작 뒤 재개 안내를 "계획을 다시 승인하면 끝난 단계는 건너뛰고 남은 단계부터 이어갑니다"로 맞춘다(기록된 발언은 이미 다시 보내지 않음).
- 시험: 시간 초과로 실패한 비판 패킷을 재요청해 평가까지 완주, 결과 불명 패킷을 확인 없이 재요청하면 거절, 호출 상한 소진 시 거절.

### W6 — 회의 결과와 무관한 변경으로 막지 않음 (D3, MAM-013 P5, E6·E7·E12·E13)

- 자료(D3): `validate_meeting_inputs`의 자료 해시 검사를 **제안 단계 전송 직전**에만 한다. 바뀌었으면 회의를 `blocked`로 두고 두 버튼을 보인다: "승인 시점 내용으로 계속"(새 명령, 스냅샷 그대로 제안 진행) / "계획 다시 검토"(기존 재개). 제안 단계 이후에는 검사하지 않고, 회의 화면에 "원본 파일이 승인 뒤 바뀌었습니다. 회의는 승인 시점 내용을 사용합니다"만 보인다.
- 연결 지문 v2: `kind`, `executable`, `endpoint`, `args`, `model_id`만으로 계산한다(`capabilities` 제외). 기존 회의 슬롯은 지문 버전이 없으므로, 검사 때 v2와 이전 계산 중 하나와 맞으면 통과시킨다.
- 인용 확인: CRLF→LF, 연속 공백 하나로 정규화한 문자열에서 찾고, 기록하는 위치는 원문 기준으로 되돌려 계산한다.
- 사용 중 팀원: 승인이 사용 중 때문에 거절되면 같은 역할 또는 참여 가능한 다른 팀원 목록을 오류와 함께 보인다(자동 교체 없음).
- 시험: 승인 뒤 자료 수정에도 비판·수정·평가 진행, 제안 전 수정 시 "계속" 경로, capabilities만 바뀐 연결로 진행, CRLF 자료의 여러 줄 인용 확인됨.

## 4. 완료 조건

- 모든 단위 시험과 `cargo check --locked --all-targets`, 두 프런트 `tsc`, `vitest`, 두 빌드 통과.
- "계획 승인 뒤 길이 오류" 속성 시험(W3) 통과.
- Windows QA-38에 새 항목: 하네스 표준 입력 확인(W2), 실제 Claude/Codex 회의 한 라운드 완주, 형식 수정 요청 1회 관찰 또는 미관찰 기록, 재요청 회복.
- WORKLOG에 단위별 결과와, 실제 공급자 확인 여부를 따로 기록.

## 5. 범위 밖

여러 라운드, 다른 토론 방식, 검토 패널, 해시 체인, MD 내보내기, Office 회의 애니메이션(MAM-012 후속 범위).

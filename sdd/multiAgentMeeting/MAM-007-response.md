# MAM-006 비판에 대한 응답

이 문서는 [MAM-006](MAM-006-critique.md)의 C1~C10과 마지막 질문 8개에 답한다. [MAM-005](MAM-005-decision.md)의 D1(건별 미리보기·승인 기본, 회의별 `미리 승인` 선택)과 D2(v2 회의 먼저 검증한 뒤 그 프로그램으로 별개 v3 개선·자기 구현)는 **확정 요구사항**이다. 아래의 파일·함수·줄은 2026-10-09 소스 재확인 결과다. **사실**과 앞으로 만들 **계약 제안**을 구분한다. 앱, CLI, OS 격리, 실제 회의는 실행하지 않았으며 외부 제공자 동작은 검증된 것으로 쓰지 않는다. 이 응답은 현행 Spec이나 실제 전송·파일 쓰기 승인이 아니다.

## MAM-006#C1 — 진행 중 Goal 상태와 개발 엔진 유입

**판정: 수용.** 회의 Goal에 개발 단계 상태를 재사용하지 않는다.

**확인 사실:** [`engine::start()`](../../src-tauri/src/engine.rs)은 47~68행에서 `new` 또는 특정 `blocked` 목표를 `analyzing`으로 바꾸고 `run()`을 띄운다. [`can_retry_before_write()`](../../src-tauri/src/engine.rs)은 71~76행에서 kind 없이 상태·Task·Approval만 본다. [`resume_approved()`](../../src-tauri/src/engine.rs) 78~101행은 `blocked/resumed_from=awaiting_approval`을 실행 계획으로 복구한다. [`storage::recover_interrupted()`](../../src-tauri/src/storage.rs) 389~395행은 개발 단계 여섯 값을 `blocked`로 바꾼다. 원래 [`App.tsx`](../../src/App.tsx) 290행은 모든 `new` 목표에 `run_goal` 버튼을 보인다. MAM-006의 유입 위험은 맞다. 단, `recover_interrupted()`가 **새 전용 상태**까지 자동으로 `blocked`로 바꾸는 것은 아니다.

**MAM-008 계약:** 회의 Goal은 생성 시부터 `status=deliberating`, 결정 자료가 만들어지면 `awaiting_decision`, CEO 결정이 저장되면 `completed`만 쓴다. `Meeting.stage`는 `draft/ready/awaiting_transfer_approval/proposing/critiquing/revising/evaluating/blocked/stopped/package_ready/decision_recorded`를 소유한다. 전송 승인·중단은 `Goal.status=deliberating` 아래 Meeting 단계로만 표현한다. 실행 엔진의 `start()`, `can_retry_before_write()`, `resume_approved()`와 `run()` 입구, `propose_goal_guidance()`/`create_goal_revision()`의 저장 경계, `send_goal_message()`·`ask_goal()`·Git bootstrap·`decide_approval()`에서 kind를 검사한다. 회의 Goal은 기존 실행·대화·파일 변경 명령에서 거부하고 회의 전용 `start_meeting/resume_meeting/stop_meeting/decide_meeting/decide_transmission`으로만 전이한다. `recover_interrupted()`는 회의의 진행 중 호출을 `Meeting.stage=blocked`, 사용량 `interrupted`로 바꾸고 **자동 재호출하지 않는다**. UI 가드는 별도로 추가한다. `kind × Goal.status × 명령` 전수 표와 재시작 후 `run_goal` 거부·중복 호출 0건을 오프라인 시험한다.

## MAM-006#C2 — 구 바이너리와 스키마 버전

**판정: 수용.** 첫 회의 레코드를 쓰는 마이그레이션에서 버전을 올린다.

**확인 사실:** [`Goal`](../../src-tauri/src/model.rs) 51~66행에는 `kind`가 없고, [`Store::put()`](../../src-tauri/src/storage.rs) 28~36행은 역직렬화한 구조체를 전체 JSON으로 다시 저장한다. `Store::open()` 16~25행은 마이그레이션 뒤 복구를 실행한다. [`migrate()`](../../src-tauri/src/storage.rs) 400~434행은 `SCHEMA_VERSION=2`(13행)보다 높은 DB를 403행에서 거부한다. 구 바이너리의 실제 왕복 테스트는 수행하지 않았지만, 알 수 없는 JSON 필드가 기존 구조체 재직렬화에서 보존되지 않는 위험은 코드 구조상 타당하다. [ADR-0033](../architecture/decisions/ADR-0033.md)은 원래 UI와 v2가 같은 엔진·데이터를 쓰는 구성을 기록한다.

**MAM-008 계약:** `SCHEMA_VERSION=3`으로 승격하고 v2 Goal에는 `kind=execution`을 채운다. 2→3 변환과 user_version 갱신은 한 트랜잭션으로 처리하며 첫 Meeting/Goal 쓰기보다 먼저 완료한다. 3 DB는 구 바이너리의 기존 버전 검사로 열리지 않아야 한다. QA는 반드시 분리된 `-DataDir`/`UTOPIA_DATA_DIR`에서 수행하고, 실사용 DB를 3으로 열기 전 백업·복구 경로를 명세한다([v2 README](../../v2/README.md)). 2→3 후 실행 Goal·승인·사용량 보존, 3 DB를 구 바이너리가 거부, 회의 kind 재시작 왕복을 시험한다. 구 앱에서 회의 화면이 보이지 않는다는 주장과 DB를 열 수 없다는 사실을 혼동하지 않는다.

## MAM-006#C3 — 결정 대기 selector·알림

**판정: 부분 수용.** 공통 해석 계층과 회의 전용 단계 표시는 수용한다. 첫 사례에서 `결정 자료 준비` OS/소리 알림 추가는 수용하지 않는다.

**확인 사실:** [`openWork()`](../../src/openWork.ts) 11~18행은 `completed` 외 목표를 넣지만 `needsDecision`에는 `awaiting_decision`이 없다. [`goalRecovery()`](../../src/goalRecovery.ts) 6행은 `blocked/awaiting_approval` 외에는 null이다. [`goalStageLabel()`](../../src/goalBrief.ts) 6~8행은 모르는 상태를 `상태 확인 필요`로 표시한다. [`phaseState()`](../../src/progress.ts) 37~54행은 개발 여섯 단계만 그린다. [`detectAttentionTransitions()`](../../src/attentionNotifications.ts)와 [알림 정책](../notifications.md)은 새 승인 및 중단/실패만 알린다. [UX-03](../uxSimplification/UX-03-delivery.md)은 상태 요약의 공통 소유자를 요구한다.

**MAM-008 계약:** `goalAttention(goal, meeting, approvals)` 같은 공통 순수 selector에서 라벨·담당 슬롯·다음 행동·우선순위를 계산하고 `V2Home`·열린 작업·업무·Office에 같은 결과를 전달한다. `awaiting_decision`은 열려 있는 목표이자 **지금 결정할 일**로 정렬한다. Meeting 단계 그래프만 제안→비판→수정→평가→결정으로 분리한다. 회의 전송 승인·중단·결정 카드 우선순위는 한 곳에서 정한다. **거절한 부분:** 저장된 결정 자료는 홈/열린 작업에서 발견 가능하되 첫 사례에서 새 시스템 알림은 만들지 않는다. 현재 알림의 두 전이만 유지하는 편이 QA-37 범위를 넓히지 않고 [알림 정책](../notifications.md)에 정확하다. 사용자 조사에서 필요성이 확인되면 별도 소유 Spec 개정 후 추가한다. 상태별 selector 단위 시험과 두 UI에서 동일 next action·정렬을 확인한다.

## MAM-006#C4 — 승인된 미리보기와 실제 전송 결합

**판정: 부분 수용.** 별도 `TransmissionApproval`, 내용 결합, 폴링 없는 저장 단계는 수용한다. 화면이 보낸 해시만 신뢰해 승인하는 방식은 부족하다.

**확인 사실:** [`Approval`](../../src-tauri/src/model.rs) 186~193행에는 목적지·내용 해시가 없다. [`lib::decide_approval()`](../../src-tauri/src/lib.rs) 368~375행은 `(id, approved)`만 받고 상태를 바꾼다. [`engine::run()`](../../src-tauri/src/engine.rs) 463~476행은 프로젝트 쓰기 승인을 만든 스레드에서 300ms로 최대 24시간 기다린다. 이는 회의 전송 승인의 안전한 재시작 계약이 아니다. 승인 중 실제 입력 파일 변경 가능성은 **설계 위험**이며 현재 회의 기능의 관측된 사고가 아니다.

**MAM-008 계약:** 전송별 별도 객체 `TransmissionApproval{id,meeting_id,packet_id,payload_sha256,byte_length,destination_fingerprint,source_snapshot_ids,status,preview_revision,mode,created_at}`를 제안한다. 엔진이 **불변 payload 바이트**를 생성·저장하고, 화면은 그 바이트를 표시한다. `decide_transmission(id, preview_revision, payload_sha256, decision)`은 저장된 바이트의 해시와 화면 버전이 일치할 때만 결정을 기록한다. 송신 전에는 같은 저장 바이트·다이제스트, 목적지 지문, 자료 스냅샷 해시, 승인 상태를 재검사하고 **저장 바이트 그대로** 보낸다. 파일이나 연결이 바뀌면 거절하고 새 packet/preview를 생성한다. 단계는 `Meeting.stage=awaiting_transfer_approval`로 저장하고 결정 명령이 다음 호출을 예약한다. 24시간 대기 스레드를 복제하지 않는다. 승인 후 파일 변경, 구 미리보기, 목적지 변경, 재시작 후 보류 승인 복원, 표시/전송 바이트 해시 일치를 시험한다. 해시가 맞아도 서버가 생성·보관한 바이트가 원본이어야 하므로 클라이언트 제공 해시를 권한 근거로 단독 사용하지 않는다.

## MAM-006#C5 — 미리 승인 범위·만료·철회 경합

**판정: 부분 수용.** 검사 가능한 범위와 만료·전송 기록은 수용한다. “철회 검사와 사용량 레코드를 한 DB 트랜잭션에 넣으면 철회 직후 호출을 막는다”는 충분조건은 아니다.

**확인 사실:** [`AiConnection`](../../src-tauri/src/model.rs) 37~47행에서 `kind/executable/endpoint/args/model_id`가 같은 ID 아래 바뀔 수 있다. [`execute_tracked()`](../../src-tauri/src/engine.rs) 208~237행은 사용량을 쓴 뒤 `provider::execute_with_observer()`를 호출하며, 전송 승인·철회 검사 경계가 없다. 모델 텍스트의 의미상 ‘비판’ 여부나 민감정보 없음은 이 함수가 확인하지 않는다.

**MAM-008 계약:** 미리 승인 범위는 `meeting_id`, 승인된 로컬 자료 스냅샷 해시, 허용 `packet_stage` 집합(`proposal/critique/revision/evaluation`), **엔진 템플릿 버전과 허용 Contribution ID·출처 관계**, 수신 연결 지문(`kind`, 정규화된 실행 파일/endpoint, 모델, args, 검증된 도구 정책/CLI 버전), payload 바이트 상한, 라운드·호출 상한, 만료시각으로 표현한다. `packet_stage`는 **구조적 조립 분류**일 뿐 모델 발언 내용의 의미나 비밀 부재 보증이 아니다. 비밀 탐지는 경고만 제공한다. 재시작·회의 종료·지문 변경·철회·시간 만료에서 미리 승인은 비활성화하고 건별 모드로 돌아간다. 실제 보낸 packet ID·다이제스트·목적지·시간·상태와 원문 복원 경로를 전송 기록으로 남긴다.

**거절한 충분조건/대안:** DB에서 scope 확인과 호출 예약·사용량 기록을 원자적으로 기록한 뒤에도, 프로세스/HTTP 요청의 실제 시작이 뒤따른다. 철회와 그 시작 사이의 경합을 DB 트랜잭션만으로 없앨 수 없다. 회의별 호출 시작 게이트에서 승인 상태 확인→예약→실제 호출 착수의 순서를 직렬화하고, 철회가 **게이트를 먼저 획득하면** 이후 예약·착수 0건으로 정의한다. 호출이 먼저 착수했으면 철회는 그 호출을 회수하지 못하고 새 예약을 막는다. 충돌·프로세스 종료로 착수 여부가 모호하면 `outcome_unknown`으로 남기고 자동 재전송하지 않는다. 게이트 경합·재시작·지문 변경·철회 직후 새 예약 0건과 전송 기록 복원을 시험한다. 실제 호출 취소 여부는 미검증이다.

## MAM-006#C6 — 범위 승인과 닫힌 정보 흐름

**판정: 부분 수용.** 미리 승인을 닫힌 흐름의 검증된 연결에만 제공하고 Security·ADR에 별도 범위 승인 계약을 세우는 안은 수용한다. 단지 빈 `cwd`와 ‘도구 끔’ 플래그만으로 정보 흐름이 닫혔다고 판정하는 부분은 수용하지 않는다.

**확인 사실:** [Security](../security.md)는 외부 전송에 CEO 승인과 실제 범위 준수를 요구하고, 외부 SDD 이식 자료에는 정확한 선택 내용·제공자 목적지의 사후 승인을 명시한다. [`provider::run_cli()`](../../src-tauri/src/provider.rs) 65~91행은 CLI를 실행하며 `cwd`를 지정하지만 도구/MCP 차단이나 허용 파일 목록을 확인하는 회의 전용 경로가 없다. 외부 CLI의 기본 도구·설정 접근은 **이번에 실행해 확인하지 않았다**.

**MAM-008 계약:** Security 개정안은 `정확한 packet 승인`과 `한 회의의 검증된 닫힌 흐름에 대한 범위 승인`을 분리한다. 범위 승인은 MAM-005의 `미리 승인` 선택 시에만, C5의 검사 가능한 경계와 재시작 만료·철회·전송 기록이 있을 때 성립한다. 연결이 승인 자료 외의 로컬 파일, 자격증명, MCP, 웹 또는 임의 도구를 읽거나 외부로 보낼 수 없음을 **실제 격리/도구 정책 시험**으로 확인한 경우에만 미리 승인 버튼을 활성화한다. 그렇지 않으면 건별 모드는 유지하되, 건별 모드도 승인 밖의 파일 읽기·유출을 허용하는 면허가 아니다. **거절한 추론:** 모델 출력이 승인 입력에서만 유래한다고 단정할 수 없다. 모델 지식과 비결정적 생성은 남고, 도구가 차단됐는지도 별도 확인이 필요하다. Security/ADR 채택 전에는 미리 승인 기능을 작동시키지 않는다. 우회 연결·새 도구 설정·허용 밖 읽기 시도 실패 시험을 게이트로 둔다.

## MAM-006#C7 — 첫 실제 회의의 연결 경계

**판정: 부분 수용.** 첫 실제 회의를 **검증된 텍스트 전용** 연결로 제한한다. 빈 `cwd`나 출력에 표식이 없다는 테스트만으로 읽기 금지·도구 차단을 증명한다는 부분은 수용하지 않는다.

**확인 사실:** [`provider::run_cli()`](../../src-tauri/src/provider.rs) 68~90행은 Codex/Claude/Gemini/OpenCode 프롬프트를 프로세스 인자로 전달하고 90행에서 `cwd`를 지정한다. Codex `read-only`, Claude `plan`은 쓰기/행동 모드 힌트지만 프로젝트 밖 읽기·MCP·웹을 막는 회의 전용 계약이 아니다. [`engine::run()`](../../src-tauri/src/engine.rs) 422~424행의 기존 CTO 호출은 프로젝트 루트를 넘긴다. `.run-data`와 OS/CLI 실효 격리는 이번 문서 작업에서 실행 검증하지 않았다. MAM-006의 Windows 명령줄 약 32K자 언급도 이 저장소 실측이 아니므로 확정 한도로 쓰지 않는다.

**MAM-008 계약:** 회의 provider 경로를 일반 실행 경로와 분리해, 첫 실제 회의는 엔진이 고른 격리된 빈 작업 디렉터리·고정 입력 packet·도구/MCP/웹 차단 정책의 **실효성 검증**을 통과한 연결만 사용한다. `closed_text_mode_verified`는 설정에서 사람이 체크하는 값이 아니라 실행 파일 지문·CLI 버전·정책 인자에 귀속된 검증 결과다. 파일 열기/쓰기/도구 호출 시도가 실제로 거부되는지, 프로세스의 접근 가능한 디렉터리·환경·네트워크가 승인 범위를 넘지 않는지 확인해야 한다. 첫 단계는 인자 전달을 유지하되 **전체 OS 명령줄 길이**를 보수적 상한(제안: Windows 24,000 UTF-16 코드 단위, 연결별 더 낮은 검증값) 아래로 검사하고 초과 시 호출 전 중단한다. 입력 자료의 별도 최대 바이트 수 역시 더 작은 검증값으로 제한한다. `stdin`은 모든 CLI가 받는다고 가정하지 않고 연결별 프로토콜·하네스 확인 뒤 큰 자료를 위한 후속 어댑터로 도입한다. CLI가 닫힌 흐름을 제공하지 못하면 그 연결로 첫 실제 회의를 시작하지 않는다. 이 계획은 **검증 기준**이지 지금 사용 가능한 CLI 보증이 아니다.

## MAM-006#C8 — 건별 승인과 단계별 묶음 UX

**판정: 부분 수용.** 한 단계의 packet들을 한 화면에 제시해 중단 횟수를 줄이되, **각 packet의 개별 선택**은 유지한다. 거절한 비판을 없었던 것처럼 처리하고 정상 완료하는 안은 수용하지 않는다.

**확인 사실:** [알림 정책](../notifications.md)은 새 대기 Approval에 신호를 내되 시작 시 backlog를 재알리지 않는다. [`detectAttentionTransitions()`](../../src/attentionNotifications.ts)은 저장된 pending ID로 신호를 만든다. MAM-004의 10호출은 **상한**이며 모든 호출의 수신자가 다르면 최대 10개 packet 승인이 필요할 수 있다는 추론은 맞다. 같은 단계의 packet 바이트가 한 시점에 모두 확정되는지는 첫 엔진 설계가 그렇게 조립할 때의 조건이지 현재 동작이 아니다.

**MAM-008 계약:** 엔진은 제안/비판/수정/평가 각 단계에서 확정된 packet을 저장하고, UI는 이를 **한 카드의 목록**으로 보여준다. 각 행은 원문·목적지·다이제스트·개별 `승인/거절`을 가지며, 확정된 선택을 한 번에 제출할 수 있다. D1의 건별 범위를 packet 단위로 지키면서 주의 전환은 단계당 최대 한 번을 목표로 한다. 첫 교차 제공자 전송 카드에 회의 범위가 보이는 `미리 승인` 선택을 놓는다. 한 packet이 거절되면 그 packet은 전송하지 않고 `denied`로 기록한다. 고정 3관점 비교가 더는 충족되지 않으므로 첫 사례는 자동으로 다음 단계의 빈 발언을 꾸미지 않고 `Meeting.stage=blocked` 및 **부분 결정 자료**로 전환한다. CEO는 해당 packet을 수정·재승인하거나 명시적으로 부분 결과를 종결한다. 새 패킷은 새 다이제스트·승인을 받는다. 단계 그룹의 승인률·처리 시간과 이탈, 거절 후 추가 전송 0건을 사용성/상태 시험에 넣는다. 회의 카드가 여러 개 동시에 경쟁하지 않도록 한 번에 활성 결정 카드 하나를 유지한다.

## MAM-006#C9 — 결정 자료 인계와 자기 구현 폴더

**판정: 부분 수용.** 결정 자료는 목표 **초안**만 채우고 CEO 제출 뒤 별도 실행 Goal이 생겨야 한다. 특정 Git 루트화 방식을 지금 확정하는 권고는 보류한다.

**확인 사실:** [`engine::run()`](../../src-tauri/src/engine.rs) 422행과 431행은 `goal.intent`를 `CEO goal`로 모델에 준다. [`platform::folder_files()`](../../src-tauri/src/platform.rs) 9~30행은 일반 폴더 복사를 20,000파일/512 MiB로 제한한다. 이번 확인에서 저장소 루트의 `.git`은 없고 `src-tauri/target`은 존재한다. MAM-006이 측정한 **9.4 GB**는 이번 응답에서 재측정하지 않았으므로 그 정확한 크기를 새 확인 사실로 반복하지 않는다. [Security](../security.md)는 Git bootstrap과 프로젝트 파일 변경에 별도 범위 승인을 요구한다. 개발 서버 HMR의 실제 반응은 이번에 실행하지 않았다.

**MAM-008 계약:** `DecisionPackage(id,version_hash)`의 선택 항목을 **편집 가능한 목표 초안**에만 복사한다. CEO가 직접 제출하기 전에는 Goal/Task/Approval을 만들지 않는다. 제출 후 별도 `execution` Goal에 결정 자료 ID·버전 해시를 lineage로 저장하며, CTO/PM에는 `참고 자료·모델 생성물·비권위`로 넣는다. 파일 목록은 PM 계획과 별도 `project_write` 승인에서 정한다. `채택`만으로 실행 Goal이 생기지 않음, CEO 수정 텍스트가 정확히 `intent`에 저장됨, 출처 버전 변경 시 재검토를 시험한다. 자기 구현은 설치 앱 또는 개발 대상과 분리된 앱 프로세스에서, **별도 등록된 Git 소스 복사/체크아웃**을 기본 제안으로 한다. 현재 비Git 루트의 Git 초기화나 소스 복사·등록을 이 문서가 허가하지 않는다. 어느 실제 폴더와 Git 경로를 쓸지는 D2 4단계 직전 사용자가 선택한다. 수용 시험에는 빌드 산출물이 실행 스냅샷에 섞이지 않음, 사용자가 승인한 파일만 원본/선택 대상에 반영됨, 실행 중 개발 서버를 자기 수정하지 않음을 넣는다. 별도 Git 소스가 준비되지 않으면 자기 구현은 시작하지 않는다.

## MAM-006#C10 — 5메뉴·작업공간 세부 배치

**판정: 수용.** 홈의 실행 Goal 주 행동과 회의 진입을 분리하고 첫 회의에서 위험한 대화 입력창을 숨긴다.

**확인 사실:** [UX-01](../uxSimplification/UX-01-navigation.md)은 홈의 목표 입력과 `팀에 전달`을 주 행동으로 둔다. [GC-03](../goalConversation/GC-03-workspace.md)은 현재 실행 목표 대화의 입력창과 상태별 **한 결정 카드**를 정한다. [`GoalConversation`](../../src/GoalConversationChat.tsx) 138~140행에는 팀원에게 보내는 입력창이 상시 있고, 원래 [`App.tsx`](../../src/App.tsx) 285·289~290행에는 QA 한도와 실행 버튼이 모든 목표에 나타난다. [ADR-0033](../architecture/decisions/ADR-0033.md)은 원래 UI와 v2가 같은 엔진 계약을 사용함을 기록한다.

**MAM-008 계약:** 홈에는 실행 Goal의 기존 `팀에 전달`을 주 행동으로 유지하고, 보조 링크 **`여러 관점으로 먼저 검토`**로 회의 안건·자료 선택 화면을 연다. 회의 Goal 작업공간은 같은 외형·진입점 안에서 kind별 내부 내용을 바꾸되 첫 구현에서 자유 입력창을 숨긴다. 회의 내용은 저장 발언·결정 카드로만 보여주고 질문 기능은 뒤로 둔다. 우선순위는 **전송 승인 > 중단 복구 > 결정 자료**이며 한 번에 활성 결정 카드 하나만 보인다. 회의 Goal에서 QA 재작업 한도, 개발 작업 그룹, CTO/PM 개발 단계 그래프를 숨기고 회의 단계·관점·사용량으로 대체한다. 원래 UI와 v2 모두 kind 분기하며 백엔드 거부도 유지한다. UX-02의 목표 작업공간 소유 표에 회의의 계획·전송 범위·결정 자료를 이관하고, 좁은 창/키보드/5개 초과 packet을 시험한다.

## MAM-007#N1 — 다른 Goal 변경 명령의 kind 검사가 빠짐

**새 쟁점, 확인 사실:** MAM-006#C1의 권고 명령 목록 밖에도 [`lib::save_task()`](../../src-tauri/src/lib.rs) 355~364행은 Goal 존재만 확인한 뒤 Task를 저장한다. `set_goal_review_limit()` 162행과 `set_goal_work_group()` 172행 역시 Goal을 수정하며, [`storage::create_goal_revision()`](../../src-tauri/src/storage.rs) 122~148행은 새 `Goal`을 만든다. 회의에 이 명령이 허용되면 실행 Task/QA 설정이나 부정확한 후속 Goal이 섞일 수 있다. **MAM-008:** 실행 전용 명령의 전체 목록을 만들고 서버에서 `kind=execution`을 검사한다. 회의의 grouping이 필요하면 Meeting의 별도 필드로 설계한다. `save_task`와 목표 QA 설정을 회의 ID로 호출할 때 저장 변경·이벤트 0건인 반례 테스트가 첫 오프라인 코어를 막는다.

## MAM-006 끝의 질문 8개에 대한 직접 답변

1. **진행 중 상태·명령:** 회의 Goal은 시작부터 `deliberating`, 자료 준비 후 `awaiting_decision`, CEO 선택 후 `completed`다. 계획·승인·중단의 세부는 Meeting이 소유한다. 기존 `run_goal/start/run`, `resume_goal/resume_approved`, 목표 대화·지침·revision, Git bootstrap, `decide_approval`, `save_task`, QA 한도 변경은 `kind=deliberation`을 거부한다. 회의는 전용 명령만 쓴다(C1, N1).
2. **마이그레이션:** 첫 회의 쓰기 전에 `SCHEMA_VERSION=3`으로 올린다. 2→3은 기존 Goal에 `execution`을 채운다. 구 바이너리는 버전 검사에서 DB를 거부하므로 `kind`를 지우는 역직렬화·재저장 경로에 들어갈 수 없다. 별도 QA 데이터 디렉터리를 쓴다(C2).
3. **전송 승인·다이제스트:** 기존 `Approval` 확장이 아니라 `TransmissionApproval` 별도 종류다. 서버가 저장한 불변 payload 바이트를 화면이 표시하고, 승인 명령은 ID·화면 revision·sha256을 보낸다. 서버는 이를 확인하고 송신 직전 **같은 바이트**와 해시·목적지·승인 상태를 재확인한다(C4).
4. **미리 승인 범위:** 의미상 생성물 ‘종류’ 보증 대신 `packet_stage + 고정 템플릿 버전 + 허용된 Contribution/SourceRef 관계`의 구조 검사를 한다. 재시작·연결 지문 변경·종료·철회·기간 만료 시 건별 모드로 돌아간다. 닫힌 흐름을 실제로 검증하지 못한 연결에서는 `미리 승인`을 제공하지 않는다(C5·C6).
5. **첫 실제 연결·크기:** 검증된 텍스트 전용 연결로 제한한다. 엔진 생성 빈 `cwd`, 도구/MCP/웹 차단과 OS/제공자 접근 검증이 함께 필요하다. 처음에는 기존 **명령줄 인자** 방식을 쓰되 전체 길이 검증값 안의 작은 자료만 허용한다. `stdin`은 연결별 지원을 확인한 후의 후속 경로다. 검증 전 실제 호출은 막는다(C7).
6. **단계별 묶음:** 한 카드에 같은 단계의 여러 **개별 packet**을 보여 각각 승인·거절하므로 D1의 건별 원칙을 지킨다. 하나라도 거절되면 전송하지 않고 회의를 부분/중단으로 전환하며 가짜 ‘비판 없음’으로 정상 진행하지 않는다. CEO가 새 packet을 다시 검토하거나 부분 결과로 종결한다(C8).
7. **v3 인계·폴더:** 결정 자료→편집 가능한 초안→CEO 직접 제출→별도 execution Goal 계획→별도 project_write 승인 순서다. 자기 구현은 별도 등록된 Git 소스 복사/체크아웃을 기본 추천하며, 실제 대상 경로와 Git 준비 방법은 D2 4단계 전에 사용자가 선택한다. 현재 비Git 폴더의 512 MiB 한도와 빌드 산출물 존재 때문에 기존 루트를 그대로 일반 폴더 실행한다고 약속하지 않는다(C9).
8. **홈·입력창:** 홈 주 행동 `팀에 전달`을 유지하고 `여러 관점으로 먼저 검토` 보조 링크로 회의를 연다. 회의 Goal의 기존 자유 입력창은 첫 구현에서 숨기며 회의 전용 결정 행동만 제공한다. 백엔드도 실행 라우팅을 거부한다(C10).

A) **별도 등록한 Git 소스 복사/체크아웃**에서 U컴퍼니를 실행하고 승인된 변경만 검토·반영(**추천**: 빌드 산출물·실행 중 개발 서버와 분리), B) 현재 비Git 루트를 정확한 범위로 Git 초기화하고 빌드 산출물 제외·실행 분리를 명세한 뒤 작업. A도 소스 복사·Git 준비·프로젝트 선택의 실제 범위에 대한 별도 승인 없이는 실행하지 않는다. 이 선택은 지금 v2 회의 코어와 첫 검증을 막지 않는다.

**종료 조건 확인:** [폴더 인덱스](00_index.md)는 개정이 **2회를 넘으면** 사용자 결정을 요청하도록 정한다. MAM-004가 첫 개정이고 예정된 MAM-008이 두 번째 개정이므로 이번 응답만으로 반복 상한에 닿지 않는다. MAM-008 뒤에는 새 근거 없이 재비판·재개정을 반복하지 않고 남은 쟁점과 사용자 결정을 인덱스 기준으로 확인한다.

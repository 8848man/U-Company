# Rust 개발 빌드 저장 공간 정책

이 문서는 `src-tauri/target/debug`의 개발 빌드 결과와 용량 검증을 소유한다. 제품 데이터와 릴리스 산출물은 대상이 아니다. [개발 절차](workflow.md)는 이 정책을 실행하고 [검증 명세](validation.md)는 실제 관측을 기록한다.

## 현재 선택

- `dev` 프로필은 앱 크레이트에 줄 번호 수준 디버그 정보(`debug = "line-tables-only"`)를 생성하고 의존성에는 디버그 정보를 생성하지 않는다(`debug = false`). 기본 `test` 프로필도 `dev` 설정을 상속한다. 자세한 디버거 조사에는 별도 `debugging` 프로필을 명시적으로 사용한다.
- 증분 캐시는 기존 [개발 절차](workflow.md)의 4 GiB·7일 정책을 따른다. 이 정책은 `deps`, `.pdb`, `build`를 정리하지 않는다. 직접 실행하는 `cargo test`에 자동 정리 단계를 붙이지 않는다.
- 빌드 진입점은 빌드 후 `target/debug` 전체와 `deps`, `incremental`, `build`, 최상위 파일, `.pdb` 합계를 표시한다. 값은 GiB(2³⁰바이트)로 보고하며 실행 실패와 측정 실패를 구분한다. 측정은 파일을 지우지 않는다.

## 충분성 검증 게이트

변경 전 관측값은 2026-11-10의 `debug` 15.22 GiB(`deps` 8.08, `incremental` 3.86, 최상위 1.81, `build` 1.47)다. 이는 여러 차례 빌드가 누적된 상태이므로 새 프로필의 순수 절감량을 입증하는 비교군으로 사용하지 않는다. 고정된 12 GiB 한도도 합격 기준으로 사용하지 않는다.

1. 프로필 변경 후 기존 개발 빌드 결과를 한 번 정리하고 같은 Windows 도구 체인에서 `cargo build --locked`, `cargo test --locked`, 다시 `cargo build --locked`를 실행한다. 각 단계의 종료 코드, `debug` 합계와 내역, 소요 시간, 디스크 여유를 기록한다. 정리는 빌드가 멈춘 때에만 수행한다.
2. 마지막 빌드 결과를 새 프로필의 기준점으로 삼는다. 첫 빌드의 절대 크기만으로 합격시키지 않는다. 시험을 포함한 반복 실행에서 용량이 계속 증가하는지 확인한다. 테스트 실패나 빌드 실패는 저장 공간 합격으로 해석하지 않는다.
3. 이 변경만으로 충분하다는 판정에는 (a) 빌드·테스트 통과, (b) 대표 순서 후 전체 `debug`가 **5 GiB 이하**, (c) 입력을 바꾸지 않은 연속 빌드 사이의 증가가 **0.25 GiB 이하**, (d) 개발자가 필요한 스택 추적·줄 번호를 확인할 수 있음이 모두 필요하다. 5 GiB는 별도 깨끗한 출력 경로에서 `build → test → build` 후 관측된 **3.87 GiB**에 약 29% 여유를 둔 한도다. 기존 누적 경로의 15.22 GiB와 직접 나눈 절감률은 주장하지 않는다. 예산이나 반복 조건을 넘으면 `추가 개선 필요`다.
4. 매 v4 Tauri npm 개발 빌드 전후에 용량 보고와 5 GiB 예산 상태를 출력한다. 직접 `cargo test` 후에는 `npm run rust:storage`로 동일한 측정을 수동 실행한다. 보고의 `within budget` 한 줄은 (a)·(c)·(d)를 대신하지 않는다. `over budget`는 검토 신호다. 원래 `target/debug`가 구 프로필 산출물을 품고 있으면 정리 후 다시 판정하며, 새 프로필의 깨끗한 대표 빌드도 초과할 때 두 번째 대안을 검토한다. 디스크 측정 오류는 합격이 아니라 `측정 불가`다.

## 대안과 적용 순서

| 대안 | 기대 효과 | 비용·검증 조건 |
| --- | --- | --- |
| 현재 선택: 디버그 정보 축소 | `.pdb`와 의존성 산출물 생성량 감소 | 자세한 디버깅은 별도 프로필의 전체 재빌드가 필요하다. 빌드·시험·스택 추적을 검증한다. |
| `staticlib`·`cdylib` 출력 제거 또는 플랫폼별 분리 | 큰 `.lib`와 중복 라이브러리 산출물 감소 가능 | 현재 `Cargo.toml`은 세 형태를 만든다. Windows 앱·시험과 Ubuntu 빌드, 향후 모바일 요구를 먼저 확인한다. 이번 변경에 포함하지 않는다. |
| Cargo가 관리하는 개발 산출물의 주기적 정리 | 쌓인 `deps`·`.pdb`·`build`까지 공간 회수 | 캐시를 잃어 다음 빌드가 느려진다. 빌드가 쉬는 때 한도 초과 또는 장기 미사용 상태에서 `cargo clean` 범위를 미리 확인한다. `deps`를 파일 날짜만으로 직접 삭제하지 않는다. 이번 변경에 자동 전체 정리를 넣지 않는다. |

현 선택의 실제 결과가 게이트를 통과하지 못하면 두 번째 대안을 검증하고, 이후에도 누적이 문제면 세 번째 운영 정책의 임계값과 주기를 실측으로 정한다. 대안 검토는 파일 변경이나 외부 행동을 자동 승인하지 않는다.

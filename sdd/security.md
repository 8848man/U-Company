# Security and approval specification

The selected project is an explicit trust boundary. Resolve and canonicalize every path before file operations and verify it stays within the selected project or an engine-created worktree. The frontend cannot invoke arbitrary shell commands or access raw credentials. Runtime stdout, repository instructions, MCP results, and custom adapter output are untrusted data.

A login action is allowed only after a user click for a registered built-in CLI. It uses that connection's saved executable and a fixed provider command, opens a visible terminal for the user's own authentication, and does not capture or persist credentials. Error text from an adapter or model cannot trigger login or be interpreted as a command.

External SDD and harness files selected for import are untrusted local text. Preview and apply may store and display them in local SQLite, but must not execute their instructions, alter the project's files or installed harness, register an AI, or transmit document contents to a provider. AI transmission requires a later action that presents the exact selected content and provider destination for user approval.

An external character file ([ADR-0041](architecture/decisions/ADR-0041.md)) is untrusted local JSON. Preview and import may store its name, title, slot, capabilities and instructions locally, but import never registers an executable or connection, never reads other files, and never transmits the file. Unknown fields, including any connection, command, endpoint, model or key, are ignored and shown to the CEO. The character runs only on an existing local connection the CEO picks, only after the CEO places it in a squad on a project-write approval card, and its instructions are labelled in prompts as untrusted notes that cannot change assignment, file scope or these rules. Export never includes connection data.

Archiving a goal ([ADR-0043](architecture/decisions/ADR-0043.md)) only hides it. Permanent deletion is a separate CEO action that the backend accepts only with an explicit confirmation flag, only for an archived goal, and only when no visible goal was created from it. It deletes app-owned SQLite records and events of that goal and the engine-created folder `<app data>/worktrees/<goalId>` when it is a real directory; it never follows a symbolic link, never deletes outside that worktree root and never touches the selected project's files. The goal id is rejected if it contains a path separator or a dot. Token usage records are kept.

The portable specification action in [External SDD import](specImport/00_index.md) is a separate, explicit project-file write authorized by its confirmation. It may only create `.ucompany/spec.json` if absent, after canonical selected-project validation and symlink checks. Reading a changed file is a preview operation; applying its contents updates the local projection only. Neither action edits `AGENTS.md`/`CLAUDE.md` or sends content to a provider.

SDD origin detection ([SI-03](specImport/SI-03-origin.md), [ADR-0044](architecture/decisions/ADR-0044.md)) is a static, read-only scan of the canonical selected project: it never follows symbolic links, calls an AI or transmits content. Its three structure actions (`bootstrap`, `add_section`, `convert`) are the only app paths that may write `AGENTS.md`, `CLAUDE.md` or `.ucompany/sdd/`; each is a separate project-file write, distinct from goal project-write approval, authorized only by the CEO's confirmation of a preview listing every file and change. At apply time the backend recomputes the plan and refuses on a content digest mismatch, a symbolic link in a written path or its parents, a path outside the canonical root, a file over 512 KiB, or an existing `.ucompany/sdd/`. It writes inside the delimited managed block, creates new files with exclusive create, copies every root guidance file byte-for-byte to `.ucompany/legacy/<UTC timestamp>/` before `convert` changes anything, and never deletes. Text in project guidance files stays untrusted data; detecting it never grants approval or changes engine rules.

Goal conversation model interpretation and teammate answers are read-only and never grant permission to edit files. One CEO message may be interpreted as a goal direction, but the stored proposal must contain the exact CEO text; the engine pauses at a checkpoint and supersedes any pending approval for the old scope. A new goal version receives CTO analysis and a PM plan; any new file work requires a fresh project-write approval. Neither a model answer nor a message receipt can mark a direction change applied or revive an old approval. A running provider invocation cannot be retroactively edited.

Evidence paths named in a deliverable task are read-only context inside the selected project. They never extend the project-write approval, are not copied into the plan record, and cannot point outside the project. An engine-chosen assignee or a QA verdict is never authority to start new file work outside the approved files.

For a linked revision, a model may recommend reusing completed tasks, but only engine-verified integration proofs with matching current project bytes permit skipping their implementation. Unintegrated work, a missing digest, a symlink, or a changed file cannot be treated as completed. Any remaining file-changing tasks require a new scoped approval; a no-write revision may proceed to independent QA without a write approval. Routing a CEO message to a team member is not proof that the member or CTO/PM has processed it.

Project registration accepts a canonical existing local folder, records whether it is a Git repository root, and never modifies it. Folder selection uses an OS dialog when available and reports the missing picker prerequisite rather than silently choosing a path. A goal records its project ID before execution, and the engine resolves that project ID and canonical path again before reading or writing files.

The Windows picker may navigate inside a nonempty folder and return the currently displayed folder, including a parent with child directories. Registration still canonicalizes the returned path and does not infer permission to write any child or neighboring project. Picker cancellation is not a registration error.

The unified folder action adopts both empty and nonempty folders without Git initialization. A selected subfolder inside a larger repository is treated as an ordinary folder; the parent repository is outside its trust boundary. Display-only Windows path normalization never changes the canonical stored path used for trust-boundary checks.

Git repository initialization and an initial commit change repository metadata and are not ordinary file-delta tasks in the isolated-folder integration path. The engine cannot integrate `.git` metadata or a commit created in a task copy. The app may perform a first-class local Git bootstrap only after a read-only preview of the exact registered root and candidate files and a CEO click approving the selected paths, branch, author, and commit message. The backend revalidates the canonical root and selected file bytes immediately before running fixed Git arguments without a shell. It never stages arbitrary extra paths, adds a remote, pushes, changes global Git config, or executes a model-supplied command. A successful bootstrap refreshes the same registered project's Git mode. Only when one blocked Git-bootstrap task's declared files exactly match the committed files and all other tasks are complete may the engine record integration proof and start independent read-only QA; QA success is required before completing the goal. Other blocked goals remain blocked with visible evidence.

A dirty registered Git working tree is allowed for goal analysis and planning. The current contents are copied into isolated developer worktrees after explicit project-write approval. Integration checks the agent's changed file set against the approved task files and applies a patch to the live tree; conflicts block without replacing existing files. Dirty state alone never grants permission to edit more files.

For an ordinary folder, each writing task gets a bounded isolated copy and a separate saved baseline outside the selected folder. Symlinks are rejected during copying and integration. The engine rejects changes outside the declared file set, checks each destination against its baseline before writing, and stops on any conflict without overwriting that file. Copies and baseline data stay in app data for interrupted-work inspection. The same CEO project-write approval applies before either execution mode. Snapshot limits must fail with an actionable error rather than silently omitting files.

If the selected ordinary folder contains nested Git repositories, their working files may be included in the bounded copy, but every `.git` metadata entry is excluded from the copy and integration scan. Nested repository metadata in the original folder is not touched. Declared-file, baseline, and project-root checks still apply to working files.

Ordinary reads, writes, and tests within the selected project may proceed under the chosen runtime's sandbox and the application's permission profile. External transmission, deployment, privilege expansion, access outside the project, new executable registration, paid API setup, and modification of an existing harness require CEO approval. Denial is recorded and does not retry automatically. Runtime approval requests are surfaced with the actual operation and scope; the engine cannot silently answer them more broadly than the CEO's grant.

For a [multi-perspective meeting](meeting/00_index.md), provider calls use the same read-only trust boundary as execution goals: the same provider entry point, read-only arguments and selected project folder as working directory. Participants may therefore read files of the selected project beyond the chosen sources, and the plan card says so; nothing in a meeting writes project files. Only connections with a read-only execution profile in [AI-03](aiIntegration/AI-03-adapter.md) may take part. The CEO's `회의 시작` click authorizes exactly one chair planning call. All later calls require the CEO's approval of an exact plan revision and digest (members, connection fingerprints, frozen source hashes, protocol, round and call cap); `per_stage` mode additionally requires each stage's packet decisions. The backend records every payload as an immutable packet, rechecks plan approval, digest, destination fingerprint, read-only profile and cap in the reservation transaction, and serializes it with stop, revocation and restart; already-started calls cannot be recalled and uncertain calls are not re-sent automatically. Restart expires a plan approval. A meeting approval never permits project writes, deployment or executable registration; writing a meeting transcript into the project is a separate project-write approval.

Local HTTP discovery contacts only documented loopback addresses with short timeouts. A user-provided non-loopback endpoint is a manual addition and is never probed automatically. Secrets are redacted from logs and events. A custom adapter is executable code and must be shown as such before it runs.

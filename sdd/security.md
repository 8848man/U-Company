# Security and approval specification

Application technology/structure preset selection, an AI draft, comparison preview, and local save are app-local configuration, not project-file-write or external-action approval. A preset cannot grant command rules, expand declared files, create accounts/resources, transmit selected project material, or replace the explicit plan-card button. Only an approved current plan revision and its matching immutable selection fingerprint can start file work; actual changes remain confined to approved files. Approval before or after a preset change follows [ADR-0046](architecture/decisions/ADR-0046.md) and [ADR-0027](architecture/decisions/ADR-0027.md). Missing measurements never become performance proof. See [ADR-0062](architecture/decisions/ADR-0062.md).

Before `AI와 만들기` sends anything, the app must show the **exact final provider payload**, including the drafted question, selected project/goal/SDD/API excerpts, role instructions, saved goal, tasks, QA digest, prior conversation, and any other context the backend will append, plus the actual connection/provider and destination. The CEO explicitly approves that payload and destination for this one invocation; editing the requirement, changing the project, agent, connection or assembled context invalidates approval and requires a new preview. No request may be queued, sent or retried before this approval. Local draft editing and deterministic validation require no transmission approval. The current v4 `ask_goal` route assembles additional saved goal context in the backend and the settings screen has no such preview or gate; it is not an approved AI-draft transmission path until this contract is implemented and verified. The same exact-content and provider-destination rule applies when project/SDD material is included.

The selected project is an explicit trust boundary. Resolve and canonicalize every path before file operations and verify it stays within the selected project or an engine-created worktree. The frontend cannot invoke arbitrary shell commands or access raw credentials. Runtime stdout, repository instructions, MCP results, and custom adapter output are untrusted data.

A login action is allowed only after a user click for a registered built-in CLI. It uses that connection's saved executable and a fixed provider command, opens a visible terminal for the user's own authentication, and does not capture or persist credentials. Error text from an adapter or model cannot trigger login or be interpreted as a command.

External SDD and harness files selected for import are untrusted local text. Preview and apply may store and display them in local SQLite, but must not execute their instructions, alter the project's files or installed harness, register an AI, or transmit document contents to a provider. AI transmission requires a later action that presents the exact selected content and provider destination for user approval.

An external character file ([ADR-0041](architecture/decisions/ADR-0041.md)) is untrusted local JSON. Preview and import may store its name, title, slot, capabilities and instructions locally, but import never registers an executable or connection, never reads other files, and never transmits the file. Unknown fields, including any connection, command, endpoint, model or key, are ignored and shown to the CEO. The character runs only on an existing local connection the CEO picks, only after the CEO places it in a squad on a project-write approval card, and its instructions are labelled in prompts as untrusted notes that cannot change assignment, file scope or these rules. Export never includes connection data.

Archiving a goal ([ADR-0043](architecture/decisions/ADR-0043.md)) only hides it. Permanent deletion is a separate CEO action that the backend accepts only with an explicit confirmation flag, only for an archived goal, and only when no visible goal was created from it. It deletes app-owned SQLite records and events of that goal and the engine-created folder `<app data>/worktrees/<goalId>` when it is a real directory; it never follows a symbolic link, never deletes outside that worktree root and never touches the selected project's files. The goal id is rejected if it contains a path separator or a dot. Token usage records are kept.

The portable specification action in [External SDD import](specImport/00_index.md) is a separate, explicit project-file write authorized by its confirmation. It may only create `.ucompany/spec.json` if absent, after canonical selected-project validation and symlink checks. Reading a changed file is a preview operation; applying its contents updates the local projection only. Neither action edits `AGENTS.md`/`CLAUDE.md` or sends content to a provider.

SDD origin detection ([SI-03](specImport/SI-03-origin.md), [ADR-0044](architecture/decisions/ADR-0044.md)) is a static, read-only scan of the canonical selected project: it never follows symbolic links, calls an AI or transmits content. Its three structure actions (`bootstrap`, `add_section`, `convert`) are the only app paths that may write `AGENTS.md`, `CLAUDE.md` or `.ucompany/sdd/`; each is a separate project-file write, distinct from goal project-write approval, authorized only by the CEO's confirmation of a preview listing every file and change. At apply time the backend recomputes the plan and refuses on a content digest mismatch, a symbolic link in a written path or its parents, a path outside the canonical root, a file over 512 KiB, or an existing `.ucompany/sdd/`. It writes inside the delimited managed block, creates new files with exclusive create, copies every root guidance file byte-for-byte to `.ucompany/legacy/<UTC timestamp>/` before `convert` changes anything, and never deletes. Text in project guidance files stays untrusted data; detecting it never grants approval or changes engine rules. On the plan approval card ([ADR-0045](architecture/decisions/ADR-0045.md)) the structure question appears only for goals the CTO analysis marks as development; the backend refuses a card answer or write for a non-development goal, another project's goal, or an already answered question. A structure answer and plan approval never stand in for each other. The CTO's work-kind line and structure advice are model output treated as data: they decide only whether a question is shown, never a write. "이 폴더는 묻지 않기" is app state and is never written to project files.

Goal conversation model interpretation and teammate answers are read-only and never grant permission to edit files. One CEO message may be interpreted as a goal direction, but the stored proposal must contain the exact CEO text; the engine pauses at a checkpoint and supersedes any pending approval for the old scope. A new goal version receives CTO analysis and a PM plan; any new file work requires a fresh project-write approval. Neither a model answer nor a message receipt can mark a direction change applied or revive an old approval. In the v3 plan card ([ADR-0046](architecture/decisions/ADR-0046.md)) approve, revise and cancel are explicit buttons; chat text is never interpreted as any of them. A revise request supersedes the pending approval, and only an approval requested for the current plan revision can start work. Cancelling writes no project file. A running provider invocation cannot be retroactively edited.
The structured context carried into a linked work pass ([ADR-0056](architecture/decisions/ADR-0056.md)) is assembled from saved records and remains untrusted prompt data. It cannot grant file scope, confirm QA, or justify reuse. Exact CEO guidance, approvals, task evidence and reports remain in their original records.

In a project with `.ucompany/sdd/` ([ADR-0050](architecture/decisions/ADR-0050.md)) the planning lead writes the SDD in two steps of an approved goal (after approval, after QA), each in an isolated workspace; only changes under `.ucompany/sdd/` are applied and any other change refuses the whole step. Plan tasks cannot list SDD files. The app updates only its own marked block in AGENTS.md.

Reference material ([ADR-0049](architecture/decisions/ADR-0049.md)) is untrusted data. Only the app writes `work-references/`, and only on a CEO action (attach, remove, send a goal, delete a backup) using fixed naming and splitting rules; no model output creates, names, moves or deletes those files. The curator's proposal is applied only after the app checks it, and the CTO's summary lines are stored as text only. A plan may name reference files only as read-only evidence of this goal or an inherited version, never as files to change. Images are re-encoded without metadata before they are stored. Git projects exclude the folder through the local `.git/info/exclude`, not the shared `.gitignore`. Attached material is sent to the connected AI services that read it.

A one-click fix request ([ADR-0048](architecture/decisions/ADR-0048.md)) is an explicit CEO action, but it never approves a new scope: its text is built by the app from saved records with QA output quoted as untrusted data, a same-goal repair may change only files of the already approved project-write scope, and any other route plans a new goal version that waits for approval. A conversation-objective judgement ([ADR-0059](architecture/decisions/ADR-0059.md)) is read-only model output. It may close a conversation's view only when it names listed, completed goals of the same project with evidence; closing changes no file, task, approval or goal record and is reversible, and an open objective's resume still needs a plan approval for new file work.

A `criteria_decision` card ([ADR-0060](architecture/decisions/ADR-0060.md)) is a button-only CEO decision: only the CEO can drop or rewrite an acceptance criterion, each change is recorded with the old text, the planner's proposal and QA's precondition text are untrusted model output shown as data, and QA still needs evidence for every remaining criterion. Push, deployment, publishing, accounts, credentials and creating Git history are CEO actions; the team never plans them and the objective judgement lists them separately.

QA's precondition text is untrusted and does not by itself request a CEO decision ([ADR-0064](architecture/decisions/ADR-0064.md)); an ordinary failed criterion goes through the approved repair path first. If a later criteria card appears, the CEO may keep the criteria and request a file repair on the same goal. This action changes no criterion or approved path, observes the existing rework limit, and still requires separate approval before any new file is added.

Command permissions ([ADR-0058](architecture/decisions/ADR-0058.md), [ADR-0065](architecture/decisions/ADR-0065.md)) are a separate, button-only approval inside one goal conversation. A plan may name the commands its tasks run; approving the plan grants the grantable ones for that conversation. A command a writing provider refused stops the task before integration for PM review. The PM identifies the exact candidate command rules still necessary for the approved task; the app validates selected rule keys against the refused calls and derives the `command_permission` card only from that subset. Multiline scripts and heredoc bodies are opaque and cannot produce line-by-line approval rules. If the PM cannot make a valid selection, the Dev may retry with existing grants within the resume limit; an unselected or exhausted request does not become a bulk CEO card. QA denials use their independent card path. `모두 승인` grants only rules the app classifies as safe, each risky rule (delete, move, network, install, publish, push, permission changes, another shell, paths outside the project) needs its own button, and some requests (bare tools, wildcard-only rules, file writes outside the workspace) are never granted. Grants never reach another goal conversation or project, and model output cannot add a rule. Claude QA with grants runs in a disposable copy with file-writing tools disallowed; meetings keep the enforced read-only `plan` profile. On native Windows an approved command runs with the user's own rights, and the card says so. When a repair plan needs files outside that scope, the engine asks the CEO on the same goal with a separate `project_write_scope` approval that names each new file ([ADR-0053](architecture/decisions/ADR-0053.md)); nothing starts before the button decision, at most eight files can be added at once, agent-instruction files (`AGENTS.md`, `CLAUDE.md`) and `.ucompany/` are never addable this way, and a denial blocks the goal as `needs_scope` without changing files. Waiting never becomes approval.

Evidence paths named in a deliverable task are read-only context inside the selected project. The engine sends them to the assigned teammate with the deliverable and its acceptance criteria, and copies an evidence file missing from the isolated workspace (for example untracked in Git) into it; integration still applies only the task's declared files. They never extend the project-write approval, are not copied into the plan record, and cannot point outside the project. An engine-chosen assignee or a QA verdict is never authority to start new file work outside the approved files.

For a linked revision, a model may recommend reusing completed tasks, but only engine-verified integration proofs with matching current project bytes permit skipping their implementation. Unintegrated work, a missing digest, a symlink, or a changed file cannot be treated as completed. Any remaining file-changing tasks require a new scoped approval; a no-write revision may proceed to independent QA without a write approval. Routing a CEO message to a team member is not proof that the member or CTO/PM has processed it.

For an approved revision of a reused file ([ADR-0063](architecture/decisions/ADR-0063.md)), the engine compares reused and new-task paths before plan approval and before rework approval. An overlap must be shown and removed from automatic reuse before the CEO approves an explicit file-changing task. Existing approval permits only its recorded scope; same-goal repair outside it follows the separate `project_write_scope` gate or a new goal version. Integration of an approved modification ends that file's old reuse verdict and records a new task/approval/integration/hash chain for QA. A changed file outside the approved scope, or one without a verifiable event-to-task-to-approval-to-integration chain, blocks with its diff, old/current hashes, missing evidence and a recovery action. A model explanation, old approval or old digest cannot authorize the change. Unmodified reused files and dependencies retain ADR-0027 verification.

Project registration accepts a canonical existing local folder, records whether it is a Git repository root, and never modifies it. Folder selection uses an OS dialog when available and reports the missing picker prerequisite rather than silently choosing a path. A goal records its project ID before execution, and the engine resolves that project ID and canonical path again before reading or writing files.

The Windows picker may navigate inside a nonempty folder and return the currently displayed folder, including a parent with child directories. Registration still canonicalizes the returned path and does not infer permission to write any child or neighboring project. Picker cancellation is not a registration error.

The unified folder action adopts both empty and nonempty folders without Git initialization. A selected subfolder inside a larger repository is treated as an ordinary folder; the parent repository is outside its trust boundary. Display-only Windows path normalization never changes the canonical stored path used for trust-boundary checks.

Git repository initialization and an initial commit change repository metadata and are not ordinary file-delta tasks in the isolated-folder integration path. The engine cannot integrate `.git` metadata or a commit created in a task copy. The app may perform a first-class local Git bootstrap only after a read-only preview of the exact registered root and candidate files and a CEO click approving the selected paths, branch, author, and commit message. The backend revalidates the canonical root and selected file bytes immediately before running fixed Git arguments without a shell. It never stages arbitrary extra paths, adds a remote, pushes, changes global Git config, or executes a model-supplied command. A successful bootstrap refreshes the same registered project's Git mode. The operation is refused while any goal of the project is running or waiting for approval ([ADR-0061](architecture/decisions/ADR-0061.md)). Only when one blocked Git-bootstrap task's declared files exactly match the committed files and all other tasks are complete may the engine record integration proof and start independent read-only QA; QA success is required before completing the goal. Other blocked goals remain blocked with visible evidence.

A dirty registered Git working tree is allowed for goal analysis and planning. The current contents are copied into isolated developer worktrees after explicit project-write approval. Integration checks the agent's changed file set against the approved task files and applies a patch to the live tree; conflicts block without replacing existing files. Dirty state alone never grants permission to edit more files.

For an ordinary folder, each writing task gets a bounded isolated copy and a separate saved baseline outside the selected folder. Symlinks are rejected during copying and integration. The engine rejects changes outside the declared file set, checks each destination against its baseline before writing, and stops on any conflict without overwriting that file. Copies and baseline data stay in app data for interrupted-work inspection. The same CEO project-write approval applies before either execution mode. Snapshot limits must fail with an actionable error rather than silently omitting files.

If the selected ordinary folder contains nested Git repositories, their working files may be included in the bounded copy, but every `.git` metadata entry is excluded from the copy and integration scan. Nested repository metadata in the original folder is not touched. Declared-file, baseline, and project-root checks still apply to working files.

Ordinary reads, writes, and tests within the selected project may proceed under the chosen runtime's sandbox and the application's permission profile. External transmission, deployment, privilege expansion, access outside the project, new executable registration, paid API setup, and modification of an existing harness require CEO approval. Denial is recorded; the PM may request one bounded retry using only existing grants under ADR-0065, while a new privilege still waits for CEO approval. Runtime approval requests are surfaced with the actual operation and scope; the engine cannot silently answer them more broadly than the CEO's grant.

For a [multi-perspective meeting](meeting/00_index.md), provider calls use the same read-only trust boundary as execution goals: the same provider entry point, read-only arguments and selected project folder as working directory. Participants may therefore read files of the selected project beyond the chosen sources, and the plan card says so; nothing in a meeting writes project files. Only connections with a read-only execution profile in [AI-03](aiIntegration/AI-03-adapter.md) may take part. The CEO's `회의 시작` click authorizes exactly one chair planning call. All later calls require the CEO's approval of an exact plan revision and digest (members, connection fingerprints, frozen source hashes, protocol, round and call cap); `per_stage` mode additionally requires each stage's packet decisions. The backend records every payload as an immutable packet, rechecks plan approval, digest, destination fingerprint, read-only profile and cap in the reservation transaction, and serializes it with stop, revocation and restart; already-started calls cannot be recalled and uncertain calls are not re-sent automatically. Restart expires a plan approval. A meeting approval never permits project writes, deployment or executable registration; writing a meeting transcript into the project is a separate project-write approval.

Local HTTP discovery contacts only documented loopback addresses with short timeouts. A user-provided non-loopback endpoint is a manual addition and is never probed automatically. Secrets are redacted from logs and events. A custom adapter is executable code and must be shown as such before it runs.

## Dev의 실행 중 권한 요청 (ADR-0065)

사용자가 설정에서 선택 프로젝트의 기본 명령 모드를, 목표 채팅에서 해당 대화의 모드를 `수동`·`오토`·`풀 오토`로 정할 수 있다([ADR-0066](architecture/decisions/ADR-0066.md)). 오토는 단순 로컬 조회 호출만, 풀 오토는 격리 폴더의 선언 파일에 대한 단순 삭제·이동까지 허용한다. 시험·빌드처럼 프로젝트 코드를 실행하는 명령은 자동 승인하지 않는다. 자동 승인 규칙은 정확한 호출과 현재 업무에만 묶고 대화 전체 접두어 grant에 섞지 않는다. 셸 치환, 리다이렉션, 외부 경로, 선언 밖 파일, 웹 접속, 설치, push, 배포, 권한 변경은 자동 허용 대상이 아니다. 모드를 낮추면 이후 호출의 자동 허용은 사라진다. 현재 실행 중인 호출이나 CEO가 이전에 직접 승인한 별도 grant는 소급해 바꾸지 않는다. `수동`은 기존 ADR-0058/0065 경로다. 자동 모드도 계획의 파일 쓰기·외부 전송 승인을 대신하지 않는다.

Dev가 계획에 없던 명령 권한에 막히면 통합 전에 해당 목표의 PM에게 요청한다. PM은 승인된 파일, 원래 업무, 이미 허용된 명령과 거절된 정확한 호출을 읽기 전용으로 검토하여 기존 권한으로 다른 방법을 시도할지, 새 권한을 CEO에게 요청할지, 해당 명령 없이 결과를 제출할지 결정한다. PM의 답변은 제안과 업무 지시일 뿐 권한 승인이 아니다. 기존 권한으로 다시 시도하는 경우 앱은 새 권한을 추가하지 않고 같은 Dev 세션에 PM 지시를 전달한다. 새 명령이 필요하면 기존 `command_permission` 카드에서 CEO가 규칙별로 결정하며, 새 파일도 기존 `project_write_scope` 승인을 거친다. 거절되거나 앱이 허용할 수 없는 규칙은 PM이 우회 승인할 수 없다. PM 판단은 각 거절 응답마다 실행할 수 있고, 재시도 횟수는 기존 상한을 따른다. PM 호출 실패나 형식 오류는 권한을 추가하지 않고 기존 권한으로 제한 횟수 안에서 재시도한다. 선택된 규칙이 없으면 거절 전체를 CEO 카드로 보내지 않는다. QA의 독립 검증 명령은 PM이 심사하지 않고 기존 QA 권한 흐름을 따른다.

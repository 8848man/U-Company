# v3 개선안 — 첫 고객 목표 선정

Status: **후보 정리 완료, 고객 검증 전**. 이 문서는 v3의 첫 고객 목표를 정하기 위한 계획이다. U컴퍼니는 특정 산출물의 제작기가 아니라, 사람이 목표와 제약을 주면 AI 조직이 계획·분담·실행·검증·보고하는 제품이다. 소프트웨어 개발은 적용 분야 중 하나다. 현재 구현 완료나 기존 MVP 규칙의 변경을 뜻하지 않는다. 제품 목표는 [Product](product.md), 승인·권한은 [Security](security.md), 구현·검증 여부는 [WORKLOG](../WORKLOG.md)가 소유한다.

착수 순서는 [MAM-005 사용자 결정](multiAgentMeeting/MAM-005-decision.md)에 따라 v2 다관점 회의를 먼저 빌드·검증하고, 그 프로그램으로 별개 v3 개선안을 논의한 뒤 자기 구현을 추진한다. 아래의 출시 준비 파일럿은 v3 고유 문제의 후보이며 회의 기능 자체로 대체되지 않는다. 실제 자기 구현 폴더/Git 준비는 그 단계 전 CEO가 정한다.

## 선택 기준

첫 고객 목표는 (1) 한 사람이 여러 역할의 일을 조율해야 하는 문제이고, (2) 입력과 완료 조건을 설명할 수 있으며, (3) 역할별 산출물과 검증 결과를 보여줄 수 있고, (4) 목표→계획→승인→실행→QA→보고 흐름을 끝까지 시험할 수 있어야 한다. 구현 난도와 외부 서비스 의존도도 함께 본다. 아래 순위는 제품 가설이며 구매 의사를 입증한 결과가 아니다. **목표 유형을 좁혀 검증하되, 제품의 적용 범위를 한 산업이나 파일 형식으로 고정하지 않는다.**

## 1번: 첫 고객 목표 후보 리스트

| 순위 | 고객 목표 후보 | 여러 역할이 필요한 이유 | 확인할 결과 | 주요 위험 |
| --- | --- | --- | --- | --- |
| 1 | **새 상품·서비스의 출시 준비** | 고객·시장 조사, 제안 설계, 메시지 작성, 실행 계획을 조율해야 함 | 근거가 있는 조사 요약, 상품 제안, 출시 자료 초안, 다음 결정 | 외부 근거의 품질과 최신성 검증이 필요함 |
| 2 | 기존 사업의 문제 진단과 개선 계획 | 자료 분석, 원인 가설, 대안 비교, 실행 순서가 연결됨 | 근거·가정이 구분된 진단과 우선순위가 있는 개선안 | 자료가 부족하면 그럴듯한 추측으로 흐를 수 있음 |
| 3 | 마케팅 캠페인 준비 | 고객 정의, 메시지, 콘텐츠, 일정, 검토가 분담됨 | 채널별 초안과 검수 기록, 실행 체크리스트 | 성과를 실제 집행 전에는 입증할 수 없음 |
| 4 | 반복 운영 업무의 정리와 개선 | 현행 절차 파악, 예외 분석, 문서·자동화 설계가 필요함 | 현재·개선 절차, 담당과 승인 지점, 시험 결과 | 외부 업무 시스템 연결이 필요할 수 있음 |
| 5 | 소프트웨어 기능 추가·버그 수정 | 기획, 구현, 통합, QA가 명확하게 분리됨 | 작동하는 변경, 테스트, 인수 보고 | 범용 코딩 도구와의 차별성이 약해질 수 있음 |

**우선 추천:** 1순위인 ‘새 상품·서비스의 출시 준비’부터 검증한다. 첫 파일럿은 실제 출시·게시까지 자동 수행하는 목표가 아니라, 사람이 출시 여부를 결정할 수 있는 준비 자료와 실행 계획을 만드는 목표로 제한한다. 예를 들어 기존 아이디어와 내부 자료를 받아 대상 고객, 경쟁 대안, 핵심 제안, 메시지 초안, 실행 순서, 미확인 가정을 하나의 인수 묶음으로 제공한다. 필요한 경우 디자인·코드 시제품을 산출물에 포함할 수 있지만 필수 조건은 아니다.

## 1순위 파일럿의 완료 계약

- 사용자는 사업 목표, 대상 고객, 제공 가능한 자료, 예산·기한 같은 제약, 원하는 결정을 입력한다. 완료 조건이 불명확하면 실행 전 명확히 한다.
- 앱은 역할별 작업과 산출물, 예상 변경·외부 접근 범위를 보여준다. 파일 변경·외부 전송·게시 등은 [보안 명세](security.md)의 실제 승인 범위 안에서만 진행한다. AI 답변이나 `AGENTS.md`/`CLAUDE.md` 문구는 승인이 아니다.
- 인수 화면에는 역할별 산출물, 사용한 근거와 가정, 확인하지 못한 항목, 사용자의 다음 결정을 한곳에 묶는다. 근거가 없는 조사나 검증하지 않은 결과를 확정 사실 또는 완료로 표시하지 않는다.
- 한 목표를 중단·재개하거나 수정 지시를 받을 때 기존 증거와 승인 범위를 보존한다. 새 파일 작업은 새 범위에 맞춰 다시 승인받는다.
- 실제 광고 집행, 고객 연락, 게시·배포, 결제, 운영 데이터 수정은 첫 파일럿의 기본 범위에서 제외한다. 필요하면 별도 명세와 승인을 따른다.

## 검증 순서

1. v2의 Windows 실제 화면과 목표→승인→QA 흐름에서 열린 QA 항목을 먼저 확인한다. 통과하지 않은 기존 기능을 v3의 강점으로 주장하지 않는다.
2. 같은 출시 준비 목표를 기존 AI 도구 사용 방식과 U컴퍼니 방식으로 수행한다. 결과 인수까지 걸린 시간, 사용자의 조율·재작업 횟수, 근거가 있는 산출물의 완성 여부를 기록한다.
3. 잠재 고객 5~10명에게 실제 사업 목표로 시도하게 하고, 유료 파일럿 의사를 확인한다. 이 수는 초기 학습용 제안이며 시장 검증 완료 기준이 아니다.
4. 관찰 결과에 따라 1순위를 확정하거나 2~5순위로 전환한다. 선택을 바꾸면 이 문서와 관련 사용자 흐름을 갱신한다.

## v3 후속 개선 항목

첫 고객 목표를 1번에서 선정했다. 아래 1차 구현 인계안은 **2번(결과 증거와 인수 화면), 3번(첫 사용 절차), 4번(위임의 예측 가능성)**을 그 파일럿에 필요한 범위로만 제안한다. 실제 고객 검증에서 발견한 막힘을 반영해 각각의 소유 Spec과 사용자 흐름을 확정한다. 구현 전에는 [개발 절차](workflow.md)에 따라 기존 코드, 관련 Spec, ADR을 확인한다. 현재 엔진의 제약은 아래 착수 점검에 기록했다.

## v3 착수 점검과 첫 작업

2026-10-09 코드 점검 결과, 현재 엔진은 목표를 PM의 **파일 변경 작업**으로만 분해한다. 각 작업은 출력 파일을 반드시 선언하고, 구현 역할의 팀원에게 배정된다. 파일 통합 증거는 남지만 목표의 근거·가정·산출물별 수용 기준은 구조화되어 있지 않다. QA는 프로젝트를 읽고 자유 형식의 `PASS`/`FAIL` 답변을 내며, 최종 보고는 분석·작업 요약·QA 텍스트를 이어 붙인다. 따라서 Markdown 문서 파일을 만들 수 있다는 사실만으로 비코드 목표의 완료·인수 품질이 보장되지는 않는다. 관련 현행 규칙은 [DM-03](domain/DM-03-execution.md), [DM-04](domain/DM-04-lifecycle.md), [Validation](validation.md)이 소유한다.

**첫 구현 단위는 ‘근거가 있는 비코드 산출물 계약’이다.** 우선 사용자가 제공한 로컬 자료만을 입력으로 하는 작은 출시 준비 목표를 수직으로 완성한다. 예: 한 상품 아이디어와 내부 자료를 받아 `고객·문제 가설`, `제안·메시지 초안`, `출시 전 확인 목록`을 각각 명시된 파일로 만들고, 독립 검토 뒤 한 묶음으로 인수한다. 웹 조사나 외부 게시가 필요한 부분은 실제 조사·집행으로 표시하지 않고 미확인 항목으로 남긴다.

착수 순서는 다음과 같다.

1. **계약 명세:** 목표 입력, 역할별 업무, 산출물 파일과 수용 기준, 근거/가정/미확인 표시, 승인 범위, 인수 조건을 [Product](product.md), [DM-03](domain/DM-03-execution.md), [DM-04](domain/DM-04-lifecycle.md), [Security](security.md), [Validation](validation.md)의 소유권에 맞게 정의한다. 파일 작업만 전제한 기존 규칙과의 차이를 해소하고, 데이터 모델·실행 경계 선택은 새 ADR에 기록한다.
2. **최소 엔진 경로:** 비코드 문서 작업을 적합한 팀원에게 배정하고, 선언된 파일만 격리 실행·통합한다. 각 산출물의 근거·가정·수용 여부를 저장한다. 재시작·실패 시 완료를 추정하지 않는다.
3. **인수 화면:** 역할별 산출물, 검증 근거, 미확인 사항, CEO의 다음 결정을 한 목표 화면에 표시한다. 기존 v2의 목표 화면을 재사용하고 새 화면이 필요한지 실제 흐름으로 판단한다.
4. **격리 파일럿:** 합성 내부 자료와 별도 데이터 디렉터리에서 계획→승인→산출물→QA→인수를 실제로 실행하고, Windows 데스크톱 결과를 기록한다. 앱 수준 QA가 통과하기 전에는 v3 완료로 표시하지 않는다.

첫 구현 단위의 합격 기준은 세 산출물이 승인된 경로에 존재하고, 각 파일의 내용과 근거가 목표의 수용 기준에 맞는지 독립 QA가 확인하며, 미확인 주장은 미확인으로 남고, 인수 화면에서 CEO가 출시 준비의 다음 결정을 내릴 수 있는 것이다. 현재의 열린 v2 QA는 별도 회귀 항목으로 유지한다.

### CEO가 실제로 쓰는 최소 흐름

1. 처음 한 번 프로젝트 폴더와 사용 가능한 AI 연결을 확인한다. 연결이 없거나 작업 능력이 확인되지 않으면 이유와 설정으로 가는 한 동작을 보여준다.
2. Home의 기존 입력창에 목표를 한 문장으로 쓴다. 필요한 자료·기한·성공 조건은 같은 목표의 선택적 세부 입력 또는 대화에서 받는다. 출시 준비 예시를 제공하되 빈 양식을 강제하지 않는다.
3. 앱은 **산출물 3개, 담당 AI, 의존 순서, 근거 자료, 변경할 파일, 승인 범위**를 한 계획 카드에 요약한다. 누락된 수용 기준이나 능력 불일치는 승인 전에 설명한다. CEO는 이 카드에서만 실제 범위를 검토하고 승인한다.
4. 실행 중 Home/Work/Office는 동일한 저장 상태를 표시한다. 기본 화면에는 현재 단계·담당자·한 가지 다음 행동만 둔다. Office 캐릭터의 이동과 말풍선은 실제 저장 이벤트와 허가 대기 상태만 반영한다. 작업 상세, 모델, 이벤트, 토큰은 기존 목표 작업공간의 `진행 정보`에서 본다.
5. 차단되면 해당 목표 카드에 **이유 → 마지막 확인된 사실 → 담당자 → 가능한 다음 행동**을 보여준다. 완료 때는 같은 공간에서 산출물·근거·가정·미확인 항목·QA 결과와 CEO의 다음 결정을 확인한다. 별도 인수 앱이나 새 메뉴는 만들지 않는다.

### AI 작업 할당 계약

- PM 계획의 각 작업은 `목표/산출물`, 선언된 출력 경로, 수용 기준, 입력 근거, 의존 작업, 필요한 능력(예: 로컬 읽기, 문서 작성, 코드 변경), 제안된 역할을 가진다. AI가 생성한 근거 주장은 출처 경로·부분과 `확인됨/가정/미확인`을 구분한다. 빈 수용 기준, 역할 없는 작업, 범위 밖 경로는 승인 카드에 올리지 않는다.
- 엔진은 **현재 등록되고 준비된 연결**, 해당 역할의 팀원, 실제 어댑터 능력, 목표의 공유 busy 상태, 필요한 권한·작업 범위를 검사해 담당자를 확정한다. 단순히 역할 이름이나 모델 선호만으로 능력을 추정하지 않는다([AI-03](aiIntegration/AI-03-adapter.md)). 적합한 후보가 없으면 차단 이유를 보여주고 연결/계획 수정으로 이끈다. 다른 AI로 조용히 교체하거나 승인 범위를 넓히지 않는다.
- 한 작업은 한 번에 한 팀원·한 실행 세션만 소유한다. 선점과 상태 전이는 SQLite 트랜잭션으로 처리하고, 동시에 선점하면 한 명만 성공한다. 독립 작업은 출력 파일 소유권과 의존성이 겹치지 않을 때만 병렬 실행한다. 다른 목표·회의의 팀원 예약도 확인한다. 계획 수정이나 재배정 시 이미 실행된 산출물과 승인 범위를 재검증한다.
- 계획·담당자·선언 경로를 **호출 전에 저장**한다. 실행 결과의 텍스트는 배정·완료의 권한이 아니다. 완료는 선언 경로의 격리 통합 증거와 산출물별 독립 QA가 있어야 한다. PM/QA와 작성자를 가능한 한 분리하고, 불가능하면 독립 검토 부족을 인수 화면에 표시한다. 기존 QA 재작업 한도와 추가 파일 재승인 규칙을 따른다.

### 중단과 작업 복구 계약

| 사건 | 엔진·UI의 다음 행동 |
| --- | --- |
| 호출 전 연결/능력/예약 실패 | 아직 시작하지 않은 작업은 `대기/차단`으로 남기고 정확한 사유와 후보 수정 행동을 표시한다. 승인·범위를 새로 확인하지 않고 우회 실행하지 않는다. |
| 앱 재시작 또는 실행 결과 불명 | 마지막 확인된 세션·이벤트를 보존한다. 네이티브 세션의 동일성·범위·재개 가능성이 소유 명세와 어댑터에서 검증된 경우에만 그 세션의 재개를 별도 구현한다. 첫 묶음의 UI는 [GC-04](goalConversation/GC-04-recovery.md)에 이미 정의된 상태별 승인/재시도/새 목표 버전 경로만 제공한다. 불명 결과는 중복 실행 가능성을 표시하고 자동 재전송하지 않는다. 사라진 프로세스, 캐릭터 애니메이션, 모델 답변만으로 완료 처리하지 않는다. |
| 승인 대기/거절 | 대기는 그대로 보존한다. 거절은 이유를 기록하고 자동 재요청·재시도하지 않는다. 실제 재시도는 현재 범위와 새 승인 판단을 거친다. |
| 파일 충돌/범위 변경 | 사용자 파일을 덮어쓰지 않고 통합을 멈춘다. 변경 경로·기존 통합 증거·필요한 새 승인 범위를 보여준다. 이전 통합 증거 재사용은 현재 프로젝트 바이트의 검증이 맞을 때만 허용한다. |
| QA 실패 | 근거와 실패 산출물을 남기고 기존 목표별 재작업 한도 안에서 승인된 경로만 수정한다. 한도 초과, 새 파일 필요, 반복 실패는 CEO 결정으로 올린다. |

감시 타이머는 첫 묶음에서 **진단 신호**로만 쓴다. 마지막 이벤트와 진행 중 호출을 보고 `오래 응답 없음`을 표시할 수 있지만, 조용하다는 이유만으로 실패·완료·재시도·승인을 확정하지 않는다. 동일한 차단 상태를 반복 알림하지 않는다. [DM-05](domain/DM-05-recovery.md), [Security](security.md), [GC-04](goalConversation/GC-04-recovery.md)의 보수적 복구 계약이 우선한다.

### Claude 구현 순서와 인수 기준

1. **기준선과 소유 문서:** v2의 열린 QA-36/QA-38과 실제 사용 제약을 기록한다. 이 제안에서 달라지는 계약을 Product, DM-03/04/05, AI-03, UX-01/02, GC-03/04, Progress Visibility, Security, Validation과 해당 사용자 흐름에 반영한다. 저장 모델·스케줄러·복구의 교차 변경은 새 ADR로 결정하고 코드에 앞서 검토한다. 기존 ADR은 소급 수정하지 않는다.
2. **배정·증거 수직 경로:** 로컬 합성 자료만으로 세 문서 작업을 계획하고, 능력/예약/파일 충돌 검사 후 명시 경로에 격리 실행한다. 각 산출물의 근거·가정·수용 기준을 저장하고 독립 QA와 통합 증거로만 완료한다. 실제 웹 조사, 고객 연락, 게시·배포는 이 경로에 넣지 않는다.
3. **복구·화면:** 재시작, 승인 거절, 불명 결과, 연결 장애, 충돌, QA 실패의 저장 상태와 단일 다음 행동을 목표 작업공간에 연결한다. Paperclip의 차단 인박스는 정보 구조만 참고하고, Office는 동일 상태를 시각화한다. 새 메뉴나 새 실행 모드는 만들지 않는다.
4. **검증:** 합성 fixture에서 동시 선점은 단 한 명만 성공, 능력 불일치는 호출 0회, 독립 파일 2개는 병렬, 동일 파일 2개는 직렬/차단, 거절·재시작·불명 결과는 자동 재전송 0회, 충돌은 원본 보존, QA 실패와 한도는 저장 후 재시작에도 일치함을 확인한다. 승인 범위 밖 파일과 저장소 지시문으로 권한을 넓힐 수 없어야 한다. 화면은 키보드·좁은 폭·동작 줄이기에서 같은 다음 행동을 읽을 수 있어야 한다. 끝으로 실제 Windows 데스크톱의 목표→승인→병렬 작업→QA→인수와 중단 복구를 기록한다. 오프라인 fixture만으로 실사용 완료를 주장하지 않는다.

각 단계는 담당자가 `변경한 소유 문서/코드`, `실행한 검증과 결과`, `남은 위험`, `다음 단계`를 [WORKLOG](../WORKLOG.md)에 적은 뒤 넘긴다. 이 패키지는 1차 구현 범위를 정하는 문서이며, 고객 검증과 후속 v3 항목의 결론은 앞 절의 검증 결과에 따라 갱신한다.

## 2차 개선 제안 — 오피스 명단과 목표별 스쿼드 (2026-10-10, Claude Cowork)

**상태: 결정됨(2026-10-10) → [ADR-0041](architecture/decisions/ADR-0041.md)로 이관.** 아래 본문은 제안 당시 기록이며, 최종 규칙은 이 절 끝의 「2차 개선 — 결정」과 ADR-0041이 우선한다.

### 문제

- 엔진은 분석·계획·검증 담당을 고정 ID `cto`·`pm`·`qa`로 찾는다. 같은 세 사람이 모든 목표에 들어가므로 두 실행 목표가 동시에 분석·계획·검증 단계에 있으면 공유 사용 중 규칙([DM-01](domain/DM-01-workspace-team.md)) 때문에 한쪽이 막힌다.
- 작성자는 ADR-0038 이후 목표마다 엔진이 고르지만, 계획 뒤에만 정해지고 "이 목표를 맡은 팀"이라는 묶음은 저장되지 않는다. Office와 목표 화면이 같은 담당 묶음을 보여 줄 근거가 없다.
- 회의(ME-01)는 이미 의장·참여자·평가자를 목표 단위로 고정하는 스쿼드 구조다. 실행 목표만 다른 모델을 쓴다.

### 제안 모델

| 개념 | 정의 | 소유 |
| --- | --- | --- |
| 오피스 명단 | 회사에 있는 모든 캐릭터: 역할, 지침, AI 연결, 모델, 자리, 숨김 여부 | 설정 > 팀, Office (현행 Agent) |
| 스쿼드 | 목표 하나에 묶인 명단의 부분집합. 역할 슬롯: **리드**(분석·계획, 기존 CTO+PM 역할 1~2명), **작성자**(산출물 담당 1명 이상), **검토자**(QA 1명, 작성자와 다른 사람) | 목표(엔진 저장 기록) |
| 스쿼드 기록 | 슬롯별 팀원 ID, 역할, 배정 이유, 연결 지문, 모델, 확정 시각, 승인 ID | 엔진 |

### 흐름

1. **목표 전달:** 엔진이 명단에서 리드와 검토자 초안을 고른다. 기준은 ADR-0038 배정 규칙과 같다(역할 일치, 사용 가능한 연결, 다른 목표·회의에 묶이지 않음, 명단 순서). 고를 수 없으면 목표 카드에 이유와 설정으로 가는 한 동작만 보인다.
2. **계획:** 리드가 산출물을 계획하면 엔진이 작성자를 정해 스쿼드에 추가한다.
3. **승인 카드:** 산출물·파일·근거와 함께 스쿼드 명단과 배정 이유가 보인다. CEO는 여기서만 팀원을 바꿀 수 있고, 바꾼 팀원도 같은 규칙으로 검증된다. 승인하면 스쿼드가 확정되며 승인 기록이 스쿼드 지문을 함께 묶는다.
4. **실행·복구:** 엔진은 확정된 스쿼드 안에서만 호출한다. 팀원의 연결이 끊기거나 숨김 처리되면 호출 전 차단(`precall`)이 되고, 목표 카드의 한 동작 "팀원 교체"로 CEO가 같은 역할의 다른 팀원을 고른다. 파일 범위가 같으면 재승인 없이 교체 기록만 남기고, 범위가 바뀌면 새 승인을 받는다. 엔진은 조용히 다른 AI로 바꾸지 않는다.
5. **완료:** 스쿼드 기록은 목표와 함께 남아 인수 화면과 토큰 화면에서 "누가 무엇을 했는지"의 근거가 된다.

### 예약 범위 (결정 필요, 권장: 단계별)

| 방식 | 내용 | 장단점 |
| --- | --- | --- |
| **단계별(권장)** | 리드는 분석·계획 중, 작성자는 맡은 업무가 `pending`~`awaiting_integration`인 동안, 검토자는 QA 중에만 사용 중 | 현행 사용 중 규칙과 같아 이행이 쉽고 명단 활용도가 높다. 단계가 겹치면 대기가 생기며, 대기 이유를 목표 카드에 보인다 |
| 엄격 | 승인부터 완료까지 스쿼드 전원 사용 중 | 예측은 쉽지만 노는 팀원도 다른 목표에 못 쓰고, 5명 기본 명단에서는 동시 목표가 사실상 하나 |

어느 방식이든 한 캐릭터는 동시에 한 세션만 갖는다(DM-01 유지).

### Office와 화면

- Office는 명단 전체를 그대로 두고, 스쿼드에 속한 캐릭터에 목표별 색 배지와 슬롯 이름(리드·작성·검토)을 붙인다. 목표 레일에서 목표를 고르면 그 스쿼드 캐릭터만 강조한다. 상태는 저장된 단계·업무·이벤트만 반영한다.
- 홈·목표 작업공간은 새 메뉴 없이 기존 카드에 "스쿼드: 리드 ○ · 작성 ○○ · 검토 ○"를 한 줄로 보인다.
- 회의는 이미 같은 구조이므로 "회의 스쿼드"(의장·참여자·평가자)로 같은 표시를 쓴다.

### 기본 명단

현재 기본 5명(CTO, PM, 개발 2, QA)으로는 동시 목표가 하나다. 동시 진행을 원하면 "출시 준비 팀" 프리셋(리드 2, 작성 3, 검토 2)처럼 더 큰 명단 프리셋을 제공한다. 기존 데이터의 `cto`·`pm`·`qa`는 역할로 해석해 그대로 쓰므로 이행 시 팀을 다시 만들 필요가 없다.

### 수용 기준 (구현 시)

- 리드·검토자가 각각 2명인 명단에서 두 실행 목표가 동시에 분석·계획·검증을 진행하고, 같은 캐릭터가 두 세션을 갖지 않는다.
- 검토자는 항상 그 목표의 작성자와 다른 캐릭터다. 불가능하면 승인 전에 막는다.
- 승인 뒤 팀원 교체는 같은 역할·같은 파일 범위에서만 재승인 없이 기록되고, 그 외에는 새 승인이 필요하다. 교체 후 자동 재전송은 없다.
- 재시작 후에도 스쿼드 기록과 Office 배지가 같은 내용을 보인다.

## 3차 개선 제안 — 업무·회의 화면을 UI/UX 철학에 맞추기 (2026-10-11, Claude Cowork)

**상태: 결정됨(2026-10-11, CEO가 권장안 D1~D3 채택) → ME-01·UF-09·정보 밀도 감사표로 이관, U1~U3 구현.** 기준은 [UI/UX 구현 철학](ux-principles.md)과 [ADR-0042](architecture/decisions/ADR-0042.md)다. 결정되면 [회의](meeting/00_index.md) ME-01/ME-02, [UF-09](userFlow/UF-09-meeting.md), [정보 밀도 UI 정책](content-density.md) 감사표와 Validation으로 이관한다.

### 요약의 출처 (UXP-5: 기존 호출에 얹기)

| 요약 | 받는 곳 | 없을 때 |
| --- | --- | --- |
| 목표 한 줄 | CTO 분석 응답 첫 줄 `요약:` | 원문 일부 |
| 회의 주제 한 줄 | 의장 계획 JSON `topicSummary` | 원문 일부 |
| 단계 한 줄 | 제안·비판·수정 응답 JSON `summary` | 결정적 문장(참여자·항목 수) |
| 회의 전체 요약, 권장안, 쟁점 | 평가 응답 `overview`, 권고의 `recommended`(최대 1개), `issues`(쉬운 말 한 줄 + 관련 비판 ID) | 평가 없음이면 결정적 문장, 쟁점은 같은 대상 주장별로 엔진이 묶음 |

모든 필드는 선택 사항이며 길이 제한·일반 텍스트이고, 상태와 결정에 쓰지 않는다. 회의 계획 승인 범위와 호출 수는 바뀌지 않는다.

### 화면

- **회의 깊이 1(한눈에):** 주제 요약 + `원문 보기`, 회의 전체 요약, 제안 최대 5개(권장안 강조·미리 선택), "아직 의견이 갈리는 점 N개", 통제 한 줄(계획 승인 · AI 호출 n/m · 보낸 자료 k개 · `보낸 내용 보기`), 결정 버튼, `회의 요약 보기`. 계획 승인·단계 전송 승인이 필요하면 그 결정 카드가 이 자리를 먼저 차지한다.
- **회의 깊이 2(흐름 요약):** 계획 → 제안 → 비판 → 수정 → 평가 단계마다 한 줄·참여자·항목 수·상태, 쟁점 목록(해결/남음/확인 필요, 관련 의견 수).
- **회의 깊이 3(자세히):** 단계별 발언·근거, 쟁점별 개별 의견과 응답, 주장 추적, 전송 원문·응답 원문, 모델 출처·사용량, 전송 기록. 현재 위치 표시와 뒤로 가기.
- **업무 탭:** 카드 제목은 요약 + `원문 보기`, "결정이 필요한 일"은 첫 줄 + `확인 열기`, 업무 목록은 산출물 이름·상태 + `AI 지시 보기`·`결과 원문 보기`. `결정 열기`는 회의 깊이 1을 연다.

# PR 워크플로우

Status: Accepted (2026-10-12, CEO). [개발 워크플로우](workflow.md)의 마지막 단계다. PR 제목·요약은 [UI/UX 구현 철학](ux-principles.md)의 세 깊이와 쉬운 말 원칙을 코드 리뷰에 적용한 것이다. 보안 경계는 [Security](security.md)를 따른다.

## 목적

`main`의 히스토리와 PR 목록만 읽어도 비전공자가 **무엇이 바뀌었고, 왜 바뀌었고, 무엇이 아직 검증되지 않았는지** 알 수 있게 한다.

## 1. 단위와 브랜치

- PR 하나는 [WORKLOG](../WORKLOG.md)의 마일스톤 하나(M#)다. 서로 무관한 변경을 한 PR에 섞지 않는다. 구조 리팩터링과 새 동작은 다른 PR로 나눈다.
- 브랜치는 `main`에서 만들고 이름은 `<종류>/<영어-소문자-요약>`이다. 종류: `feature`(새 기능), `fix`(버그), `docs`(문서만), `refactor`(동작 변화 없음), `chore`(빌드·설정).
  - 예: `feature/goal-archive`, `fix/meeting-summary`, `docs/pr-workflow`.
- `main`에는 직접 커밋하지 않는다. 첫 커밋은 예외였다.

## 2. PR 제목

형식: `[영역] 무엇을 할 수 있게 됐는지` — 50자 안쪽의 한국어 문장.

- 영역은 다음 중 하나: `목표`, `회의`, `Office`, `팀`, `설정`, `엔진`, `화면`, `문서`, `빌드`.
- 결과를 쓴다. 구현 방법, 파일명, ADR 번호, 영어 전문용어, 마일스톤 번호는 제목에 쓰지 않는다.
- 동작 변화가 없으면 무엇이 쉬워지는지 쓴다.

| 좋은 예 | 나쁜 예 |
| --- | --- |
| `[목표] 끝난 목표를 숨기고 설정에서 영구 삭제할 수 있게 함` | `M11: archive.rs + purge_goal (ADR-0043)` |
| `[회의] 회의 결과를 요약부터 보여 줌` | `MeetingPanel depth refactor` |
| `[문서] PR 이름과 요약 작성 규칙을 정함` | `docs: add pr-workflow.md` |

PR은 squash merge로 합친다. 그러면 PR 제목이 `main`의 커밋 제목이 된다.

## 3. PR 요약 (본문)

[`.github/pull_request_template.md`](../.github/pull_request_template.md)의 세 깊이를 순서대로 채운다.

1. **한눈에** — 정확히 세 줄, 쉬운 말.
   - 무엇이 바뀌었나 (사용자가 보거나 할 수 있게 된 것)
   - 왜 바꿨나
   - 리뷰어·사용자가 할 일 (예: 앱 재시작 필요, 수동 QA 번호). 없으면 "없음".
2. **흐름 요약** — 바뀐 덩어리마다 한 줄: `엔진`, `화면`, `문서`, `시험` 등. 다섯 줄 이하.
3. **자세히** — `<details>` 안에 둔다.
   - 관련 명세·ADR 링크
   - 주요 변경 파일
   - 실행한 검증과 결과 수치 (예: Rust 시험 100 통과)
   - **검증하지 못한 것** — 비울 수 없다. 실제 앱, 실제 AI 호출, 실제 운영체제를 실행하지 않았다면 그렇게 쓴다. 없으면 이유와 함께 "없음".
   - 남은 위험

제목과 한눈에 세 줄은 깊이 1·2 규칙(UXP-6)을 따른다: ID·해시·영어 전문용어를 쓰지 않는다. 자세히에는 써도 된다.

## 4. 보안

저장소는 공개될 수 있다. PR 제목·본문·커밋 메시지에는 다음을 넣지 않는다: 저장된 CEO 목표 원문, 프로젝트 문서 내용, AI 응답 원문, 토큰·비밀값, 개인 이메일, 사용자 컴퓨터의 절대 경로. 예시가 필요하면 시험에 쓰는 합성 예시만 쓴다. 이 규칙은 [Security](security.md)의 전송 경계와 같다.

## 5. 역할

| 단계 | 담당 |
| --- | --- |
| 브랜치 생성, 커밋, 시험 | Claude (또는 작업자) |
| PR 제목·본문 작성 | Claude가 `.pr/<브랜치의 />를 -로 바꾼 이름>.md`에 저장. 첫 줄이 제목, 빈 줄 다음부터 본문이다. `.pr/`은 커밋하지 않는다. |
| push, PR 생성 | CEO가 Windows에서 `powershell -ExecutionPolicy Bypass -File .\scripts\open-pr.ps1` 실행. 스크립트는 현재 브랜치를 push하고, `gh`가 있으면 PR을 만들고, 없거나 실패하면 제목을 채운 GitHub PR 작성 페이지를 열고 본문을 클립보드에 넣는다(붙여 넣고 `Create pull request`). 작업 브랜치가 아니거나 커밋하지 않은 변경이 있거나 PR 본문 파일이 없으면 아무것도 보내지 않고 멈춘다. |
| 리뷰, squash merge | CEO |
| 기록 | merge 후 WORKLOG 해당 마일스톤에 PR 번호와 merge 여부를 남긴다. |

작업자가 PR을 대신 만들 권한을 가진 경우에도 push와 PR 생성은 CEO가 그 작업에서 요청했을 때만 한다. 문서의 이 규칙 자체를 승인으로 보지 않는다.

## 6. 점검표

PR을 만들기 전에 확인한다.

1. 마일스톤 하나만 담았는가.
2. 제목이 형식을 지키고, 비전공자가 읽고 무엇이 바뀌었는지 말할 수 있는가.
3. 한눈에가 세 줄이고 할 일이 적혀 있는가.
4. 검증하지 못한 것이 채워져 있는가.
5. 4절의 금지 내용이 없는가.
6. 소유 명세·ADR·WORKLOG가 같은 브랜치에서 갱신됐는가.

# DM-03 — Task, evidence, and approval

## Entity definitions

- **Task integration proof:** per-file digest captured when an approved task's declared changes reach the selected project. It is evidence for later reuse, not a grant to write or a substitute for QA. Older tasks without proof remain ineligible for automatic reuse.
- **Reused-file ownership transition ([ADR-0068](../architecture/decisions/ADR-0068.md)):** before a linked plan or repair approval, compare normalized reused-file and dependency paths with new task declarations and the exact approval scope; show overlaps and reject an unchanged reused task ID that owns a proposed modification. Removing the reuse designation requires a new explicit task and valid scoped approval. When that task's change is integrated, stop applying the previous reuse verdict to its modified files and persist their old/new SHA-256, new goal/task/approval IDs, declared scope, integration event/time, diff and provenance. Keep old proof as history. A task with only some files redone is not automatically completed by reuse; other unchanged files and dependencies still require their old proofs. An unintegrated, unchanged or unproven repair cannot claim a transition. QA reads the new proof for converted files and ADR-0027 proof for all other reused files and dependencies.
- **Task:** goal-scoped work unit with assignee, dependency IDs, acceptance criteria, worktree and artifact references. A *deliverable task* ([ADR-0038](../architecture/decisions/ADR-0038.md)) also stores a one-line deliverable, 1–8 acceptance criteria, 0–8 read-only evidence paths inside the project, a required capability (`document` or `code`) and the engine's assignment reason. Older tasks without these fields stay readable and follow the earlier QA rule.
- **Earlier results and file names ([ADR-0057](../architecture/decisions/ADR-0057.md)):** a teammate's brief also carries, bounded and labelled as untrusted teammate output, the results of completed tasks it depends on and of earlier completed tasks in its repair round; a repair brief adds the criteria the newest QA review failed with QA's evidence. QA receives what the round's repair tasks reported, to verify in the files. Planned file and evidence paths are rewritten to an approved name or the existing file's name, and prompts list approved files exactly as planned, so a teammate never creates `readme.md` beside `README.md`; a case-only rename in a folder workspace is applied to the original file.
- **Focused execution guidance:** the PM names the existing evidence files and useful focused checks for each task. The worker first follows required project guidance and reads its declared evidence, then inspects other files as needed for the acceptance criteria. It favors targeted searches and concise command output over repeated whole-project listings, runs focused checks during implementation, and runs every required broader validation before reporting completion. This guidance cannot narrow declared output files, omit acceptance criteria, skip required project instructions or tests, or change the approved write scope. The engine still performs the same isolated execution, integration, and independent QA; CLI behavior remains advisory until a real run verifies it.
- **Assignment:** the engine, not the planner, picks exactly one enabled implementation character per task whose saved connection is usable and can write files in an isolated workspace and who is not busy under [DM-01](DM-01-workspace-team.md) for another goal or meeting. It balances by tasks already assigned in the plan, then by roster order, and records why. QA, PM and CTO never receive implementation tasks. With no eligible candidate the plan blocks before approval; another AI is never substituted silently.
- **Display summary:** the analysis lead's reply starts with one `요약:` line (plain Korean, ≤ 80 characters) that the engine stores as a `goal_summary` record for goal titles ([ADR-0042](../architecture/decisions/ADR-0042.md)). It is display-only and optional: a missing line changes nothing, the stored analysis keeps the full reply, and no state, approval or assignment reads it.
- **Work kind ([ADR-0045](../architecture/decisions/ADR-0045.md)):** the next line is `업무: 개발` or `업무: 기타`. The engine stores it, with the static SDD origin detection, as a `goal_origin` record. A missing or unclear line counts as `기타`. Only a `개발` goal may get the planning card's structure question ([SI-03](../specImport/SI-03-origin.md)); when that question could be asked and static detection listed unclassified rule files, the prompt names only those files and the CTO may add one display-only `구조 조언:` line. The record never changes the plan, approval, assignment or project files.
- **Claim:** the `pending → running` change is one SQLite transaction that re-checks pending status, completed dependencies, a still-approved project-write approval, and the assignee's enabled state, usable capable connection, absence of another running task and of a meeting reservation. A workspace is prepared and a provider called only after the claim commits; a failed claim leaves the task `pending` and makes no call.
- **Deliverable review:** for deliverable tasks, independent QA returns one structured verdict per task with one result per acceptance criterion (`met` and concrete evidence) and unverified items. The engine stores it per task and QA round. It is evidence for the CEO's acceptance, not a write grant.
- **Session:** one runtime execution for one agent/task, with native session identifier and resume capability.
- **Event:** ordered, append-only fact about a goal, task, session, approval, or artifact.
- **Progress event:** a bounded, persisted event tied to goal, task when applicable, and agent. It records verified runtime or engine milestones such as tool start/completion, stage change, integration, or failure. It never represents model private reasoning.
- **Approval:** a requested material decision with pending/approved/denied status and actor.
- **Preset contract:** a preset definition has immutable `id`, `version`, `stage`, `purpose`, `decisions`, `defaults`, `allowedRange`, `dependencies`, `conflicts`, `artifactRules`, and `validation`. The first three stages are `beginner`, `intermediate`, `advanced`; each project selects zero or one at each stage. Defaults are recommendations, not grants. `decisions` cannot hold credentials, endpoints, commands or approval rules; service entries name roles only. Paths are normalized project-relative paths and cannot escape the root or follow symlinks. The deterministic validator checks completeness and known definition digest, application applicability, type/range, stage count, dependencies, prohibited combinations, existing SDD/file/API ownership, and measurement feasibility before activation, planning, approval and claim. For SDD/API ownership it compares a proposed decision and artifact impact with the project's current owning SDD sections, API contracts and declared file owners; a differing or unknown owner is reported with the affected source and field as `충돌` or `질문 필요`, never silently replaced by a preset default. It returns field-specific `통과`, `질문 필요`, `충돌`, or `검증 환경 미확보` with reasons. Questions/conflicts keep the previous active selection and block a new plan; missing measurement environment preserves a numeric target as `미검증` and requires a visible measurement task or explicit unverified item. AI prose cannot waive a failure. The plan receives resolved decisions, a QA checklist and expected artifact impact, never automatic file edits ([ADR-0062](../architecture/decisions/ADR-0062.md)).

## 관계와 소유 경계

Dev가 작업 중 선언되지 않은 명령에 막히면 통합 전에 목표의 계획 PM이 한 번 검토한다([ADR-0065](../architecture/decisions/ADR-0065.md)). PM은 기존 승인만으로 작업을 다시 지시하거나, 새 권한을 CEO에게 요청하거나, 해당 명령 없이 결과를 제출하게 할 수 있다. PM 지시 자체는 권한이 아니며 새 명령과 새 파일의 승인 소유자는 CEO다. QA 명령 거절은 독립 검증 흐름에서 처리한다.

목표의 명령 모드는 프로젝트 기본 또는 목표 대화의 명시적 재정의를 따른다([ADR-0066](../architecture/decisions/ADR-0066.md)). 자동 승인 가능한 정확한 명령은 그 업무에서만 재시도하고, 나머지 거절은 PM 검토와 CEO 카드로 이어진다. 설정 변경은 다음 권한 판단부터 적용된다.

| 관계 | 대상 | 의미 |
| --- | --- | --- |
| belongs_to | [DM-02 목표](DM-02-goal.md) | 업무·승인·증거는 해당 목표와 연결된다. |
| transitions | [DM-04 수명주기](DM-04-lifecycle.md) | 완료는 통합 결과와 검증에 근거한다. |
| recovers | [DM-05 중단 복구](DM-05-recovery.md) | 앱 재시작 때 미완료 세션과 승인을 다시 판단한다. |

# Product specification

## Goal

The human acts as CEO: they provide an intent, constraints, and expected outcome in natural language. An AI organization plans, delegates, executes, verifies, recovers, and reports work. Office visualization is a view of that process, not the process itself.

The v2 multi-perspective meeting is a Goal-bound decision workflow before execution in which existing Office characters debate. The Home composer offers `목표 수행` (default) and `회의` modes. In a meeting, the PM (else CTO) chair proposes the objective, constraints, participants, evaluator, protocol, sources and call cap; the CEO approves that plan once (or chooses per-stage review); participants debate with the same read-only access as execution goals; and the result is an inspectable decision package whose claims, critiques and evidence can be traced. It does not edit project files. The validated v2 meeting will then help plan distinct v3 improvements; the broader v3 customer-job target remains separate. [Meeting Spec](meeting/00_index.md) owns process details and [WORKLOG](../WORKLOG.md) owns actual delivery evidence.

## MVP experience and capabilities

The step-by-step user journeys and their relationships are owned by the [user flow index](userFlow/00_index.md). This section defines product capabilities and boundaries; flow files link to the owning domain, security, and interaction specifications.

1. A workspace contains multiple registered local folders, with or without Git. One folder-selection action adopts the chosen existing folder unchanged, including empty and nonempty folders and folders that contain other folders. The selected folder itself is the project root; no child folder is required to be empty or separately registered. On Windows, the picker uses the Explorer-style folder selection dialog with breadcrumb navigation, search, and the ability to choose the current folder. A Git repository root with an initial commit uses Git-aware execution; any other folder uses isolated copies. Registration never initializes Git or creates a README. Selecting an already registered folder again rechecks its execution mode while preserving the project ID, goals, and QA preset; this lets a folder converted to a committed Git root outside the app become a Git project for future work. The user can switch the active project from a visible list. Every goal remains bound to the project selected when it was created. Display paths are readable native paths; canonical paths remain internal for safety checks.
2. Start from an editable team of CTO, PM, two Developers, and QA/Reviewer with useful role-instruction presets. Office shows distinct pixel characters rather than initials: drag a character to position it, click it to open that member's activity and individual role/model settings, and preserve custom edits. Office has a separate team settings view for adding members, bulk AI assignment, and hiding/restoring members. Bulk assignment selects active members explicitly, updates their connection in one transaction, and clears obsolete per-member model overrides; it affects future invocations rather than rewriting saved history. Registering an AI connection fills only team members whose connection is blank. A member's model override is selected from verified available model IDs when the provider exposes a catalog; otherwise the provider default is used. One character owns one active agent session at a time; multiple characters may use the same runtime or model.
3. Enter a CEO goal. The CTO analyzes it; the PM proposes tasks and dependencies. The engine schedules independent tasks concurrently, collects artifacts, integrates changes, runs validation, requests rework when needed, and delivers a CEO report.
   A requested single-file deliverable remains one file and may be one implementation task. Parallel execution applies when the plan has independent, separately owned files.
   For non-code work such as the first v3 pilot (three launch-preparation documents from local material), each task names its deliverable, acceptance criteria and local evidence; the engine assigns a capable, free teammate and the CEO accepts the result per deliverable with QA evidence and explicit unverified items ([DM-03](domain/DM-03-execution.md)).
4. Show the same persisted state in command/report, project list, AI connection setup, task board/event log, and Office views. Keep actions understandable without requiring knowledge of Git worktrees, model adapters, or coordinates. A blocked action remains clickable and explains the exact unmet condition and next step in a dialog. Successful actions use a short-lived, nonblocking action toast; custom AI entry opens a focused dialog instead of occupying the main page. Cards and section groups retain consistent spacing at desktop and narrow widths.

   Office and the board follow the shared [일의 진행 UI 표시 정책](progress-visibility.md) so the user can identify the active teammate, inspect confirmed progress, and reach the relevant settings.

   Every screen follows the [UI/UX 구현 철학](ux-principles.md): a non-specialist, even a primary-school child, understands the first screen (summary, decision, at most five choices with one recommended), while the user can always reach what was approved, sent and argued.
5. Ask the CEO only for material decisions defined in the security spec. Waiting never silently becomes approval.

The project's 0–5 QA rework cap is a preset for new goals. Each goal card has its own 0–5 cap and confirmation dialog; changing it while the goal runs applies at its next QA decision. Changing the project preset never changes existing goals. Cancel leaves the saved value unchanged. Goals without a project binding cannot be run.

A dedicated token usage menu shows the current project's total and its goals. The project card expands to show token counts by teammate; each goal card expands to show its own teammates. Goal and teammate lists can sort by token count. All ratio bars use the current project's total as 100%, even inside an expanded goal. Each invocation retains its connection and model identity as used at execution time, plus input/output, reported/estimated provenance, and status. Missing historical model identities display as unknown rather than being inferred from a teammate's current settings. The final panel offers evidence-based suggestions for reducing token use, without claiming token counts are costs or provider quotas. Office keeps each character's current-run and current-project figures.

The sidebar and top app bar keep their position and dimensions while switching tabs or reading long pages. Only the content region below the app bar scrolls vertically; confirmation dialogs remain in the viewport.

All screens follow the [정보 밀도 UI 정책](content-density.md): repeated records default to five visible items with a disclosure control, and tall read-only card content has a recoverable preview. The policy records explicit exceptions for urgent approvals and controls.

Office team settings lets the CEO hide an implementation teammate from the active roster without erasing their identity, past tasks, events, or token records. A teammate with unfinished assigned work cannot be hidden; the UI explains which work must finish first. Hidden teammates and their restore controls appear only in team settings. Individual character settings contain only that member's own identity, role, reporting line, AI, model, and instructions. The CEO desk presents a deterministic short form of each long goal, with an explicit control to reveal the full original intent and report; summarization uses no AI invocation.

The board shows a progress graph for every goal in the selected project, rather than only the latest active goal. The CEO may assign a shared work-group label to related goals; goals with the same label appear under one visual group while each retains its own graph, tasks, approvals, QA limit, and report. Grouping does not merge execution or approval scopes. Office's fuller current-goal view is planned in [Office goal visibility plan](office-goal-visibility-plan.md).

Each goal has a [goal-scoped conversation and direction-change flow](goalConversation/00_index.md). The CTO can answer a read-only understanding question from actual saved state. A clear CEO direction is interpreted from the same conversation, pauses the old goal at a safe engine checkpoint, and automatically starts a linked goal version for analysis and planning. New file work requires fresh scoped approval. The Office active-goal rail is a navigation projection of the same saved goal state.

A goal requiring CEO confirmation offers a visible `확인하기` action that opens the relevant pending approval details. A blocked goal without a pending approval offers an explanation dialog with its recorded reason and a safe next step; it must not imply that a nonexistent approval can be confirmed.

## MVP boundaries

The application runs locally on Windows x64 and Ubuntu 24.04 LTS x86_64. Ubuntu development build and app execution are required; distributing Linux packages and supporting other distributions are later work. No cloud backend, team accounts, billing, or custom foundation model is part of the MVP.

The first end-to-end scenario is one real Git project with two independent implementation tasks, integration, QA, and a CEO report. Execution must be based on actual agent/runtime events, not a visual simulation.

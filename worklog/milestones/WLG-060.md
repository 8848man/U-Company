## Milestone

- **Model and validator.** `technology_presets.rs` is a separate model with the nine built-ins (`B-WEB`…`A-AVAILABILITY`, version `1.0.0`). Built-ins and drafts both go through `validate_definition`, which checks:
  - required fields, ID prefix and semver;
  - allowed range and that every decision has a range rule;
  - no keys or values that look like credentials, endpoints, commands or approvals;
  - safe relative paths (no `..`, absolute paths, `.git`, `.ucompany` or the SDD folder);
  - dependency and conflict structure;
  - `autoWrite` is always false.

  `validate_choices` checks combinations and returns `pass`, `question`, `conflict` or `unmeasured` per field. It covers one preset per stage, unknown digests, unresolved values, missing numeric measurement conditions, dependencies, prohibited pairs, and project paths that are existing files or symlinks.
- **Storage.** Migration v5 adds SQLite tables for:
  - immutable definitions (an `UPDATE` trigger blocks changes);
  - inactive drafts;
  - per-project selections;
  - per-plan-revision snapshots (`UPDATE` and `DELETE` triggers block changes), keyed `(projectId, goalId, planRevision)` with a unique `approval_id`;
  - a list of the `project_write` approvals that existed before the migration (legacy).

  Built-ins are registered with `INSERT OR IGNORE`.
- **Activation.** Saving a draft never activates it. `select` accepts only actor `ceo`, an optional preview fingerprint, and a passing check. If the check blocks, the previous selection stays. Saving the same ID and version with different content is refused (a change needs a new version).
- **Plan binding.**
  - **Before the PM plans:** `engine::run` resolves the selection before each PM pass. It applies only to goals whose `goal_origin` is `development`, and a blocking check stops the plan.
  - **When the card is created:** `bind_plan` writes the approval, the `approval_requested` event and the snapshot in one transaction. The snapshot holds full definitions, resolved values, the QA checklist, the expected impact, and the planned task files.
  - **At approval:** `decide_approval` (and the e2e harness) runs `verify_binding_in_tx`. It checks project, goal, latest revision, fingerprint, definition digests and declared files, and accepts an optional new `preset_fingerprint` argument.
  - **Before claim:** `verify_claim` runs before `claim_wave`; a failure blocks as `precall`.
  - **Revisions:** `개선` produces revision N+1, so the older card fails as stale. A change after approval goes to a linked goal, which gets its own snapshot and approval.
- **Recovery.** If a definition is lost, approval and claim are blocked with restore guidance. `restore_definition` restores the exact copy saved in the snapshot. Legacy approvals from before v5 can still run without a snapshot.
- **New Tauri commands.** `get_tech_presets`, `save_tech_preset_draft`, `preview_tech_preset`, `select_tech_preset`, `get_plan_preset_snapshot`, `restore_plan_preset_definitions`. No frontend calls them yet.
